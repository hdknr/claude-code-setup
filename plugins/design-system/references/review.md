# 検査とレビュー

デザインシステムを決める 1 周の形と、design-system の検査・判定役の原本である（#1613）。

## 1 周

screen-spec と同じく、**仕様の検証と Q&A の反映を繰り返す**（利用者と決めた）。

1. design-system のスキルで表と散文を書く（`init` で始める——子の Issue）。
2. **検査**（下の「機械の検査」）——違反と起票の候補を出す。番号は振らない。
3. **判定役のレビュー**（下の「判定役」）——部品の状態とアクセシビリティを突かせ、指摘を振り分けて起票の候補にする。
4. spec-loop の **req-loop** で、候補を Q&A 表に起票し（番号を振る）、レビュー会の資料を作る。資料の質問からサイトの頁へのリンクは `qa-to-pptx.py --links` に渡す JSON を design-system が作る（`references/spec-loop.md` の「spec-loop に要る口」の 4）。
5. **レビュー会**——生成したドキュメントのサイト（`references/outputs.md`）を見ながら回答をもらう。
6. req-loop が回答を表に反映する——2 に戻る。
7. 決まったら 2 つのサインオフのタグ（承認する人はタグの時点から作ったサイトを読む）→ 生成物の `--check` → `release-v<n>`。

**見た目は範囲の中である**——トークンの値・部品の状態の見た目は、表に列のある決定として共有の Q&A 表に起票する。
spec-loop の「見た目」の線（spec-loop の `references/spec-scope.md` の「見た目」）がこれを見送らないようにするのは、spec-loop の側の口である（`references/spec-loop.md` の「spec-loop に要る口」の 2）。

## 誰が決めるか

起票の候補は、決める人で 2 つに分ける（spec-loop の共有と内部の Q&A 表——原本は spec-loop の `references/qa-csv.md`）。

| 決めること | 決める人 | 起票する表 |
| --- | --- | --- |
| トークンの値・部品の見た目と状態・振る舞い・パターン・規則・文言 | デザインシステムの決定者（デザインの担当・製品の代表） | `shared/qa.csv` |
| 生成物の形だけに効くこと（トークンの名前の付け方・描画キットの描き方の都合） | 開発者 | `spec/qa-dev.csv` |

## 機械の検査

`check-design-system.py`（子の Issue）が、spec-loop の重ね方で重ねた全体の表に当てる。終了コードの分け方は screen-spec の `check-screens.py` と同じ形（0 通る・1 違反・2 判定していない・3 違反は無いが未決定の印か必須の欄の空がある・4 検査の前に止めた——screen-spec の `references/tables.md` の「検査（`check-screens.py`）」）にする。
**ファイルを書かず、Q&A の番号を振らない**——違反と `起票の候補: ` の行を出すだけ。

| 検査 | 違反（1）か候補か |
| --- | --- |
| 表の形（見出し行・鍵・必須の欄・語彙・`根拠` の Q&A の番号が Q&A 表に在る） | 違反 |
| トークンの別名の行き先が在る・別名が循環しない・`種類` と値の形が合う | 違反 |
| 部品の仕様の `文字色`・`背景色`・`枠線`・`ほかのトークン` が在るトークンを指す・`部品ID` が在る・パターンの `使う部品` が在る | 違反 |
| **文字色と背景色のコントラスト比**——部品の仕様の行ごとに、別名を解いた 2 つの色から WCAG のコントラスト比を計算し、基準（値を置く場所は `references/tree.md` の「決めていないこと」。無ければ候補として基準を訊く）を下回る行 | 候補（決めるのは決定者） |
| 部品に `フォーカス`・`無効` の状態の行が無い・`キーボード操作` が空・`読み上げ` が空 | 候補 |
| どの部品の仕様からも参照されない `部品` の層のトークン・どのパターンからも使われない部品 | 候補 |
| 規則の `確かめ方` が `機械` なのに検査が見られない規則 | 候補（検査を足すか `判定役`・`人` に変える） |
| 未決定の印（spec-loop の `find_markers`） | 3 |

## 判定役

利用者と決めた（#1613 の D4）——**部品の状態とアクセシビリティを判定役に突かせる**。spec-loop の spec-review は使わず（`references/spec-loop.md` の「spec-loop のどの段を使うか」）、design-system が自分のレビューのスキル（`review`——子の Issue）と判定役を持つ。
利用者が D4 で選んだ値は「spec-review も通す」で、この形はそれを代えたものである（設計の周の関門の指摘を受けて利用者に確かめた。2026-11-27）。
理由: spec-review の抜ける条件（`spec/` のチェックリスト・テストケース・形式検査）と中間表現はデザインシステムの表に合わず、そのまま通すには spec-loop を改修することになる。代えたのは道具で、判定役（書き込みツールなし・別ティア）に突かせることは同じ。

- 判定役は design-system の `agents/` に置き、spec-loop の判定役と同じ決まりに従う——**書き込みツールを持たず、`model` を書かない**（呼ぶ側が別のティアを指定する。このリポジトリの `check-plugin-versions.py` が全プラグインの `agents/` で見る）。
- 判定役の案:

  | 判定役 | 突くもの |
  | --- | --- |
  | 状態の判定役 | 部品の状態とバリエーションの抜け・矛盾（`無効` なのに押せる・`エラー` の伝え方が無い）、パターンと部品の振る舞いの食い違い |
  | アクセシビリティの判定役 | キーボード操作・読み上げ・フォーカスの見え方・動き（`duration` のトークン）を WCAG に照らす。機械の検査のコントラスト比の結果を受けて、例外の扱いを見る |
  | 規則の判定役 | 規則の表の `確かめ方` が `判定役` の規則に、部品・パターン・文言が合うか。社内規約・既存の製品と食い違わないか（spec-loop の Domain Checker に当たる） |

- 指摘の振り分けは spec-loop の spec-review の振り分け（spec-loop の `references/spec-scope.md` の「振り分けの区分」）に倣う——決定者に見える結果が変わるものは共有の Q&A 表の候補、生成物の形だけに効くものは内部の Q&A 表の候補、誤った指摘は理由をつけて退ける。
- **起票の候補にして、番号は振らない**——判定役の指摘も req-loop が起票する（上の「1 周」）。
- 判定役の報告と指摘の記録の形・レビューを抜ける条件（機械の検査が 0 で、最後のレビューの指摘が全部振り分け済み、の形を基にする）・形式検査（部品の状態の遷移）を使うかは、レビューの子の Issue で決める。
  spec-loop の指摘の表（spec-loop の `scripts/check-findings-csv.py`）を読み込んで使えるかを、そこで確かめる。
