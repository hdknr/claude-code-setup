# 散文の仕様書

画面ごとの仕様書（`requirements/screens/<slug>.md`。画面の表の `仕様書` の列が指す）と共通仕様（`common.md`）の原本である——
`scripts/check-screens.py` が見る形（下の「表と仕様書の相互のつながり」と「節」）・雛形（「雛形」）・書き方（「書き方」）・レビュー観点・共通仕様。表の形は `references/tables.md`。
検査の本体の定数はこの文書の写しで、テスト test-check-screens.py が突き合わせる。雛形（このプラグインの `templates/`）がこの文書に合うかは、テスト test-write-screens.py が見る。

## 表と仕様書の相互のつながり

- 画面の表の `仕様書` が指すファイルが在ること。
- 仕様書の最初の `# ` の見出しに、その画面の `画面ID` を書くこと（例: `# S-001 受注一覧`）。
- `requirements/screens/` の直下の Markdown のうち `common.md` のほかは、どれかの画面の `仕様書` から指されていること（表から指されない仕様書を残さない）。

## 節

仕様書は、次の `## ` の見出しをこの順に持つ（13 次元と未決の論点）。この順を崩さなければ、間にほかの `## ` の見出し（profile の節「実現方式: web-spa」など）を置いてよい。

| 見出し | 表で持つか |
| --- | --- |
| `## 1. 基本情報` | 表で持つ |
| `## 2. 画面概要` | 表で持つ |
| `## 3. レイアウト` | 表で持つ |
| `## 4. データ表示` | 表で持つ |
| `## 5. 操作とアクション` | 表で持つ |
| `## 6. 入力とバリデーション` | 表で持つ |
| `## 7. 状態` | 散文 |
| `## 8. 権限とデータの見える範囲` | 表で持つ |
| `## 9. 他システム連携` | 散文 |
| `## 10. 同時編集` | 散文 |
| `## 11. 表示ルール` | 散文 |
| `## 12. 一覧・表の能力` | 表で持つ |
| `## 13. 画面遷移` | 表で持つ |
| `## 未決の論点` | 散文 |

- 「表で持つ」節は、表に置いた次元を手で二重に書かない——本文に表を出す印 `<!-- screen-spec: 表 -->` を置く（MkDocs のフックが、その画面の行を表として節に出す。節ごとの行と列は `references/mkdocs.md`）。
  印だけの節は空ではない。散文の節に印を置いても、空の節のまま数える。
- 空の節は違反である。書くことが無い節は `N/A` と書き、続けて理由を書く（例: `N/A。他のシステムとやりとりしない`）。`N/A` だけで理由の無い節も違反である。
  `N/A` は大文字小文字を問わず、強調・コード・箇条書き・引用の印を付けても `N/A` だけなら理由が無い。見出しは行頭から 3 つまでの空白で字下げしてよい（CommonMark の見出し）。HTML のコメント（表を出す印のほかのもの）と小見出し（`### `）の行は中身に数えない。
  HTML のコメントの中に書いた見出しは、節の見出しに数えない。
- 本文に書いた Q&A の番号は、画面の表の `根拠` と同じく重ねた Q&A 表に在ること。未決定の印も表のセルと同じく数える（`references/tables.md` の「検査」）。
- `common.md` は節を見ない（下の「共通仕様」の節は検査の外）。Q&A の番号と未決定の印だけを見る。

## 雛形

`add` は、仕様書を雛形から作る（`references/tables.md` の「`init` と `add`」）。雛形はこのプラグインの `templates/spec.md` で、`init` が案件の `requirements/screens/templates/spec.md` に写す。
案件に固有の語（データの見える範囲の単位の呼び名など）は、案件の雛形を直して入れる——このプラグインの雛形は案件に依らない。

- **最初の見出し**は `# {{画面ID}} {{画面名}}`。`add` が `{{画面ID}}` と `{{画面名}}` を差し込む（案件の雛形もこの 2 つを使う）。
- **見出しの後**に、画面の表の行・ワイヤーフレーム（`wireframes/<画面ID>.svg`）・共通仕様へのリンクと、目次（`[TOC]`。MkDocs の `toc` が節の一覧に置き換える）を置く。
- **上の「節」の 14 の節を、その順に置く。**
- **表で持つ節は、表を出す印（上の「節」の印）だけを持つ**——表に置いた次元を散文に二重に書かない。
  表と散文の両方で持つ次元（画面概要・権限とデータの見える範囲・一覧・表の能力）は、表に置けない補う説明だけを、印の下に足してよい（見える範囲は散文に書く）。
- **散文の節は、既定の文を持つ**——状態・同時編集・表示ルールは「共通仕様のとおりで、この画面に固有の差は無い」、他システム連携は「やりとりしない」、未決の論点は「無い」を、
  `N/A。` と理由の形で置く。足した直後の仕様書が検査を通るためで、既定の文は書き直す前提である（画面の表の `ステータス` が `下書き` のあいだは、レビュー観点で見る）。
- **雛形の中に、spec-loop の未決定の印・Q&A の番号・「決定」「確定」の語を置かない**——足した直後の仕様書が未決定や、Q&A 表に無い番号の違反にならないように。
  HTML のコメントも検査が数えるので、コメントにも置かない。

## 書き方

- **N/A**: 書くことが無い節は `N/A` と書き、続けて理由を書く（上の「節」）。表で持つ節には書かない（表を出す印を置く）。
- **未決定**: まだ決まっていないことは、spec-loop の未決定の印（`TBD`・`TODO`・`未定`・`要確認`）と、その件の Q&A の番号を書く（`references/tables.md` の「書き方の共通の決まり」と同じ）。
  番号がまだ無ければ印だけを書く——検査が「起票の候補」として出し、spec-loop の req-loop・spec-review が番号を振る（`references/spec-loop.md`）。
  `⚠️` などの独自の印は MkDocs で見せる飾りで、印の代わりにならない。未決の論点の節にも、同じ印と番号で 1 件ずつ書く。
- **「決定」「確定」を使わない**——決めたのは Q&A 表の回答と spec-loop の 2 つの承認で、仕様書が自分で「確定」と書くと、承認を経ていない記述が決まったものに見える。
  決まったことは、その根拠の Q&A の番号を添えて書く。
- **共通仕様との差だけを書く**——状態・表示ルール・同時編集は、共通仕様（`common.md`）と違うところだけを画面の仕様書に書く。

## レビュー観点

仕様書をレビューする人（利用者・spec-loop の仕様レビュー）が見ること。検査（`check-screens.py`）は形だけを見るので、中身はここで見る。

- 画面の表の行（目的と背景・できること・項目・遷移）が、要求（spec-loop の `requirements/` と Q&A 表の回答）から辿れるか。`根拠` が行の中身を支えているか。
- 散文の節の既定の文（`N/A。…固有の差は無い` など）が、この画面に本当に当てはまるか——`add` が置いたまま書き直していない節が残っていないか。
- 共通仕様のとおりと書いた節について、共通仕様（`common.md`）の該当する節が書いてあるか（空のままなら、差が無いと言えない）。
- 権限とデータの見える範囲: ロールの可否を spec-loop の権限一覧（`roles.csv`）に書き直していないか。見える範囲を散文に書いたか。
- 未決のことに、spec-loop の未決定の印と Q&A の番号が付いているか。「決定」「確定」の語を使っていないか。
- profile の節（`## 実現方式: <profile>`。profile を使う案件だけ）が、core の節と同じことを二重に書いていないか。

## 共通仕様

`requirements/screens/common.md` は、画面をまたいで同じになる決まりを 1 か所に書く。`init` がこのプラグインの `templates/common.md` から置く。

- 節は、ロールと権限・データの見える範囲・共通の状態表現・表示ルール・入力チェックのメッセージ・元に戻せない操作・同時編集・用語。案件で要る節を足してよい。
- **ロールと権限は、spec-loop の権限一覧（`requirements/roles.csv`）を正とし、ロール別の可否を書き直さない**——ここにはロールの呼び名と割り当て方を書く。
- 実現方式で変わること（共通ヘッダー・左メニュー・対象デバイス）は書かない——profile の節に書く。
- 未決定の書き方と「決定」「確定」を使わないことは、上の「書き方」と同じ。
- 書いていない節は空のままでよい（検査は共通仕様の節を見ない）。画面の仕様書が「共通仕様のとおり」と書く節は、上の「レビュー観点」で見る。
