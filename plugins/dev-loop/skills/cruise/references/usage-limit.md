# 利用上限から戻る（cruise。#1507）

**これは `cruise` スキルの一部である。** `SKILL.md` §3 の 4 が再開タイマーの限界として名指しし、上限から戻る経路は**ここを正とする**と指している。
**親が読むのは、§3 の 4 の問いの画面に限界と経路を出すときである**——経路の操作（外側のループを起こす・crontab に行を足す）は**利用者がする**。
親は crontab を書かず、外側のループも起こさない（親は `/dev-loop:cruise` を起動した会話の中にいて、上限で止まるのはその親自身である）。

## 観測したこと（#1401。1 例）

- dev-loop 2.14.1 の cruise（`--absent`・子 4 本の並行。spin-dd/taihei-prm#116）で、親のセッションと子 4 本が 2026-11-20 23:51（JST）に 5 時間の利用上限に当たった（解除の時刻は「resets 2am」と出た）。
- 再開タイマー（`CronCreate`・`7,37 * * * *`・`/dev-loop:cruise 116 --absent --timer`）は、上限の前は 23:37 まで 30 分おきに発火していた。
- 上限の後は、00:07〜08:07 の約 17 回分（解除の時刻 2am より前の 4 回と、後の 13 回）の発火が親の transcript に 1 件も無かった。`CronList` にはジョブが残っていた。
- 次に発火したのは 08:25 で、「上限がリセットされた」の知らせと同時だった。解除の時刻からおよそ 6.5 時間、cruise は止まっていた。

## 確かめていないこと

- **原因**——Claude Code 側の挙動と見込んでいるが、確かめていない。
- **いつもそうなるか**——観測は 1 例である。上限の種類（5 時間・週）・Claude Code の版・張った間隔で変わるかは分からない。
- **08:25 の発火を何が起こしたか**——「上限がリセットされた」の知らせと同時だったことしか分からない。

**だから、タイマーを張っても、利用上限の後に解除の時刻で戻るとは言えない**——戻らないと断定もしない。
不在のあいだに上限に当たりうる cruise では、下の経路を、利用者が離れる前に選んでもらう。

## 上限から戻る経路

**経路は、cruise の親を外側のループ（`scripts/outer-loop.py`）で起こす形だけである**——解除の時刻の後に外側のループを起こし直し、止まった周の続きは台帳から再開する（`../dev-loop/references/ledger.md` の「どう再開するか」）。
**対話のセッションで回している cruise には、離れたまま上限から戻す経路は無い**——そのセッションの親は、タイマーか自動継続（`autoContinueAtUsageLimit`）でいつ戻るかが分からず、
外から別の親を起こすと同じ台帳を 2 体が回しうる（下の「気をつけること」）。対話のセッションで回すなら、上限に当たったら利用者が戻ってから続ける（`SKILL.md` §1 の再開）。
**離れる前に上限から戻る経路を用意するなら、対話のセッションの cruise を終え（タイマーはセッションと一緒に消える）、外側のループで起動し直してから離れる**（タイマーと併用しない）。
**外側のループも上限で止まって通知するだけで、ひとりでには戻らない**——離れたまま戻すには、上限の通知を受けた利用者が、解除の時刻を見て下の 2 の cron の行を足せる（Remote Control などで手が届く）ことが要る。**連絡がつかなければ、利用者が戻るまで止まったままである。**

### 1. 外側のループで起動する・起こし直す

メインの作業ツリーで、cron と同じロックのファイルを通して起こす（手で起こしたループと cron が起こしたループが並ばないように。下の 2）:

```bash
cd <メインの作業ツリー>
/usr/bin/lockf -t 0 <ロックのファイル> python3 <このスキルの base ディレクトリ>/scripts/outer-loop.py <親> --absent -- --permission-mode auto
```

- **`outer-loop.py` は利用上限を読まず、解除の時刻まで待たない**——docstring の 1 回の起動の手順に上限の扱いは無く、「守らない」には、上限で終わった起動の `result` に費用が載るかは測っていない、とある。
  上限に当たった起動は、たとえば次のどれかで止まる——**全部を挙げたのではなく、どれになるかも測っていない**（上限で終わった起動の出力の形も測っていない）:
    - `claude` が 0 以外で終われば **8**。
    - `--max-total-usd` を渡していて、その起動の出力から費用を取れなければ **12**（費用を取れない）——**費用の問題ではなく、上限で止まったのかもしれない**。
    - 0 で終わって台帳が進まなければ前進なしに数えられ、続けて `--max-stalls` 回（既定 2）で **6**。
    - ほかに、上限の前に周が人待ちになっていれば **3**、起動の総数が `--max-launches` に届けば **7** で止まりうる。`claude -p` が上限のあいだ戻らずに待てば、ループは止まらず通知も来ない（`outer-loop.py` は 1 回の起動を時間で打ち切らない——docstring の「守らない」）。
  **止まった後は、解除の時刻を過ぎてから同じ引数で起こし直す**——手で打つか、下の 2 の cron に任せる。止まった理由はループの出力の最後の行と、台帳の隣の `cruise-issue-<親>-loop/` の出力で見る。
- **起こし直しても、済んだ cruise を回し直さない**——起動の前に毎回 `ledger.py status` を見て、0（進められる周がある）のときだけ `claude` を起こす（3・5・4 では起こさずに止まる）。
- **費用の合計（`--max-total-usd`）はループを起こし直すと 0 から数える**——上限で止まった前のループの分は足されない（`outer-loop.py` の docstring の「費用の数え方」）。

### 2. OS の cron で、解除の時刻の後に 1 回だけ起こす

上限に当たったと知った後（`StopFailure` の hook の通知・ループの止まった通知など）に、解除の時刻を見て、利用者が `crontab -e` で 1 行足す（親は書かない）。
**起こすのは上の 1 の外側のループ**で、`claude` を直に起こさない——`status` を見て止まる条件と通知は `outer-loop.py` が持つ。

```text
# 例: 11 月 21 日 2:10 に 1 回（解除の時刻の後）。済んだら行を消す
10 2 21 11 * { export PATH='<対話のシェルの PATH>' && cd <メインの作業ツリー> && /usr/bin/lockf -t 0 <ロックのファイル> <python3 の絶対パス> <このスキルの base ディレクトリの絶対パス>/scripts/outer-loop.py <親> --absent --claude <claude の絶対パス> -- --permission-mode auto; } >> <ログのファイル> 2>&1
```

- **1 回きりにする**——分・時・日・月を決めて書き、済んだら消す。**30 分おきのような繰り返しにしない**——`outer-loop.py` は止まるたびに通知する
  （済んだ・人待ちでも）ので、繰り返すと同じ通知が並び、上限が解けていなければ起動のたびに `claude` を起こしては止まる。
- **cron の環境は対話のシェルより貧しい**——`PATH` が短く、シェルの rc で置いた変数も無い。`outer-loop.py` は自分の環境をそのまま `claude` に渡すので、
  行の先頭で `export PATH=` に対話のシェルの値（`echo $PATH`）を置く——親と周の体が使う `gh`・`git`・`node` を見つけるため。rc で `CLAUDE_CONFIG_DIR` などを置いているなら、それも `export` して行に置く。
  **値は引用符で囲む**——空白を含む `PATH`（`/Applications/… .app/bin` など）は、囲まないと `export` が失敗して後ろが走らない。cron の行では `%` に `\%` が要る。行全体を `{ …; }` で括るのは、`cd` の失敗もログに残すため。
  `export` を落とさない——環境に無い変数を `NAME=値 &&` で置いても子のプロセスには渡らない（`env -i` の `sh` で、`export` の有無で `python3` の子に `PATH` が渡るかを手元で確かめた。2026-11-25）。
  パスは絶対パスで書く——`python3`・`claude` の場所は `command -v python3`・`command -v claude` で調べた値（`/usr/bin/python3` は Command Line Tools の shim のことがある）。
  **このスキルの base ディレクトリは版を含む**（プラグインのキャッシュ）ので、プラグインを更新したら行を書き直す。
- **`lockf -t 0` で、外側のループが 2 本並ばないようにする**——同じロックのファイルを握ったループが走っていれば、2 本目は起こさずに終わる（終了コード 75）。
  **手で起こすループ（上の 1）にも同じロックのファイルを通す**——片方だけが握ると、もう片方は並んで起きる。ロックのファイルはメインの作業ツリーの外に置く。
  macOS の `/usr/bin/lockf` で、握っているあいだは 75 で断り、離した後は走ることを手元で確かめた（2026-11-25）。**cron から実際に起こしたことは無い**。
- **その時刻に Mac が眠っていると、cron は起こさない**——逃した時刻を後から走らせず、ログにも何も残らない。不在のあいだスリープさせない設定は、起動時の点検（`check-unattended-env.py` のスリープの項）を正とする。
- **cron から起こした `claude` の認証は確かめていない**——macOS では対話ログインの資格情報がキーチェーンにあり、cron の起動から読めるかは分からない。
  長期トークンの起動口（`../dev-loop/scripts/launch-with-long-token.sh`）を `--claude` に渡して `-p` で起こす形も確かめていない（`outer-loop.py` の docstring の「守らない」）。
  cron の環境で、親が `gh`・`git` を見つけて周を進められるか、`osascript` の通知が画面に出るかも確かめていない。
  **動かなければ、ログ（`>>` の先）と台帳の隣の `cruise-issue-<親>-loop/` の出力を見る。**

## 気をつけること

- **同じ台帳を回す親は 1 体だけにする**——`outer-loop.py` も `lockf` も、対話のセッションで走っている cruise を見ない（`outer-loop.py` の docstring の「守らない」）。
  **1・2 の経路を使うのは、対話のセッションの cruise を終えた後だけである**（上の「上限から戻る経路」）。
  セッションを残したままだと、上限が解けた後でタイマーが発火するか（#1401 では 08:25）自動継続で親が戻り、cron が起こした親と 2 体になりうる。
- **利用者が席に戻ったら、cron の行を消し、ログと台帳（`ledger.py show issue-<親>`）を見る。**
