# 周を `claude -p` の子プロセスで回す（#491）

**これは cruise スキルの一部である。** `SKILL.md` から分けてあるのは、**周を子プロセスで回すと決めたときにしか要らない**からで、
**規範として弱いからではない。**

**読む条件**: cruise の `SKILL.md` の「4. 周を回す」の 2 で、周を `claude -p` の子プロセスで回すと決めたとき。
**既定はサブエージェントのままである**——子プロセスは選べる形で、**下の「確かめた範囲」の 1・3 が実際の周で確かめられるまで既定にしない**。
**サブエージェントで回す cruise では読まなくてよい。**

## なぜ子プロセスか

- **周の担当の寿命を、親のセッションから切り離す。** サブエージェントは親の `/clear`・終了の道連れになりうる。
  子プロセスは**親から切り離して**起こすので（新しいセッション）、親が `/clear` しても、終わっても走り続ける。
- **子は起動のたびに、その時点で入っている dev-loop の版を読み込む**（下の「版」）。親が古い版のまま長く回っても、各周は新しい版で回る。
- **親の文脈に積まれるのは、要約の行だけ**——子の出力（stream-json）はファイルに落ちる。

## 回し方

1. **委譲文を作る**——`prompts/child-cycle.md` の `---` より下を、**メインの作業ツリーの `.claude/plans/` の下**に写して差し込みを全部埋める。
2. **起こす**——メインの作業ツリーから、**素の 1 行で**:
   ```bash
   python3 <このスキルの base ディレクトリ>/scripts/child-cycle.py launch issue-<親> <番号> --brief <委譲文> --permission-mode <許可モード>
   ```
   **許可モードは利用者が名指しした値を渡す**（下の「確かめた範囲」の 2）——**起動時の点検（cruise の `SKILL.md` §3）には許可モードを決める段が無い**。
   利用者が名指ししていなければ、子で回さずにサブエージェントで回す（親が推測で選ばない）。`--allowed-tools`・`--model`・`--max-budget-usd` は任意。
   **終了コード・記録の場所・何を守り何を守らないかは `scripts/child-cycle.py` の docstring を正とする。**
3. **台帳に書く**——`ledger.py set issue-<親> <番号> state=impl agent=claude-p:<起動口が出した記録のパス>`。
   **書くのは親だけ**（`../dev-loop/references/ledger.md`）。子には委譲文で書かないよう頼むだけで、**止める仕組みは無い**。
4. **要約を読む**——`python3 <…>/scripts/child-cycle.py status issue-<親> <番号>`。**出力ファイルを丸ごと読まない**
   （失敗の中身を見るときだけ、要約が名指しした範囲を読む——`../dev-loop/SKILL.md` の「道具の生出力を、親の文脈に積まない」）。
5. **終わったら、子の報告を実物で確かめてから台帳を書く**——`gh pr view <PR>`・`gh pr checks <PR>`・計画ファイルの再開点。
   **`status` が 0 でも「周が済んだ」ではない**——言えるのは「子が要確認の印なしに終わった」までである。
   **既定で起動口は結果の形を渡す**（下の「結果の形」）ので、0 には「子が形どおりに、PR を作って CI が通ったと申告した」も加わる——**申告は子の言い分で、実物で確かめるのは変わらない。**
6. **同じ Issue の子が走っている間は、2 体目を起こさない**（起動口が拒む）。並行に回してよいのは、台帳上で互いに依存しない周だけ（cruise の `SKILL.md` の「4. 周を回す」の 1）。

**周に掛かる必須は 1 つも外れない**——worktree → PR・2 つの関門・2 パス・受入基準の受け渡し・マージは親（cruise の `SKILL.md` の「4. 周を回す」の 2）。
**子を起こしたことは、周の必須を子に渡したことではない**——子は dev-loop のスキル本文と委譲文だけを読む。

## 親が `/clear` した後・タイマーで起動し直した後

`../dev-loop/references/ledger.md` の「どう再開するか」のとおり台帳から再開し、`agent` が `claude-p:` で始まる周は:

- **`status` が 1（走っている）なら、続きを起こさない**——待つ。待つあいだも枠の持ち主を見る（子は `SendMessage` で宛てられないので、知らせられないと台帳に書き、止める段の待ち（`STALL`）から進む）——`references/parallel.md` の「止まっている枠の持ち主」を正とする（#899）。
- **0 か 3 なら終わっている**——上の「回し方」の 5 のとおり実物で確かめる。3 の印（利用上限の拒否・拒否された操作・殺された体など）は要約の行に出る。
- **4 なら判定できていない**——「終わった」とも「走っている」とも読まない。記録のパスを確かめる。
- **周の続きを回すなら、同じ形でもう 1 体起こす**——子は dev-loop の「途中から再開する周」（`find-cycle.py`）で自分の周を見つけ、計画ファイルの再開点から続ける。

## 版

**子が読み込む dev-loop の版は、main の版とは限らない。**
**実測**（2026-10-29）: main が 1.63.8 のとき、子の init の `plugins` は dev-loop **1.63.6** だった。
**言えるのはここまでである**——その時点の `~/.claude/plugins/installed_plugins.json` の記録の版（全体に入れた項）も、キャッシュの最大版も 1.63.6 で、
**どちらが決めたかは判別していない**。記録にはプロジェクトだけに入れた項もある（このリポジトリの外のプロジェクトで別の版を名指ししていた）ので、
**別のプロジェクトで cruise を回すと、子は別の版を読み込みうる。**
**版は起動の時点で決まるとも限らない**——試し 2 では同じプロセスで init が 3 回出て、2 回目から他のプラグイン（cmux・orca・spec-loop）の版が変わった（dev-loop は 3 回とも同じ）。
**新しい版で回したいなら、子を起こす前に `claude plugin update` で記録を進める**——これは利用者の操作で、cruise は打たない
（プロジェクトの `CLAUDE.md` の「キャッシュに在ることは、読み込まれることではない」）。
**`status` は子が読み込んだ版を出す**（最初の init の版。途中の init で変わったら両方）——親は、子がどの版で回ったかをそこで見る。

## 認証

**子の環境は親の Bash の環境を写して作る**——ただし **Claude Code 2.1.316 は起動時の `CLAUDE_CODE_OAUTH_TOKEN` を Bash の環境から外す**ので、
写すだけでは、長期トークンで起動した親（`launch-with-long-token.sh`）の子が長期トークンを継がない。
**2026-11-02 に実プロセスで観測した**（#785。値は出さず、変数の名前の有無だけを見た）: `launch-with-long-token.sh` で起動した `claude -p`（haiku・小さな 1 回）の Bash から
直す前の `child-cycle.py launch` で子（偽の `claude`）を起こすと、**起動した `claude` の環境には `CLAUDE_CODE_OAUTH_TOKEN` が在るのに、Bash の環境にも子の環境にも無かった。**

**だから起動口は、Bash の環境に `CLAUDE_CODE_OAUTH_TOKEN` が無ければ、親のセッションを起動した `claude`（最寄りの祖先）の環境から読み、
空でなければ子の環境に置く**——読み方は `../dev-loop/scripts/check-unattended-env.py` の点検の「認証」と同じ（`launcher_auth_env`）。
直した `child-cycle.py` で同じ観測をして、子の環境に在ることを確かめた（#785。どちらの回も、記録として残っているのは `claude -p` が probe の出力を写した結果である）。

- **Bash の環境にあれば、それを継ぐ**（祖先は見ない）。
- **祖先を読めない・祖先に `claude` が無い・そこにも無い（対話ログインの親）なら、子は Bash の環境だけを継ぐ**——いままでと同じで、起動時の出力の「認証:」の行がそう言う。
- **子の環境から認証の変数を消す設定（`CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`・`GITHUB_ACTIONS`）なら、祖先から渡さない。**
- **値は出力・記録に出さない**——記録の `.json` の `auth` は名前と、渡したか・どこから渡したかだけである。
- **子が受けたかは、子のプロセスの環境を名前だけで見る**——`ps eww -o command= -p <記録の pid> | tr ' ' '\n' | grep -c '^CLAUDE_CODE_OAUTH_TOKEN=.'` が 1 なら在る
  （値は出ない。`auth` は渡した側の記録で、子が受けた値ではない）。**0 は「無い」とは限らない**——`ps` に環境が見えないプロセスでも 0 になるので、
  同じ形で `grep -c '^PATH='` も数え、1 であること（環境が見えていること）を確かめてから 0 を「無い」と読む。

**確かめたのは「子の環境に置いた」までである**——子がそのトークンで認証して 8 時間を超えて回ることは、この観測では見ていない
（子は偽の `claude`。8 時間の観測は #584 の受入基準 1）。何を守り何を守らないかは `scripts/child-cycle.py` の docstring を正とする。
**認証の点検と長期トークンでの起動は #584 を正とする**（ここに再掲しない）。

## 結果の形（#991）

**起動口は既定で `--json-schema` に結果の形を渡し、`status` は最後の `result` の `structured_output` を記録に残した形で検査する**——子の最後の報告の文を親が読んで決めていた部分（PR を作ったか・CI・止まった理由・利用者に要ること）を、スクリプトの判定に寄せるため。
**形の欄・検査・終了コード・何を守り何を守らないかは `scripts/child-cycle.py` の docstring と `RESULT_SCHEMA` を正とする**（ここに欄を列挙しない）。`--no-structured` で外せる。

**2026-11-12 に、Claude Code 2.1.322・`--model haiku`・リポジトリの外の空のディレクトリを cwd にした小さな子 5 回で測った**（計約 $0.04。数えたのは出力ファイルの `result` の行の実物）:

- **`--json-schema` を渡すと init の道具に `StructuredOutput` が足され（`--tools ""` でも）、`result` に `structured_output` が載る。渡さなければ道具も欄も無い**（陽性・陰性の対照）。
- **スキルを入口にし（`--plugin-dir` のスキルを `/<プラグイン>:<スキル> 7` で起動）、Bash と背景の `Agent`（`sleep 15`）を使い、上限 0 で待った子は、`result` を 2 つ出した**——
  **1 つ目の `structured_output` は背景の体を待つ前の `stopped`、最後が `done`**（init は 2 回・殺された体 0）。**だから読むのは最後の `result` だけである。**
- **予算切れ（`--max-budget-usd 0.001`）の `result` は `error_max_budget_usd` で、`structured_output` は無い**——`status` は「成功でない」と「structured_output が無い」の両方で 3 にする。
- **`RESULT_SCHEMA` そのもの（`null` を許す型の配列を含む）を CLI が受け、形どおりの `structured_output` を返した**（道具なしの 1 回）。

**確かめていないこと**: **実際の dev-loop の 1 周（関門 × 2 パス・`/code-review` の fork・数十分）で、最後の `result` に `structured_output` が載るか**——
載らなければ `status` は 3 になる（黙って 0 にはならない）。**形を渡したことで子のターンの終え方が変わるか**（`StructuredOutput` を早く呼ぶことは、上の試しで見た）。
測るのは下の「利用者が測る手順」の 1 である。

## 実際の 1 周で観測したこと（2026-11-02、#778 の子）

**数えたのは cruise #474 の親で、子の報告ではなく出力ファイルの実物である**（[#491 のコメント](https://github.com/hdknr/claude-code-setup/issues/491#issuecomment-6568196968)）。
子は `claude -p`・許可モード `auto`・dev-loop 1.63.6（そのときの main は 1.74.0）・費用 $10.18 の 1 回。

- **受入基準 1（関門 × 2 パスが子の中で終わる）: 満たしていない。** `dev-loop:dev-loop-verifier` の `Agent` は 2 つ、`code-review` の `Skill` は 2 つ、
  計画ファイルの再開点は 2 パス目まで書かれていたが、**最後の `result` の `subagent_stats.killed` が `{'parent': 0, 'user': 0, 'system': 1}`** だった。
  止められたのは背景で起こした 2 パス目の Verifier で、子の標準エラーは
  `Background tasks still running 10m after the last turn (subagent "Verifier pass 2 for #778", …); stopping them. Set CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0 to wait indefinitely.`
  と言った。子は `SendMessage` でその Verifier を再開して報告を回収し、関門は 2 パスまで回りきった（PR #780・CI 緑）が、
  **「関門が子の中で回りきるか」の答えは「背景の体は、最後のターンの後の待ちの上限で止められうる」である。**
  ほかに、1 パス目の `/code-review` に受入基準を渡せていなかった（子が PR #780 に申告した）。
- **受入基準 2（親の `/clear` から拾う）: 満たした。** 子は親の `/clear` をまたいで同じ pid のまま走り続け、再開した親は `status` で「走っている」と読み、
  2 体目を起こさず、PR #780 と CI を実物で確かめてから台帳を書いた。
- **子が最終報告の後も自分で終わらなかった（記録だけ。直さない）。** 最終報告から 10 分以上たっても子のプロセスは終わらず
  （残っていた子孫は cmux のフックと cmux-cua の MCP だけ）、親が TERM で止めた。**原因は特定していない**（cmux の環境に固有かもしれない）。
  **「子が自分で終わる」は確かめていない**——利用者の決定（2026-11-02）で、また起きたら直す。

**手当て（受入基準 1 について）**: 起動口は子の環境に **`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`** を置く——親の環境に別の値があっても 0 で上書きし、
上書きしたことを出す（理由と、何を守り何を守らないかは `scripts/child-cycle.py` の docstring を正とする）。
**0 が背景の体を止めずに待たせることは、子の標準エラーの文言によるだけで、まだ測っていない。** 待ち続けた体が終わらなければ子も終わらない
——そのときの `status` は 1（走っている）のままである。

**測り直しは、次に子で回す周のついでに行う**（利用者の決定、2026-11-02）——下の「利用者が測る手順」の 1 で、0 を渡した子について数え直す。
**それまで受入基準 1 は満たしていない扱いで、既定はサブエージェントのままである。**

## 利用者が測る手順（#491 の受入基準 1・2）

**この 2 つは、cruise の親（メインの作業ツリーのセッション）でしか測れない**——1 周は数ドル以上かかり、`/clear` は人の操作である。

1. **1 周を子で回す**（受入基準 1）:
   1. 不在の cruise をいつもどおり起動し、着手できる周を 1 つ選ぶ（小さい周がよい）。
   2. 上の「回し方」の 1〜3 で子を起こす。許可モードは起動時の点検で決めた値。
   3. 終わったら `status` を読み、**出力ファイルから次を数える**——`Agent` の `tool_use` のうち `subagent_type` が `dev-loop:dev-loop-verifier` のもの（2 つ以上・狭いパスがあれば 3 つ）、
      `Skill` の `code-review` の呼び出し（2 つ）、`subagent_stats.killed` が 0 であること、計画ファイルの再開点が 2 パス目まで書かれていること。
      **標準エラーに `Background tasks still running` の行が無いことも見る**（上の「実際の 1 周で観測したこと」）。
      **記録の `.json` の `env` は起動口が子に渡した値で、子が受けた値ではない**——渡したのに上限が効いたかは、この標準エラーの行と `killed` で見る。
      **数えるのは出力ファイルの実物である**——子の報告は数えない。
      **結果の形を渡した子（既定）なら、最後の `result` に `structured_output` が在り、`status` の「結果の形:」の行が欄を出すことも見る**（#991。上の「結果の形」の確かめていないこと）。
2. **親の `/clear` から拾う**（受入基準 2）:
   1. 子が走っている間（`status` が 1）に、親のセッションで `/clear` する。
   2. メインの作業ツリーで同じ引数（`/dev-loop:cruise <親> --absent`）で起動し直す。
   3. 再開した親が、その周を `status` で「走っている」と読み、2 体目を起こさず、終わった後に実物（PR）で確かめて台帳を書いたことを見る。
      **`ps -o pid,lstart,command -p <記録の pid>` で、子が `/clear` の前から同じ pid で走り続けていたことも見る。**
