# dev-loop スキル

GitHub Issue 1 件を、**検証が通ることを停止条件**として 1 周させるループ志向開発の手順。
どのプロジェクトでも使えるよう汎用化してある。プロジェクト固有の事情（実機検証コマンド・
デプロイ経路・一次ソースのドキュメント）は、**対象リポジトリの `CLAUDE.md`** から発見して従う。
無ければ下記の汎用手順に縮退する。

設計の背景（なぜループ志向か・verify を停止条件に据える理由・Dreaming・トークンコスト・
アンチパターン）は「dev-loop の設計」を参照:
<https://hdknr.github.io/claude-code-setup/plugins/dev-loop-design/>

引数: `/dev-loop <issue-number>`（省略時は現在の作業対象 Issue を尋ねる）。

## はじめに — プロジェクト固有設定の発見

サイクルに入る前に、対象リポジトリのローカル文脈を 1 度だけ確認する。**該当が無い項目は読み飛ばす**。

1. `CLAUDE.md`（ルート／サブディレクトリ）を読む。以下を拾う:
   - **実機検証（verify）の手順・コマンド** — 例: 開発サーバ起動スクリプト、実データ接続、E2E 実行。
   - **デプロイ経路** — 何をどうマージ／ビルド／apply すると本番に反映されるか。変更種別で経路が分かれるか。
   - **やってはいけない制約** — 破壊的操作・自律発注・特定 apply の前提条件など。
   - **一次ソースのドキュメント** — 開発フローや運用 runbook が別ファイルにあれば、それを正とする。
2. `.claude/dev-loop.md` があれば、それをこのプロジェクト向けの追補設定として最優先で従う（任意）。
3. どれも無ければ、テスト実行（`Makefile` / `package.json` scripts / CI 定義から推測）と
   アプリ起動の**汎用手順に縮退**する。`/run` スキルが使える環境ならアプリ起動はそれに委ねてよい。

## 原則

- **停止条件は verify**。「テストが緑」だけでは完了にしない。ロジック変更は
  **実際に動かして期待挙動を目視**するまで完了扱いにしない。
- **PR を出す変更は必ず worktree 上で行う（必須）**。メインの作業ツリーを汚さず、
  他の周・他の Issue と並行できる状態を保つ。worktree に入らずに PR を作ってはならない。
- **対象リポジトリの `CLAUDE.md` のルールを守る**（コーディング規約・図版規約・製本／デプロイ制約など）。
- **本番への破壊的操作・不可逆操作は勝手に実行しない**。CLAUDE.md の制約と、明示の承認に従う。

## サイクル

対象 Issue に対して、以下を順に実施する。5↔4 は verify が通るまで繰り返す。

### 1. Issue 選択

```bash
gh issue view <issue-number>   # 要件・受入条件・関連 PR を把握（必須）
```

### 2. 文脈収集

- 関連する設計ドキュメント・過去の議論・既存実装を読む。
- Issue の受入条件を「何を目視できれば満たしたと言えるか」に翻訳しておく（後の verify の基準になる）。
- GSD を使う運用なら `/gsd:discuss-phase` で文脈を固める（任意）。

### 3. 計画

- **変更範囲を切り分ける**。CLAUDE.md でデプロイ経路が変更種別ごとに分かれている場合、
  どの経路に乗るかをここで決める（後の本番反映手順が変わる）。
- **設定／フラグで挙動を切替できないか**を先に判断（可能なら再ビルドや再デプロイを避けられる）。
- GSD を使う運用なら `/gsd:plan-phase`（任意）。

### 4. 実装

- **最初に worktree を開始する（必須）**。ファイルを 1 行も触る前に、Issue 用の worktree に入る。
  PR を作る周では例外を認めない（PR 作成時点で worktree 上にいる必要があり、実装後に
  移し替えるのは手戻りになる）。
  ```bash
  # EnterWorktree ツールが使える環境ではそれを使う（後片付けまで面倒を見てくれる）。
  # 使えない環境の同等操作:
  git worktree add ../<repo>-issue-<issue-number> -b issue/<issue-number>-<説明>
  ```
  - すでに worktree 上にいる（`git rev-parse --git-common-dir` と `--git-dir` が異なる）なら、
    そのまま続けてよい。
  - メインの作業ツリーに未コミットの変更を作ってしまっていた場合は、`git stash` →
    worktree 作成 → `git stash pop` で移送してから続ける。
  - ブランチ名は対象リポジトリの CLAUDE.md の命名規約に従う（規約が無ければ
    `issue/<番号>-<説明>`）。
- 対象リポジトリの CLAUDE.md のルールに従って変更する。既存コードの流儀（命名・コメント量・
  イディオム）に合わせる。
- GSD を使う運用なら `/gsd:execute-phase`（任意）。

### 5. 検証（停止条件）— ここがループの本体

局面に応じて verify を通す。**通らなければ 4 に戻る。**

- **実機確認**: はじめに発見した verify 手順（開発サーバ起動・実データ接続・E2E 等）で、
  期待する挙動を**実際に目視**する。無ければ汎用手順（テスト＋アプリ起動での手動確認、`/run`）で代替。
- **設定変更で反映できる場合**: 対象のフラグ／環境変数を更新し、反映されることを確認する。
- **別モデル Verifier（牽制）**: 実装したエージェントは自分の変更に甘い。受入条件の充足を
  **実装とは別モデルの検証エージェント**で判定させる（`Agent` ツールで `subagent_type` に
  `feature-dev:code-reviewer` 等、`model` に実装時と別ティア＝例: 実装が Opus なら `sonnet` を指定）。
  「受入条件◯◯を満たさない反証を探せ。証拠（テスト結果・ログ・目視項目）で示せ」と指示し、
  **反証が挙がれば 4 に戻る**。同一モデルだと盲点を一緒に見逃すため、モデルを変えるのが要点。

### 6. レビュー → PR

- `/code-review` で差分をレビューし、指摘を反映する。
- **PR 作成の前提条件（必須）: worktree 上にいること**。作成前に必ず確認する:
  ```bash
  test "$(git rev-parse --git-dir)" != "$(git rev-parse --git-common-dir)" \
    && echo "worktree OK" || echo "NOT in a worktree"
  ```
  - `NOT in a worktree` の場合は **PR を作らない**。手順 4 の worktree 開始に戻り、
    変更を worktree へ移送してから（未コミットなら `git stash` → worktree 作成 →
    `git stash pop`、コミット済みなら worktree でそのブランチを checkout）PR を作る。
  - デフォルトブランチ上にいる場合も同様に、worktree でブランチを切り直してから作る。
- worktree 上のブランチを push して PR を作成する（`gh pr create`）。
- **レビュー結果は必ず PR コメントに残す**（`gh pr comment <n> --body ...`）。発見・修正した実問題、
  検証して問題なしと確認した項目、意図的スキップ、残課題を記録し、後追いできるようにする。
  実データ照合を行った場合はその結果も同様にコメントする。

### 7. 本番反映

対象リポジトリの CLAUDE.md ／ deploy runbook に従う。固有手順が無い一般的なプロジェクトでは:

1. レビュー承認 → merge
2. CI／CD の完了を待つ（`/loop` で完了待ちを自動化してよい）
3. デプロイ後の疎通・マイグレーション等、リポジトリの手順に従って本番状態を確認

**破壊的・不可逆な反映（DB マイグレーション・インフラ apply 等）は CLAUDE.md の前提条件を確認し、
必要なら人間の承認を得てから**実行する。

### 8. 経験の還元（次の周を賢くする）

1 周で得た学びを**リポジトリ側の恒久資産に焼き戻して**からループを閉じる。「モデルは忘れる、
リポジトリは忘れない」——ここをサボると次の周が同じ所で同じ事故を踏む。該当するものだけでよい:

- **成功の型** → CLAUDE.md / 該当 Skill / リポジトリ内 docs の手順・テンプレートに反映。
- **失敗の教訓** → 再発防止の「やってはいけない」を CLAUDE.md か該当 Skill に追記。
- **非自明な事実**（コードや git 履歴から辿れないもの）→ 永続メモリに 1 ファイル 1 事実で保存し
  `MEMORY.md` に 1 行追加（メモリ機能を使う環境の場合）。既存メモリと重複するなら更新する。
- **CLAUDE.md・Skill・メモリの変更は必ず PR で人間レビューを通す**（自律ループに載せない）。

## 待ち時間・定時処理は別スキル

- ビルド／CI／デプロイの**完了待ち**は `/loop`（間隔指定 or 自走）。
- inbox トリアージ・夜間バッチ結果の**定時点検**や、週次の自己改善（Dreaming）は `/schedule`。
  産物は必ず PR で人間レビューを通す。

これらは Claude Code の汎用スキル。導入していない環境では、手動での待機・確認に読み替えてよい。
