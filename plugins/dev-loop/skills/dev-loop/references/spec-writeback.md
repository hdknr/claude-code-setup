# 仕様にある振る舞いを変える周を、正本に戻す（#1001）

**このファイルは、対象リポジトリに spec-loop の正本があるときに読む**（`SKILL.md` 手順 3・6 と `references/spec-gap.md` から指している）。
正本があるとは、次のどちらかである（判定の式は `scripts/check-spec-writeback.py` の docstring の「読むもの」を正とする）:

- **同じリポジトリ**に版のディレクトリ `docs/v<数字>/`（中に `shared/`・`requirements/`・`spec/` のどれか）がある
- **別のリポジトリ**にあり、対象リポジトリの `.claude/dev-loop.md` に `仕様の正本: <owner>/<repo>` の行があるか、根に `scaffold-source.txt`（spec-loop プラグインの `tree.md` の「Red テストを CI で走らせ続ける」）がある

**正本が無いリポジトリでは読まなくてよい**——申告も求めない。
**ここに書いてある `（必須）` は、`SKILL.md` に書いてあるのと同じ重さで効く。**

## なぜ要るか

spec-loop → dev-loop は、**仕様からコードへ**の向きのずれを何重にも見ている（機能の指紋・Red テストの sha256・基準コミットの点検。`references/spec-gap.md`）。
**コードから仕様へ**の向き——spec-loop から来ていない周（障害の修正・小さな改修・依存の更新に伴う変化）が、仕様にある機能の利用者に見える振る舞いを変えた——には道が無く、
次の版の差分の周を始めるまで誰も気づかなかった。仕様をシステムと一緒に進めるには、**変えた周が、変えたことを正本に残す**必要がある。

## 申告（必須）

**正本があるリポジトリの周は、計画ファイルに次の 1 行を書く**——手順 3 で、手を動かす前に:

```text
仕様の振る舞い: <値>
```

| 値 | いつ |
| --- | --- |
| `変える` | この周が、**仕様にある機能の、利用者に見える振る舞い**を変える |
| `変えない` | 変えない——内部のリファクタリング・実現の手段の変更・仕様に無い振る舞いだけ |
| `spec-loop の Issue` | Issue が spec-loop から来た（本文の先頭が `<!-- spec-loop-handoff: v` の印）——振る舞いは仕様が決めていて、`references/spec-gap.md` が受け持つ |

- **行頭から書く**（箇条書きの `- ` は前に置いてよい）。**1 ファイルに 1 本だけ。** コードフェンスの中の行は数えない。
- **「仕様にある機能」は、重ね合わせた全体（spec-loop の `merge-versions.py` で作る `build/merged/`）の `spec/`・`requirements/`・`shared/` の表が述べる機能である。**
  名前の grep だけで決めない（`SKILL.md` 手順 3 の「エンティティ名の grep だけで数えない」）——変える振る舞いを述べている箇所を読む。
- **「利用者に見える振る舞い」の線は、spec-loop の `spec-scope.md` の縦の線と同じ**——仕様に書くのは利用者に見える結果で、内部の値・実現の手段は書かない。
  **それらだけを変える周は `変えない`。** **迷ったら `変える`**（下の行を残すだけで、周は止まらない）。
- **周の途中で変えることになったら、手を動かす前に書き直す**（手順 4 の「変更範囲の外へ、黙って出ない」と同じ）。

## 振る舞いを変える周が残すもの（必須）

**仕様（`spec/`・`requirements/`・`shared/` のほかの表）は、周の中で直さない。** 正本の Q&A 表に、**変えたことを利用者に訊く行**を 1 行足す
——仕様の変更はサインオフ（要求確定・仕様レビュー）を通る決まりで、開発の周が仕様を直すとそれを飛ばす。行は次の `req-loop` が拾い、
反映されるまで spec-loop の `check-spec-exit.py` が数えるので、次の版の仕様レビューを抜けられない——**忘れられない。**

- **同じリポジトリ**: 作業中の版（`docs/` の版で番号が最大のもの）の**共有の** Q&A 表 `docs/v<n>/shared/qa.csv` に、この周の worktree の中で 1 行足す
  （手順 3 の「変更範囲」に表を足してから書く）。**内部の表（`qa-dev.csv`）・リリースした版（凍結）・`build/merged/` には書かない。**
  列の決まりは `references/spec-gap.md` の「差し戻す」の 2 の表を正とする（`No` は開発の印の番号・起票元 `開発（#<この Issue>）`・回答 `未回答`・反映先 `—`・状態 `確認中`）。違うのは中身だけ:
    - **`質問`**: 何をどう変えたかを、利用者が答えられる言葉で書く（例: 「締め日が休日のとき、請求日を前の営業日にずらすように直した。仕様もそう直すか」）
    - **`選択肢`**: 少なくとも `A: 仕様をこの振る舞いに直す / B: 前の振る舞いに戻す`（B を選ばれたら、この周の変更を戻す Issue になる）
    - **`推奨`**: 開発が推すもの（ふつうは A。この周の Issue がその振る舞いを求めているので）と、`推奨の理由`
  spec-loop の `check-qa-csv.py` が手元にあれば、それで表を検査する。
- **別のリポジトリ**: **正本へ書きに行かない**（worktree の外を触ることになる。`references/spec-gap.md` の「差し戻す」の 2 と同じ。権限があっても無くても同じ）。
  上と同じ列の 1 行を CSV で計画ファイルに書き（`No` は空——振るのは正本の表に書く人）、PR コメントにも同じ行と正本の名前を書いて人に渡す:

  ```text
  正本に起票する行: ,開発（#123）,締め日が休日のとき…,A: 仕様をこの振る舞いに直す / B: 前の振る舞いに戻す,A,…,未回答,—,確認中,
  ```

- **PR コメントに「仕様に戻す行」の見出しで**、足した行の No（別のリポジトリなら行そのものと正本の名前）を名指しする。
- **この行は確認の Issue を兼ねない**——問いの宛先は利用者（`req-loop`）で、`references/absent-lines.md` の「確認の Issue の書き方」の対象ではない。不在の周でも同じ形で残す。
- **周はふつうに閉じてよい**——この周の受入基準はこの周の Issue のもので、行は「変えたこと」の記録である。**ただし下の「Red テストが赤になったら」に当たる変更は閉じない。**

## Red テストが赤になったら（必須）

**緑のケースの一覧（`scaffold-green.txt`）に載った Red テストは、仕様にある振る舞いを機械で確かめている**（spec-loop プラグインの `tree.md` の「Red テストを CI で走らせ続ける」）。
この周の変更で `green-list.py check` が 1（載ったケースが緑でない）になったら——申告が `変えない` でも `変える` でも:

- **Red テストを直さない。一覧から行を外さない。`record --accept-changed` で落とさない。** どれも、仕様が決めた振る舞いを周の中で書き換えることになる
  （`--accept-changed` は、作り直しで仕様がそのケースを変えたと人が確かめたときだけのもの）。
- **コードの誤りなら、直す**——この周の変更がケースを壊したなら、その変更が誤っている。
- **仕様を直すべき変更なら、`references/spec-gap.md` の「差し戻す」に従う**——Red テストと食い違う穴として、上の行を起票し、その部分の実装を止め、PR を draft にして周を閉じない。
  **不在の線の `仕様の穴 = 推奨で決めて起票` でも推奨で進めない**（`references/absent-lines.md` の「spec-loop から来た Issue の穴」の「Red テストと食い違う穴」と同じ線）。
- **どちらか決められなければ、仕様を直すべき変更として扱う**（`spec-gap.md` の「境目に迷ったら、穴として扱う」）。

## PR の前に当てる（必須）

**正本があるリポジトリでは、PR を作る前に、worktree を cwd にして素の 1 行で当てる**——終了コードで分岐する（`SKILL.md` 手順 6 の「終了コードで分岐するスクリプトは、包まずに素の 1 行で呼ぶ」）:

```bash
python3 <このスキルの base ディレクトリ>/scripts/check-spec-writeback.py <周の base の SHA>
```

**main を取り込んだ後は、`SKILL.md` 手順 4 の式を当て直した base を渡す。** 正本が無いリポジトリでは何も求めずに 0 を返すので、どのリポジトリで当ててもよい。

**0**: 正本が無いか、申告と残すものが揃っている。**1**: 申告が無い・値が違う・`変える` なのに行が無い・緑のケースの一覧から載った行が減った
——**PR を作らない。** 計画に申告を足すか、上の行を足すか、一覧の行を戻して上の「Red テストが赤になったら」に従ってから当て直す。
**2**: 判定できない（緑ではない）。終了コードの中身と、何を守り何を守らないかはそのスクリプトの docstring を正とする。

**このスクリプトが見るのは、申告の行と残したものの形までである**——**申告の真偽**（本当は振る舞いを変えたのに `変えない` と書く）は、
緑のケースの一覧が覆う振る舞いだけを製品の CI の `green-list.py check` が赤にする。Red テストの無い振る舞いの申告漏れは機械では見えないので、
**申告を決めるときは、変えた振る舞いを仕様の原文と照らす**（上の「申告」）。
