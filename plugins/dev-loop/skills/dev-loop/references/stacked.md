# 積んだ周（stacked）

**これは `dev-loop` スキルの一部である。** `SKILL.md` から分けてあるのは、
**別の周のブランチに積んで始めた周でしか要らない**からで、**規範として弱いからではない**
——**`（必須）` はここでもそのまま効く。**

**読む条件**: **下の周の PR がまだマージされていないうちに、そのブランチの上に積んで周を始めるとき**、
**積んだ周を再開するとき**、**下の周がマージされたとき**、**下の周にコミットが足されたとき**に読む。
**既定ブランチから切った周では読まなくてよい。**

**周の base の式は `SKILL.md` 手順 4 の「周の base は 1 つに決まっている」を正とする**（ここに複製しない）。
**以下は、その式を積んだ周の連鎖にどう当てるか**である（[#392](https://github.com/hdknr/claude-code-setup/issues/392)）。

## なぜ要るか

#389 の周では、依存のある課題を、**下の課題の API が固まった時点で未マージのブランチの上に積んで**先に始めた。
`prepare-worktree.sh` は `DEV_LOOP_BASE_REF` で積んで切れるが、**切った後の連鎖**——下の PR がマージされたら
上をどうするか——は書いていなかった。そこに 2 つの落とし穴がある:

- **下の PR を squash すると、下の元のコミットは既定ブランチに入らない。** 上の周は下の元のコミットの上にあるので、
  **base の式を当て直すだけでは、下の変更が上の差分に「追加」として混ざる**
  （一時リポジトリで再現した——`git merge-base main HEAD` からの差分に、下の周のファイルが出た）。
  **素の `git rebase main` は、下の元のコミットを載せ直そうとして衝突しうる**（同じ再現で、下に後からコミットを足した場合に衝突した）。
- **`merge-pr.py` でマージした下のブランチは残る。** `merge-pr.py` はブランチを消さない（squash したブランチは `git branch -d` が通らない。docstring）。
  **上の PR の base を下のブランチのままにしてマージすると、上の変更は既定ブランチではなく下のブランチへ入る**
  ——**止まらないので気づけない。**
- **下のブランチが消えると（「Automatically delete head branches」）、GitHub は上の PR の base を付け替える。
  head は下の元のコミットを持ったままである**——**base の名前だけ見ても、載せ替えていないことが分からない**
  （[#427](https://github.com/hdknr/claude-code-setup/issues/427) で本物の GitHub で確かめた。timeline に `automatic_base_change_succeeded` が残る。
  **確かめたのは下を既定ブランチへ出した形**で、上の base は既定ブランチへ付け替わった。下を別のブランチへ出した形は確かめていない）。
- **`merge-pr.py` は、載せ替えていない積んだ周の PR をマージしない**——**何で見分けるか（と、見分けられない形）は docstring を正とする**
  （[#426](https://github.com/hdknr/claude-code-setup/issues/426)。**base が既定ブランチでないことだけでは止めない**）。

## 積むと決めたら

1. **積むのは、下の周の PR が出ていて、上が使う部分（API・型・ファイルの置き場所）が下の関門を通った後**にする。
   **積むかどうかは人間が決め、その判断を計画ファイルに書く（必須）。** 利用者不在のときに誰が決めてよいかは、ここでは決めない。
2. **切るのは `prepare-worktree.sh` に `DEV_LOOP_BASE_REF=<下のブランチ>` を渡して**（`SKILL.md` 手順 4）。
   リモートの下のブランチ（`origin/<下のブランチ>`）を渡せば、取り直してから切る。
3. **計画ファイルの「周の在り処」に、次を書く（必須）**——`SKILL.md` 手順 3 の 5 番目に足す分である:
    - **積み先**: 下のブランチの名前・下の Issue と PR の番号
    - **base**: 参照の名前（`DEV_LOOP_BASE_REF` に渡したもの）と解決した SHA（`prepare-worktree.sh` の出力をそのまま写す）
    - **載せ替えの履歴**: 載せ替えるたびに 1 行（いつ・何の上へ・前の base → 新しい base）。**前の行を消さない**
      ——**base の SHA を書き換えた跡が無いと、再開した側は古い SHA と新しい SHA のどちらが正か決められない。**
4. **PR は下のブランチを base にして出す（必須）**——`gh pr create --base <下のブランチ>`。
   **素の `gh pr create` は既定ブランチを base にする**ので、**下の周の差分がまるごと上の PR に載る。**
   PR の本文に「#<下の PR> に積んでいる。下がマージされたら載せ替える」と書く。
5. **上の周の自分のコミットは、いつでも `<記録した base>..HEAD` である。** **下を `git merge` で上に取り込まない**
   ——**マージコミットが入ると、この範囲が上の周のコミットだけを指さなくなる。**

## 下の周にコミットが足されたら

下の関門の指摘対応で、下のブランチが進むことがある。**上が下の新しいコミットを要るなら、`rebase --onto` で載せ直す**。
**`<積み先の参照>` は「周の在り処」に書いた参照の名前**である——**`origin/<下のブランチ>` で切った周は、先に取り直す**
（下のコミットは別の worktree かリモートにあり、手元の参照は取り直すまで動かない。古い参照のまま載せると古い先端に載る）:

```bash
git push origin <上のブランチ>                       # 手元のコミットをリモートに揃える（force しない。前提は次の節の 2）
git rev-parse HEAD                                   # 載せ直す前の HEAD——控えておく（push の lease で使う）
git fetch origin                                     # 積み先がリモート追跡の参照のとき
git rebase --onto <積み先の参照> <記録した base>
git merge-base <積み先の参照> HEAD                   # 新しい base——控える（履歴に書くのは push の後）
git push --force-with-lease=<上のブランチ>:<載せ直す前の HEAD> origin <上のブランチ>
```

**載せ直したら、その場で push する**（形は次の節の 5 と同じ。**期待する SHA を名指しする**）。
**載せ替えの履歴に 1 行書くのは、その push の後**である（次の節の 5 と同じ）。
**push しないまま次の節へ進むと、リモートには載せ直す前のコミットが残るので、次の節の 2 の素の push が `non-fast-forward` で拒否される**
（一時リポジトリで再現した。他の clone が無くても起きる）
——**そこで `--force`・素の `--force-with-lease` に手を伸ばすと、次の節の 5 が塞いだ危険に戻る。**
**PR の base は下のブランチのまま**にする（付け替えるのは下がマージされた後）。

**上が要らないなら載せ直さなくてよい**——下がマージされるときに一緒に片付く（次の節）。

## 下の周がマージされたら（必須）

**上の周の PR をマージする前に、必ず載せ替える。** 載せ替えるまで、上の周は手順 7 に進めない。

1. **下の PR が `MERGED` であることを実物で確かめる**（`gh pr view <下の PR> --json state`）。子や台帳の報告で代えない。
2. **上の周の自分のコミットを push し、載せ替える前の HEAD を控えてから**、既定ブランチを取り直し、**取り込まれる歯止めを先に見て**、上の周の自分のコミットだけを載せ直す:
   ```bash
   git push origin <上のブランチ>                           # 手元のコミットをリモートに揃える（force しない）
   git rev-parse HEAD                                       # 載せ替える前の HEAD——控える（4 と 5 で使う）
   git fetch origin
   git diff --name-status --no-renames HEAD...origin/<既定ブランチ> -- scripts/ 'plugins/*/scripts/*'   # 6 で掛かる歯止め
   git rebase --onto origin/<既定ブランチ> <記録した base>
   ```
   **控える前に push するのは、5 の lease の前提だから（必須）**——lease が比べるのは**リモートの現在値**で、
   控えるのは**手元の** HEAD である。**push していないコミットがあると 2 つが食い違い、5 の push が `stale info` で拒否される**
   （一時リポジトリで再現した）。**この push は force しない**——**拒否されたら、リモートに手元に無いコミットがある**
   ——**他の clone・別のセッションが push したか、自分が前に載せ替え・書き換えたまま push していない**
   （後者は `non-fast-forward` で、他の clone が無くても起きる。一時リポジトリで再現した）。
   **どちらかは手元からは決めきれないので、載せ替えに進まず、人間に訊く。** **`git pull` で取り込まない**——
   **後者なら載せ替える前の古いコミットが上のブランチに混ざる**（「積むと決めたら」の 5）。
   **`--force`・素の `--force-with-lease` で通さない**——**5 が塞いだ危険（他の clone のコミットを消す）に戻る。**
   **計画ファイルに未コミットの変更があれば、先にコミットしてから push する**（下のとおり、未コミットなら rebase が断る）。
   **控えた値は、まだ計画ファイルに書かない**——**計画ファイルは追跡されている**ので、**未コミットなら rebase が断り**、
   **コミットすると HEAD が動いて 4 の `range-diff` に `>` が出る**（どちらも一時リポジトリで再現した）。
   **計画ファイルに書くのは 5 の push の後**（載せ替えの履歴の 1 行と一緒に）。
   **歯止めの一覧は rebase の*前*に見る**——**後では 3 点の diff が空になる**（取り込んだ分が HEAD の祖先になるので）。
   **`<記録した base>` は計画ファイルの最新の行**（下に載せ直していれば、その後の値）。
   **rebase の直後なら `ORIG_HEAD` も載せ替える前の HEAD を指す**が、**次に HEAD を動かす操作で上書きされる**ので、控えた値を正とする。
3. **base を当て直して、新しい base を控える**——参照の名前は `origin/<既定ブランチ>` に変わる。
   **式は `SKILL.md` 手順 4 のまま**で、**変わるのは「切った元の参照」だけ**である。
   **載せ替えの履歴にはまだ書かない**——**書いてコミットすると HEAD が動き、4 の `range-diff` に `>` が出る**
   （2 と同じ理由。**書くのは 5 の push の後**）。
4. **パッチが変わっていないかを見る（必須）**:
   ```bash
   git range-diff <前の base>..<載せ替える前の HEAD> <新しい base>..HEAD
   ```
   **全行が `=` のときだけ、関門を通したパッチのままである。** **それ以外は全部「変わった」と読む**——
   `!`（中身が変わった。衝突を手で解いた・下の squash と重なった）、`<`（上の周のコミットが消えた。中身が下に入っていて空になった）、
   `>`（コミットが増えた）。**変わった行は関門を通っていない**——**変わった分にだけ、手順 6 の狭いパスと同じ形で Verifier を 1 回当てる**
   （パスには数えない。指摘の扱いも狭いパスと同じ）。
5. **push してから、PR の base を既定ブランチに付け替える（順序を逆にしない）**:
   ```bash
   git push --force-with-lease=<上のブランチ>:<載せ替える前の HEAD> origin <上のブランチ>
   gh pr edit <上の PR> --base <既定ブランチ>
   ```
   **base を先に付け替えると、push が済むまでの間、base が既定ブランチで head が載せ替える前の PR ができる**
   ——**`merge-pr.py` を通らないマージ（画面・素の `gh pr merge`）では、載せ替えていない head がそのまま入る。**
   **期待する SHA を名指しする**——**素の `--force-with-lease` は直前の `git fetch` で手元の追跡参照が進むので何も守らず**
   （他の clone が push したコミットを消した）、**上流を持たないブランチでは失敗する**（一時リポジトリで確かめた）。
   **上の周の自分のブランチにだけ使う。** 既定ブランチ・下のブランチには使わない。
   **lease が `stale info` で拒否されたら、素の `--force-with-lease`・`--force` で通さない**——**リモートが控えた値から動いている。**
   `git rev-parse origin/<上のブランチ>` と控えた値を見比べて、**人間に訊く**（2 の push を飛ばしたなら、そこが原因である）。
   **push と付け替えが済んでから、載せ替えの履歴に 1 行書き**（3 で控えた新しい base）、計画ファイルをコミットして
   **`git push origin <上のブランチ>`（force しない。2 と同じ形——宛先を書かない素の `git push` は上流を持たないブランチで失敗する）で送る**——**載せ替えの後に足すコミットなので、4 の `range-diff` には出ない。**
   **この push を落とさない（必須）——既定ブランチと比べる CI は、この push でしか回らない。** 上の lease の push で起動した CI は
   **付け替えの前の base（下のブランチ）と比べている**。**付け替え（`edited`）では、型を指定しない `pull_request:` は回り直さず、
   検査の再実行も前の base のまま回る**（[#427](https://github.com/hdknr/claude-code-setup/issues/427) で本物の GitHub で確かめた）。
   **`merge-pr.py` は、付け替えより前に届いた head の PR をマージしない**（docstring）。
6. **歯止めを全部回し、PR *側*の CI を見る**（`SKILL.md` 手順 6 の「PR を作ったら、PR *側*の状態を見る」と同じ）。
   **載せ替えで既定ブランチの新しい歯止めが掛かる**——取り込みと同じである。**どれが新しいかは 2 で見た一覧で分ける。**
7. **さらに上に積んだ周があれば、下から 1 段ずつ。** いま載せ替えた周（B）の上に積んだ周（C）にとって、
   **B の載せ替えは「下の周にコミットが足された」と同じ**である——C は上の節のとおり
   `git rebase --onto <B のブランチ> <C の記録した base>` で B の新しい先端へ載せ直し、PR の base は B のままにする。
   **C を既定ブランチへ載せ替えるのは、B がマージされた後**（この節を C について繰り返す）。

## 台帳を使う周では

**台帳は積んでいることを鍵として持たない。** **依存先がマージ済みでないのに `impl`・`gate`・`pr` にいる Issue は、
積んでいる**——`ledger.py show` の依存と状態の列から読める。**積み先と base は計画ファイルを正とする**
（台帳の `branch`・`base` はポインタ。`references/ledger.md` の「台帳と計画ファイルの分担」）。

- **積んで始めたら、`note` に `積み先: #<下の Issue>` と書く**——人間が台帳だけ見たときに分かるように。
- **依存先を `merged` にする*前に*、それに積んでいる Issue 全部（`note` が `積み先: #<下の Issue>` のもの。** **状態に依らない** **——`blocked` も含む）の `note` を
  `積み先: #<下の Issue>（載せ替え待ち）` にする（必須）。** **`merged` にした後は、依存と状態の列から
  積んでいたことが読めなくなる**——その間にセッションが終わると、再開した側は載せ替え待ちを通常の `pr` と区別できない。
  **載せ替え待ちの Issue は、上の「下の周がマージされたら」へ送り、載せ替えるまで `merge-pr.py` に渡さない**
  （渡しても `merge-pr.py` は載せ替えていない PR を止めるが、見分けられない形がある——docstring。止まるのを当てにしない）。
- **載せ替えたら `note` を `積み先: #<下の Issue>（載せ替え済み）` にする。** 台帳の `base` もポインタなので書き直す。
