# コミットの検証の印と、任意の関門（#1192）

**このファイルは、周でコミットするとき（手順 4・6）に、トレーラーの書き方を知るために読む**（`SKILL.md` 手順 4 から指している）。
**関門の hook を入れる・上げるときも、ここを読む。** hook は任意で、入れなくてもトレーラーの規定は効く。

出典は、Claude Code チームの運用——各コミットに「どう検証したか」の印を付け（`none` もあり、検証されなかったコミットを後から検索できる）、
セッションで検証が走っていなければコミットを止める関門を off・observe・enforce の 3 段で入れる
（Addy Osmani「How the Claude Code team thinks about verification」。比較の経緯は hdknr/blogs#837）。
dev-loop は検証の結果を PR コメントと計画ファイルに残すが、**コミット単位の印**が無く、PR を開かずに「このコミットは何で確かめたか」を引けなかった。

## 検証の印（必須）

**周が作るコミットのメッセージの最後の段落に、`Verified:` の 1 行を書く。** `Co-Authored-By:` と同じ段落に置く（間に空行を入れない。
git は最後の段落しかトレーラーと読まない）。

```text
Verified: tests,gates
Verified: verify,code-review
Verified: none (計画ファイルのみ)
```

| 手段 | 意味（**そのコミットの木に対して、実際に回した**ものだけを書く） |
| --- | --- |
| `tests` | その周で書いた・関係するテストを回した |
| `gates` | 対象リポジトリの「歯止めを全部回す 1 本」（手順 6）を回した |
| `verify` | 手順 5 の検証（実機確認と別ティアの Verifier）を、この木に当てた |
| `code-review` | `/code-review` を、この木に当てた |
| `none (<理由>)` | 何も回していない。**理由を必ず書く**（`none` だけは満たさない） |

- **書くのは実際に回したものだけ。** 回していない手段を書くのは、手順 5 の「落とした手順を『実施した』と報告しない」と同じ誤りである。
  **関門を通した後の木と、コミットした木が違うなら、通したと書かない**（指摘対応のコミットは、当て直すまで `verify`・`code-review` を名乗らない）。
- **周の途中のコミットは `none` でよい**（実装役の最初のコミット・計画ファイルだけのコミット）。**`none` を避けるために手段を盛らない。**
  `none` のコミットが後から引けること自体が、この印の目的である。
- **squash マージの後は、PR 単位の手がかりになる。** squash のメッセージには各コミットのメッセージが行頭のまま並ぶ（`#1352` で確かめた。ただし #1352 のコミットは印を付ける前のもので、`Verified:` の行を持つ squash は**確かめていない**）。
  **並ぶなら `--grep='^Verified: none'` は「`none` の途中コミットを含む PR」を引き、「検証されなかったコミット」にはならない**——コミット単位で引けるのは、squash の前の PR のブランチの履歴である。

**引き方**（コミット単位で見るのは、PR のブランチの履歴）:

```bash
git log --format='%h %s' --grep='^Verified: none'        # 検証されなかったコミット
git log --format='%h %s' --grep='^Verified: ' --invert-grep   # 印そのものが無いコミット
```

**計画ファイルの関門の記録（`dev-loop-gates`。`check-gates.py` が履歴と照合する）とは別物である。** あちらは周の関門の通し方を見る。
**この印は、コミットが自分で名乗る手段で、`check-gates.py` は印を読まない。** 印の中身が事実かを突き合わせる機械は、いまは無い（Verifier と人間のレビューが見る）。

## 関門の hook（任意。既定は off）

**enforce が強制するのは「検証の印を名乗ること」で、「検証が走ったこと」ではない。** 止められたモデルは、メッセージに `Verified:` を書き直せば通る（実際に回したかは見ない）。
Issue の関門（検証が走っていなければ止める）の全部ではなく、**入口の 1 段**である。印の中身と履歴の突き合わせは、いまは無い（別の周で足すなら、`check-gates.py` が読む計画ファイルの関門の記録と照らす口になる）。

**プラグインは hook を登録しない。** `scripts/commit-gate.py` を置いてあるだけで、**入れるかどうかは利用者が決める**（入れなければ何も起きない）。

**設定**（対象リポジトリの**メインの作業ツリー**の `.claude/dev-loop.md`。worktree の中の写しは読まない——周のブランチが自分でモードを変えられないように。行頭から 1 行ずつ）:

```text
検証の関門: observe
検証の関門の逃げ道: 理由を書けば通す
```

| 項目 | 値 | 既定 | 意味 |
| --- | --- | --- | --- |
| `検証の関門` | `off`・`observe`・`enforce` | `off` | off は何もしない。observe は通して「止めていたはず」を記録する。enforce は満たさないコミットを止める |
| `検証の関門の逃げ道` | `理由を書けば通す`・`なし` | `理由を書けば通す` | `なし` は `Verified: none (理由)` も止める（手段を 1 つ以上名乗るコミットだけが通る） |

- **誤記は `off` に倒れる**（値が表に無い・同じ行が 2 本以上・行頭から書いていない・コードフェンスやコメントの中だけ）。止める側には倒さない。`commit-gate.py status` が名指しするのは、**値の誤り・2 本・行頭から書いていない行**で、フェンスやコメントの中の行は「行が無い」と同じ扱いで名指ししない。
- **逃げ道の既定を `理由を書けば通す` にした理由**: `なし` だと、計画ファイルだけのコミットのように検証する対象が無いコミットも止まり、**手段を盛るか、関門を外すしかなくなる**
  （印の目的が崩れる）。dev-loop の周は関門（手順 5・6）を飛ばさない方針なので、**関門の飛ばしは、この hook でなく手順 5・6 と `check-gates.py` が止める**。厳しくしたい利用者が `なし` を選ぶ。
  **「同じセッションで 2 回止めたら次は通す」は採っていない**（セッションの状態を持つ必要がある）。**宣言は利用者の判断で、周が選ばない**。

**入れ方**（利用者が `settings.json` に書く。`<パス>` は `commit-gate.py` の絶対パス）:

```json
{ "hooks": { "PreToolUse": [ { "matcher": "Bash", "hooks": [ { "type": "command", "command": "python3 <パス>/commit-gate.py" } ] } ] } }
```

**依存**: `python3`（標準ライブラリのみ）と `git`。**書く場所**: `git rev-parse --git-common-dir` の下の `dev-loop-gate.jsonl`（全 worktree で共有。commit されない）。
**権限**: hook は Claude Code が走らせるので、記録の書き込みに追加の許可は要らないと読めるが、**確かめていない**。

**動かせない・効かない環境（落とした主張）**:

- **本物の Claude Code に登録して発火させた確認は、この周で取れていない。** スクリプトは hook の stdin を真似た JSON で呼んで確かめた（リポジトリの `test-commit-gate.py`）。
  **stdin の鍵（`tool_name`・`tool_input.command`・`cwd`）と、終了コード 2 が止める意味は、公式の説明に従った**もので、実機では測っていない。**入れたら、まず observe で 1 件コミットして記録が残ることを見る。**
- **hook が動かない環境では、何も止まらない**（python3 が無い・登録していない・読まれない）。**スクリプトは判定できないとき通す**（enforce でも）——**だから enforce は保証ではない**。
- 見るのは**形**（手段を名乗っているか）で、**名乗りが事実かは見ない**。`git commit` を直接呼ばない形（別名・スクリプトの中・IDE）は見ない。
  `-C`／`-c` とエディタを開くコミットはメッセージを読めず、満たさない扱い（`missing`）になる。
  **マージの締め（`MERGE_HEAD` がある）と、メッセージを渡さない `--no-edit` は見ない**（通す。取り込みの merge コミットに印は付かない）。`Verified:` は**メッセージのどこにあっても**読む（git がトレーラーと読むのは最後の段落だけなので、最後の段落に置く）。
  **ヒアドキュメントは、引用符の外の `<<` で始まるものだけを読み（`-m "$(cat <<'EOF' … )"` の `$( … )` の中は読む）、`-m`／`--message` を渡したコミットでは数えない**（git は stdin を読まない。`-F -` は読む。#1368）。
  **連結したコマンドは `git commit` の呼び出しごとにその部分だけを読み、1 本でも満たさなければ止める。** `bash -c "…"`・`git --git-dir <パス> commit`・`cd <dir> && git commit -F <相対パス>` は見ない／読めない。
  **値は、閉じの引用符（後ろが空白・行末・区切り）か文字のままの `\n` で終わる**——理由の中に「引用符＋空白」を書くと切れて満たさなくなる。`Verified:` は行頭か引用符の直後に置く。

## observe から enforce に上げる

**閾値は決めない**——実測が無く、数字を決めるとその下が素通りになる（`SKILL.md` 手順 3 の周の大きさと同じ扱い）。手順だけ書く。

1. `検証の関門: observe` にして、周を何周か回す。**止めていたはず**が記録に残る。
2. 記録を数える:

   ```bash
   python3 <パス>/commit-gate.py report
   ```

   結果（pass・would_stop）と理由（missing・malformed・none_without_reason・none_not_allowed）ごとの数と、**would_stop の 1 件ずつ**が出る。
3. **would_stop を 1 件ずつ人が見て、誤検知かを決める。** 誤検知とは、**実際は検証していたのに止めていたはずになったもの**（印の書き忘れ・形が合わない・メッセージを読めない形のコミット）。
   **本当に印が無かったものは誤検知ではない**——関門が効いた件数である。**判定はスクリプトにさせない**（形しか見ないので、事実の誤検知は数えられない）。
4. **誤検知の原因が直る（周の指示・実装役の指示・hook の読み方）まで直し、もう一度 observe を回す。** 誤検知が残らなくなったと人が判断したら `enforce` に上げる。
5. 上げた後に止まって困るなら、observe に戻す（設定の 1 行を変えるだけ）。

**この手順の実測は無い**（この周では記録を貯めて回していない）。
