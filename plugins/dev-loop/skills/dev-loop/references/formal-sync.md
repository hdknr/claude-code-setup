# 形式検査のモデルと実装を揃えておく（#1178）

**このファイルは、対象リポジトリに spec-loop の形式検査のモデル（`docs/v<n>/spec/formal/<対象>/README.md`）があるときに読む**（`SKILL.md` 手順 3・6 から指している）。
正本が別のリポジトリにあるなら、その写しの根を `--canon` で渡す（読み方は `scripts/formal-sync.py` の docstring を正とする）。
**モデルの無いリポジトリでは読まなくてよい**——`formal-sync.py check` は何も求めずに 0 を返す。
**ここに書いてある `（必須）` は、`SKILL.md` に書いてあるのと同じ重さで効く。**

## なぜ要るか

spec-loop のモデルは、仕様と揃えて保たれる（spec-review が保存したモデルから始めて走らせ直す）。だが**実装の周と、spec-loop を通らない変更（不具合の修正・リファクタリング）は、モデルを見ない**——
モデルが守る性質のうち反例の出なかったものは、実装の上で確かめていない。記録の `実装の対応`（モデルの行為 → 実装のファイルと関数）で、周が触れたモデルを引き、**今のコードに当てて走らせ直す**。
記録の 2 項目の形と、spec-loop の側が引き継ぐ決まりは、spec-loop プラグインの `references/tree.md` の「形式検査のモデル」の「実装との対応」を正とする（このプラグインの外にある）。

## 周の手順（必須）

`<spec-loop>` は spec-loop プラグインの base ディレクトリ（`scripts/check-formal-rerun.py` を持つ）——プラグインで入れていれば `claude plugin list --json` の `installPath`、
このリポジトリを clone していればその `plugins/spec-loop`。**写さずに読み込むので、spec-loop が無い・古い（#1178 より前）なら判定できない（2）**——申告して止まる（`SKILL.md` の原則「必須手順を落とすときは、黙って落とさない」）。

1. **触れたモデルを引く**——実装を終えて、1 パス目の関門に渡す前に、worktree を cwd にして素の 1 行で:
   ```bash
   python3 <このスキルの base ディレクトリ>/scripts/formal-sync.py touched <周の base の SHA> --spec-loop <spec-loop>
   ```
   **触れたモデルが無ければ、2〜5 は無い**（`check` も行を求めない）。
   **`対応の無いモデル` が出たら、この周がそのモデルの行為を実装したかを見る**——実装したなら 5 の条件で対応を書く（書けなければ PR コメントで渡す）。`対応が古い` も PR コメントで渡す。
2. **コードのモデルを書く**——触れたモデルごとに、保存したモデルのディレクトリを**リポジトリの外**（scratchpad）に丸ごと写し、**`実装の対応` に挙げた行為の定義だけを、今のコードがすることに書き直す**。
   対応の関数を読み、その関数が状態をどう変えるかを、保存したモデルと同じ変数で書く（書き直した行為が使う定義は足してよい）。
   **ほかは変えない**——設定（`.cfg`）・性質の定義・`Init`・陽性対照・記録の一覧を変えると `rerun` が `判定できなかった` にする（性質やモデルを弱めて通さない）。
   コードが保存したモデルの行為のとおりなら、写したまま（書き直さない）でよい。
3. **走らせる**——同じく素の 1 行で:
   ```bash
   python3 <このスキルの base ディレクトリ>/scripts/formal-sync.py rerun <保存したモデルの対象のディレクトリ> --code-model <書いたコードのモデル> --spec-loop <spec-loop>
   ```
   結果ごとに:
    - **`反例なし`**——4・5 へ。
    - **`反例あり（コードの不具合）`**——**この周の変更が性質を破っている。コードを直し、2 から当て直す**（性質・モデルを直して通さない）。直せないなら周を閉じない（`SKILL.md` 手順 6 の「満たしていない受入基準」と同じく名指す）。
    - **意図した変更で反例が出た**（この周の Issue が、モデルの性質を破る振る舞いを求めている）——**`--intended` を付けて当て直し、`反例あり（モデルのずれ）` を残す**。性質を変えることは仕様を変えることなので、
      `references/spec-writeback.md` の「振る舞いを変える周が残すもの」のとおり `仕様の振る舞い: 変える` と `正本に起票する行:` を計画に書く（モデルは周の中で直さない——直すのは spec-loop の spec-review）。
      **不在の線の `仕様の穴 = 推奨で決めて起票` でも推奨で進めない**——コードの不具合か意図かを決めるのは仕様である。`references/absent-lines.md` の「spec-loop から来た Issue の穴」の「Red テストと食い違う穴」と同じ線で、PR を draft にして周を閉じない。
      **どちらか決められなければ、コードの不具合として扱う**。
    - **`判定できなかった`**——出力の理由（弱めた違い・保存したモデルが通らない・空振り・呼び方の行が無い）を読む。コードのモデルの書き方の誤りなら直して当て直す。
      **保存したモデルが通らないなら、この周では直さない**（spec-loop の spec-review で直す）——PR コメントに「判定できなかった」の見出しで、出力の 1 行と一緒に渡す（`SKILL.md` 手順 5 の BLOCKED と同じく、緑と書かない）。
4. **計画に書く**——`rerun` の出力の最後の行（`形式検査の再検査: <対象> <結果>`）を、計画ファイルに行頭からそのまま写す（`- ` を前に置いてよい。コードフェンスに入れない。1 つの対象に 1 本）。
   同じ節に、書いたコードのモデルの絶対パスと、書き直した行為を 1 行ずつ残す（関門に渡すため）。コードを直して当て直したら、行を書き直す。
5. **確かめたコミットを進める**——`反例なし` で、**モデルの版が正本の作業中の版で、リリースしていない**とき（正本の根で spec-loop の `formal-baseline.py target` が 0 で出す `書く場所` の下にモデルがある）だけ、
   記録の `対応を確かめたコミット` を、`rerun` を走らせた時点の HEAD の SHA（コードを commit した後）に書き直し、関数を動かした・行為を実装したなら `実装の対応` も直して、
   `formal-baseline.py check <対象のディレクトリ>` を当てて 0 にする（どちらも spec-loop の `scripts/` にある）。
   **それ以外は書き直さない**——凍結した版を直すと `check-frozen.py` が落ち、別のリポジトリの正本は worktree の外である（`references/spec-writeback.md` の「同じリポジトリの表に足さない理由」と同じ）。PR コメントに、進めなかったことと SHA を書く。
   **squash でマージすると、書いた SHA は既定ブランチの祖先にならない**（PR の `refs/pull/<n>/head` には残る）——比べるときは中身で比べる。

## 関門に渡す（必須）

**Verifier と `/code-review` の両方に、毎パス、計画の再検査の行・コードのモデルのパス・書き直した行為を渡し、「コードのモデルの行為が、対応の関数が今することを写しているか」を確かめさせる。**
`rerun` が機械で見るのは、行為のほかを変えていないことと TLC の結果だけで、**行為の書き直しが今のコードに合っているかは見ない**——ここが著者の自己申告になる。
関門が「書き直しがコードと合わない」と示したら、採否の表に載せる（`SKILL.md` 手順 6）。**関門の体は、コードのモデルを書き直さない**（リポジトリの外でも、周の記録を変えることになる）。

## PR の前に当てる（必須）

**PR を作る前に、worktree を cwd にして素の 1 行で当てる**——終了コードで分岐する（`SKILL.md` 手順 6 の「終了コードで分岐するスクリプトは、包まずに素の 1 行で呼ぶ」）:

```bash
python3 <このスキルの base ディレクトリ>/scripts/formal-sync.py check <計画ファイル> <周の base の SHA> --spec-loop <spec-loop>
```

**main を取り込んだ後は、`SKILL.md` 手順 4 の式を当て直した base を渡す。** モデルの無いリポジトリでは何も求めずに 0（`--spec-loop` も要らない）。

**0**: 触れたモデルが無いか、どれも行がある（`判定できなかった` は PR コメントで渡す）。**1**: 触れたモデルの行が無い・値が違う・2 本ある・`反例あり（コードの不具合）`・
`正本に起票する行:` の無い `反例あり（モデルのずれ）`——**PR を作らない。** 上の手順に戻る。**2**: 判定できない（緑ではない）。
**見るもの・見ないもの（行の真偽・コードのモデルの写し方・対応の網羅）は `scripts/formal-sync.py` の docstring を正とする。**
