# 不安定（flaky）なテストの扱い（#1193）

**このファイルは、テストが落ちたとき・回し直したら緑になったとき・差分にテストの待ちや外しが入るときに読む**（`SKILL.md` の原則から指している）。
**どれも無い周では読まなくてよい。**

出典は、Claude Code チームの運用——不安定なテストに対して Claude は skip・sleep の追加・通るまでのリトライをせず、
根本原因が見つからなければテストを削除して理由を残す（Addy Osmani「How the Claude Code team thinks about verification」。
比較の経緯は hdknr/blogs#837）。回し直して緑になる失敗が続くと、エージェントは「直す」ではなく「回し直す」を覚える——
**回し直すこと自体は禁じず、緑にするための小細工と、緑になった事実を黙って消すことを禁じる。**

## 緑にするための小細工をしない（必須）

**落ちたテストを緑にするために、次を差分に入れない。**

- **skip・xfail・無効化**（`skip`・`xfail`・`@Disabled`・`it.skip`・コメントアウトなど、テストを走らせなくする印）
- **sleep・待ち時間・タイムアウトの延長**（落ちる原因を直さずに、待ちを足して通す）
- **リトライ・再実行の追加**（テストの設定・テストランナーの再実行の回数・CI の失敗時の自動再実行）
- **テスト・assert の削除、期待のゆるめ**（`SKILL.md` 手順 5 の「実装しながら基準を緩めない」と同じ操作）

**例外は 1 つだけ**——待ち合わせそのものが受入基準で、それを実装する周（例: 時間切れの挙動を作る）。**待ちを入れる理由を手順 3 の計画に書き**、
Verifier に見せる（見せずに入れると、緑のための sleep と区別できない）。

**これは回し直しを禁じるものではない。** 実装もテストも変えずに、同じものをもう一度走らせるのは構わない（cruise の回し直しの条件は
`../cruise/references/parallel.md` の「負荷による偽の失敗」が決める）。**回し直したなら、結果が緑でも次の節に従って残す。**

## 回し直して緑になった失敗は、「不安定なテスト」として残す（必須）

**黙って消さない。** 1 回目が落ちて回し直しで緑になった失敗は、緑の根拠として数えてよいが、**無かったことにはしない**:

1. **周の記録に 1 行書く**——計画ファイルの「既知の限界・決着済みの論点」に、次の形で（テストごとに 1 行。行頭から書く）:

   ```text
   不安定なテスト: <テストの名前または検査の名前> — 1 回目: 落ちた（<要点>）／回し直し: 緑（<どう回したか>）／根因: <分かったこと。分からなければ「不明」>
   ```

2. **PR コメントの残課題に、見出し「不安定なテスト」で同じものを書く**（手順 6）。**cruise の周は、子の報告にも名指しする**——親が終える報告で渡す（cruise の `SKILL.md` 6）。
3. **起票は手順 6 の「新しい Issue を起票するのは」の 3 条件のまま**——周の中で勝手に Issue にしない。

**この周の差分が触れたテスト・コードの失敗は、回し直しで緑になっても、不安定と決めつけない。** 差分が原因（競合・順序依存・待ちの不足）の可能性を先に潰し、
潰せなければ「不安定」ではなく差分由来の失敗として扱う（関門にその旨を見せる）。**回し直しの緑は、実装が正しいことの証拠にならない。**

## 根本原因が見つからないとき

**周は、テストを削除も隔離（skip）もしない。人間が決める**——どちらもテストが守っていたものを減らす操作で、受入基準を変える操作にあたるからである。
**PR コメントの残課題「不安定なテスト」に、次を書いて渡す**:

- 観測: 何回走らせて何回落ちたか・見た範囲（観測窓。窓の外は分からない）
- 調べたこと・見つからなかったこと
- 推奨と理由: **そのテストが守る性質を別の検査でも見られるなら削除して理由を残す、見られないなら隔離して Issue にする**（隔離は skip の印と Issue の番号を残し、
  期限なしの無効化にしない）

**人間が決めるまで、周は PR にテストの変更を入れない。** 落ち続けるテスト（回し直しても緑にならない）は不安定ではなく本物の失敗で、直す。
