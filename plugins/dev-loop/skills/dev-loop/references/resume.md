# 途中から再開する周

**これは `dev-loop` スキルの一部である。** `SKILL.md` から分けてあるのは、
**再開の周でしか要らない**からで、**規範として弱いからではない**
——**`（必須）` はここでもそのまま効く。**

**読む条件**: `SKILL.md` の「途中から再開する周」が指示するとおり、
**`scripts/find-cycle.py` が何かに当たったとき**に読む。
**新規の周では読まなくてよい。**

**探索そのものは `scripts/find-cycle.py` が行う**（このファイルと同じスキルの下にある）。
**以下は、当たったものをどう扱うか**である。

**このスキルは、周の途中で起動されることがある。** 手順 4 と手順 6 に**割り目**があり、
そこで `/clear` したあと `/dev-loop <issue-number>` で入り直すからである（手順 4）。
**そのときは手順 1 から順に走らせてはならない**——積み直した文脈が、割った意味を消す。

1. **まず計画ファイルを探す**（`docs/plans/issue-<n>.md` か `.claude/plans/issue-<n>.md`、
   対象リポジトリの CLAUDE.md に規約があればそこ）。
    - **1 つのパスが空振りしただけで「無い」と決めない（必須）。** 上の 2 つは手順 3 の
      置き場の**規約**だが、**実物がその名前どおりに置かれているとは限らない**——
      サブディレクトリに入っていることも、別名のこともある。**この規範を書いた周自身が
      `.claude/plans/issue-96/issue-96-plan.md` に置いており、規約のパスに一致していなかった。**
      **だからディレクトリを再帰的に見る**——`find docs/plans .claude/plans -path '*<n>*' -type f`
      （**`-name` では足りない。`-name` は basename にしか当たらない**ので、
      `issue-<n>/plan.md` のように**番号がディレクトリ名の側にある**と、出るのは
      ディレクトリだけでファイル本体に届かない。`ls` が足りないのと**同じ失敗**である。
      **これは実際に踏んだ**——`-name` で「届いた」と確かめたつもりだったが、
      当の計画ファイルが `issue-96-plan.md` で**番号が basename にもあった**ため、
      **主張が偽でも同じ出力が出る配置**で測っていた）。
      **厳密一致に頼ると、規約どおりに置かれていない実物を、在るのに見落とす。**
      **当たったものを確かめてから開く（必須）**——`-path '*<n>*'` は部分一致なので、
      `*96*` は `issue-960` にも `issue-1962` にも当たる（**下の `--list '*<n>*'` と同じ穴**）。
      **空振りしたら、置き場が無いのか・在るが一致しないのか・コマンドが違うのかを
      選り分ける**——`find` はどれでも同じ空出力を返す（相対パスなので、リポジトリの
      直下でない cwd から走らせても黙って 0 件になる）。
    - **いまいる作業ツリーに無い、は「無い」ではない（必須）。** 計画ファイルは**その周の
      ブランチの上にコミットされている**ことがあり、そのときデフォルトブランチの作業ツリーには
      **存在しない**。**メインの作業ツリーから再開した周は、ここで必ず空振りする。**
    - **だから探索は作業ツリーの外まで伸ばす（必須）**——`git worktree list` と
      `git branch --all --list '*<issue-number>*'` を見て、**その周の worktree ／ ブランチ**を探す。
      **`--all` を落とさない**——`git worktree remove` は**ブランチを消さない**ので手元に残るが、
      **別のマシンで回した周・手元のブランチを消した周は、リモートにしかない**。
    - **ただし、この 2 本はどちらも「名前に番号が入っている」ことに乗っている（必須）。**
      **その前提は道具に任せると崩れる**——`EnterWorktree` のブランチ名は
      **`worktree-` ＋ 渡した `name`** で、**`name` を渡さなければランダム名が生成される**
      （道具の説明文。接頭辞は #96 の 3 例からの観測）。
      **番号を含まない名前で作られた周は、`git worktree list` を番号で眺めても
      `--list '*<n>*'` でも映らない**——そして**両方が空振りすると「新規の周」と判定される**。
      **B2 が防ごうとした誤判定そのものを、命名規約への依存が作り直している。**
      **だから番号に依らない探索を必ず併せる（必須）**:
      ```bash
      git worktree list                      # 番号で絞らず全件見る（数は多くない）
      git log --all --diff-filter=A --name-only --format= -- '*issue-<issue-number>*'
      git log --all --grep '#<issue-number>' --oneline   # Fixes #<n> を含むコミット
      ```
        - **抜けているのは*ブランチ名*依存であって、番号依存ではない（必須）。**
          2 本目・3 本目は**番号を引数に埋めている**ので、番号そのものには依存したままである。
          **ブランチ名に番号が入っていなくても当たる**、が正確な言い方
          （[#110](https://github.com/hdknr/claude-code-setup/issues/110) の 1 パス目で、
          **「番号依存から抜ける唯一の足場」と書いたラベルが誤り**だと指摘された）。
        - **2 本目が効くのは、番号が*計画ファイルのパス*に入っているから**
          （`docs/plans/` にコミットしている周に限る。gitignore した周には効かない——
          下の `git show` の項と同じ限界）。**3 本目はコミットメッセージの
          `Fixes #<n>` 規約に依存する。**
        - **3 本目も部分一致である（必須）。** `--grep` はコミットメッセージに対する
          **アンカーされていない**照合なので、**`#11` は `#110` にも当たる**
          （`-path '*<n>*'` と `--list '*<n>*'` と**同じ穴**）。
          **3 本目は最初の 2 本が空振りしたときの落とし先**なので、
          **誤ヒットは再開した周を別の Issue のブランチへ送る**。
          **当たったものは確かめてから入る。**
        - **番号にも名前にも依らないのは 1 本目だけ（必須）。** `git worktree list` を
          **全件見る**と、絞ると**ランダム名の worktree が出力から消える**のに対し、
          全件なら**在ることは見える**。**各 worktree の HEAD は、この 1 本の出力に
          既に入っている**ので、**当たり直す必要が無い。**
            - **ただしブランチ名は、出るとは限らない（必須）。** 出力は
              `<パス> <SHA> [<ブランチ>]` だが、**detached HEAD の worktree は
              `(detached HEAD)` になる**（`man git-worktree` の `list`:
              「the branch currently checked out (**or "detached HEAD" if none**)」）。
              **この周の手順自体が detached を作りうる**（`remotes/origin/<名前>` を
              そのまま渡した場合。手順 4 の該当項）ので、**名前が出ない worktree は実在する。**
              **そのときは SHA で引く**——`git log --oneline -1 <SHA>`。
              **ブランチ名が無いことを「見つからない」と読まない。**
            - **`git -C <パス>` で当たり直さない（必須）。** worktree 隔離セッションでは
              **`-C` が拒否されることがある**——**実測**（2026-09-18、
              [#110](https://github.com/hdknr/claude-code-setup/issues/110) の 2 パス目）:
              `this command redirects git to the shared checkout via -C`。
              **通ることも拒否されることもある**（[#112](https://github.com/hdknr/claude-code-setup/issues/112) に件数）。
              **「外を指したから拒否された」とも「内側なら通る」とも読んではならない（必須）**
              ——**理由節が `-C .` を名指しした拒否も実測されている**（[#112](https://github.com/hdknr/claude-code-setup/issues/112)）。
              **当てにできないことが理由であって、必ず拒否されるからではない。**
              **以前ここには `git -C <path> log --oneline -1` と書いていた**が、
              **この項が想定している再開の局面（worktree の中）でこそ走らない**コマンドだった。
            - **中身を見たいときはブランチ名で引く**——**参照は全 worktree で共有**なので、
              **他の worktree が checkout しているブランチでも**
              `git log --oneline -1 <ブランチ>` が**自分の worktree の中から読める**
              （実測・同上）。
        - **3 本とも空振りする周はある。ただし 3 本目を無条件に死んだ扱いにしない（必須）。**
          計画ファイルを gitignore し、worktree も畳んだ周では 1 本目・2 本目が落ちるが、
          **3 本目は別の条件に乗っている**——**畳み方が `git worktree remove` なら
          ブランチは残る**（上の `--all` の項）ので、**`Fixes #<n>` の規約に従っていれば
          3 本目は当たる**。
            - **畳み方によっては 3 本目も落ちうる（必須）。** **`ExitWorktree` の
              `action: "remove"` は「the worktree directory **and its branch**」を消す**とされる
              （道具の説明文）。**ブランチが実際に消えた周では、`git log --all --grep` も
              空になりうる**（ローカルにもリモートにも参照が残っていない場合）。
              - **ただし「消える」を前提にしない（必須）。** **この周で唯一取れた実測では、
                ブランチは消えなかった**——手順 4 の「改名すると後片付けと噛み合わない」項の
                とおり、**ディレクトリだけ消えてブランチ側は黙って no-op になった**。
                **push 済みなら `refs/remotes/origin/<名前>` も残る**ので、
                **2 本目・3 本目とも当たる。**
              - **だから 3 本の生死は、どちらにも決め打ちできない。**
                **走らせて、出たもので判断する**——「必ず当たる」も「必ず落ちる」も
                **同じ誤り**である（#110 の 3 パス目で前者を、4 パス目で後者を指摘された）。
          **3 本目も空振りした**ときに初めて、
          「途中から再開する周」の**読めないと分かったときの扱い**（人間に指示を仰ぐ）に落ちる。
          **「どれも当たらない」と決めてから人間に上げると、在るものを見ずに諦める**
          （#110 の 2 パス目で指摘された）。**逆に「3 本目は必ず当たる」と書くのも誤り**
          （同 3 パス目で指摘された）——**どちらにも倒さず、実際に走らせて決める。**
        - **改名の跡にも注意**——`ExitWorktree` で畳んだのに残ったブランチが混ざる
          （手順 4 の「改名すると後片付けと噛み合わない」）。**当たったものは確かめてから入る。**
        - **同じ Issue に worktree ／ ブランチが 2 本以上当たることがある（必須）**——
          前の周の畳み残りと今回の分、`--force` で作った 2 本目、`path` 無しの
          `EnterWorktree` が生やした 2 本目。**多いほうが新しいとは限らない。**
          **どれを選ぶかは、計画ファイルの「周の在り処」（ブランチ名・worktree のパス・
          起点コミット。手順 3 の 5 番目）と突き合わせて決める**——
          **記録が無ければ選べないので、人間に指示を仰ぐ**（下の「読めないと分かったとき」と
          同じ扱い。**新しそうなほうで代用しない**）。
    - **ブランチが見つかっても、worktree が無ければ中身は読めていない（必須）。**
      **ブランチ名の一覧は計画ファイルではない。** worktree を持たないブランチの計画ファイルは、
      **コミットされていれば** `git show <ブランチ>:<パス>` で読む
      （`git log --all --diff-filter=A --name-only --format= -- '*issue-<n>*'` で場所を当てる。
      **`--name-only` を落とすとコミットの見出しだけが出て、パスが 1 つも出ない**
      ——`git show` に渡す `<パス>` が作れない）。
      **「ブランチがあった」で止めると、受入基準を持たないまま再開する。**
    - **ただし `git show` が効くのは、コミットされている置き場に限る（必須）。** 手順 3 は
      `.claude/plans/` を**作業メモとして gitignore する場合**の置き場として挙げている。
      **gitignore されているなら**どのコミットにも乗らないので、**その周の worktree が
      畳まれていたら計画ファイルは読めない**——`git show` も空振りする。
      **`.gitignore` を見て確かめる**（`git check-ignore -v <パス>`）——**gitignore して
      いない対象リポジトリでは `git show` で読めるので、試さずに諦めない。**
      **読めないと分かったときを「新規の周」と判定してはならない。** 受入基準が失われていることを**人間に伝えて指示を仰ぐ**——
      黙って手順 3 を回し直すと、**割り目の前に決めた基準が黙って変わる**。
      **割り目を置く周は、この点でコミットする側（`docs/plans/`）のほうが後から復元できる。**
    - **`--list '*<n>*'` は部分一致なので、広すぎることがある（必須）。** `*96*` は
      `issue/960-…` にも `issue/1962-…` にも当たる。**当たったものを確かめずに入らない**
      ——**別の周のブランチで再開するのは、新規と誤判定するより悪い。**
    - **「無ければ新規の周」と即断しない（必須）。** 新規と判定してよいのは、**上を全部見て
      どこにも無かったとき**だけである。実測では、メインの作業ツリーから再開した周が
      既定の 2 パスだけ空振りし、**2 本目の worktree を作って実装をやり直した**
      （[#96](https://github.com/hdknr/claude-code-setup/issues/96)）。
      **なお、その周は計画ファイルを探すより前に手順 1 から走り直している**（1 手目が
      `gh issue view`）——**空振りが走り直しの原因ではなく、両方が起きた。**
      **新規の周は、ここを全部見てから始まる。**
2. **あれば、その「関門の進捗（再開点）」を読んで、再開する手順を決める**:

    **表で突き合わせない（必須）。** 状態の一覧を作ると、**一覧に無い状態が、似た行に
    誤って一致する**。実際この節は 2 度それで穴を開けた——1 度目は「指摘対応済み」を
    1 行に丸めて**手順 5 の当て直し**を飛ばせ、2 度目は「手順 5 を通過・1 パス目が未」の行が
    無いために**1 パス目を飛ばして 2 パス目**に着地できた。

    **代わりに、関門を 1 つずつ数える:**

    1. **未着手の関門のうち、一番早いものから再開する。** 関門は順に
       **手順 5 の Verifier → `/code-review` 1 パス目 → 指摘対応 → 手順 5 の当て直し →
       `/code-review` 2 パス目**（2 パス目のあとに指摘が出たら、この 3 つがもう 1 周する）。
    2. **飛ばしてよいのは、その関門より前にあって、かつ*結果まで*書いてあるものだけ。**
       「起動済み」「報告待ち」は済んでいない。
    3. **「指摘対応が済んだ」は 1 つの状態ではない。** 後に残るのは**手順 5 の当て直し**と
       **`/code-review` 2 パス目**の**両方**なので（手順 6）、**別々に数える**。
    4. **どれか 1 つでも判断がつかなければ、その関門から回し直す**（安全側に倒す）。
    5. 実装が未了なら手順 4 へ、反証が挙がって差し戻し中なら手順 4 へ戻る。
       いずれも**手順 1〜3 は飛ばしてよい**（`gh issue view` の再取得を含む）。

3. **飛ばしてよいのは「済んだと*結果まで*書いてあるもの」だけ（必須）。** 「起動済み」
   「報告待ち」は済んでいない——**その関門は回し直す**。判断がつかなければ**回し直す側に倒す**。
4. **worktree は作り直さない（必須）。** 既にブランチがあるので、**その worktree に入る**
   ——手順 4 の「既に worktree がある場合」に従う。**新規作成の形で呼んではならない**
   （何が起きるかはそこに書いてある）。
    - **いま worktree の中にいても、それが*その周の* worktree とは限らない（必須）。**
      **`--git-dir` ≠ `--git-common-dir` は「どれかの worktree にいる」しか言わない**ので、
      **その周のブランチ／コミットの上にいるかを肯定的に確かめる**（**原本は手順 4**）。
      **#96 で壊れた周は worktree の中にいた。**
5. **受入基準は計画ファイルのものをそのまま使う**（手順 3 を回し直して**作り直さない**——
   作り直すと、割り目の前に決めた基準が黙って変わる）。

**再開した周でも、関門の数とパスの数は変わらない。** 割ったこと自体は、
Verifier ／ `/code-review` ／ 2 パスのどれの免除にもならない。
