# コードに対するプロパティテスト（#1190）

**このファイルは、手順 3 で不変条件に「往復・冪等性・等価性・数値の境界」があると分かったときに読む**（`SKILL.md` 手順 3 から指している）。
**そういう不変条件が無い周は、計画ファイルに `プロパティテスト: なし（理由）` の 1 行を書くだけで、読まなくてよい。**

出典は、Claude Code チームの運用——性質を書き、ライブラリが生成した大量の入力で反例を探すプロパティテストは、エージェントと同じバイアスで作られていない入力でエッジケースを突く
（Addy Osmani「How the Claude Code team thinks about verification」。比較の経緯は hdknr/blogs#837）。手で選んだ例のテストは、実装した側と同じ想定の中しか試さない。
**これは例のテストを置き換えるものではない**——入力の空間が広く、例を手で選ぶと偏る不変条件を、広く確かめる手段を足す。

## 手順 3 で印を付ける（必須）

**不変条件のうち、次の 4 つの型に当たるものに印を付け、プロパティテストで確かめる行にする。** 迷ったら付ける（付けて外すほうが、付けずに黙って落とすより安い）。

| 型 | 性質の形（任意の入力 x について） |
| --- | --- |
| 往復 | `decode(encode(x)) == x`（変換と逆変換。シリアライズ・パース・エンコード・圧縮） |
| 冪等性 | `f(f(x)) == f(x)`（正規化・整形・重複排除・再実行しても同じ） |
| 等価性 | 最適化版と素朴な版が同じ結果を返す（別実装・キャッシュあり／なし・旧い版と新しい版） |
| 数値の境界 | 範囲・単調性・桁あふれ・丸めが、境界の近くを含む任意の値で保たれる |

**付けないもの**: 入力が少数の列挙で尽くせるもの（値が 3 つの列挙型など）・コードの入力を持たない変更（文書・設定・スキル）。**付けない周も、判定そのものを計画に書く**
（`プロパティテスト: なし（<理由>）`。黙って触れないのは「飛ばした」と区別できない——生成物の該当判定と同じ扱い）。

**付けたら、計画ファイルに表を書き、受入基準にも入れる**——関門に渡す受入基準に無いと、プロパティテストが空振りしていても反証にならない:

```text
プロパティテスト: あり
```

| 不変条件の番号 | 型 | 性質（任意の x について） | テストの名前 | ライブラリ | 生成の設定 |
| --- | --- | --- | --- | --- | --- |
| I1 | 往復 | `decode(encode(x)) == x` | `test_roundtrip_I1` | Hypothesis | 例の数 200・seed 固定なし・生成器は全バイト列 |

- **テストの名前に不変条件の番号を入れる**——表の行とテストが、名前の grep で辿れる。
- **受入基準に 1 行足す**: 「表の各行のプロパティテストが、性質を破る変異で反例を出して落ちる（Verifier が示す）」。

## 書く（必須）

**ライブラリは、その言語で使うもの**を使う（Python は Hypothesis、JS/TS は fast-check、Rust は proptest。ほかの言語はその言語で広く使われるもので、名前を表に書く）。

- **期待値を実装と同じ計算で作らない**——性質は実装の外から言える形で書く（往復なら元の入力、等価性なら別実装）。同じ計算を 2 度書いても、どちらかの誤りは見えない。
- **生成器は入力の空間を覆う**——境界・空・最大・負・非 ASCII など、手で選ぶと落とす値を含む。**`assume`・filter で捨てる入力が多すぎない**ようにする（有効な入力がほとんど残らないと、通っても何も確かめていない）。
- **例の数・seed を、緑にするために弱めない**（`max_examples`・`numRuns` を下げる、seed を固定して毎回同じ入力にする）。実行が重くて下げるなら、**下げた値と理由を表の「生成の設定」に書く**。
- **反例が出たら、実装の誤りか性質の誤りかを切り分ける。** 見つけた反例の入力は、例のテストとして残す。**性質を緩めて通すのは、受入基準を緩める操作**で、手順 5 の「実装しながら基準を緩めない」が掛かる。
- **手で選んだ例のテストは残す**——プロパティテストは足すもので、置き換えない。

## ライブラリが無いとき（必須）

**「無い」とは、対象リポジトリの依存の定義にも lockfile にも無いことである**（`prompts/implementer.md`・`prompts/verifier.md` もこの定義）。確かめずに「無い」と書かない（依存の定義と lockfile を見る）。
**宣言にあるのに環境に入っていないのは「無い」ではない**——走らせて落ちるので、環境の不備として報告する（代替しない）。

- **ライブラリを足すのは依存の追加である**——`references/dependencies.md` の手順に載る（計画に `依存の追加・更新: あり`、Verifier の包ごとの表）。**Issue か利用者が頼んでいない依存を、周が黙って足さない。**
- **「無い」と報告する**——実装役は書かずに止まって報告する（`prompts/implementer.md`）。作者が直接書く周は、計画ファイルと PR コメントに書く。
- **例のテストで代替するなら、黙って差し替えず、計画ファイルの表の行に書く**——

  ```text
  ライブラリ: 無い（<言語>の<ライブラリ>が依存の定義にも lockfile にも無い）／代替: 例のテスト（<テストの名前>）／理由: <足さない理由>
  ```

- **代替したら、受入基準の行を、実際に測れる範囲まで弱めて書く**——「表の各行のプロパティテストが…落ちる」を「代替の例のテストが、性質を破る変異で落ちる」に直し、
  **落とした主張（入力の空間の偏りを確かめていないこと）を、手順 6 の PR コメントに名指しで残して人間のレビューに回す**（手順 5 の「分類する前に、その欠落に寄りかかっている主張を弱められないか」と同じ扱い。
  弱めた跡は差分に残らない）。**BLOCKED にも「未証明」にもしない**——測れる範囲を測っていて、落とした主張は名指しされている。
  **代替の分類が誠実か（本当にライブラリが無いのか、探していないだけか）は Verifier が見る。**

## Verifier が返すもの（必須）

**計画に `プロパティテスト: あり` の周は、手順 5 の Verifier（1・2 パス目と狭いパス）に `prompts/verifier.md` の差し込み 10 を入れる。** Verifier は表の行ごとに次を返す:

1. **性質を破る変異を入れ、プロパティテストが反例を出して落ちたか**（陽性対照）。**変異は Verifier が設計する**（著者の変異は添えて渡す）。反例の入力（縮小されたもの）を書く。
   **緑のまま素通りしたなら、そのプロパティテストは空振りしている**——反証として報告し、**変異が性質を実際に破っていること**（例の入力で直に示す）も添える（手順 5 の「緑を『砦の穴』と読む前に、変異が届いているかを疑う」）。
2. **生成の設定**——例の数・seed（固定か）・deadline・health check の抑止・生成器の範囲・`assume`／filter で捨てた割合（取れるなら）。
3. **空振りの形があるか**——期待値が実装と同じ計算・生成器が入力の空間より狭い・捨てる入力が多い・例の数が少ない／seed が固定で毎回同じ入力・`@example` だけで走らせている。

**手順 5 が差し込みを入れることを求める（`SKILL.md` 手順 5）。** **表が返らない・行が欠けるなら、その行は未検証である**（「反証なし」と読まない。同じ差し込みで 1 回だけ当て直す。手順 5 の「Verifier が報告を返さなかったら」）。
**変異を当てる場所は、リポジトリの外で、手順 5 の「実行されない主張は、関門に当てさせる」の注意（`.git` の指す先・失敗したら止まる）に従う。**
