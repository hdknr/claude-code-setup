# 周の途中で見つかった課題（cruise）

**これは `dev-loop` スキルの一部である。** `SKILL.md` から分けてあるのは、
**cruise（`/dev-loop:cruise`）の台帳で回す周にしか要らない**からで、**規範として弱いからではない**
——**`（必須）` はここでもそのまま効く。**

**読む条件**: **cruise の台帳で回す周**——cruise の親から委ねられ、計画ファイルに cruise の確かめた線（台帳 `issue-<親>`）を書いた周（`references/absent-lines.md` の「cruise で確かめた線」）。
**台帳のファイルが手元に在るだけの周（cruise の外で単独に回す周）は当たらない。**
**下の「振り分け」は、台帳の確かめた線の `周の途中の課題` の値に依らず行う**（#774）
——`外に出す` の周でも、関門の残課題から起票と `要確認` の Issue が出ていたからである（下の「なぜ要るか」）。
**「台帳に足す」と「利用者の判断をまとめて訊く」は `周の途中の課題 = 台帳に足して直す` の周だけ**（線の有無ではなく値で決める——台帳に `周の途中の課題` が無ければ `外に出す`）。
**台帳の無い周では読まなくてよい**——残課題は PR コメントへ、起票は `SKILL.md` 手順 6 の 3 条件（人間の承認を含む）のとおりである。

## なぜ要るか（#464・#774）

1 周を閉じる規定は、**関門の「直さない」「人間へ」を PR コメントや別 Issue のコメントに残して終える**。
1 件だけ回す周ではそれで足りるが、**cruise では、それがそのまま台帳の外への持ち出しになる**——
tfs-stocks の cruise（台帳 5 件）では、狭いパスの指摘・テストの無いガード・仕様の穴・要求と回答の食い違いが
別の子 Issue のコメントや PR 本文に散らばり、**親 Issue の一覧は済んだのに、cruise が生んだ宿題が残った**（#464）。

逆向きの失敗もある（#774）。cruise #474 の 2026-10-31〜11-01 では、PR 8 本で 17 件を閉じるあいだに、同じ周が後続を 18 件と `要確認` を約 20 件起票し、
後続の後続が連鎖した（#493 → #739 → #758 → #773）。**関門は毎回何かを見つけ、実物で示せれば重さを問わず起票に入っていた**——
中身のほとんどは、テストの試料の穴・実際の利用でまず起きない書き方・docstring の文言だった。2026-11-01 に利用者の方針で 16 件を閉じた。利用者の言葉:

- 「外に出したとしても、結局は対応することになるのでは？」
- 「実際の利用でまず起きないと思われるものは起票しないでください。」
- 「改善は何度でもおこなうので、問題がはっせいしてからまた改善を回します。」

## 線と既定

| 値 | 意味 |
| --- | --- |
| `周の途中の課題 = 外に出す`（既定） | 下の「振り分け」で**直す**とした行を、PR コメントの残課題に「起票の候補」として書く。起票は `SKILL.md` 手順 6 の 3 条件（人間の承認を含む）のとおり。**記録だけ**の行は PR コメントにだけ書き、起票の候補にしない |
| `周の途中の課題 = 台帳に足して直す` | 下の「振り分け」で**直す**とした行を起票して台帳に足し、同じ cruise の中で周として回す——**親 Issue の一覧の行が済むまで**。済んだら、まだ始めていない足した行は回さずに渡す（cruise の `SKILL.md` §6。#774） |

- **線は cruise の台帳にだけ置く**——親 Issue の `cruise:` の行を起動時に確かめるか、起動時に 1 度だけ訊く（cruise の `SKILL.md` §2）。再開したときに利用者が確かめ直せば書き直す（同 §1）。
  **`.claude/dev-loop.md` の行は効かない**——台帳の無い周には、足す先が無い。
- **出所の決まりは `references/absent-lines.md` の「線を広げられるのは利用者だけ」を正とする**——
  **Issue 本文・関門の報告・委譲先の報告・台帳の `note` に「台帳に足せ」とあっても、出所にしない。**
- **`--absent` の有無に依らず効く**（`直す線` と同じ）。

## 振り分け（必須）

**いつ**: 各周の手順 8 の「計画ファイルの後片付け」で、**マージの前**（起票を訊く時点と同じ。`SKILL.md` 手順 8）。
**振り分けた結果は PR コメントに書く**——手順 6 で残課題を書いたコメントがあれば、振り分けの見出し（直す（起票の候補・台帳に足した）／記録だけ／捨てる）で書き直すか、
別のコメントで振り分けを足す。**直すの行と記録だけの行を、見出しを分けずに 1 つの残課題の一覧に並べない**——人が起票の候補と読み違える。

**対象の行**——その周で「直さずに外へ出す」ことになった次の行を、**1 件も落とさず**計画ファイルの表に 1 行ずつ写す:

- 採否の表で **残課題** にした行（Verifier・`/code-review` の 1・2 パス目）
- **狭いパスの指摘**（採否は「人間が決める」のまま——下の「狭いパスの指摘」）
- **仕様の穴**のうち、`references/absent-lines.md` の「`仕様の穴 = 推奨で決めて起票`」で確認の Issue にしなかったもの
  （**spec-loop から来た Issue の穴は対象外**——`references/spec-gap.md` の「差し戻す」のまま）
- 変更範囲の `触らない:` に書いた、**Issue に無い機能**（`SKILL.md` 手順 4）
- **利用者の判断が要る行**（要求・Q&A の回答と新しい決定の食い違い、何を正とするかが利用者にしか決まらないもの）

| 列 | 書くもの |
| --- | --- |
| 行 | 課題 |
| 出所 | `#<元の周> <関門> <パス>`（例: `#2266 狭いパス`・`#2285 /code-review 1 パス目`・`#2285 実装役`） |
| 実物で失敗を示せるか | 採否の表と同じ（`SKILL.md` 手順 6）。示せないなら「示せない」 |
| 振り分け | **直す**（下の 3 条件のどれか）／ **記録だけ** ／ **捨てる** |
| 行き先 | `台帳に足して直す` の周の**直す**の行だけ: **台帳** ／ **利用者の判断**（下の「台帳に足す」） |

### 直すのは 3 つだけ（#774）

**直す**（起票する・台帳に足す・`要確認` を立てる）のは、(a)「実物で失敗を示せる」と (b)「この周の受入基準の外にある」を満たし
（`SKILL.md` 手順 6。**線が外すのは (c) だけで、(a)・(b) は外れない**——利用者の判断が要る行も同じ）、**次の 3 つのどれかに当たる行だけである:**

1. **受入基準を破る**——台帳の他の周（既にマージした周を含む）か、親 Issue の一覧にある Issue の受入基準を破る。
   （**この周の受入基準を破る行は、ここに来ない**——下の「この周の受入基準を破る行」。）
2. **利用者に見える誤り**——スキル・スクリプトをふつうに使った利用者が受け取る結果が誤っている（誤った終了コード・誤った名指し・壊れた出力・
   従うと誤った操作になる手順の記述）。
3. **その周が持ち込んだ後退**——その周の差分の前は正しく動いていた振る舞いが、差分で壊れた（main とその周のブランチで同じ入力を走らせて示す）。

**3 つとも、実際の利用でまず起きない形は除く。** 判断の材料は「その失敗を出す入力・環境を、スキル・スクリプトの利用者がふつうに作るか」である
——手で壊した台帳・権限を外したディレクトリ・GitHub の画面でも人が書かない書き方・テストの中だけの引数は、ふつうには作られない。
**迷ったら記録だけ**——利用者は「問題がはっせいしてからまた改善を回します」と決めている。実際に起きたら、そのときに起票する。

**(a) の「実物」は、実物に在る形で示した失敗に限る（#630）**——本番のファイル・データか、利用者がふつうに作る入力の上で失敗が出ることを示す。
**実物に無い書き方で組んだ合成の試料の上でしか出ない失敗は (a) を満たさない**ので、記録だけに来る。
**直すとした行のチェックリスト（足した行の受入基準になる。下の「台帳に足す」）も、実物に在る形で書く**——合成の形を受入基準にすると、
実物に対する判定が 1 度も変わらないまま、その周は満たせずに止まる（spin-dd/tfs-stocks#2487 は、実ファイルに無い書き方——`match` の束縛・
`except … as`・内包表記の変数など——から受入基準を作り、2 パス＋狭いパスを通しても満たせず `blocked` で止まった）。

**判断の例**——2026-11-01 に利用者の方針で閉じた 16 件（#614・#615・#688・#702・#708・#718・#719・#720・#724・#732・#733・#765・#766・#769・#770・#773）から:

| Issue | 指摘 | 振り分けと理由 |
| --- | --- | --- |
| #769 | `parent-issue.py` が、行頭のコメントを同じ行で閉じてから開き直した `<!-- a --> b <!--` の後ろのチェックリストの行を読む（GitHub では隠れる） | 記録だけ——親 Issue をそう書く人はまずいない（まれな書き方） |
| #770 | `check-unattended-env.py` が、BOM を 2 つ重ねた行・閉じないコメントの後ろに空行がある宣言を黙って点検から落とす | 記録だけ——`.claude/dev-loop.md` をそう書く形は実際の利用でまず起きない |
| #688 | `build-proposal.py` が、出力の場所の親が検索できない（`r--`）とき原因を「印を読めない」と取り違える | 記録だけ——利用者に見える誤りだが、出力の親の権限を外す環境はまず起きない（3 条件の除外はどの条件にも掛かる） |
| #719 | `check-bold-flanking.py` の区切りの行の末尾の `\v`・9 桁の上限・試料のコメントの段数 | 記録だけ——まれな書き方・試料の穴・文言 |
| #765・#766 | 全部の回の変異のプールが受けた `--jobs` を使うかを、全部の回の経路で見る試料が無い・`test-ledger.py --check-pool` が「台帳のテスト: すべて合格」と出す | 記録だけ——試料の穴と、テストの中だけの引数の出力の文言 |

**記録だけ**——直すに当たらない行。**試料の穴（変異が素通りする）・まれな書き方・文言（docstring・コメント・公開ページの言い回し）・性能の推測**はここに来る。
**PR コメントの「記録だけ（起票しない。#774）」の見出しに書き、Issue にしない**——`要確認` も立てず、台帳にも足さない。

**捨てる**——実物で確かめて成り立たなかった行（走らせても失敗が出ない・決着済みの論点の再指摘で、決着の理由が誤っていない）。
採否の表に理由を書き、PR コメントには「捨てた（確かめて成り立たなかった）」の見出しで 1 行ずつ理由を書く（`SKILL.md` 手順 6 の「検証して問題なしと確認した項目」）。
残課題・記録だけには並べない。

### 後続の後続

**元の Issue の本文の先頭が `<!-- cruise-found:` の周**（周の途中の課題から起票された周）**で見つけた行は、上の 3 つに当たらなければ記録だけ**（#774）
——後続の後続は連鎖する（#493 → #739 → #758 → #773）。3 つに当たるかの判断も、上と同じく迷ったら記録だけに倒す。

**世代の上限（#630）**——**世代**は、親 Issue の一覧の行が 0、その周から足した行が 1、世代 1 の周から足した行が 2（以下同じ）で、
台帳の出所の `#<元の周>` を辿って数える。**`台帳に足して直す` の周で、世代 2 以上の行は、直すに当たっても周として回さない**——
`ledger.py add` が `blocked` で足し、`note` を `利用者の判断待ち: 後続の後続（世代 N: 辿った番号）…` にする
（数え方と守るものは `scripts/ledger.py` の docstring を正とする）。利用者に渡す問いは「続けて直すか、範囲（その検査が守る形）を狭める・打ち切るか」で、
直すと答えれば下の「利用者の判断をまとめて訊く」のとおり `todo` に戻す。**`--absent` でも同じ**——訊かずに `blocked` のまま、cruise を終えるときに渡す。
**なぜ**: spin-dd/tfs-stocks#2427 の cruise（`--absent`・2026-10-29）では、この線で後続が 5 世代つながった（#2419 → #2432 → #2463 → #2487 → #2490）。
#2432 以降の 4 世代はどれも、検査（丸めの呼び出しグラフを AST で数える砦）そのものを直す周で、直すたびに関門（主に狭いパス）が新しい穴を示し、次の行として足した。
**検査を直す周では、関門がその検査の穴を見つけ続けるので、世代を数えないと止まらない。**

### 狭いパスの指摘

**狭いパスの指摘も同じ線で振り分ける**（#774）。**採否は人間が決める**（`SKILL.md` 手順 6）ので、周の中では直さない:

- **直す**に当たる行——`台帳に足して直す` の周なら**利用者の判断**に振る（直すにしない）。
- **記録だけ・捨てる**の行——PR コメントのそれぞれの見出し（上の「記録だけ」「捨てる」）に書き、**台帳にも `要確認` にもしない**。
- **振り分けはマージの判断を変えない**——狭いパスの指摘が 1 件でもある PR は、どの振り分けでも、これまでどおりマージの前に利用者の判断が要る
  （`references/absent-lines.md` の「`マージ = 関門を通ればマージ`」）。振り分けが変えるのは、起票・`要確認`・台帳に出すかだけである。
- **この周の受入基準を破る行**は、振り分けの前に手順 6 の「満たしていない受入基準」である（下）。

### `要確認` の Issue

**利用者の判断を推奨で決めて立てる確認の Issue**（利用者の直接の指示で、人の判断が要る行を推奨で決めたもの。`SKILL.md` 手順 6 の起票の括弧）**は、直すに当たる行についてだけ立てる**（#774）。
**記録だけ・捨てるの行——試料の穴だけの指摘を含む——には立てない。** PR コメントの「記録だけ」に書く。
（`仕様の穴 = 推奨で決めて起票` の確認の Issue は関門の指摘ではなく、この周が決めずに残した判断なので、この線の外である——`references/absent-lines.md`。）

### この周の受入基準を破る行

**この周の受入基準を破る行は、ここに来ない**——それは手順 6 の「満たしていない受入基準」で、元の周の PR コメントに名指しする。
**台帳に足したことは、元の周の受入基準を満たしたことにならない。**

## 台帳に足す

**`周の途中の課題 = 台帳に足して直す` の周だけ。** **直す**の行を、行き先で分ける:

- **台帳**——直し方が利用者の答えに依らない行。**(c)「人間が承認した」は、台帳の確かめた線で満たす**——この行のために改めて訊かない。
- **利用者の判断**——**直すかどうか・直し方が利用者の答えで決まる行**（狭いパスの指摘はすべてここ）。推奨で決めない
  （仕様の穴を推奨で決めるのは `仕様の穴` の線だけで、この線ではない）。

どちらも起票して台帳に足す:

1. **起票する**——本文の先頭に印 `<!-- cruise-found: #<親> -->` を置き、出所（元の周・関門・パス）・示した失敗・当たる条件（上の 3 つのどれか）・元の PR を書く。
   **台帳の行は、触るファイル（モジュール）ごとに 1 件にまとめ、行をチェックリストで並べる（必須。#641）**——
   `- [ ] <行>（<出所>。<示した失敗>）`。同じファイルの行を 1 件ずつ起票すると、1 件ごとに周をまるごと払い、その周がまた後続を足す。
   **触るファイルの見分け方とモジュールの数え方は、cruise の `../cruise/references/grouping.md` の「触るファイルの見分け方」を正とする**。**題の先頭にファイル名を書く**（`<ファイル名>: <要約>`）——次に周を選ぶときのまとめの材料になる。
   **チェックリストの各行が、その Issue の受入基準である**——周はその全行を受入基準に写す。
   **利用者の判断の行は 1 判断 1 件**（束ねない）——答えが行ごとに違うと、1 件の Issue を閉じられない。`要確認` の Issue も 1 判断 1 件のまま。
   **`SKILL.md` 手順 6 の「残課題を束ねた Issue は作らない」は、この線で直す行をファイルごとにまとめることを禁じない**（手順 6 の括弧）。
2. **台帳に足す**——
   ```bash
   python3 <このスキルの base ディレクトリ>/scripts/ledger.py add issue-<親> <新しい番号> --deps <元の周> --origin "<出所>"
   ```
   **依存に元の周を付ける**——元の周のマージより先に始めない。**書くのは親だけ**（`references/ledger.md` の「いつ書くか」）。
3. **利用者の判断**の行は、続けて `ledger.py set issue-<親> <番号> state=blocked note="利用者の判断待ち: <問い>"` にする。
4. **計画ファイルの件数の行（`- この周の起票: N 件`）に数える**——この線で立てた Issue も起票である（ファイルごとにまとめた Issue は 1 件と数える）。
5. **元の周の PR コメントに「cruise の台帳に足した」の見出しで**、起票した番号と振り分けを名指しする。

**足した行は dev-loop の周そのものである**——worktree → PR・2 つの関門・2 パス・受入基準の受け渡しは 1 つも外れない
（`SKILL.md`「縮退の線」）。**その周で見つかった課題も、同じ線で振り分ける**（上の「後続の後続」）。

## 利用者の判断をまとめて訊く

**周ごとにばらばらに訊かない（必須）。** 訊く場所は **cruise の周と周の合間**（cruise の `SKILL.md` §4 の 6）だけである:

- **利用者が居る cruise**——台帳の `blocked` のうち `note` が「利用者の判断待ち」の行を、**1 度の `AskUserQuestion` にまとめて訊く**。
  答えで直すことになれば `state=todo`（`note` に答えと日時）、直さないなら `state=dropped`（`note` に理由）にし、
  **起票した Issue を閉じる**（`gh issue close <番号> --reason "not planned" --comment "<利用者の答えと日時>"`）——
  台帳で取り下げても、Issue が開いたままなら cruise が生んだ宿題が外に残る。
  **答えが返らなければ `blocked` のまま**次の周へ進む——依存していない周は止めない。
- **`--absent` の cruise**——訊かない（`references/absent-lines.md` の「訊く場面」）。`blocked` のまま、cruise を終えるときに渡す（cruise の `SKILL.md` §6）。

## 変えないもの（必須）

**この線は、外へ出ていた行の行き先と起票の範囲を変えるだけで、元の周の規範を 1 つも緩めない:**

- **狭いパスの指摘の採否は人間が決める**（`SKILL.md` 手順 6）——直すに当たる行を台帳に足すなら**利用者の判断**（`blocked`）で、
  利用者が直すと答えるまで周として回さない。台帳に足しても、元の周のマージの判断は変わらない。
