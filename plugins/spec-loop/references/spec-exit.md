# 仕様レビューを抜ける条件

開発者向けの仕様（置き場所は `tree.md`）が**確定した**と言える条件。
`spec-review` はこれを満たしたときだけ「抜けた」と報告し、`scaffold` は
これを満たした仕様だけを入力にする。

**条件 2〜4 は、範囲の中で、性質の水準で読む**——範囲の外の場面と実現の手段の細部は、
これらの条件を「満たさない」根拠にならない。線と振り分けの区分は `spec-scope.md` を正とする。

**表の条件をすべて満たして、はじめて抜けられる。** 1 つでも満たさないか、
**満たしたかどうかを判定できなかったなら、抜けていない。**

| # | 条件 | 誰が判定するか |
| --- | --- | --- |
| 1 | Q&A 表（共有の `shared/qa.csv` と内部の `spec/qa-dev.csv`）に、仕様に反映した状態（`反映済み`・`暫定反映`。`qa-csv.md`）でない行が 0 件で、仕様に下の「未決定の印」が 0 件 | 同梱のスクリプト（下） |
| 2 | 仕様チェックリスト（下）の項目が、範囲の中の機能ごとに、仕様のどこに書いてあるかを指せる——**指せないことの指摘のうち、重さ（下の「指摘の重さ」）が `判断が要る`・`結果が割れる` のものが 0 件** | 判定役（Red Team） |
| 3 | 決定表の各行と、範囲の中の各シナリオに、対応するテストケース（入力と期待結果）が仕様の中にある。範囲の外の場面には書かない——**欠けの指摘のうち、重さが `判断が要る`・`結果が割れる` のものが 0 件** | 判定役（Red Team） |
| 4 | 形式検査の対象（下。**作業中の版の改修の性質で選ぶ**）ごとに、検査器が範囲の中で反例を出さず、**空振りでない**ことを確かめた。対象が無ければ「対象なし」と書く | 判定役（Formal Checker）と検査器の出力 |
| 5 | 最後のレビュー（下の「最後のレビュー」）で判定役が挙げた指摘（案が「範囲の外」「実装に渡す」の行を含む）が、1 件残らず振り分け済み（区分は `spec-scope.md` の「振り分けの区分」。**根拠を確かめていない行は振り分け済みに数えない**） | `spec-review` の報告（振り分けの表） |

**最後のレビューとは、その回で最後に回したレビュー（2 回目を回したなら 2 回目）と、そのあとの狭いパス（下の「2 回目のあとの直し — 狭いパス」）を合わせたもの**である。
2 回目のレビューのあとで仕様か範囲の文書を直したなら、**狭いパスがその直しを確かめ、下の 3 つを満たすまで、抜けていない**——
**「抜けた」と報告する時点に、レビューを通っていない直しは残らない。**

条件 5 で Q&A 表に起票した指摘は、その行が `反映済み`（か `暫定反映`）になるまで条件 1 を満たさない。

**`暫定反映` の行が残っていても抜けられる**——仕様には反映済みなので。ただし利用者の確認は済んでいない。
**確認が済むまで要求確定のサインオフは付けない**（`signoff-tags.md`）。スクリプトは暫定の行の件数を出す。
**抜けても、`暫定反映` の行が Q&A 表に残るうちは scaffold が何も作らない**（中間表現が指すかどうかに依らない。`spec-ir.md`）。

**判定役が案を「範囲の外」「実装に渡す」とした行を、呼び出し元が範囲の中の区分（仕様を直す・起票する）に振り分けたら**、
その判定役の条件 2〜4 の判定（`満たす`）は**その回はそのまま使わない**——判定役はその行を判定から外していたので、
その条件は `満たさない` とする（仕様を直したなら次のレビューで判定し直す）。

**テストケースを書き起こせない仕様は、まだ確定していない。**

**範囲の文書（`spec/scope.md`）が無くても、抜けられなくはならない**——`spec-scope.md` の既定の線で読む。

## 条件 1 を確かめる

```bash
python3 <spec-loop の base ディレクトリ>/scripts/check-spec-exit.py <Q&A 表のパス> <仕様のディレクトリ>
```

0 なら条件 1 を満たす。**条件 2〜4 はこのスクリプトでは判定しない。**
内部の表は、仕様のディレクトリの中の `qa-dev.csv` をスクリプトが自分で読む（あれば）。内部の行は資料に載らないが、
**決めて反映した記録が無ければ条件 1 を止める**。内部の表の文は未決定の印として数えない（表として検査する）。
終了コードと、何を見て何を見ないかは、スクリプトの docstring を正とする。

## 未決定の印

仕様の本文にこれらが残っていれば、未決定の事項が残っている。
英字の印は大文字・小文字を区別せず、**全角も半角と同じに数え**（`ＴＢＤ`）、
**語として**現れたときだけ数える（`TODOS` や `mastodon` は数えない）。

| 印 |
| --- |
| `TBD` |
| `TODO` |
| `未定` |
| `要確認` |

**`未定義` は印に当たらない**（「未定義の状態に遷移しない」のように、決まったことを書く語なので）。

**決まっていないことは、印を残すか、Q&A 表に起票する。** 印を消して黙って決めない。

## 仕様チェックリスト

機能（画面の操作・API・バッチなど、仕様が書き分けている単位）ごとに、次が書いてあること。

| 項目 | 書くもの |
| --- | --- |
| 入出力 | 受け取るもの・返すもの・その型と単位 |
| エラー | 起こりうる失敗と、そのときの振る舞い（通信断・二重送信・権限なしを含む） |
| 境界値 | 上限・下限・空・ゼロ・端数の扱い |
| 状態遷移 | 状態を持つものは、状態と遷移の条件。取り消し・やり直しを含む |

該当しない項目は「該当なし」と書く（空欄は書き忘れと区別できない）。

**書くのは性質であって、実現の手段ではない**（`spec-scope.md` の「縦の線」）。エラーは範囲の中の失敗について書き、
範囲の外のまれな失敗は範囲の文書の原則で受ける。

## 形式検査の対象

| 対象 | 見つけるもの |
| --- | --- |
| 決定表・計算ルール | どのルールにも当てはまらない入力（抜け）、結果が食い違う入力（矛盾） |
| 並行・リトライ・取り消しを含む業務フロー | 通信断や同時操作で、データが食い違ったまま残る実行順 |
| 権限・ロール | 見えてはいけないデータが見えてしまう組み合わせ |

**画面・文言・使い勝手は対象外。** 順番どおりに進むだけのフローも対象にしない。

### 改修の性質で選ぶ

**検査の深さは、作業中の版の改修の大きさに釣り合わせる。** 表の対象があっても、次に当たらなければ形式検査はしない
（「対象なし」とし、理由を書く）:

| 対象 | 形式検査をするとき | しないときに受けるもの |
| --- | --- | --- |
| 決定表・計算ルール | 作業中の版で決定表・計算ルールを足した・変えた | — |
| 並行・リトライ・取り消しを含む業務フロー | 作業中の版の改修が、**改修するシステムに状態を持つ業務フローを新しく足す**か、**既存のフローの状態・遷移を変える** | **既存の書き手に排他を足すだけ**（状態と遷移は変わらない）なら、同時実行で成り立つべき性質とそのテスト（条件 2・3）で受ける |
| 権限・ロール | 作業中の版でロール・権限の組み合わせを足した・変えた | — |

**決定表・計算ルールと権限・ロールは版から見て決め、業務フローは改修するシステムから見て決める。** 決定表とロールは、
版で足した・変えたものがそのまま検査の対象になる。業務フローは、**版で初めて仕様に書いたフローでも、
システムに前からあるなら「新しく足す」に当たらない**（既存システムを改修する v1 がこれに当たる）。

**どれを対象にするかは `spec-review`（Planner）が決めて、理由と一緒に Formal Checker に渡す。** フローがシステムに前からあるかは、
要求と既存システム（Domain Checker の照合先）を読まないと決まらず、Formal Checker はそれを持たないからである。
**照合先も Formal Checker に渡す。** Formal Checker は、渡された選び方が上の表に反すると判断したら、指摘として挙げる（黙って広げも狭めもしない）。

**形式検査をするときも、構成（書き手・利用者・ジョブの数など）は性質が破れうる最小（ふつう 2〜3）から始める。**
その構成で正常な状態に到達でき、陽性対照で反例が出るなら、**構成を広げない**——広げても新しい反例が出るとは限らず、
状態の数だけが増えて検査が判定できなくなる（#364 で書き手 10 人の構成が一度判定できなかった）。
広げるのは、最小の構成では性質を言えない理由（例: 3 人目が来て初めて起きる順序）を書けるときだけ。

**形式化するのは範囲の中の業務フローで、性質（不変条件）の水準である**——特定のロックの方式や書き込みの順序を
前提にしない（それは手段。`spec-scope.md`）。反例ごとに、**重なっている独立した事象**（よく起きる／まれの別）と**影響**を書く。
範囲の外かは、頻度と影響を合わせて `spec-scope.md` の既定の線で決める——**まれでも影響が大きい反例は範囲の中**である。

**「反例なし」は空振りを疑う。** 次の 2 つを確かめて、はじめて「反例なし」と言える:

- **正常な状態に到達できる**（モデルが何も許さない形になっていない）
- **わざと壊した版で反例が出る**（陽性対照）

**形式化で置いた前提**（端数処理・割引の適用順など）は形式化した側の解釈なので、
利用者の判断が要るなら Q&A 表で確かめる。

## 指摘の重さ

**判定役は、範囲の中の指摘ごとに重さを付ける。** 判定役は毎回何かを見つけるので、**見つけたものが 1 件でもあれば満たさない、では収束しない**
（#363 では、条件 2 の根拠が 1 件まで細っても、直すと別の箇所に次の指摘が出る回が 6 回続いた）。条件 2・3 に効くのは上の 2 つだけである:

| 重さ | 当てはまるもの | 条件 2・3 |
| --- | --- | --- |
| `判断が要る` | 選択肢によって利用者に見える結果が変わり、利用者が決める（振り分けの案は「共有の Q&A 表に起票する」） | **効く** |
| `結果が割れる` | **同じ入力に対して、仕様から結果が 1 つに決まらない**——2 つの結果を書いている（矛盾）か、書いていないので作り手によって結果が変わる（チェックリストの項目・テストケースの欠け） | **効く** |
| `補い` | **結果は仕様から 1 つに決まる**——言い回し・重複・説明の追加、既に書いた性質を別の入力で確かめるテストの追加、「該当なし」の書き忘れで他の記述から該当しないと読めるもの | 効かない |

- **見分け方**: **その指摘を直さずに 2 人が別々に作ったとき、外から確かめるテストで区別できる違いが出うるか。** 出うるなら `結果が割れる`（か `判断が要る`）、出ないなら `補い`。
- **付けるのは判定役、確かめるのは呼び出し元**（振り分けと同じ）。**迷ったら重いほうに付ける。**
  呼び出し元が重さを軽くしてよいのは、根拠を開いて**仕様から結果が 1 つに決まる箇所（`ファイル:行`）を示せたときだけ**——示せなければ判定役の重さのまま。
- **条件 2・3 の判定は、確かめたあとの振り分けの表から呼び出し元が決める。** 範囲の中で、重さが `判断が要る`・`結果が割れる` の行が
  1 件でも残れば `満たさない`、0 件なら `満たす`。**判定役の書いた判定と表が食い違ったら、表を取る**
  （`補い` だけで `満たさない` と書いていても、自分の表に `結果が割れる` の行がありながら `満たす` と書いていても）。
  **判定し直させない**——呼び直せば 3 回目のレビューになる。判定役が `判定できなかった` と書いたら（読めないファイル・動かない道具）、それはそのまま使う。
- **範囲の外・実装に渡す の行は、重さを問わず条件に効かない**（今までどおり。`spec-scope.md` の「振り分けの区分」）。
  #329 で「軽微」と呼んだのはこれらの行で、**重さは範囲の中の行に付ける 2 つめの軸**である——振り分けの区分を置き換えない。
  `判断が要る` は区分の「共有の Q&A 表に起票する」に当たり、`結果が割れる` と `補い` は多くが「仕様を直す」に当たる
  （`補い` は直さなくてよい。下の「2 回目のあとの直し — 狭いパス」）。
- **条件 4 は重さで変えない**——範囲の中の反例は、定義上 `結果が割れる`（同じ実行順で、データが食い違ったまま残る）である。
- **条件 5 は重さを問わない**——`補い` の行も、振り分けの表に 1 件 1 行で載せ、振り分ける。

## 2 回目のあとの直し — 狭いパス

`spec-review` は 1 回の実行でレビューを 2 回までしか回さない。**2 回目のレビューのあとで仕様か範囲の文書を直したら、
その直しの差分だけを判定役に 1 回確かめさせる**——これを**狭いパス**と呼ぶ（dev-loop の「2 パス目で直した分は、その差分だけに Verifier を 1 回当てる」と同じ形）。

- **当てる役**: 直しの元の指摘を挙げた役。直しが 2 つの役の指摘にまたがれば、**役ごとに 1 体**。
- **渡すもの**: 直しの差分（直す前と後）と、その元になった 2 回目の指摘の行。抜ける条件・範囲の線・信頼できない入力の扱いは**まるごと渡す**（絞るのは差分だけ）。
- **返させるもの**: 元の指摘ごとに `解消した`／`解消していない`／`判定できなかった`、**差分の中の新しい指摘**（重さつき）。
  Formal Checker なら、直した仕様でモデルを走らせ直した結果（陽性対照を含む）。
- **狭いパスの指摘は、その回は直さない・当て直さない**（ここで止める。直せば、またレビューを通っていない直しが残る）。
  ただし **`判断が要る` の指摘は共有の Q&A 表に起票する**——起票は仕様の直しではなく、起票しなければ利用者の判断が残ったまま条件 1 も止まらない。
  ほかの指摘は報告に載せ、次の回で扱う。
- **2 回目の `補い` は、その回は直さない**——直せば狭いパスが要り、直しが次の指摘を呼ぶ。報告に載せ、次の回で直してよい。

**2 回目のあとで仕様か範囲の文書を 1 か所でも直したなら、2 回目の判定が何であっても、次をすべて満たすときだけ抜けられる**
（2 回目に条件を満たしていて、条件を判定しない Domain Checker の指摘を直した場合や、範囲の文書に 1 行足しただけの場合も同じ）:

1. 狭いパスが、当てた**すべての役から返った**（再実行しても返らなければ満たさない）
2. 直した元の指摘**すべて**について `解消した` が返った
3. 狭いパスの新しい指摘に、**効く重さ（`判断が要る`・`結果が割れる`）のものが 0 件**

**どれかを満たさなければ、抜けていない**——記録の表の `条件2〜4` には、新しい指摘が `判断が要る` だけなら `回答待ち`、
それ以外なら `満たさない` と書く（下の「記録の表」）。

**2 回目の `満たさない` を解消済みに置き換えてよいのも、上の 3 つを満たし、かつ 2 回目に条件を `満たさない` にした効く重さの指摘が
すべて直しの対象になっていたときだけ**である（`判断が要る` は起票した時点で条件 1 を止めるので、ここで解消済みにはならない）。

## 実行の上限と記録

**判定役に収束を委ねない。** 「どこで止めるか」を判定役が決める形では、利用者が消耗して打ち切るまで回り続ける
（#363 の 13・14 回目は、利用者が「範囲を絞って」と打ち切った）。だから**回数の上限で、利用者に判断を返す**。

### 記録の表

**正本リポジトリの `spec-review/v<n>.csv`**（`<n>` は作業中の版の番号）に、**出来事ごとに 1 行**足す（置き場所は `tree.md`）。
**会話からは数えない**——`spec-review` は再開点を表とファイルから読むので、上限も表から決まらなければ効かない（`spec-scope.md` の歯止めと同じ理由）。

**`docs/` の外に置く。** `docs/v<n>/` の中に置くと、版の重ね合わせで前の版の記録に上書きされ、版の差分（`diff-versions.py`）が
記録の変更を仕様の変更として出し、判定役の差分と提案書の「前の版からの変更」に載る。`spec/` の中に置くと、条件 1 のスクリプトが
記録を仕様のファイルとして数え、**仕様を 1 行も書いていないのに条件 1 を満たす**（記録だけで「仕様 1 ファイル」になる）。

| 列 | 書くもの |
| --- | --- |
| `回` | 表の中の行の通し番号（1 から。どの行にも振る） |
| `日付` | `YYYY-MM-DD` |
| `結果` | `抜けた`／`抜けていない`（実行の行）／`上限`（上限に達して判定役を起動しなかった行）／`利用者の判断`（下） |
| `条件2〜4` | 実行の行だけ: 条件 2〜4 と狭いパスがすべて通れば `満たす`。**通らなかった理由が、効く重さの指摘が `判断が要る` だけ**（起票して回答待ち）なら `回答待ち`。それ以外（`結果が割れる` の指摘・範囲の中の反例・狭いパスの `解消していない`）なら `満たさない`。判定役の報告が欠けたか判定できなかったなら `判定できなかった`。ほかの行は `-` |
| `要求の行` | 実行の行だけ: 利用者向けの要求（`requirements/` の Markdown すべて）の行数。重ね合わせた全体で数える。ほかの行は `-` |
| `決定表の行` | 実行の行だけ: 共有の決定表のデータの行数（見出しを除く）。同上 |
| `テストケース` | 実行の行だけ: 仕様の中のテストケースの数（下の「仕様の規模」の数え方）。同上 |
| `仕様の行` | 実行の行だけ: 仕様（`spec/` の Markdown。範囲の文書を含む）の行数。**参考に出すだけで、引き金には使わない**（下）。同上 |
| `判断` | `利用者の判断` の行だけ: 選んだもの（下の 3 つの名前）。ほかの行は `-` |
| `機能` | 実行の行で `条件2〜4` が `満たさない` のとき: 効く重さの指摘があった機能の名前（仕様チェックリストを埋めた見出しをそのまま写す。2 つ以上なら `;` で区切る）。ほかは `-` |

**条件 1 か条件 5 だけで抜けられなかった実行の行は、`条件2〜4` が `満たす` になる**——どちらも判定役の空回りではない
（条件 1 は利用者の回答待ち、条件 5 は呼び出し元の振り分けの残り）。

### 上限

**数え始め**は、`判断` が `続ける` か `範囲を決め直す` の最後の行の後（無ければ表の最初）。**そこから後の実行の行で、
`条件2〜4` が `満たさない` か `判定できなかった` の行が 3 つあれば、次の回は判定役を起動しない。**
**最後の `利用者の判断` の行が `止める` なら、数えずにそのまま利用者に訊く**——`止める` は数え直しの理由にならない
（呼び直しただけで判定役が動き出さないように）。

訊くときは次の 3 つから選んでもらい、`結果` が `上限` の行と、選ばれた `利用者の判断` の行を足す:

| 判断 | すること |
| --- | --- |
| `続ける` | 数え直して、もう一度回す |
| `範囲を決め直す` | 数えた行の `機能` の列に出てくる機能について、`spec-scope.md` の「回を重ねたときの歯止め」の形の質問を共有の Q&A 表に起票して止まる（回答が来るまで条件 1 が止める） |
| `止める` | 止まる。仕様は確定していない（抜けていない）。次に呼ばれたときも、まず訊く |

- **数えない行**: `回答待ち`・`満たす`（条件 1・条件 5 だけで抜けられなかった回を含む）。利用者の回答待ちや呼び出し元の振り分けの残りは、判定役の空回りではない。
- **N=3 の根拠**: #363 の実案件の記録（`review-log.md` の各回の最後のパスの「判定:」の行）に、**判定の行をそのまま**当てると、
  3〜5 回目が続けて満たさず、**6 回目の前に**利用者に返ることになる（実際には 8 回目のあとで利用者が「性質とテストに絞る」と指示して止めた）。
  ただし**これは旧い規則の判定**で、3〜5 回目の根拠を重さで分け直してはいない。新しい規則で当て直すと 10 回目は形式検査の対象が無くなりうる
  （上の「改修の性質で選ぶ」）ので、9 回目のあとは 11・12 回目の 2 つしか数えず、**13 回目の前には返らない**。
  **N=3 は、1 案件の旧い判定に当てた 1 点からの選びである**——プロジェクトの `CLAUDE.md` で N を変えてよい。
- **歯止め（`spec-scope.md`）とは別の数である。** 歯止めは機能ごとに Q&A の行を数え、上限は版ごとに実行を数える。両方を当てる。
- **版が変われば数え直す**——表は版ごとのファイルに分ける。

## 仕様の規模

**仕様が要求に比べて膨らむのを、記録の表のテストケースの数で見る。** #364 の実案件では、要求（`requirements/` の Markdown 2 ファイル）190 行
（主のファイルは 89 行）・決定表 15 行に対して、仕様の主のファイルが 768 行・テストケースが 300 件になった（Issue によれば最初の版は 414 行・129 件）。

- **テストケースの数え方**: 仕様の中の「入力と期待結果」の組を 1 件と数える。**仕様がテストケースに番号を振っていれば番号の数**
  （例: 表の行の先頭の `F1-5b`）、振っていなければテストケースの表のデータの行の数。**同じ版の中では同じ数え方を続ける。**
- **引き金にはテストケースだけを使う。** 仕様の行は、記録・設計メモのような別のファイルや節を `spec/` に置く運用で毎回増え、
  手段を設計メモへ移しても減らないので、引き金にすると見直しが空振りする。
- **毎回、記録の表の規模の列を報告に出す**（直前の実行の行との差も）。
- **直近 2 つの実行の行を比べ、テストケースの増え方（割合）が、要求の行と決定表の行を合わせた増え方（割合）より大きければ、
  次の回の判定役を起動する前に「減らす見直し」をする**——要求が変わっていないのにテストケースが増えた回は、必ずこれに当たる。
  前の回の中で判定役の指摘に応えて増えた分は、その 2 つの行の間に出る。**その版に実行の行が 1 つしか無ければ、比べない。**
  見直しでは、仕様の中の**重複**・**実現の手段**（`spec-scope.md` の「縦の線」。設計メモへ移すか消す）・**要求に無い決まり**
  （利用者に見える結果を決めているなら起票し、そうでなければ消す）を削る。
  要求より速くテストケースが増えるのは、判定役の指摘に応えて細かくなった分である。**割合で比べるのは**、回答の反映で要求が数行だけ変わった回に、
  見直しが黙って外れないようにするため（#364 の 10〜14 回目には、回答の反映で要求を書き足した回がある）。
- **絶対の閾値（テストケースは要求の何倍まで、など）は既定では置かない**——手元の実データは 1 案件だけで、線を引く根拠が無い。
  **プロジェクトが目安の比を `CLAUDE.md` に書いたら、それを超えた回も見直しをする。**
- **判定役は、仕様を減らせる指摘（重複・手段の記述・要求に無い決まり）を、足す指摘より先に挙げる。**
