# 仕様レビューを抜ける条件

開発者向けの仕様（置き場所は `tree.md`）が**確定した**と言える条件。
`spec-review` はこれを満たしたときだけ「抜けた」と報告し、`scaffold` は
これを満たした仕様だけを入力にする。

**条件 2〜4 は、範囲の中で、性質の水準で読む**——範囲の外の場面と実現の手段の細部は、
これらの条件を「満たさない」根拠にならない。線と振り分けの区分は `spec-scope.md` を正とする。

**表の条件をすべて満たして、はじめて抜けられる。** 1 つでも満たさないか、
**満たしたかどうかを判定できなかったなら、抜けていない。**

| # | 条件 | 誰が判定するか |
| --- | --- | --- |
| 1 | Q&A 表（共有の `shared/qa.csv` と内部の `spec/qa-dev.csv`）に、仕様に反映した状態（`反映済み`・`暫定反映`。`qa-csv.md`）でない行が 0 件で、仕様に下の「未決定の印」が 0 件 | 同梱のスクリプト（下） |
| 2 | 仕様チェックリスト（下）の項目が、範囲の中の機能ごとに、仕様のどこに書いてあるかを指せる——**指せないことの指摘のうち、重さ（下の「指摘の重さ」）が `判断が要る`・`結果が割れる` のものが 0 件** | 判定役（Red Team） |
| 3 | 決定表の各行と、範囲の中の各シナリオに、対応するテストケース（入力と期待結果）が仕様の中にある。範囲の外の場面には書かない——**欠けの指摘のうち、重さが `判断が要る`・`結果が割れる` のものが 0 件** | 判定役（Red Team） |
| 4 | 形式検査の対象（下。**作業中の版の改修の性質で選ぶ**）ごとに、検査器が範囲の中で反例を出さず、**空振りでない**ことを確かめた。対象が無ければ「対象なし」と書く | 判定役（Formal Checker）と検査器の出力 |
| 5 | 最後のレビュー（下の「最後のレビュー」）で判定役が挙げた指摘（案が「範囲の外」「実装に渡す」の行を含む）が、1 件残らず振り分け済み（区分は `spec-scope.md` の「振り分けの区分」。**根拠を確かめていない行は振り分け済みに数えない**） | `spec-review` の報告（振り分けの表） |

**最後のレビューとは、その回で最後に回したレビュー（2 回目を回したなら 2 回目）と、そのあとの狭いパス（下の「2 回目のあとの直し — 狭いパス」）を合わせたもの**である。
2 回目のレビューのあとで仕様か範囲の文書を直したなら、**狭いパスがその直しを確かめ、下の 3 つを満たすまで、抜けていない**——
**「抜けた」と報告する時点に、レビューを通っていない直しは残らない。**

条件 5 で Q&A 表に起票した指摘は、その行が `反映済み`（か `暫定反映`）になるまで条件 1 を満たさない。

**`暫定反映` の行が残っていても抜けられる**——仕様には反映済みなので。ただし利用者の確認は済んでいない。
**確認が済むまで要求確定のサインオフは付けない**（`signoff-tags.md`）。スクリプトは暫定の行の件数を出す。
**抜けても、`暫定反映` の行が Q&A 表に残るうちは scaffold が何も作らない**（中間表現が指すかどうかに依らない。`spec-ir.md`）。

**判定役が案を「範囲の外」「実装に渡す」とした行を、呼び出し元が範囲の中の区分（仕様を直す・起票する）に振り分けたら**、
その判定役の条件 2〜4 の判定（`満たす`）は**その回はそのまま使わない**——判定役はその行を判定から外していたので、
その条件は `満たさない` とする（仕様を直したなら次のレビューで判定し直す）。

**テストケースを書き起こせない仕様は、まだ確定していない。**

**範囲の文書（`spec/scope.md`）が無くても、抜けられなくはならない**——`spec-scope.md` の既定の線で読む。

## 条件 1 を確かめる

```bash
python3 <spec-loop の base ディレクトリ>/scripts/check-spec-exit.py <Q&A 表のパス> <仕様のディレクトリ>
```

0 なら条件 1 を満たす。**条件 2〜4 はこのスクリプトでは判定しない。**
内部の表は、仕様のディレクトリの中の `qa-dev.csv` をスクリプトが自分で読む（あれば）。内部の行は資料に載らないが、
**決めて反映した記録が無ければ条件 1 を止める**。内部の表の文は未決定の印として数えない（表として検査する）。
終了コードと、何を見て何を見ないかは、スクリプトの docstring を正とする。

## 未決定の印

仕様の本文にこれらが残っていれば、未決定の事項が残っている。
**形式検査のモデル（`spec/formal/`）の中は見ない**——仕様から書き起こした写しで、記録の「置いた前提」に未決定のことを書き残してよい
（未決定は Q&A 表と仕様の本文で決まる。`tree.md` の「形式検査のモデル」。#908）。
英字の印は大文字・小文字を区別せず、**全角も半角と同じに数え**（`ＴＢＤ`）、
**語として**現れたときだけ数える（`TODOS` や `mastodon` は数えない）。

| 印 |
| --- |
| `TBD` |
| `TODO` |
| `未定` |
| `要確認` |

**`未定義` は印に当たらない**（「未定義の状態に遷移しない」のように、決まったことを書く語なので）。

**決まっていないことは、印を残すか、Q&A 表に起票する。** 印を消して黙って決めない。

## 仕様チェックリスト

機能（画面の操作・API・バッチなど、仕様が書き分けている単位）ごとに、次が書いてあること。

| 項目 | 書くもの |
| --- | --- |
| 入出力 | 受け取るもの・返すもの・その型と単位 |
| エラー | 起こりうる失敗と、そのときの振る舞い（通信断・二重送信・権限なしを含む） |
| 境界値 | 上限・下限・空・ゼロ・端数が出るところ（境界ちょうどの倒し方と丸めの規則は下の「境界の細部」の行に書く） |
| 状態遷移 | 状態を持つものは、状態と遷移の条件。取り消し・やり直しを含む |
| 呼ぶ側の分岐 | 機能が入力を受け取る・ほかの処理を呼ぶところ（ジョブ・端末・データベース・API・WebSocket などとの結線）で、次の 3 組の分岐ごとに**利用者に何を見せるか**（画面・通知・業務の判定）。**入力**が欠ける・遅れる・順が崩れる／**呼ぶ処理**が失敗する・やり直される・再起動する／**量**が上限を超える・重なる（下の「呼ぶ側の分岐」） |
| 測る値 | 値を数える・測って閾値と比べ、合否や判定を出すところ（件数・率・時間・性能など）で、測る値ごとに**閾値と合格の基準**に加えて、**数える単位**（何を 1 回と数えるか）・**除く範囲の境目**（開区間か閉区間か・除く条件と数える条件のどちらを先に判定するか）・**標本が基準の期間（か必要な件数）に満たないときの合否の出し方**（下の「測る値」） |
| 文書どうしの定義 | 機能の入力・値を `spec/` の中の 2 つ以上の箇所（概要・規則・API・範囲の文書と、同じファイルの中の節・設計メモの節など）が定義しているなら、**どの箇所の定義も同じであること**。書き方は、定義を 1 つの箇所に置き、ほかはそこを指す（下の「文書どうしの定義」） |
| 境界の細部 | 境界と、数を比べる・丸める計算ごとに、**境界ちょうどの値がどちら側か**・**小数の比べ方**（どの桁まで等しいとみなすか）・**丸めの規則**（どの桁で・どの規則で・計算のどの段で）・**符号付きゼロ**（`-0` を `0` と同じに扱い・表示するか）。Red テストが判別しない形なので、性質として書く（下の「境界の細部」） |

該当しない項目は「該当なし」と書く（空欄は書き忘れと区別できない）。

**書くのは性質であって、実現の手段ではない**（`spec-scope.md` の「縦の線」）。エラーは範囲の中の失敗について書き、
範囲の外のまれな失敗は範囲の文書の原則で受ける。

### 呼ぶ側の分岐

**機能の決定表を詰めても、その機能を「いつ・何を入力に・失敗したらどう」呼ぶかは詰まらない**——#402 の実案件では、
実装の途中で立った要確認の Issue 22 件のうち 13 件（59%）が利用者に見える仕様の穴で、どれもこの結線の層だった
（欠落・遅延・失敗・再実行のときに何を見せるか）。だから、チェックリストの「エラー」（機能そのものの失敗）とは別の行にする。

- **分岐ごとに書く。** 入力が欠ける／遅れる／順が崩れる、呼ぶ処理が失敗する／やり直される／再起動する、量が上限を超える／重なる（同じ処理が同時に走る）
  ——それぞれについて、利用者に何が見えるか（画面・通知・業務の判定の結果）を書く。
  **起きない分岐は、分岐ごとに「該当なし」と理由を書く**（例: 入力は 1 回の要求で全部そろって届く）。
  **入力も呼び出しも外と結ばない機能**（純粋な計算）は、行ごと「該当なし」でよい。
- **書くのは見えるもの（性質）で、手段ではない**——再試行の回数・待つ時間・キューの分け方は書かない（`spec-scope.md` の「縦の線」。手段の指摘も `spec-scope.md` の「決める順」を上から当てる——範囲の外に当たらなければ 4 で、性質とテストが欠けていれば仕様を直す）。
  **利用者が待つ時間**のように見えるものは手段ではない（`spec-scope.md` の「迷う例」）。
- **何を見せるかが仕様から決まらず、選択肢で利用者に見える結果が変わるなら、共有の Q&A 表に起票する**（`spec-scope.md` の「決める順」の 5）。
  開発者が決めてよい（見える結果が変わらない）なら仕様を直す。
- **範囲の線（頻度 × 影響）は、ほかの場面と同じく `spec-scope.md` の「横の線」で読む**——既定の線に、範囲の文書（`spec/scope.md`）と正本の `CLAUDE.md` が変えたところを重ねて当てる（食い違ったら範囲の文書を取る。`spec-scope.md` の「既定の線」）。分岐の場面に重なる独立した事象で頻度を決め（事象がよく起きるかまれかは `spec-scope.md` の事象の表）、影響と合わせる。
    - **よく起きる分岐**（よく起きる事象 1 つのもの——例: 通信断で入力が遅れる・呼ぶ処理が通信断で失敗してやり直される・二重送信で同じ処理が重なる）は、範囲の中で分岐ごとに書く。
      **同じ分岐でも、重なる事象で頻度は変わる**——呼ぶ処理が失敗する分岐でも、相手が応えないことによるものは「まれ」である（`spec-scope.md` の事象の表）。
    - **まれな分岐**（まれな事象を含むか、独立した事象が 2 つ以上重なるもの——例: 遅れた入力の取り直しの最中に再起動する）は、**分岐ごとに書かず、原則 1 本で受けてよい**
      ——**影響が小さければ範囲の外**（範囲の文書に 1 行、受ける原則を名指しする）、**影響が大きければ範囲の中で原則 1 本**（原則のテストケースを 1 つ以上書く）。
      どちらにするか・原則の書き方は `spec-scope.md` の「原則 1 本で受ける」を正とする。
    - **影響が大きいか小さいか決まらない分岐は、範囲の外にしない**（`spec-scope.md` の「既定の線」）。
- **移行（spec-loop 0.54.0 で足した行）**: この行を足す前に条件 2 を満たした仕様は、次に `spec-review` を回したとき、
  その回のレビューの対象の機能（v2 以降の差分モードなら作業中の版の機能）についてこの行を埋める。
  埋まっていなければ、条件 2 の書き漏れとして判定する（重さは「指摘の重さ」のとおり——見せるものが決まらず結果が割れるなら `結果が割れる`）。
  **前の版で抜けた仕様を、この行のためだけに版を立てて見直す必要はない。**

### 測る値

**閾値と合格の基準を書いても、何をどう数えるかが決まっていなければ、同じ記録から作り手ごとに違う合否が出る**——#402 の実案件では、
関門の「仕様の意味」についての指摘が測定の周 2 本に集まり（10 件）、実装の途中で立った要確認の Issue のうち 4 件が測定の定義
（数える単位・境目・小さい標本での合否）だった。仕様の測る値は、閾値と合格の基準は書いていたが、操作的な定義が無かった。

- **測る値とは**、仕様が値を数える・測って閾値と比べ、合否や判定（画面の表示・通知・業務の判定）を出すところである
  ——例: 誤判定の率が 5% を超えたら警告する／応答が 2 秒以内に返る割合が 95% 以上で合格／直近 7 日の欠測が 3 回以上なら止める。
  **測る値を持たない機能は、行ごと「該当なし」でよい。**
- **測る値ごとに、次の 5 つを書く**。前の 2 つは今までも書いていたもので、**後ろの 3 つが必須として足したもの**である:

  | 書くもの | 決めること | 例 |
  | --- | --- | --- |
  | 測る値 | 名前と単位 | 誤判定の率（%） |
  | 閾値と合格の基準 | 比べる値と、どちら側が合格か | 5% 以下で合格 |
  | **数える単位** | **何を 1 回と数えるか**——分母と分子のそれぞれ。1 回の測定で合否を出す値なら、何を 1 回の測定とするか（時間なら始点と終点）。期間の窓の取り方（直近 7 日の移動か暦の週か）・採る間隔・集計の仕方も、合否が変わるならここに書く | 1 件の判定を 1 回と数える。同じ対象のやり直しの判定は最後の 1 件だけ数える。直近 7 日は判定の時刻から遡る移動の窓で取る |
  | **除く範囲の境目** | 除く範囲と閾値の端が**開区間か閉区間か**（「以上」か「を超える」か）と、**除く条件と数える条件のどちらを先に判定するか** | ちょうど 5% は合格。保守の時間帯の判定を先に除いてから、残りで率を出す |
  | **標本が基準の期間（か必要な件数）に満たないときの合否** | 基準の期間（直近 7 日など）や必要な件数に標本が満たないとき（導入の直後・欠測。**率なら分母が 0 件のときを含む**）に、合格・不合格・判定を出さない（何を見せるか）のどれか | 7 日に満たない間は判定を出さず、「判定に足りない」と表示する |

  **当てはまらない項目は、項目ごとに「該当なし」と理由を書く**——除く範囲が無い値の境目は「該当なし（除く範囲が無い）」と書いて閾値の端の開閉だけを書く、
  1 回の測定でそのまま合否を出す値の標本の項目は「該当なし（1 回の測定で合否を出す）」。**数える単位は該当なしにしない**（1 回の測定でも、何を測るかは決める）。
  **率は分母が 0 件になりうるので、標本の項目を該当なしにしない。**
- **落とす条件**: 後ろの 3 つのどれかが仕様から 1 つに決まらなければ、条件 2 の書き漏れである。
  **重さは「指摘の重さ」の見分け方のとおり**——決まらないと同じ記録から合否が割れうるので `結果が割れる`（条件 2 に効く。利用者が選ぶべき選択なら `判断が要る`）。
  他の記述から 1 つに決まると読める（`ファイル:行` を示せる）なら `補い`——たとえば閾値の「5% 以下で合格」は閾値の端の開閉を決めている。
- **3 つは性質であって、手段ではない**——同じ記録に 2 通りの数え方を当てると合否が変わり、外から確かめるテストで区別できる（`spec-scope.md` の「縦の線」の見分け方）。
  **同じ見分け方で、期間の窓の取り方・採る間隔・集計の仕方も、同じ事象の列から合否が変わるなら性質として、数える単位の項目に書く。**
  **書かないのは、合否を変えない手段**——測る道具・記録の置き場所と形など。決まらないときの振り分けは `spec-scope.md` の「決める順」を上から当てる。
- **この行はスクリプトでは見ない**——仕様は Markdown で、測る値の書き方の形（表・列）は決めていない。列が埋まっていることは、
  境目や合否が 1 つに決まることを示さない。判定は条件 2 の判定役（Red Team）である。
- **移行（#854 で足した行）**: この行を足す前に条件 2 を満たした仕様は、次に `spec-review` を回したとき、
  その回のレビューの対象の機能（v2 以降の差分モードなら作業中の版の機能）についてこの行を埋める。
  埋まっていなければ、条件 2 の書き漏れとして判定する（重さは上の「落とす条件」のとおり）。
  **前の版で抜けた仕様を、この行のためだけに版を立てて見直す必要はない。**

### 文書どうしの定義

**同じ入力・同じ値を 2 つの文書が定義していると、片方だけ直したときに定義が割れ、作り手がどちらを読んだかで結果が変わる**——#402 の実案件では、
実装の途中で立った要確認の Issue のうち 2 件の背景に、仕様の文書どうしの食い違いがあった（概要の文書と規則の文書で同じ入力の定義が割れていた・
仕様と設計メモで範囲が割れていた）。どちらの文書も、それだけを読めば書き漏れは無かった。

- **見るのは、機能の入力・値（型・単位・取りうる範囲・既定の値・意味）を定義している仕様の箇所**——`spec/` の中の Markdown の文書どうしと、
  **同じファイルの中の節どうし**（概要の節と規則の節・本文と設計メモ）で、範囲の文書（`spec/scope.md`）を含む。**設計メモは、見出しに「設計メモ（参考・拘束しない）」と書いた節か、そう書いたファイルである**（`spec-scope.md` の「縦の線」）——節に置いてもファイルに分けても扱いは同じ。
  **内部の Q&A 表（`spec/qa-dev.csv`）の回答も、定義している箇所に入れる**——spec-review 自身が書き、決めた値を仕様に反映する表なので、回答と本文が割れていれば同じ食い違いである。
  **`spec/` の中でも、仕様から書き起こした写しは見ない**——中間表現（`spec_ir.json`。scaffold が抜けた仕様から書き起こす）と形式検査のモデル（`formal/`。Formal Checker が形式化する）。
  spec-review はこれらを直さないので、突き合わせると直せない食い違いで条件 2 が止まる。
  **定義している箇所が 1 つだけなら、行ごと「該当なし」でよい。**
- **2 つ以上の文書が定義しているなら、どれも同じ定義であること**。書き方は、**定義を 1 つの箇所に置き、ほかの箇所はそこを指す**（「入力の範囲は `rules.md` の『入力』を正とする」）。
  同じ定義を写して持つと、次に片方だけ直したときに割れる。
- **設計メモは拘束しないが、性質と食い違えば指摘する**（`spec-scope.md` の「縦の線」のまま）——#402 の「仕様と設計メモで範囲が割れていた」はこれに当たる。
  **設計メモとの食い違いは、条件 2 を止めない**——拘束するのは性質の側なので結果は 1 つに決まっている（`spec-scope.md` の「判定役は設計メモを『満たさない』の根拠にしない」）。重さは `補い` で、設計メモを性質に合わせて直す。
- **ほかの食い違いは、今までの担当のまま**——要求（`requirements/`・共有の決定表）と仕様の食い違いは Red Team の「矛盾」、
  既存システム・社内規約との食い違いは Domain Checker が見る。
- **v2 以降の差分モードでは、作業中の版の差分が定義する入力・値を、重ね合わせた全体の中の同じものの定義と突き合わせる**——
  全体は矛盾を見るための参照で、差分の外どうしの食い違いは見ない（`spec-review` の `SKILL.md` の手順 3 の「参照」）。
  版をまたいで同じパスに置いた文書は置き換わる（`versions.md`）ので、別のパスの文書が前の版の定義を持ち続けていないかを見る。
- **落とす条件**: 拘束する 2 つの箇所（設計メモの外）が同じ入力・値に違う定義を書いていれば、条件 2 の書き漏れ（矛盾）である。**重さは「指摘の重さ」の見分け方のとおり**——
  同じ入力に 2 つの結果が出うるので `結果が割れる`（どちらを取るかで利用者に見える結果が変わり、利用者が選ぶべきなら `判断が要る`）。
  定義は同じで重複しているだけなら `補い`（仕様を減らせる指摘——1 つに寄せて、ほかは指す）。
- **この行はスクリプトでは見ない**——仕様は Markdown で、定義の書き方の形は決めていない。同じ語が 2 つの文書に現れることは、同じものの定義であることを示さない。
  判定は条件 2 の判定役（Red Team）である。
- **移行（#873 で足した行）**: この行を足す前に条件 2 を満たした仕様は、次に `spec-review` を回したとき、
  その回のレビューの対象の機能（v2 以降の差分モードなら作業中の版の機能）についてこの行を埋める。
  埋まっていなければ、条件 2 の書き漏れとして判定する（重さは上の「落とす条件」のとおり）。
  **前の版で抜けた仕様を、この行のためだけに版を立てて見直す必要はない。**

### 境界の細部

**仕様が境界値を書いていても、境界ちょうどの値の倒し方や数の表し方の細部が決まっていなければ、Red テストを通る作りが 2 通り残る**——
Red テスト（`scaffold.py` が仕様のテストケースから作る）は、テストケースの入力が境界ちょうどに無ければ「以上」と「を超える」を区別しない。
#402 の実案件では、関数の側（Red テストつきの 13 機能）の関門の実装の指摘 13 件が、境界値ちょうど・浮動小数の誤差・符号付きゼロなど、この形だった
（いずれも dev-loop の関門で拾えた——仕様に性質として書いてあれば、関門は推測ではなく仕様に照らして判定できる）。

- **「境界値」の行との違い**: 「境界値」の行は**どこに境界があるか**（上限・下限・空・ゼロ・端数）を書く。この行は、**その境界と計算で結果がどちらに倒れるか**を書く。
  **「測る値」の閾値の端の開閉は「測る値」の行（除く範囲の境目）で書く**——この行には写さない。**測る値の計算の小数の比べ方・丸め・符号付きゼロは、この行で書く**
  （「誤判定の率 7% 以下で合格」でも、100 件中 7 件を二進の浮動小数で `7/100*100` と計算すると `7.000000000000001` になり、比べ方を決めなければ合否が割れる）。
  この行が受けるのは、入力の検証・決定表の条件・計算の結果の境界と、測る値の計算の小数の比べ方・丸め・符号付きゼロ（閾値の端の開閉は除く）である。
- **境界と計算ごとに、次の 4 つを書く**:

  | 書くもの | 決めること | 例 |
  | --- | --- | --- |
  | **境界ちょうどの値** | 境界の値そのものがどちら側に入るか（「以上」か「を超える」か・「以下」か「未満」か） | 数量 100 ちょうどは受け付ける。101 から断る |
  | **小数の比べ方** | 小数を等しい・大小で比べるとき、どの桁まで等しいとみなすか（比べる前に丸めるならその桁） | 金額は円単位に丸めてから比べる。率は小数 2 桁（%）に丸めてから閾値と比べる（`7/100*100` は `7.00` として 7% 以下に入る） |
  | **丸めの規則** | どの桁で・どの規則で（四捨五入・切り捨て・切り上げ・偶数丸め）・計算のどの段で（明細ごとか合計か）丸めるか | 消費税は明細ごとに円未満を切り捨てる |
  | **符号付きゼロ** | 計算の結果が負の側から 0 になったとき（負の小さい値を丸めた結果など）に、`0` と同じに扱い・表示するか | -0.004 を小数 2 桁に丸めた結果は `0.00` と表示する（`-0.00` と表示しない）。正と負で分ける判定（請求か返金か）では、負に入れない（0 と同じに扱う） |

  **当てはまらない項目は、項目ごとに「該当なし」と理由を書く**——整数だけを扱う計算なら小数・丸め・符号付きゼロは「該当なし（整数だけを扱う）」、
  負の値を経ない計算（掛ける・引く・丸める相手に負の値が無い）なら符号付きゼロは「該当なし（負の値を経ない）」——**「結果は 0 以上」は理由にならない**（`0.0 * -5` は `-0.0` で、`-0.0 >= 0` は真）。**境界も数の計算も持たない機能は、行ごと「該当なし」でよい。**
- **4 つは性質であって、手段ではない**——境界ちょうどの入力・負の側から 0 になる入力を外から与えるテストで、2 通りの作りを区別できる（`spec-scope.md` の「縦の線」の見分け方）。
  **数の型（十進か二進の浮動小数か）・使うライブラリは手段で、書かない**——ただし型で外から見える結果は変わりうる（二進の浮動小数では `0.1 + 0.2 == 0.3` が偽）。
  **だから、変わる結果のほう（比べる桁・丸めの規則）を性質として書く**——それを書けば、どの型でも同じ結果になるように作るのは dev-loop である。
- **範囲の線（頻度 × 影響）との関係**——ほかの場面と同じく `spec-scope.md` の「横の線」で読む（既定の線に、範囲の文書と正本の `CLAUDE.md` が変えたところを重ねる）。
    - **頻度は、その境界の値を出す入力で決める。** 境界ちょうどの入力（`spec-scope.md` の事象の表の「上限ちょうど」）と、ふつうの入力の計算が出す端数・`-0` は、
      利用者のふつうの操作で起きる——**よく起きる**ので範囲の中で、**境界と計算ごとに書く**。
    - **まれな事象のときだけ出る値の境界**（例: 時計が戻ったときにだけ出る負の経過時間）は**まれ**——既定の線のとおり、影響が大きければ範囲の中で原則 1 本、
      小さければ範囲の外（範囲の文書に 1 行）。原則の書き方は `spec-scope.md` の「原則 1 本で受ける」を正とする。
    - **影響**は、倒し方の違いで何が変わるかを、`spec-scope.md` の影響の表で読む（お金に関わる・利用者が気づけないまま誤った結果を使う、などのどれか 1 つで**大きい**。
      小さいのは、失敗が利用者に見え、**かつ**やり直せば戻るときだけ）。
      **倒し方を変えても外から確かめる結果が変わらない**（画面・通知・API やファイルの出力・業務の判定が同じになる。`spec-scope.md` の「縦の線」の見分け方）なら、その項目は「該当なし」と理由を書く。
- **落とす条件**: 4 つのどれかが仕様から 1 つに決まらなければ、条件 2 の書き漏れである。
  **重さは「指摘の重さ」の見分け方のとおり**——決まらないと同じ入力から作り手ごとに結果が割れうるので `結果が割れる`
  （端数の扱いが料金・請求のように利用者の業務の決まりで、利用者が選ぶべきなら `判断が要る`）。
  他の記述から 1 つに決まると読める（`ファイル:行` を示せる）なら `補い`——たとえば「100 以下を受け付ける」は境界ちょうどの倒し方を決めている。
- **条件 3（テストケース）は、この行のために変えない**——テストケースの決まりは今までどおり（決定表の各行・範囲の中の各シナリオ）。
- **この行はスクリプトでは見ない**——仕様は Markdown で、境界の書き方の形は決めていない。判定は条件 2 の判定役（Red Team）である。
- **移行（#873 で足した行）**: この行を足す前に条件 2 を満たした仕様は、次に `spec-review` を回したとき、
  その回のレビューの対象の機能（v2 以降の差分モードなら作業中の版の機能）についてこの行を埋める。
  埋まっていなければ、条件 2 の書き漏れとして判定する（重さは上の「落とす条件」のとおり）。
  **前の版で抜けた仕様を、この行のためだけに版を立てて見直す必要はない。**

## 形式検査の対象

| 対象 | 見つけるもの |
| --- | --- |
| 決定表・計算ルール | どのルールにも当てはまらない入力（抜け）、結果が食い違う入力（矛盾） |
| 並行・リトライ・取り消しを含む業務フロー | 通信断や同時操作で、データが食い違ったまま残る実行順 |
| 権限・ロール | 見えてはいけないデータが見えてしまう組み合わせ |

**画面・文言・使い勝手は対象外。** 順番どおりに進むだけのフローも対象にしない。

### 改修の性質で選ぶ

**検査の深さは、作業中の版の改修の大きさに釣り合わせる。** 表の対象があっても、次に当たらなければ形式検査はしない
（「対象なし」とし、理由を書く）:

| 対象 | 形式検査をするとき | しないときに受けるもの |
| --- | --- | --- |
| 決定表・計算ルール | 作業中の版で決定表・計算ルールを足した・変えた | — |
| 並行・リトライ・取り消しを含む業務フロー | 作業中の版の改修が、**改修するシステムに状態を持つ業務フローを新しく足す**か、**既存のフローの状態・遷移を変える**。**既存の書き手に排他を足すだけ**（状態と遷移は変わらない）の改修でも、**守るべき性質が比べる値が、足す排他の外にある状態から来て、その状態が書き手の動いている間に変わりうる**なら | **既存の書き手に排他を足すだけ**で、左に当たらない（**性質が比べる値が全部その排他の中の状態から来る**か、排他の外の状態が書き手の動いている間に変わらない）なら、性質が複数のステップをまたいでも、同時実行で成り立つべき性質とそのテスト（条件 2・3）で受ける |
| 権限・ロール | 作業中の版でロール・権限の組み合わせを足した・変えた | — |

**決定表・計算ルールと権限・ロールは版から見て決め、業務フローは改修するシステムから見て決める。** 決定表とロールは、
版で足した・変えたものがそのまま検査の対象になる。業務フローは、**版で初めて仕様に書いたフローでも、
システムに前からあるなら「新しく足す」に当たらない**（既存システムを改修する v1 がこれに当たる）。

**「排他を足すだけ」を分けるのは、守るべき性質が比べる値が排他の外の状態から来て、それが書き手の動いている間に変わりうるかである**——性質が複数のステップをまたぐかではない（#909）。

- **排他の外にある状態**は、足す排他を取らずに変わる状態である——版・設定など、書き手どうしの排他とは別の経路（デプロイ・設定の変更）で変わるもの。
  書き手どうしは排他で守れていても、その状態は書き手の動いている間に割り込んで変わりうる。
- **書き手の動いている間に変わりうる**は、1 つの書き手が処理の途中で読み直す値が変わることだけでなく、**値の違う書き手が同時に動きうること**も含む
  ——処理の初めに読んだ値やプロセスの起動時に決まる値（コードの定数など）でも、デプロイの前後で古い値の書き手と新しい値の書き手が重なるなら当たる。
- **「排他の外の状態から来る」は、値の出どころで決める**——書き手が排他の外（コードの定数・設定・切り替わる版）から取った値を、
  **そのまま**書く・比べるときに当たる。値がいまどこに置かれているか（書いた先の行・表）では決めない——性質が比べる値が排他の中の行に
  置かれていても、書き手がその値を排他の外から取ってそのまま書いたなら当たる。
- **性質が比べない値は数えない**——どの書き手のコードも設定もデプロイで変わるので、性質が比べない値（処理の書き方など）まで数えると、
  排他を足す改修がほぼ全部当たる。

| 例 | 性質が比べる値が排他の外の状態から来て、書き手の動いている間に変わりうるか | 扱い |
| --- | --- | --- |
| 在庫を読む・0 より多いか確かめる・1 減らして書くの 3 ステップを、全部排他で守る | 来ない（性質「在庫が負にならない」が比べる在庫は、書き手が排他の中で読んだ在庫から 1 を引いて書く値で、出どころは排他の中で読んだ在庫。減らす量の 1 はコードの定数だが、そのまま書く・比べる値ではない） | 形式検査はしない。性質とテストで受ける |
| 既存のバッチの書き手に排他と版の順序の守りを足す。性質は「下落監視と表示が同じ版の行を採る」で行の版を比べ、書き手が書く版はコードの定数でプロセスの起動時に決まる。デプロイで新しい版の書き手が動き出したとき、古い版の書き手がまだ動いていることがある（#363・#364 の実案件の R21-10。TLC が反例を見つけた） | 来る（比べる行の版は排他の中に置かれるが、書き手はその版を排他の外の定数から取って書く。デプロイで値の違う書き手が重なる） | 形式検査の対象に残す |

**線を「性質が複数のステップをまたぐか」にしない**——排他を足すのは、処理が複数のステップでできていて間に割り込まれると壊れるからなので、
排他を足す改修はほぼ全部またぐ。またぐかで分けると「排他を足すだけ」に残る改修が無くなり、TLC を回す回数が #373 で絞る前に戻る。
**対象に残すときも、構成は下の段落のとおり性質が破れうる最小から始める**——対象を広げても、1 回の検査の構成は広げない。

**どれを対象にするかは `spec-review`（Planner）が決めて、理由と一緒に Formal Checker に渡す。** フローがシステムに前からあるか・
性質が比べる値が排他の外の状態から来るかは、要求と既存システム（Domain Checker の照合先）を読まないと決まらず、Formal Checker はそれを持たないからである。
**照合先も Formal Checker に渡す。** Formal Checker は、渡された選び方が上の表に反すると判断したら、指摘として挙げる（黙って広げも狭めもしない）。

**形式検査をするときも、構成（書き手・利用者・ジョブの数など）は性質が破れうる最小（ふつう 2〜3）から始める。**
その構成で正常な状態に到達でき、陽性対照で反例が出るなら、**構成を広げない**——広げても新しい反例が出るとは限らず、
状態の数だけが増えて検査が判定できなくなる（#364 で書き手 10 人の構成が一度判定できなかった）。
広げるのは、最小の構成では性質を言えない理由（例: 3 人目が来て初めて起きる順序）を書けるときだけ。

**形式化するのは範囲の中の業務フローで、性質（不変条件）の水準である**——特定のロックの方式や書き込みの順序を
前提にしない（それは手段。`spec-scope.md`）。反例ごとに、**重なっている独立した事象**（よく起きる／まれの別）と**影響**を書く。
範囲の外かは、頻度と影響を合わせて `spec-scope.md` の既定の線で決める——**まれでも影響が大きい反例は範囲の中**である。

**「反例なし」は空振りを疑う。** 次の 2 つを確かめて、はじめて「反例なし」と言える:

- **正常な状態に到達できる**（モデルが何も許さない形になっていない）
- **わざと壊した版で反例が出る**（陽性対照）

**形式化で置いた前提**（端数処理・割引の適用順など）は形式化した側の解釈なので、
利用者の判断が要るなら Q&A 表で確かめる。

### TLC は既定で必須の前提（#912）

業務フローの検査器の TLC は、spec-loop を使う正本で**既定で必須**である——どの版で業務フローが対象になるかは周を回すまで決まらない。
**正本の `CLAUDE.md` に `TLC の呼び方: <コマンド>` の行を書き、spec-review の確かめ・autopilot の点検・Formal Checker はこの呼び方だけを使う**（`command -v` では探さない）。
業務フローを一度も形式検査しない正本は `業務フローの形式検査: しない` で外せる。**行の書き方・確かめ方・終了コードは `scripts/check-tlc.py` の docstring を正とする**
（用意のしかたは `README.md` の「前提」）。Alloy（権限・ロール）は必須にしていない——下の「Alloy は呼び方の行だけで使う」。

#### 0.73.0 より前から使っている正本の移行（1 度だけ）

0.73.0 から、TLC を `command -v` で探さなくなり、autopilot が TLC の前提を確かめて止まるようになった（壊れる変更）。正本ごとに次のどれか 1 つを行う:

1. **`PATH` の `tlc`（包みのスクリプトなど）で TLC を使っていた正本**——正本の `CLAUDE.md` に `TLC の呼び方: tlc`（か、その絶対パス）を書く。
   呼び方は `sh` に渡すので、`PATH` の `tlc` がそのまま通る。書かないと spec-review は業務フローを選んだ回に TLC が無いとして、判定役を起動せずに訊く（autopilot は Formal Checker を起こす段の始めで止まる）。
2. **jar を `java -cp` で使っていて、呼び方を `CLAUDE.md` に自由な書き方で書いていた正本**——`TLC の呼び方: java -cp <jar の場所> tlc2.TLC` の 1 行に書き直す。
3. **TLC を入れておらず、業務フローを形式検査しない正本で autopilot を回す**——`業務フローの形式検査: しない` を書く。書かないと autopilot が Formal Checker を起こす段（`round1`・`round2`・`narrow`）の始めで止まる。

書いたら `python3 <spec-loop の根>/scripts/check-tlc.py <正本の根>`（3 なら `--autopilot` を付ける）が 0 になることを確かめる。

### Alloy は呼び方の行だけで使う（#922）

権限・ロールの検査器の Alloy は必須の前提ではない——権限・ロールを形式検査の対象に選んだ回に、spec-review が確かめる。

## 指摘の重さ

**判定役は、範囲の中の指摘ごとに重さを付ける。** 判定役は毎回何かを見つけるので、**見つけたものが 1 件でもあれば満たさない、では収束しない**
（#363 では、条件 2 の根拠が 1 件まで細っても、直すと別の箇所に次の指摘が出る回が 6 回続いた）。条件 2・3 に効くのは上の 2 つだけである:

| 重さ | 当てはまるもの | 条件 2・3 |
| --- | --- | --- |
| `判断が要る` | 選択肢によって利用者に見える結果が変わり、利用者が決める（振り分けの案は「共有の Q&A 表に起票する」） | **効く** |
| `結果が割れる` | **同じ入力に対して、仕様から結果が 1 つに決まらない**——2 つの結果を書いている（矛盾）か、書いていないので作り手によって結果が変わる（チェックリストの項目・テストケースの欠け） | **効く** |
| `補い` | **結果は仕様から 1 つに決まる**——言い回し・重複・説明の追加、既に書いた性質を別の入力で確かめるテストの追加、「該当なし」の書き忘れで他の記述から該当しないと読めるもの | 効かない |

- **見分け方**: **その指摘を直さずに 2 人が別々に作ったとき、外から確かめるテストで区別できる違いが出うるか。** 出うるなら `結果が割れる`（か `判断が要る`）、出ないなら `補い`。
- **付けるのは判定役、確かめるのは呼び出し元**（振り分けと同じ）。**迷ったら重いほうに付ける**——`補い` と効く重さで迷ったら効く重さ、
  **`判断が要る` と `結果が割れる` で迷ったら `結果が割れる`**（`判断が要る` だけで止まった回は上限に数えないので、そちらへ寄せると上限が効かなくなる。
  利用者に訊くべきだと思えば、重さは `結果が割れる` のまま起票してよい）。
  呼び出し元が重さを軽くしてよいのは、根拠を開いて**仕様から結果が 1 つに決まる箇所（`ファイル:行`）を示せたときだけ**——示せなければ判定役の重さのまま。
- **条件 2・3 の判定は、確かめたあとの振り分けの表から呼び出し元が決める。** 数える行は、**最後のレビュー（2 回目を回したなら 2 回目）で
  Red Team が挙げた範囲の中の行**と、判定役が範囲の外・実装に渡すとした案を**呼び出し元が範囲の中へ振り直した行**——
  1 回目の行（2 回目が判定し直している）、Domain Checker の行（条件を判定しない。`判断が要る` は起票して条件 1 が止める）、
  Formal Checker の行（条件 4）、狭いパスの行（上の 3 つで扱う）は数えない。そのうち重さが `判断が要る`・`結果が割れる` の行が
  1 件でもあれば `満たさない`、0 件なら `満たす`。**判定役の書いた判定と表が食い違ったら、表を取る**
  （`補い` だけで `満たさない` と書いていても、自分の表に `結果が割れる` の行がありながら `満たす` と書いていても）。
  **判定し直させない**——呼び直せば 3 回目のレビューになる。判定役が `判定できなかった` と書いたら（読めないファイル・動かない道具）、それはそのまま使う。
- **範囲の外・実装に渡す の行は、重さを問わず条件に効かない**（今までどおり。`spec-scope.md` の「振り分けの区分」）。
  #329 で「軽微」と呼んだのはこれらの行で、**重さは範囲の中の行に付ける 2 つめの軸**である——振り分けの区分を置き換えない。
  `判断が要る` は区分の「共有の Q&A 表に起票する」に当たり、`結果が割れる` と `補い` は多くが「仕様を直す」に当たる
  （`補い` は直さなくてよい。下の「2 回目のあとの直し — 狭いパス」）。
- **条件 4 は重さで変えない**——範囲の中の反例は、定義上 `結果が割れる`（同じ実行順で、データが食い違ったまま残る）である。
- **条件 5 は重さを問わない**——`補い` の行も、振り分けの表に 1 件 1 行で載せ、振り分ける。

## 2 回目のあとの直し — 狭いパス

`spec-review` は 1 回の実行でレビューを 2 回までしか回さない。**2 回目のレビューのあとで仕様か範囲の文書を直したら、
その直しの差分だけを判定役に 1 回確かめさせる**——これを**狭いパス**と呼ぶ（dev-loop の「2 パス目で直した分は、その差分だけに Verifier を 1 回当てる」と同じ形）。

- **2 回目のあとで直してよいのは、2 回目の指摘への直しだけ**——元の指摘の無い直し（気づいた箇所を直す・言い回しを揃える）は、
  その回はしない（次の回で直す）。当てる役が決まらず、下の 3 つが空のまま成り立ってしまう。
- **当てる役**: 直しの元の指摘を挙げた役に加えて、**直しが触れたものを判定する役すべて**——仕様チェックリストの項目・テストケースに
  触れたら Red Team、形式検査の対象にしたもの（下の「形式検査の対象」。決定表・計算ルール・状態と遷移・権限）に触れたら Formal Checker、
  既存システム・規約に照らす記述に触れたら Domain Checker。**どれに触れるか迷ったら、3 体すべて**。役ごとに 1 体。
  元の指摘を挙げた役だけに当てると、ほかの役の 2 回目の判定（たとえば条件 4 の `満たす`）が、**直す前の仕様への判定のまま**使われる。
- **渡すもの**: 直しの差分（直す前と後）と、その元になった 2 回目の指摘の行。抜ける条件・範囲の線・信頼できない入力の扱いは**まるごと渡す**（絞るのは差分だけ）。
- **返させるもの**: 元の指摘ごとに `解消した`／`解消していない`／`判定できなかった`（元の指摘を挙げていない役は、この欄を返さない）、
  **差分の中の新しい指摘**（重さつき。直しが自分の条件を破っていないかを含む）。
  Formal Checker なら、直した仕様でモデルを走らせ直した結果（陽性対照を含む）。
- **狭いパスの指摘は、その回は直さない・当て直さない**（ここで止める。直せば、またレビューを通っていない直しが残る）。
  ただし **`判断が要る` の指摘は共有の Q&A 表に起票する**——起票は仕様の直しではなく、起票しなければ利用者の判断が残ったまま条件 1 も止まらない。
  ほかの指摘は報告に載せ、次の回で扱う。
- **2 回目の `補い` は、その回は直さない**——直せば狭いパスが要り、直しが次の指摘を呼ぶ。報告に載せ、次の回で直してよい。

**2 回目のあとで仕様か範囲の文書を 1 か所でも直したなら、2 回目の判定が何であっても、次をすべて満たすときだけ抜けられる**
（2 回目に条件を満たしていて、条件を判定しない Domain Checker の指摘を直した場合や、範囲の文書に 1 行足しただけの場合も同じ）:

1. 狭いパスが、当てた**すべての役から返った**（再実行しても返らなければ満たさない）
2. 直した元の指摘**すべて**について `解消した` が返った
3. 狭いパスの新しい指摘に、**効く重さ（`判断が要る`・`結果が割れる`）のものが 0 件**

**どれかを満たさなければ、抜けていない**——記録の表の `条件2〜4` には、狭いパスが返らなかったか `判定できなかった` を返したなら
`判定できなかった`、新しい指摘が `判断が要る` だけなら `回答待ち`、それ以外なら `満たさない` と書く（下の「記録の表」）。

**2 回目の `満たさない` を解消済みに置き換えてよいのも、上の 3 つを満たし、かつ 2 回目に条件を `満たさない` にした効く重さの指摘が
すべて直しの対象になっていたときだけ**である（`判断が要る` は起票した時点で条件 1 を止めるので、ここで解消済みにはならない）。

## 実行の上限と記録

**判定役に収束を委ねない。** 「どこで止めるか」を判定役が決める形では、利用者が消耗して打ち切るまで回り続ける
（#363 の 13・14 回目は、利用者が「範囲を絞って」と打ち切った）。だから**回数の上限で、利用者に判断を返す**。

### 記録の表

**正本リポジトリの `spec-review/v<n>.csv`**（`<n>` は作業中の版の番号）に、**出来事ごとに 1 行**足す（置き場所は `tree.md`）。
**会話からは数えない**——`spec-review` は再開点を表とファイルから読むので、上限も表から決まらなければ効かない（`spec-scope.md` の歯止めと同じ理由）。

**`docs/` の外に置く。** `docs/v<n>/` の中に置くと、版の重ね合わせで前の版の記録に上書きされ、版の差分（`diff-versions.py`）が
記録の変更を仕様の変更として出し、判定役の差分と提案書の「前の版からの変更」に載る。`spec/` の中に置くと、条件 1 のスクリプトが
記録を仕様のファイルとして数え、**仕様を 1 行も書いていないのに条件 1 を満たす**（記録だけで「仕様 1 ファイル」になる）。

| 列 | 書くもの |
| --- | --- |
| `回` | 表の中の行の通し番号（1 から。どの行にも振る） |
| `日付` | `YYYY-MM-DD` |
| `結果` | `抜けた`／`抜けていない`（実行の行）／`上限`（上限に達して判定役を起動しなかった行）／`利用者の判断`（下） |
| `条件2〜4` | 実行の行だけ: 条件 2〜4 と狭いパスがすべて通れば `満たす`。**通らなかった理由が、効く重さの指摘が `判断が要る` だけ**（起票して回答待ち）なら `回答待ち`。それ以外（`結果が割れる` の指摘・範囲の中の反例・狭いパスの `解消していない`）なら `満たさない`。判定役の報告が欠けたか判定できなかったなら（狭いパスが返らなかったか `判定できなかった` を返した場合を含む）`判定できなかった`。ほかの行は `-` |
| `要求の行` | 実行の行だけ: 利用者向けの要求（`requirements/` の Markdown すべて）の行数。重ね合わせた全体で数える。ほかの行は `-` |
| `決定表の行` | 実行の行だけ: 共有の決定表のデータの行数（見出しを除く）。同上 |
| `テストケース` | 実行の行だけ: 仕様の中のテストケースの数（下の「仕様の規模」の数え方）。同上 |
| `仕様の行` | 実行の行だけ: 仕様（`spec/` の Markdown。範囲の文書を含む）の行数。**参考に出すだけで、引き金には使わない**（下）。同上 |
| `判断` | `利用者の判断` の行だけ: 選んだもの（下の 3 つの名前）。ほかの行は `-` |
| `機能` | 実行の行で `条件2〜4` が `満たさない` のとき: 効く重さの指摘があった機能の名前（仕様チェックリストを埋めた見出しをそのまま写す。2 つ以上なら `;` で区切る）。ほかは `-` |

**条件 1 か条件 5 だけで抜けられなかった実行の行は、`条件2〜4` が `満たす` になる**——どちらも判定役の空回りではない
（条件 1 は利用者の回答待ち、条件 5 は呼び出し元の振り分けの残り）。

### 上限

**数え始め**は、`判断` が `続ける` か `範囲を決め直す` の最後の行の後（無ければ表の最初）。**そこから後の実行の行で、
`条件2〜4` が `満たさない` か `判定できなかった` の行が 3 つあれば、次の回は判定役を起動しない。**
**最後の `利用者の判断` の行が `止める` なら、数えずにそのまま利用者に訊く**——`止める` は数え直しの理由にならない
（呼び直しただけで判定役が動き出さないように）。

訊くときは次の 3 つから選んでもらい、`結果` が `上限` の行と、選ばれた `利用者の判断` の行を足す:

| 判断 | すること |
| --- | --- |
| `続ける` | 数え直して、もう一度回す |
| `範囲を決め直す` | 数えた行の `機能` の列に出てくる機能について、`spec-scope.md` の「回を重ねたときの歯止め」の形の質問を共有の Q&A 表に起票して止まる（回答が来るまで条件 1 が止める） |
| `止める` | 止まる。仕様は確定していない（抜けていない）。次に呼ばれたときも、まず訊く |

- **数えた行の `機能` がすべて `-` なら**（数えた行がどれも `判定できなかった`）、`範囲を決め直す` は選択肢に出さない——起票する機能が無い。
  代わりに、判定できなかった理由（返らなかった判定役・動かなかった検査器）を示して `続ける`／`止める` を訊く。
- **上限の問いの外で、利用者が打ち切りを指示したときも行を足す**——実行の途中で「範囲を絞って」「止めて」と言われたら、
  `利用者の判断` の行（範囲を絞るなら `範囲を決め直す`、止めるなら `止める`）を足してから、そのとおりにする。
  書かなければ、次の回は打ち切る前の行を数え続ける（範囲を決め直したのに上限が来る・止めたのに判定役が動く）。

- **数えない行**: `回答待ち`・`満たす`（条件 1・条件 5 だけで抜けられなかった回を含む）。利用者の回答待ちや呼び出し元の振り分けの残りは、判定役の空回りではない。
- **N=3 の根拠**: #363 の実案件の記録（`review-log.md` の各回の最後のパスの「判定:」の行）に、**判定の行をそのまま**当てると、
  3〜5 回目が続けて満たさず、**6 回目の前に**利用者に返ることになる（実際には 8 回目のあとで利用者が「性質とテストに絞る」と指示して止めた）。
  ただし**これは旧い規則の判定**で、3〜5 回目の根拠を重さで分け直してはいない。#373 の線（「既存の書き手に排他を足すだけ」は全部外す）で当て直すと、
  10 回目は形式検査の対象が無くなりうるので、9 回目のあとは 11・12 回目の 2 つしか数えず、13 回目の前には返らない。
  **今の線（上の「改修の性質で選ぶ」。#909）では、10 回目の並行の検査も対象に残りうる**——11 回目に反例（R21-10）が出た性質 (c) は 10 回目の時点の仕様にもあり、同じ書き手を見ている。
  **残ったときに 10 回目を数えるかは、この記録からは決まらない**——10 回目は TLC が無いまま判定役を走らせて `判定できなかった` になったが、
  今の `spec-review` は検査器が足りなければ判定役を起動せずに訊き、`用意してから呼び直す` なら記録に行を足さない（数えない）。
  **N=3 は、1 案件の旧い判定に当てた 1 点からの選びである**——プロジェクトの `CLAUDE.md` で N を変えてよい。
- **歯止め（`spec-scope.md`）とは別の数である。** 歯止めは機能ごとに Q&A の行を数え、上限は版ごとに実行を数える。両方を当てる。
- **版が変われば数え直す**——表は版ごとのファイルに分ける。

## 仕様の規模

**仕様が要求に比べて膨らむのを、記録の表のテストケースの数で見る。** #364 の実案件では、要求（`requirements/` の Markdown 2 ファイル）190 行
（主のファイルは 89 行）・決定表 15 行に対して、仕様の主のファイルが 768 行・テストケースが 300 件になった（Issue によれば最初の版は 414 行・129 件）。

- **テストケースの数え方**: 仕様の中の「入力と期待結果」の組を 1 件と数える。**仕様がテストケースに番号を振っていれば番号の数**
  （例: 表の行の先頭の `F1-5b`）、振っていなければテストケースの表のデータの行の数。**同じ版の中では同じ数え方を続ける。**
- **引き金にはテストケースだけを使う。** 仕様の行は、記録・設計メモのような別のファイルや節を `spec/` に置く運用で毎回増え、
  手段を設計メモへ移しても減らないので、引き金にすると見直しが空振りする。
- **毎回、記録の表の規模の列を報告に出す**（直前の実行の行との差も）。
- **直近 2 つの実行の行を比べ、テストケースの増え方（割合）が、要求の行と決定表の行を合わせた増え方（割合）より大きければ、
  次の回の判定役を起動する前に「減らす見直し」をする**——要求が変わっていないのにテストケースが増えた回は、必ずこれに当たる。
  前の回の中で判定役の指摘に応えて増えた分は、その 2 つの行の間に出る。**その版に実行の行が 1 つしか無いか、前の行のテストケースか要求と決定表の行の合計が 0 なら、比べない**（割合が決まらない。報告には数を出す）。
  見直しでは、仕様の中の**重複**・**実現の手段**（`spec-scope.md` の「縦の線」。設計メモへ移すか消す）・**要求に無い決まり**
  （利用者に見える結果を決めているなら起票し、そうでなければ消す）を削る。
  要求より速くテストケースが増えるのは、判定役の指摘に応えて細かくなった分である。**割合で比べるのは**、回答の反映で要求が数行だけ変わった回に、
  見直しが黙って外れないようにするため（#364 の 10〜14 回目には、回答の反映で要求を書き足した回がある）。
- **絶対の閾値（テストケースは要求の何倍まで、など）は既定では置かない**——手元の実データは 1 案件だけで、線を引く根拠が無い。
  **プロジェクトが目安の比を `CLAUDE.md` に書いたら、それを超えた回も見直しをする。**
- **判定役は、仕様を減らせる指摘（重複・手段の記述・要求に無い決まり）を、足す指摘より先に挙げる。**
