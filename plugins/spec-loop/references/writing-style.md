# 文書の文章の記法

spec-loop のスキルが正本リポジトリに書く文書の文章は、この記法で書く（#913）。
置き場所・列・中身は、ほかの決まり（`tree.md`・`spec-exit.md`・`spec-scope.md` など）を正とする。
**ここが決めるのは文章の書き方だけである。**

## 掛かる範囲

**スキルが `docs/v<n>/` に書く Markdown の文章に掛かる**

- 掛かるのは `requirements/`・`spec/`（範囲の文書 `scope.md`・設計メモ・形式検査のモデルの記録 `formal/<対象>/README.md` を含む）・`feasibility/`・`proposal/` の Markdown である。
- 書くスキルは req-loop・spec-review（Planner）・feasibility・proposal（手書き部分の下書き）である。
- 正本を人が書くときも、同じ記法に揃える。

**CSV・生成物・報告には掛からない**

- Q&A 表・決定表・見積り・スケジュール・`spec-review/v<n>.csv` のセルには掛からない。
- スクリプトが作るもの（提案書と仕様書の生成部分・スライド・`scaffold/`・Issue の本文）には掛からない。
- 生成物の形は、それぞれのスクリプトを正とする。
- 正本の `CLAUDE.md` と、スキルが利用者に返す報告には掛からない。

## 決まり

**要点を太字の見出し 1 行にし、残りを一文ずつの箇条書きにする**

- 見出しの行は、その段落の要点を言い切る 1 文にする。
- 「人日の幅」のような名詞だけの見出しにしない。
- 見出しの行には句点を付けない。
- 見出しの行の後には空行を 1 つ置く（置かないと MkDocs が箇条書きとして描かない）。
- 箇条は、結論の補足・条件・例外の順に並べる。

**1 つの箇条には 1 つの文だけを書く**

- 句点は箇条の末尾に 1 つだけ置く。
- 並べるだけの語は「・」でつないで 1 文にしてよい（例: 「cvm 側との調整・現場での受け入れは縮みにくい。」）。
- 1 文の長さの目安は 60 字程度とする（標準の値ではなく、spec-loop が置く目安である）。

1 文だけの短い段落は、無理に見出しを作らずに 1 文の段落のまま書く。

**太字は見出しの行にだけ使う**

- 箇条の中の語を太字で強調しない。
- 太字が増えると、どれが要点か分からなくなる。
- 箇条の中の太字は、CommonMark の flanking の規則で崩れやすい。

**Markdown の見出し（`##`）を増やさず、太字の行にする**

- 太字の行は目次とアンカーを作らないので、書き換えでリンクが壊れない。
- 既にある Markdown の見出しは変えない（下の「変えないもの」）。
- ただし、ほかの決まりやスクリプトが見出しで探す節は、新しく書くときも `##` の見出しにする（下の項）。

**ほかの決まりやスクリプトが見出しで探す節は、太字の行にせず `##` の見出しで書く**

- 範囲の文書（`spec/scope.md`）の「原則」と「範囲の外」の節は、`## 原則`・`## 範囲の外` の見出しにする（`spec-scope.md` の「範囲の文書」）。
- 仕様の設計メモを節に置くなら、見出しに「設計メモ（参考・拘束しない）」と書いた `##` の見出しにする（`spec-scope.md` の「縦の線」）。
- 提案書と仕様書の手書き部分（`proposal/*.md`・`proposal/spec/*.md`）の節は、`##` の見出しにする（`tree.md` の「置き方の決まり」）。
- `build-proposal.py` と `scaffold.py` は「範囲の外」の節を Markdown の見出しで探すので、太字の行にすると範囲の外の行を 1 つも載せない。
- PPTX（`qa-to-pptx.py`）は `#`・`##` の見出しごとに 1 枚を作るので、手書き部分の節を太字の行にすると、その節が前のスライドに寄る。
- 節の中の段落の要点は、今までどおり太字の行にする。

**番号つきの項は、番号を残して 1 行目を太字の見出しにする**

- `1.`・`4a.` の番号はそのまま残す。
- 1 行目を太字の見出しにし、空行を 1 つ置いて、残りを箇条書きにする。
- `1.` の形（Markdown の番号つきリスト）なら、箇条を 4 スペース字下げする。
- `4a.` の形（Markdown が番号つきリストと読まない番号）なら、箇条を字下げしない。
- `4a.` の後で字下げすると、MkDocs はその箇条をコードの囲みとして描く（Python-Markdown 3.10.2 で確かめた）。

**仕様の性質の見出しは「〜のとき、〜は〜する」の形で書く**

- 見出しには、守る性質を 1 文で書く（EARS の型）。
- 条件は 1 つずつ箇条にする。
- 例外は「ただし」で始まる箇条に分ける。

**根拠の番号は、その文の末尾に括弧で置く**

- 根拠の番号だけの括弧（`（Q-R-004）`）は、その文に残す。
- 独立した文の括弧書きは、括弧を外して別の箇条に出す。
- 根拠の番号を見出しに置くのは、見出しの要点そのものの根拠であるときだけとする。

**入れ子は 2 段までにし、字下げは 4 スペースにする**

- 4 スペースなのは、MkDocs の Python-Markdown が 4 スペースで入れ子を読むからである。
- 3 段目が要るときは、その箇条を別の見出しと箇条に分ける。

**要求と仕様で記法を変えない**

- 利用者向けの要求（`requirements/`）と開発者向けの仕様（`spec/`）を、同じ記法で書く。
- 利用者が仕様を読む場面（レビュー会・提案書）でも、同じ読み方で読める。

## 変えないもの

**表・見出し・印・コードは、記法のために変えない**

- 表（`|` で始まる行）は、行も列も変えない。
- Markdown の見出し（`#` で始まる行）とそのアンカーは変えない。
- 印（`<!-- spec-loop: qa -->` などの HTML のコメント）は変えない。
- コード（囲みのコードとインラインのコード）は変えない。
- 未決定の印（`spec-exit.md` の「未決定の印」）は変えない。

## 例

前（1 つの箇条に 4 文を詰めている）:

```markdown
- 人日の幅は、Claude Code を使って作ることを前提にした目安（D-F-002 の回答 C）。仕様・テストケース・Issue が先に揃うので、実装・詳細設計・単体テストは縮む。実機での iPad の送信の確かめ・実データでの移行のリハーサル・cvm 側との調整・現場での受け入れ・人のレビュー・基盤の立ち上げは縮みにくい。
```

後:

```markdown
**人日の幅は、Claude Code を使って作ることを前提にした目安（D-F-002 の回答 C）**

- 仕様・テストケース・Issue が先に揃うので、実装・詳細設計・単体テストは縮む。
- 実機での iPad の送信の確かめは縮みにくい。
- 実データでの移行のリハーサルは縮みにくい。
- cvm 側との調整・現場での受け入れ・人のレビュー・基盤の立ち上げは縮みにくい。
```

番号つきの性質（前は 1 つの項に条件と例外を続けて書いている）:

```markdown
4a. 検品の結果を確定すると、その入荷の在庫が引き当てられる。数量が発注を超えるときは確定できない。ただし管理者が承認した入荷は超えて確定できる（Q-S-012）。
```

後:

```markdown
4a. **検品の結果を確定したとき、その入荷の在庫は引き当てられる**

- 数量が発注を超えるときは、確定できない。
- ただし、管理者が承認した入荷は、発注を超えて確定できる（Q-S-012）。
```

`1.` の形なら、箇条を 4 スペース字下げする:

```markdown
1. **検品の結果を確定したとき、その入荷の在庫は引き当てられる**

    - 数量が発注を超えるときは、確定できない。
```

## 判定役の指摘で性質を直すとき

**条件を足すときは箇条を 1 行足し、見出しは伸ばさない**

- spec-review で判定役の指摘に応えて性質を直すときも、この記法で書く。
- 足す条件は 1 文の箇条にして、その性質の箇条に足す。
- 例外を足すなら、「ただし」で始まる箇条にする。
- 1 つの見出し・1 つの箇条に、条件・例外・根拠を続けて詰め込まない。

## 前の書き方の正本を移す

前の書き方で書いた正本リポジトリは、次の手順で移す。
**移すのは文を分ける・並べ替えることだけで、中身（決まり・数・条件）は変えない。**

**移すのは作業中の版のファイルだけにする**

- リリースした版（`release-v<n>` のタグがある版）の `docs/v<n>/` は書き換えない（`versions.md` の「凍結」。`check-frozen.py` が 1 で落とす）。
- 前の版のファイルを、記法のためだけに作業中の版へ写さない。
- 写すと中身の文字列が違うので、版の差分（`diff-versions.py`）が `変更` に出し、変更の提案書の「前の版からの変更」にも載る（`versions.md` の「版の差分」）。
- 前の版のファイルを中身を直すために作業中の版へ写したら、直しの commit の後に、移しだけの commit で移す（下の「移しだけの commit にする」）。

**その版のサインオフを取る前に移す**

- 2 つのサインオフの照合（`check-signoff.py`）は、2 つのタグの時点の `shared/`・`requirements/`・`spec/` などの中身を比べる（`signoff-tags.md`）。
- 一方のタグの後に移すと、2 つのタグの中身が違い、照合が一致しない。
- 取った後に移したなら、移した後の中身で承認を取り直す。

**移しだけの commit にする**

- 中身の直しを、移しの commit に混ぜない。
- 混ぜると、下の確かめが中身の直しと記法の書き換えを見分けられない。
- 意味が一意に読めない文は、推測で分けずにそのまま残し、利用者に確かめる。

**移した後に、数が前後で同じかをスクリプトで確かめる**

- 確かめるのは、表の行・見出し・印・囲みのコード・番号つきの項・未決定の印の数と、根拠の番号（`Q-R-004`・`D-F-002`・`F-001` の形）の集まりである。
- 正本リポジトリの根で、移す前のコミット（移しの commit の直前）と作業中の版のディレクトリを渡して走らせる。
- どれかが違えば、そのファイルと項目を出して 1 で終わる。
- 最後に比べたファイルの数を出す。
- 比べたファイルが 0 件なら、確かめていないので 2 で終わる（移しの commit の後のコミットを渡した・ディレクトリの名前を打ち間違えた、など）。
- 句点の数は前後を並べて出すだけで、違っても落とさない（文を分けると増え、見出しにすると減る）。
- 句点の数が大きく変わったら、文を足したか消したかを疑う。

```bash
python3 - <移す前のコミット> docs/v<n> <<'EOF'
import re, subprocess, sys, unicodedata
from pathlib import Path

base, root = sys.argv[1], sys.argv[2]
COUNTS = {
    "表の行": re.compile(r"^\s*\|", re.M),
    "見出し": re.compile(r"^#{1,6}\s", re.M),
    "印": re.compile(r"<!--"),
    "囲みのコード": re.compile(r"^\s*(```|~~~)", re.M),
    "番号つきの項": re.compile(r"^\s*[0-9]+[a-z]?\.\s", re.M),
    # 未決定の印は spec-exit.md の「未決定の印」の写し（全角は NFKC で半角に寄せてから数える）
    "未決定の印": re.compile(r"(?i)(?<![a-z])(?:tbd|todo)(?![a-z])|未定(?!義)|要確認"),
}
NUMBER = re.compile(r"(?<![A-Za-z0-9])[A-Z]-(?:[A-Z]+-)?[0-9]+[a-z]?(?![A-Za-z0-9])")
# -z で読む（日本語・空白を含む名前を git が引用符で囲まないように）
names = subprocess.run(["git", "diff", "--name-only", "-z", base, "--", root],
                       capture_output=True, text=True, check=True).stdout.split("\0")
names += subprocess.run(["git", "ls-files", "--others", "--exclude-standard", "-z", "--", root],
                        capture_output=True, text=True, check=True).stdout.split("\0")
bad = 0
compared = sorted(set(n for n in names if n.endswith(".md")))
for name in compared:
    old = subprocess.run(["git", "show", f"{base}:{name}"], capture_output=True, text=True)
    if old.returncode != 0:
        print(f"{name}: 移す前に無い"); bad = 1; continue
    if not Path(name).is_file():
        print(f"{name}: 移した後に無い"); bad = 1; continue
    before = unicodedata.normalize("NFKC", old.stdout)
    after = unicodedata.normalize("NFKC", Path(name).read_text(encoding="utf-8"))
    for label, pattern in COUNTS.items():
        b, a = len(pattern.findall(before)), len(pattern.findall(after))
        if b != a:
            print(f"{name}: {label} {b} → {a}"); bad = 1
    lost = set(NUMBER.findall(before)) - set(NUMBER.findall(after))
    added = set(NUMBER.findall(after)) - set(NUMBER.findall(before))
    if lost or added:
        print(f"{name}: 根拠の番号 消えた {sorted(lost)} 増えた {sorted(added)}"); bad = 1
    print(f"{name}: 句点 {before.count('。')} → {after.count('。')}")
print(f"比べたファイル: {len(compared)} 件")
if not compared:
    # 0 件は「数が同じ」ではない——移す前のコミットかディレクトリの取り違えで、何も比べていない
    print(f"{root}: {base} から変わった Markdown が無い——移す前のコミットとディレクトリを確かめる")
    sys.exit(2)
sys.exit(bad)
EOF
```

**数が同じことは、意味が同じことではない**

- スクリプトが見るのは数と番号だけで、文の中身が変わっていないかは見ない。
- 移した差分は、利用者か開発者が読んで、意味が変わっていないかを確かめる。

**要求か仕様を移したら、記録の表に `記法の移行` の行を足す**

- 足す先は正本の `spec-review/v<n>.csv` で、列は `spec-exit.md` の「記録の表」を正とする。
- 移した回は、要求の行と仕様の行が記法だけで増える。
- その行を跨ぐ 2 つの実行の行は、「仕様の規模」の比べ方で比べない（`spec-exit.md` の「仕様の規模」）。
