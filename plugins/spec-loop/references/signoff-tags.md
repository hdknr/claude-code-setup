# サインオフのタグ

承認は **git のタグ**で記録する。タグはコミットを指すので、
「誰が、どの時点の中身を承認したか」が正本リポジトリの履歴に残る。

**承認は版（`docs/v<n>/`。`versions.md`）ごとに取る。** タグの名前は `signoff/` の下に版を持つ。

| 承認する人 | タグ | 例 |
| --- | --- | --- |
| 利用者（要求の確定） | `signoff/v<n>/req-<k>` | `signoff/v2/req-3` |
| 予算責任者（範囲・開発費・運用費・期間の合意） | `signoff/v<n>/budget-<k>` | `signoff/v2/budget-1` |

- `<n>` は承認した版の番号。`<k>` は 1 から始まる整数で、その版の中で取り直すたびに 1 つ上げる
  （**版が変われば 1 から数え直す**）。どちらも先頭に 0 を付けない。**付け直さない**（同じ名前のタグを
  別のコミットに動かさない）。古い承認の記録が消えるため。
- 2 つの回数は**独立に数える**。`signoff/v2/req-3` と `signoff/v2/budget-1` が組になってよい。
  **別の版のタグは組にしない。**
- **`signoff/` を根に置くのは、素の `v<n>` タグと衝突しないため。** git は `refs/tags/v1` と `refs/tags/v1/...` を
  同時に持てない（どちらかがあると他方を作れない）。版を根にした名前（`v1/req-signoff-1`）では、リリースを
  `v1`・`v2` と付けているリポジトリで、**リリース済みの版の承認を記録できず**、**承認を先に記録した版は
  `v<n>` でリリースできなかった**。
- **同じ理由で、名前の途中までと同じ名前のタグとは共存できない**——素の `signoff` と `signoff/v<n>`
  （例: `signoff/v2` があると `signoff/v2/req-1` を作れず、逆も同じ）。どちらも付けない。
  凍結のタグ `release-v<n>` は衝突しない。
- **以前の名前は読まない**——`v<n>/req-signoff-<k>`・`v<n>/budget-signoff-<k>`（#260）も、版を分ける前の
  `req-signoff-v3` も。それで記録した承認は、**承認した人に**この名前で取り直してもらう
  （**タグはスキルが付けない**）:
    - **#260 の名前**は、同じ版のこの名前で取り直してもらう（`v2/req-signoff-1` なら `signoff/v2/req-1`）。
      **取り直したあとで、#260 の名前のタグを手元とリモートの両方から消す**——残っていると
      `refs/tags/v<n>/` が埋まったままで、**`v<n>` でリリースできないまま**になる（取り直しても消えない）。
      **他の clone の手元にも残る**——素の `git fetch` では消えないので、各 clone で
      `git fetch --prune --prune-tags origin` を走らせる（残したまま `git push --tags` するとリモートに戻る）。
      **上の「付け直さない」の例外ではない**——同じ名前を動かすのではなく、読まない名前を片付けるだけで、
      承認の記録は新しい名前のほうに残る。
    - **版を分ける前の名前**は、`versions.md` の「移し方」で版に移してから取り直す。

## 2 つの承認が同じ範囲を見ていたか

開発に進む前の関門では、**同じ版の最新の 2 つのタグの時点で、その版の共有の範囲が一致するか**を確かめる。
プラグインに同梱の照合を使う（**LLM に判断させない**）:

```bash
python3 <spec-loop の base ディレクトリ>/scripts/check-signoff.py              # 作業中の版
python3 <spec-loop の base ディレクトリ>/scripts/check-signoff.py --version 1  # 版を指定
```

- **比べる場所は `docs/v1/shared/`〜`docs/v<n>/shared/` と `docs/v2/removed.csv`〜`docs/v<n>/removed.csv`。**
  v<n> の時点の共有の範囲は、前の版の `shared/` と、行を消す `removed.csv` にも依る。
  凍結した版（`versions.md`）は動かないので、前の版を含めても誤って食い違うことはない。
  **`removed.csv` は `shared/` に効く行だけを比べる**（種類 `Q&A` で対象が共有の表の番号（`Q-`）の行と、種類 `ファイル` で対象が `shared/` から始まる行）。**内部の Q&A 表（`spec/qa-dev.csv`。番号 `D-`）は比べない**——開発者が決めて記録するもので、サインオフの後に内部で決めても照合は割れない（`qa-csv.md` の「層」）。
  `requirements/` や機能の削除は共有の範囲の外なので、それだけが違っても一致する。
- **版を指定しなければ、作業中の版**（作業ツリーの `docs/` で番号が最大の版）。
- **最新**は、`<k>` を**数として**比べて最大のもの（`-10` は `-9` より新しい）。
  **`signoff/v2/req-3-fix` のような、命名に合わないタグは数えない。**
- **どちらかの時点で比べる場所が無い・空なら、一致とは言わない**（判定していない）。
  比べる中身が無いときも `git diff` は「差分なし」を返すので。**どちらかの時点に `docs/v<n>/` が無いときも同じ**
  （前の版の `shared/` があっても、その時点に版 n はまだ無い）。
- **作業ツリーの版の並びが決まりに反すれば、版を指定しても判定しない。**

一致しなければ、2 つの承認は別の範囲を見ていたことになる。**どちらかを取り直す。**
**提案書（`proposal`）は、一致したときだけ作る。**
CI で走らせるなら、タグを取得できるよう履歴をすべて取る（GitHub Actions なら
`actions/checkout` に `fetch-depth: 0`）。

**タグはスキルが付けない。** 承認は人間の判断なので、スキルの仕事は
「どのコミットを承認してもらうか」をそろえて止まるところまでである。

## 暫定の回答が残るうちは、要求確定のサインオフを付けない

Q&A 表に `暫定反映`（暫定の回答で仕様に反映し、利用者の確認待ち。`qa-csv.md`）の行が残っているうちは、
**要求確定のサインオフ（`req-<k>`）を付けない**——利用者が確かめていない回答を承認したことになる。
暫定の回答をレビュー会で確かめてもらい、`反映済み`（か、答えが変わったなら反映し直す）にしてから付ける。

照合（上のスクリプト）は、**要求確定のタグの時点の v1〜v<n> の Q&A を版の順に重ねて**（同じ `No` は後の版が置き換え、
`removed.csv` の行で消す。`versions.md`）、`暫定反映` の行が残っていれば **3** で終わる——一致するかどうかとは別に見る。
**3 なら提案書を作らない。** 予算の合意のタグの時点は見ない（暫定を数えるのは要求確定の側）。
**一致しないうえに暫定も残るときも 3** で、出力には両方が出る。
**3 のあとは、要求確定と予算の合意の両方を取り直す**——暫定の行を確かめると `shared/qa.csv`（`状態` と `回答`）が変わるので、
一致していた予算の合意のタグとも一致しなくなる（要求確定だけを取り直すと、次の照合は 1 で落ちる）。
