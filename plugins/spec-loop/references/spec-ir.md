# 仕様の中間表現（`docs/v<n>/spec/spec_ir.json`）

確定した仕様（`docs/v<n>/spec/`。抜ける条件は `spec-exit.md`）を、**機械で読める形**に書き起こしたもの。
`scaffold` がこれを書き、同梱のスクリプトがここから OpenAPI・型・Red テスト・Issue の本文を作る。

**書き起こすのは判断、そこから先は答えが一意に決まる。** 仕様を JSON にするのは `scaffold`（LLM）の仕事で、
生成はスクリプトが行う。だから**この JSON に書いていないことは、生成物にも Issue にも現れない**。

決まりどおりかどうかは、生成のスクリプトが生成の前に確かめる（通らなければ 1 バイトも書かない）:

```bash
python3 <spec-loop の base ディレクトリ>/scripts/scaffold.py --repo <正本リポジトリ> --dry-run
```

## ファイル

- 文字コードは UTF-8。JSON のオブジェクト 1 つ。
- 置き場所は `tree.md`。**版の `spec/` の中に置く**ので、未決定の印（`spec-exit.md`）の検査はこのファイルにも掛かる。
- **v2 以降は、その版で足した・変えた機能だけを書く**（`features` 以外のキーは省いてよい）。消すのは `removed.csv`。
  **下の決まりは、版を重ね合わせた全体に当てる**（重ね方は `versions.md`。生成のスクリプトが自分で重ねる）。

## 全体

| キー | 書くもの |
| --- | --- |
| `spec_ir_version` | `1`（整数。`1.0` は不可） |
| `title` | 仕様の題（空にしない・1 行で） |
| `features` | 機能の配列（1 つ以上） |
| `impl_module` | （任意）実装を置く Python のモジュール名（`app.core` の形）。省けば `spec_impl`。**Red テストと Issue の本文はこれを指す**——引数ではなくここに書くので、作り直しても変わらず、`--check` もこれで比べる |

**どの文字列にも、孤立したサロゲート（`"\ud800"` のような、JSON として読めるが UTF-8 で書けない文字）を入れない**——キーも値も。

## 機能（`features` の要素）

**1 機能が Issue 1 件になる。**

| キー | 書くもの |
| --- | --- |
| `id` | `F-` に 3 桁以上の数字（`F-001`）。重複させない |
| `title` | 機能の名前（空にしない・1 行で）。Issue の題になる |
| `source` | この機能を書いた仕様のファイルの配列（1 つ以上）。**重ね合わせた全体の根からのパス**（`spec/order.md`。版のディレクトリのパス `docs/v1/spec/order.md` ではない——後の版で変えても指し先が動かないように）で、**重ね合わせた全体の `spec/` の中の実在するファイル**。**`.` で始まるディレクトリ・ファイルは指さない**（未決定の印の検査がそこを見ない） |
| `qa` | この機能の決定の根拠にした Q&A の `No` の配列（空でもよい）。**Q&A 表に実在し、状態が `反映済み`**。**`暫定反映` は指さない**——利用者が確かめていない回答を開発へ渡さない（scaffold はサインオフの照合を通らない。`qa-csv.md`） |
| `operation` | 入口 1 つ（下） |
| `cases` | テストケースの配列（1 つ以上）。**1 ケースが Red テスト 1 本になる** |

## 入口（`operation`）

| キー | 書くもの |
| --- | --- |
| `id` | 関数名にもなる名前。英小文字で始まり、英小文字・数字・`_` だけ（`calc_discount`）。Python の予約語（`class`・`from` など）は使わない。全機能で重複させない。**`_` を外して語頭を大文字にした名前（型の名前。`calc_discount` → `CalcDiscount`）も重複させない**（`a_1` と `a1`） |
| `method` | 下の「メソッド」のどれか |
| `path` | `/` で始まる 1 行。**パスの変数**（`/orders/{order_id}`）は `{` と `}` で項目名を 1 つ囲み、**その名前は `input` の項目でなければならない**（下の「パスの変数」） |
| `input` | 入力の項目（下の「項目」）。空のオブジェクトでもよい |
| `output` | 正常時に返す項目（下の「項目」）。1 つ以上。**`error` という項目は置かない**（失敗の形と見分けられない） |
| `errors` | 失敗時に返すエラーの名前の配列（空でもよい）。英大文字で始まり、英大文字・数字・`_` だけ（`INVALID_RANK`）。重複させない |

`method` と `path` の組は全機能で重複させない。

### パスの変数

- **`{…}` の中身は `input` の項目名**。`input` に無い名前・空の `{}`・対にならない `{` `}`・同じパスに同じ変数を 2 度は書かない。
- **変数の名前だけが違うパスを並べない**（`/items/{id}` と `/items/{key}`）。メソッドが違っても——OpenAPI では同じパスになり、無効になる。
- 生成する OpenAPI では、パスの変数は `in: path`・`required: true` のパラメータになり、**クエリ・ボディには重ねない**。
  残りの項目は、`GET`・`DELETE` ならクエリ、それ以外ならボディ（パスの変数を持つ入口では `<型の名前>Body`）に載る。
  **実装の関数には、パスの変数も `input` の項目の 1 つとして渡る**（Red テストと型は変わらない）。
- **この決まりを外すのは 1 箇所だけ**（#319）——v<n> を作るときに、**機能を追加・変更・削除に分けるための比べる相手**
  として読む v<n-1> の全体。spec-loop 0.13.0 より前の `scaffold.py` はパスの変数を見ずに通したので、凍結した版が反していても
  直せない。比べる相手の中間表現は、分けること・前の版の Red テスト・Issue の本文（前の版を指す行）にしか使わず、OpenAPI を作らない。
  **それ以外——今の版と、`--upto <n-1>` で前の版の時点を作る・確かめるとき——には当てる**（生成するので外せない）。
  **今の版が反していれば、前の版から持ち越した誤りでも止まる**——v<n> で直す。

#### 0.13.0 より前に作った `scaffold/` の移行（1 度だけ）

0.13.0 から、パスの変数を持つ入口の OpenAPI が変わった（path パラメータを宣言し、ボディは `<型の名前>Body` を指す。
前の出力は path パラメータを宣言しない、OpenAPI として無効なものだった）。そのため、それより前に作って commit した
`scaffold/` は、**この決まりに合う中間表現でも、中間表現を変えていなくても** `scaffold.py --check`
（と `--check --upto <n-1>`）で古いと言われる。パスの変数を持たない入口だけなら、出力は変わらず、古くもならない。
**中間表現が決まりに反するなら**、古いではなく「決まりに反する」と言われる（下の 2・3）。

下では、次に作る（または作った）版を v<n>、その比べる相手を v<n-1> と書く——`docs/v<n>/` がまだ無ければ、v<n-1> は最新の版である。
**分かれ目は v<n-1> の中間表現で、最新の版ではない**（`docs/v<n>/` が既にあると、最新の版は v<n> になる）。

1. **v<n-1> の中間表現が決まりに合うなら、`docs/v<n>/` を作る前に、`scaffold.py` で作り直して `scaffold/` を
   commit する。** 以後は `--check` が 0 になる。**`docs/v<n>/` を作った後で、v<n> が出力を変えているなら、作り直しは
   v<n> の時点を書くので、`--check --upto <n-1>` は 1 のまま残る**（書き込みは `--upto` を取れない）——そのときは
   `docs/v<n>/` を **`docs/` の外へ**退けて作り直し、戻す（`docs/` の中に別の名前で置くと、版の名前の形に合わずに止まる）。
2. **v<n-1> の中間表現が決まりに反するなら、v<n-1> が凍結しているか（`release-v<n-1>` のタグがあるか。`versions.md` の「凍結」）で分かれる。**
    - **凍結していなければ、`docs/v<n-1>/` をその場で直して作り直す**——パスの変数を `input` に足すか、パスから外す。
      v1 しか無い正本リポジトリで v1 をリリースしていなければ、これに当たる。
    - **凍結していれば、次の版 v<n> で直す**——v<n> の中間表現で同じように直す。v<n> は作れる
      （比べる相手の v<n-1> には決まりを当てない。上）。**v1 しか無い正本リポジトリも、v1 をリリースしていれば v2 を作って直す。**
3. 2 の凍結しているとき、**v<n-1> の時点の `--check --upto <n-1>` は 1 で止まり続ける**（生成するので、決まりを外せない）。
   `versions.md` の「差分の周を始める前に」の 1 つ目はこの版では確かめられないので、**v<n> で直してから作り、`--check` で確かめる**。

### 項目

`{"<項目名>": {"type": "<型>", "enum": [...]}}` の形。項目名は英小文字で始まり、英小文字・数字・`_` だけで、Python の予約語は使わない。
`enum` は省いてよく、書くなら 1 つ以上の値を、その型で、重複させずに並べる。

| 型 | 値 |
| --- | --- |
| `string` | 文字列 |
| `integer` | 整数（`true`・`false` は整数に数えない） |
| `number` | 数（整数でもよい。`true`・`false`・`NaN`・`Infinity` は数に数えない） |
| `boolean` | `true`・`false` |

**入れ子のオブジェクト・配列・null は、いまは持たない。** 要るなら、この決まりを先に広げる。

## テストケース（`cases` の要素）

| キー | 書くもの |
| --- | --- |
| `id` | 機能の `id` に `-C` と数字（`F-001-C1`）。全機能で重複させない |
| `title` | 何を確かめるか（空にしない・1 行で） |
| `input` | 入力。**`operation.input` の項目をちょうど全部**、その型（と `enum`）で |
| `expected` | 正常時に返すもの。**`operation.output` の項目をちょうど全部**、その型（と `enum`）で |
| `error` | 失敗するケースなら、`expected` の代わりに `operation.errors` のどれか |
| `qa` | このケースの根拠にした Q&A の `No` の配列（省いてよい）。機能の `qa` と同じ決まり |

**`expected` と `error` は、ちょうど片方だけ書く。** **決まりに無いキーは書かない**——書いても生成物に現れないので、検査が落とす。

実装は、`input` を受け取って、正常なら `expected` と等しいオブジェクトを、失敗なら
`{"error": "<エラーの名前>"}` を返す。**Red テストはこの等しさと、各項目の型を見る**
（`True == 1 == 1.0` なので、等しさだけでは `boolean` に `1` を返す実装が通る。`number` は整数でも小数でもよい）。

## 書き起こすときの決まり

- **仕様に書いていないことを足さない。** ケースは仕様のテストケース（`spec-exit.md` の条件 3）から写す。
  足したくなったら、仕様のほうを直す（利用者の判断が要るなら Q&A 表に起票する）。
- **決まっていないことを、もっともらしい値で埋めない。** 書けないなら仕様が確定していない——`spec-review` に戻す。

## 例

```json
{
  "spec_ir_version": 1,
  "title": "注文",
  "features": [
    {
      "id": "F-001",
      "title": "注文の割引額を計算する",
      "source": ["spec/order.md"],
      "qa": ["Q-001"],
      "operation": {
        "id": "calc_discount",
        "method": "POST",
        "path": "/orders/discount",
        "input": {"rank": {"type": "string", "enum": ["silver", "gold"]}, "amount": {"type": "integer"}},
        "output": {"discount": {"type": "integer"}},
        "errors": ["INVALID_AMOUNT"]
      },
      "cases": [
        {"id": "F-001-C1", "title": "シルバーで 10000 円未満は割引なし",
         "input": {"rank": "silver", "amount": 9999}, "expected": {"discount": 0}, "qa": ["Q-001"]},
        {"id": "F-001-C2", "title": "金額が負なら拒否する",
         "input": {"rank": "gold", "amount": -1}, "error": "INVALID_AMOUNT"}
      ]
    }
  ]
}
```
