# 仕様の中間表現（`docs/v<n>/spec/spec_ir.json`）

確定した仕様（`docs/v<n>/spec/`。抜ける条件は `spec-exit.md`）を、**機械で読める形**に書き起こしたもの。
`scaffold` がこれを書き、同梱のスクリプトがここから OpenAPI・型・Red テスト・Issue の本文を作る。

**書き起こすのは判断、そこから先は答えが一意に決まる。** 仕様を JSON にするのは `scaffold`（LLM）の仕事で、
生成はスクリプトが行う。だから**この JSON に書いていないことは、生成物にも Issue にも現れない**。

決まりどおりかどうかは、生成のスクリプトが生成の前に確かめる（通らなければ 1 バイトも書かない）:

```bash
python3 <spec-loop の base ディレクトリ>/scripts/scaffold.py --repo <正本リポジトリ> --dry-run
```

## ファイル

- 文字コードは UTF-8。JSON のオブジェクト 1 つ。
- 置き場所は `tree.md`。**版の `spec/` の中に置く**ので、未決定の印（`spec-exit.md`）の検査はこのファイルにも掛かる。
- **v2 以降は、その版で足した・変えた機能だけを書く**（`features` 以外のキーは省いてよい）。消すのは `removed.csv`。
  **下の決まりは、版を重ね合わせた全体に当てる**（重ね方は `versions.md`。生成のスクリプトが自分で重ねる）。

## 全体

| キー | 書くもの |
| --- | --- |
| `spec_ir_version` | `1`（整数。`1.0` は不可） |
| `title` | 仕様の題（空にしない・1 行で） |
| `features` | 機能の配列（1 つ以上） |
| `impl_module` | （任意）実装を置く Python のモジュール名（`app.core` の形）。省けば `spec_impl`。**Red テストと Issue の本文はこれを指す**——引数ではなくここに書くので、作り直しても変わらず、`--check` もこれで比べる |

**どの文字列にも、孤立したサロゲート（`"\ud800"` のような、JSON として読めるが UTF-8 で書けない文字）を入れない**——キーも値も。

## 機能（`features` の要素）

**1 機能が Issue 1 件になる。**

| キー | 書くもの |
| --- | --- |
| `id` | `F-` に 3 桁以上の数字（`F-001`）。重複させない。**機能一覧（`requirements/features.csv`）があれば、その `id` と同じ番号にする**——入口の機能が一覧に無い・一覧の id が中間表現に無いと、生成のスクリプトが止まる（`tree.md` の「機能一覧と中間表現の照合」。#957） |
| `title` | 機能の名前（空にしない・1 行で）。Issue の題になる |
| `source` | この機能を書いた仕様のファイルの配列（1 つ以上）。**重ね合わせた全体の根からのパス**（`spec/order.md`。版のディレクトリのパス `docs/v1/spec/order.md` ではない——後の版で変えても指し先が動かないように）で、**重ね合わせた全体の `spec/` の中の実在するファイル**。**`.` で始まるディレクトリ・ファイルと、形式検査のモデル（`spec/formal/` の中。`tree.md` の「形式検査のモデル」）は指さない**（未決定の印の検査がそこを見ない。scaffold が断る） |
| `qa` | この機能の決定の根拠にした Q&A の `No` の配列（空でもよい）。共有の表の `Q-` も内部の表（`spec/qa-dev.csv`）の `D-` も指せる。**その表に実在し、状態が `反映済み`**。**`暫定反映` は指さない**——利用者が確かめていない回答を開発へ渡さない（scaffold はサインオフの照合を通らない。`qa-csv.md`）。**指していなくても、`暫定反映` の行が表に残れば scaffold は止まる**——仕様には反映されているので、どの機能に効いているかを中間表現からは決められない。**例外は、利用者が仮回答のまま渡すと決めて `scaffold.py --provisional` で作るときだけ**——`暫定反映` の行を指してよく、**効く機能とケースの全部から指す**（どこからも指されない `暫定反映` の行が残れば止まる。指し漏らした機能の本文には仮回答の印が付かない。`handoff-issue.md` の「仮回答の印」。#875） |
| `operation` | 入口 1 つ（下） |
| `cases` | テストケースの配列（1 つ以上）。**1 ケースが Red テスト 1 本になる** |
| `called_by` | （任意）**この機能が他の機能から呼ばれる判定の関数なら**、呼ぶ機能の `id` の配列（1 つ以上）。下の「呼ばれる機能」 |
| `out_of_scope` | （任意）**この機能に関わる範囲の外の行**の原文の配列（1 つ以上）。下の「作らないもの」 |
| `nfr` | （任意）**この機能に効く性能の要求**——`shared/nfr.csv` の行の `No` の配列（1 つ以上）。下の「性能の要求」 |
| `branches` | （任意）**この機能の呼ぶ側の分岐**——分岐の名前から、見せるもの（`shows`）か該当なし（`none`）の仕様の原文への対応。下の「呼ぶ側の分岐」 |

## 呼ばれる機能（`called_by`。#609）

**仕様が、機能を「API・画面・バッチから呼ばれる判定の関数」として書いている**（「この関数を呼ぶ側は、ここでは定めない」のように）なら、
その機能の `called_by` に**呼ぶ機能**——その関数を呼ぶ入口の機能——の `id` を書く。

- **呼ぶ機能も、中間表現に機能として書き起こす。** 関数だけを Issue にすると、それを呼ぶ入口（API がクエリを受けて関数を呼ぶ・応答に欄を足す）が
  どの Issue にも載らず、関数がマージされても利用者からは使えない（#609）。呼ぶ側の振る舞いは、呼ぶ機能のケース（Red テスト）に書く——呼ぶ機能が変わらない版では、その版の Red テストは呼ぶ側を新しく確かめない（下の知らせ）。
- **仕様が呼ぶ側の振る舞いを書いていなければ、仕様が確定していない**——呼ぶ機能をもっともらしく足さず、`spec-review` に戻す。
- **`called_by` の各 `id` は、重ね合わせた全体の中間表現に在る機能**でなければならない。自分自身・重複・空の配列は書かない。
  **呼ぶ関係は循環させない**（辿った先に、`called_by` を持たない入口の機能が要る）。どれかに反すれば、生成のスクリプトは止まる（1）。
  **呼ぶ機能を `removed.csv` で消すなら、`called_by` からも外す**（外さなければ止まる）。
- **`called_by` を書かない機能は、入口（API・画面・バッチ）と読む。** 機械は申告の整合だけを見る——関数に `called_by` を書かなければ通る。
- **v2 以降で、`called_by` を持つ機能を足す・変えるのに、呼ぶ機能をどれもその版で足さず変えていなければ、生成のスクリプトは止めずに名指しで知らせる**（0）。
  関数の中だけの直しはありうるので止めないが、**呼ぶ入口の振る舞いも変わるなら、仕様にその入口の変化を書き、この版の中間表現でも変える**
  ——書かなければ、呼ぶ側の課題がどの Issue にも載らない。
- `called_by` を v2 で足す・外すだけでも、その機能は変更になる（機能のオブジェクトが変わる。ケースは全部 `回帰`）。
- Issue の本文の `## 仕様` に、呼ぶ機能の `id` と題が載る（`handoff-issue.md`）。

## 作らないもの（`out_of_scope`。#851）

**範囲の文書（`spec/scope.md`。`spec-scope.md`）の「範囲の外」の節の行のうち、その機能に関わるもの**——その機能を作る人が、
範囲の外として作らずにおくべき場面——を、機能の `out_of_scope` に**行の原文のまま**並べる。Issue の本文の `## 作らないもの` に写る
（`handoff-issue.md` の「作らないもの」。「次の版の候補」を含む行はそちらの小見出しに分かれる）。

- **原文のまま書く**——重ね合わせた全体の `spec/scope.md` の、見出しに「範囲の外」を含む節の 1 行と、前後の空白を落として一致する文字列。
  表の行なら `| ディスクがいっぱい | 失敗を見せる | 既定の線 |` のような本文の 1 行をそのまま（**表の見出しと区切りの行は挙げない**——本文には生成のスクリプトが付ける）。
  **要約・言い換え・複数行は書かない。** 範囲の文書の行を直したら、ここも同じ文字列に直す（直さなければ生成のスクリプトが止まる）。
- **1 つ以上・重複させない。** 関わる行が無い機能には書かない（本文には「無い」と出る）。
- **どの行が関わるかは書き起こす側の判断**で、機械は原文が在ることだけを見る——関わらない行を挙げても、関わる行を落としても通る。
  **範囲の文書に無い場面を足さない**（足したくなったら `spec-review` に戻して範囲の文書に書く）。
- **`out_of_scope` を v2 で足す・変える・外すだけでも、その機能は変更になる**（機能のオブジェクトが変わる。ケースは全部 `回帰`。`called_by` と同じ）。

## 性能の要求（`nfr`。#852）

**性能の要求の表（`shared/nfr.csv`。列は `nfr.md`）の性能の行のうち、その機能に効くもの**の `No` を、機能の `nfr` に並べる。
Issue の本文の `### 性能予算` に行の数字が写り、性能テスト `scaffold/perf/perf_<機能>.py` が作られる（`handoff-issue.md` の「作らないもの」・`nfr.md`）。

- **指す行は、重ね合わせた全体の `shared/nfr.csv` に 1 行だけ在り、性能の行の形**（`指標` が `p50`・`p95`・`p99`・`最大` のどれか・`上限` が正の数・`単位` が `ms`・
  `対象`・`条件`・`根拠` が空でない 1 行）**でなければならない**。反すれば生成のスクリプトは止まる（1）。**指していない行は見ない**。
- **1 つ以上・重複させない。** 効く行が無い機能には書かない（本文の性能予算は「要求なし」——`nfr.md` の「既定の原則」）。
- **どの行が効くかは書き起こす側の判断**で、機械は行の在ることと形だけを見る。**表に無い数字を足さない**（足したくなったら `spec-review` に戻す）。
- **`nfr` を v2 で足す・変える・外すだけでも、その機能は変更になる**（`out_of_scope` と同じ）。**行の数字だけを変えても機能は変わらない**——
  数字を変えるときは新しい `No` の行にし、`nfr` を差し替える（`nfr.md` の「列」）。

## 呼ぶ側の分岐（`branches`。#855）

**仕様チェックリストの「呼ぶ側の分岐」の行（`spec-exit.md`）を、入口の機能ごとに書き起こす。** 生成のスクリプトは、ここから
**課題一覧（案）**（`tree.md` の「生成物の置き場所」の `proposals.md`）を作る——Red テストは関数の入力と出力しか確かめないので、
入力が遅れる・呼ぶ処理がやり直されるといった結線の振る舞いは Red テストの外に残る。#402 の実案件では、その結線の課題を手で起票し、
仕様の穴を実装役が実装の途中で見つけた。課題一覧（案）は、その課題の案ごとに**未決定事項**（ここに書き起こしていない分岐）・
**受入基準の雛形**（見せるものの原文）・**作らないもの**（Issue の本文の `## 作らないもの` と同じ中身。`handoff-issue.md`）を付けて出す。
**案は Issue の本文ではなく、生成のスクリプトは登録しない**——登録するかは利用者が決める（scaffold の `SKILL.md` の手順 7）。

```json
"branches": {
  "入力が欠ける": {"shows": "- 入力が欠ける: 「データ欠落」と表示する"},
  "入力の順が崩れる": {"none": "- 入力の順が崩れる: 該当なし（1 回の要求で全部そろって届く）"}
}
```

- **鍵は下の「分岐の名前」のどれか**で、値は `{"shows": <原文>}`（見せるもの）か `{"none": <原文>}`（該当なしと理由）の**どちらか 1 つ**。
  **行ごと該当なし**（入力も呼び出しも外と結ばない純粋な計算。`spec-exit.md` の「呼ぶ側の分岐」）は `{"none": <原文>}` **だけ**を書く（分岐の鍵と混ぜない）。
- **原文は、機能の `source` のどれかの 1 行**——前後の空白を落として一致する文字列（表の行ならその行をそのまま）。**要約・言い換え・複数行は書かない。**
  仕様の行を直したら、ここも同じ文字列に直す（直さなければ生成のスクリプトが止まる）。**その行がその分岐を決めているかは書き起こす側の判断**で、機械は原文が在ることだけを見る。
- **仕様が決めていない分岐は書かない**——課題一覧（案）の未決定事項に出る。**もっともらしい見せるものを足さない**（足したくなったら `spec-review` に戻す）。
  `branches` を書かない入口の機能は、8 分岐が全部未決定と出る。**未決定事項があっても生成のスクリプトは止めない**（案は登録しないので。件数を出す）。
- **呼ばれる関数（`called_by` を持つ機能）には書かない**——分岐は呼ぶ入口の機能に書く（書けば生成のスクリプトが止まる）。課題一覧（案）にも呼ばれる関数の案は無い。
- **案を作るのは、作業中の版で追加・変更した入口の機能だけ**——変わっていない機能・撤去する機能の案は無い（案が無ければ「無い」と出る）。
  **`impl_module` を変えただけで変更になった機能（機能のオブジェクトは前の版と同じ）の案も無い**（Issue の本文は作る——`handoff-issue.md`）。
  凍結した前の版を信じずに全部を追加にしたとき（`versions.md` の「前の版の時点が崩れていたら」）は、変わったかを決められないので全部の入口の機能に案を作る。
- **`branches` を v2 で足す・変える・外すだけでも、その機能は変更になる**（機能のオブジェクトが変わり、機能の指紋も変わる。ケースは全部 `回帰`）。
  **`out_of_scope`・`nfr` と違い、Issue の本文の中身は指紋のほかに変わらない**——変わるのは課題一覧（案）である。そのため、変えていない機能に `branches` を書き足すと、
  実装することの無い変更の Issue ができる。**前の版で抜けた機能に、`branches` のためだけに書き足さない**——その版で足す・変える機能に書く。
  **同じ版で Issue を登録した後に書き足すと、その Issue の機能の指紋が合わなくなる**（dev-loop が差し戻す）——未決定事項は登録の前に片づける（scaffold の `SKILL.md` の手順 4）。

### 分岐の名前

`spec-exit.md` の仕様チェックリストの「呼ぶ側の分岐」の 3 組（入力・呼ぶ処理・量）を、分岐ごとに分けたもの。

| 分岐 |
| --- |
| `入力が欠ける` |
| `入力が遅れる` |
| `入力の順が崩れる` |
| `呼ぶ処理が失敗する` |
| `呼ぶ処理がやり直される` |
| `呼ぶ処理が再起動する` |
| `量が上限を超える` |
| `量が重なる` |

## 入口（`operation`）

| キー | 書くもの |
| --- | --- |
| `id` | 関数名にもなる名前。英小文字で始まり、英小文字・数字・`_` だけ（`calc_discount`）。Python の予約語（`class`・`from` など）は使わない。全機能で重複させない。**`_` を外して語頭を大文字にした名前（型の名前。`calc_discount` → `CalcDiscount`）も重複させない**（`a_1` と `a1`） |
| `method` | 下の「メソッド」のどれか |
| `path` | `/` で始まる 1 行。**パスの変数**（`/orders/{order_id}`）は `{` と `}` で項目名を 1 つ囲み、**その名前は `input` の項目でなければならない**（下の「パスの変数」） |
| `input` | 入力の項目（下の「項目」）。空のオブジェクトでもよい |
| `output` | 正常時に返す項目（下の「項目」）。1 つ以上。**`error` という項目は置かない**（失敗の形と見分けられない） |
| `errors` | 失敗時に返すエラーの名前の配列（空でもよい）。英大文字で始まり、英大文字・数字・`_` だけ（`INVALID_RANK`）。重複させない |

`method` と `path` の組は全機能で重複させない。

### パスの変数

- **`{…}` の中身は `input` の項目名**。`input` に無い名前・空の `{}`・対にならない `{` `}`・同じパスに同じ変数を 2 度は書かない。
- **変数の名前だけが違うパスを並べない**（`/items/{id}` と `/items/{key}`）。メソッドが違っても——OpenAPI では同じパスになり、無効になる。
- 生成する OpenAPI では、パスの変数は `in: path`・`required: true` のパラメータになり、**クエリ・ボディには重ねない**。
  残りの項目は、`GET`・`DELETE` ならクエリ、それ以外ならボディ（パスの変数を持つ入口では `<型の名前>Body`）に載る。
  **実装の関数には、パスの変数も `input` の項目の 1 つとして渡る**（Red テストと型は変わらない）。
- **この決まりを外すのは 1 箇所だけ**（#319）——`v<n>` を作るときに、**機能を追加・変更・削除に分けるための比べる相手**
  として読む `v<n-1>` の全体。spec-loop 0.13.0 より前の `scaffold.py` はパスの変数を見ずに通したので、凍結した版が反していても
  直せない。比べる相手の中間表現は、分けること・前の版の Red テスト・Issue の本文（前の版を指す行）にしか使わず、OpenAPI を作らない。
  **それ以外——今の版と、`--upto <n-1>` で前の版の時点を作る・確かめるとき——には当てる**（生成するので外せない）。
  **今の版が反していれば、前の版から持ち越した誤りでも止まる**——`v<n>` で直す。

#### 0.13.0 より前に作った `scaffold/` の移行（1 度だけ）

0.13.0 から、パスの変数を持つ入口の OpenAPI が変わった（path パラメータを宣言し、ボディは `<型の名前>Body` を指す。
前の出力は path パラメータを宣言しない、OpenAPI として無効なものだった）。そのため、それより前に作って commit した
`scaffold/` は、**この決まりに合う中間表現でも、中間表現を変えていなくても** `scaffold.py --check`
（と `--check --upto <n-1>`）で古いと言われる。パスの変数を持たない入口だけなら、出力は変わらず、古くもならない。
**中間表現が決まりに反するなら**、古いではなく「決まりに反する」と言われる（下の 2・3）。

下では、次に作る（または作った）版を `v<n>`、その比べる相手を `v<n-1>` と書く——`docs/v<n>/` がまだ無ければ、`v<n-1>` は最新の版である。
**分かれ目は `v<n-1>` の中間表現で、最新の版ではない**（`docs/v<n>/` が既にあると、最新の版は `v<n>` になる）。

1. **`v<n-1>` の中間表現が決まりに合うなら、`docs/v<n>/` を作る前に、`scaffold.py` で作り直して `scaffold/` を
   commit する。** 以後は `--check` が 0 になる。**`docs/v<n>/` を作った後で、`v<n>` が出力を変えているなら、作り直しは
   `v<n>` の時点を書くので、`--check --upto <n-1>` は 1 のまま残る**（書き込みは `--upto` を取れない）——そのときは
   `docs/v<n>/` を **`docs/` の外へ**退けて作り直し、戻す（`docs/` の中に別の名前で置くと、版の名前の形に合わずに止まる）。
2. **`v<n-1>` の中間表現が決まりに反するなら、`v<n-1>` が凍結しているか（`release-v<n-1>` のタグがあるか。`versions.md` の「凍結」）で分かれる。**
    - **凍結していなければ、`docs/v<n-1>/` をその場で直して作り直す**——パスの変数を `input` に足すか、パスから外す。
      v1 しか無い正本リポジトリで v1 をリリースしていなければ、これに当たる。
    - **凍結していれば、次の版 `v<n>` で直す**——`v<n>` の中間表現で同じように直す。`v<n>` は作れる
      （比べる相手の `v<n-1>` には決まりを当てない。上）。**v1 しか無い正本リポジトリも、v1 をリリースしていれば v2 を作って直す。**
3. 2 の凍結しているとき、**`v<n-1>` の時点の `--check --upto <n-1>` は 1 で止まり続ける**（生成するので、決まりを外せない）。
   `versions.md` の「差分の周を始める前に」の 1 つ目はこの版では確かめられないので、**`v<n>` で直してから作り、`--check` で確かめる**。

### 項目

`{"<項目名>": {"type": "<型>", "enum": [...], "nullable": true}}` の形。項目名は英小文字で始まり、英小文字・数字・`_` だけで、Python の予約語は使わない。
`enum` は省いてよく、書くなら 1 つ以上の値を、その型で、重複させずに並べる。
`nullable` も省いてよく、書くなら `true` だけ（下の「null を許す項目」）。

| 型 | 値 |
| --- | --- |
| `string` | 文字列 |
| `integer` | 整数（`true`・`false` は整数に数えない） |
| `number` | 数（整数でもよい。`true`・`false`・`NaN`・`Infinity` は数に数えない） |
| `boolean` | `true`・`false` |

**入れ子のオブジェクト・配列は、いまは持たない。** 要るなら、この決まりを先に広げる。

### null を許す項目（#487）

**`"nullable": true` を書いた項目だけが、その型の値か `null` を持てる**——入力にも出力にも書ける（「ラベル無し」を `null` で返す、など）。
**書かない項目は `null` を拒む**（`nullable` を足す前と同じ。生成物も変わらない）。

- **`true` だけを書く。** `false` は書かない——null を許さないなら省く（同じ意味の書き方を 2 つ作ると、機能の指紋が違う値になる。`handoff-issue.md`）。
- **`enum` と一緒に書いてよい。** `null` は `enum` に並べない——`enum` の値はその型のものだけで、`null` は `nullable` が許す。
- **パスの変数（上の「パスの変数」）には書かない**——パスの値は `null` にならない。
- ケースの `input`・`expected` では、その項目に `null` を書ける。
- 生成物では、OpenAPI の schema の `type` が `["<型>", "null"]` になり（`enum` があれば `enum` の最後に `null` を足す）、
  `types.py` の型は `null` を許さないときの型の後ろに ` | None` を足したもの（`str | None`。`enum` があれば `Literal['a', 'b'] | None`）になる。Red テストは、その出力の項目が `None` のときだけ型を見ない（`None` 以外の値の型は今までどおり見る）。

## テストケース（`cases` の要素）

| キー | 書くもの |
| --- | --- |
| `id` | 機能の `id` に `-C` と数字（`F-001-C1`）。全機能で重複させない |
| `title` | 何を確かめるか（空にしない・1 行で） |
| `input` | 入力。**`operation.input` の項目をちょうど全部**、その型（と `enum`）で（`nullable` の項目は `null` でもよい。上の「null を許す項目」） |
| `expected` | 正常時に返すもの。**`operation.output` の項目をちょうど全部**、その型（と `enum`）で（`nullable` の項目は `null` でもよい） |
| `error` | 失敗するケースなら、`expected` の代わりに `operation.errors` のどれか |
| `qa` | このケースの根拠にした Q&A の `No` の配列（省いてよい）。機能の `qa` と同じ決まり |
| `ref` | このケースの元になった、仕様の中の行の番号（決定表の `R-F10`・テストケースの `F1-5b` など。省いてよい）。**仕様が番号を振っていれば書く**——生成と `--check` が、機能の `source` の原文にその番号が在るかを確かめる（#465。値が一致するかまでは見ない） |

**`expected` と `error` は、ちょうど片方だけ書く。** **決まりに無いキーは書かない**——書いても生成物に現れないので、検査が落とす。
**`input`・`expected`・`error` の代わりに `trace` を書いたケースは、トレースのケースである**（下の「トレースのケース」）。**機能には入出力のケース（`trace` でないもの）を 1 つ以上置く**——性能テストはその入力を使う。

実装は、`input` を受け取って、正常なら `expected` と等しいオブジェクトを、失敗なら
`{"error": "<エラーの名前>"}` を返す。**Red テストはこの等しさと、各項目の型を見る**
（`True == 1 == 1.0` なので、等しさだけでは `boolean` に `1` を返す実装が通る。`number` は整数でも小数でもよい。`nullable` の項目が `null` のときは型を見ない）。

## トレースのケース（`trace`。#923）

**形式検査（Formal Checker）が範囲の中で出した反例の実行順を、実装の上で再現する Red テストにする。** 並行のテストを流すだけでは、
反例の順はめったに起きない——**実装の口で順を強制する**。仕様を直して反例が消えた後も、そのトレースが「同じ順で同じ誤りを起こさない」ことを確かめる回帰になる。
仕様の側では、spec-review が反例のトレースを仕様のテストケースとして書く（spec-review の `SKILL.md` の手順 4「仕様を直す」）。ここにはそれを写す。

```json
{"id": "F-003-C2", "title": "同じ品を同時に引き当てても売り越さない", "ref": "R-F3",
 "trace": {
   "formal": "stock-reserve",
   "setup": [{"operation": "set_stock", "input": {"item": "a", "qty": 1}, "expected": {"stock": 1}}],
   "calls": {"first": {"operation": "reserve", "input": {"item": "a", "qty": 1}},
             "second": {"operation": "reserve", "input": {"item": "a", "qty": 1}}},
   "steps": [["first", "read"], ["second", "read"], ["first", "write"], ["second", "write"]],
   "outcomes": [{"ok": true}, {"error": "OUT_OF_STOCK"}],
   "after": [{"operation": "get_stock", "input": {"item": "a"}, "expected": {"stock": 0}}]}}
```

| キー | 書くもの |
| --- | --- |
| `formal` | 反例を出した形式検査の対象の名前——重ね合わせた全体の `spec/formal/<対象>/README.md` が在ること（`tree.md` の「形式検査のモデル」。名前は英小文字・数字・ハイフン） |
| `calls` | 同時に走る呼び出し（2 つ以上）。呼び出しの名前（英小文字で始まり英小文字・数字・`_`）→ `{"operation": <入口の id>, "input": <入力>}`。入口は**重ね合わせた全体の中間表現のどの機能の入口でもよい**（書き手と読み手が別の機能のとき）。入力はその入口の `input` の項目をちょうど全部 |
| `steps` | トレース——`[呼び出しの名前, 段の名前]` の並び（2 つ以上）。**段はモデルの行為**（在庫を読む・書く、など）で、名前は英小文字で始まり英小文字・数字・`_`。`calls` の呼び出しはどれも 1 回以上出る |
| `setup` | （任意）呼び出しの前に順に呼ぶもの——`{"operation", "input", "expected" か "error"}` の配列（1 つ以上）。初めの状態を作る |
| `outcomes` | （任意）呼び出しの結果——`calls` と同じ数の、`expected` の形か `{"error": <名前>}` の配列。**どの呼び出しがどれを返すかは問わない**（多重集合として比べる——正しい実装でも、どれが先に通るかは順で変わる） |
| `after` | （任意）呼び出しが全部終わった後に順に呼んで確かめるもの（`setup` と同じ形）。**`outcomes` と `after` の少なくとも片方を書く** |

**ケースの `id`・`title`・`qa`・`ref` は入出力のケースと同じ決まり**で、`input`・`expected`・`error` は書かない。

### 実装に求める口

トレースのケースを持つ機能の Red テストは、実装に次の口を求める（Issue の本文の `## Red テスト` にも出る）:

| 口 | 書くもの |
| --- | --- |
| `checkpoint` | `calls` の呼び出しの入口の関数が受け取るキーワード引数（既定は何もしない関数。`setup`・`after` の呼び出しには渡さない）。**トレースの段の全部について、その段の操作の直前に `checkpoint("<段の名前>")` を呼ぶ**——結果で書かない分岐（在庫が足りず書かずに返す、など）でも、その段の前で呼ぶ。**その段のために排他を取る前に呼ぶ**（テストは呼び出しを `checkpoint` で止めるので、排他の内側で呼ぶと、止められている間ほかの呼び出しが排他で待ち、トレースの順に進められない）。**先にまとめて呼ばない**——続けて呼んでよいのは、1 回の原子的な操作で読むと書くをまとめる実装が、その操作の直前に呼ぶときだけ。1 回も呼ばない・段を飛ばして終わる・トレースの順で次の段と違う段に来る呼び出しがあれば、順を強制できないので失敗にする（口を無視する・一部の段だけに呼ぶ・名前を違える競合する実装を素通りさせない） |
| `reset_state` | `impl_module` のモジュールの関数。状態を空に戻す。トレースのケースのテストの初めに呼ぶ |

**口は手段ではなく観測点である**——段の名前は仕様（モデル）の行為の名前で、実装は段の前で知らせるだけ。排他の取り方・書き方は決めない。
**入口の名前に `reset_state`、トレースが呼ぶ入口の入力の項目に `checkpoint` は使えない**（口と重なる。生成のスクリプトが止める）。

### Red テストが確かめること

1. `reset_state()` を呼び、`setup` を順に呼んで期待と比べる。
2. `calls` の呼び出しをスレッドで同時に走らせ、`checkpoint` で止めて、`steps` の順に 1 段ずつ進める
   （進めた呼び出しが次の段に来るか終わるまで、ほかを進めない）。
3. **その呼び出しが決まった時間（1 段 2 秒）のうちに段に来ない**（排他を待っている）なら、**その順にはならないと読んで、順の強制をやめて全部を走らせる。**
   正しい実装はどの順でも正しいので、これで緑になる。**段に来ずに終わった・トレースの順で次の段と違う段に来た**なら、そこで順の強制をやめ、
   全部の呼び出しが終わった後に失敗にする（口の約束——段の全部について、その段の前で呼ぶ——を守っていない）。
4. 全部の呼び出しが終わったら（上限 60 秒。超えれば固まったと読んで失敗）、例外・`checkpoint` を呼ばなかった呼び出し・3 の段に来なかった呼び出しを失敗にし、`outcomes` を多重集合として、`after` を順に比べる。

**競合する実装**（排他で守らない）はトレースの順を最後まで進められ、反例と同じ誤りの結果になって失敗する。
**守らないこと**: 負荷で呼び出しが 1 段の時間より遅れると、順の強制をやめるので、競合する実装を見逃すことがある。
**口の約束を破る競合する実装**——段の `checkpoint` を排他の内側で呼ぶ・先にまとめて呼んでから操作する——**も見逃しうる**（機械では約束を守ったかを見分けられない。止められた呼び出しが排他を持っていると、ほかが来ないのを排他待ちと読む）。
**口の約束を守る正しい実装を失敗にすることは無い**——ただし、テストは呼び出しを段で止めたまま（排他を持ったまま）ほかを最大 1 段の時間待たせるので、
**排他を待つ時間に上限を持ち、待てなければ段を呼ばずに返す実装**は、その間に待ちを打ち切って失敗になる（段を呼ばずに終わる——3）。
Red テストは Python の `unittest` で、スレッドで走らせる——プロセスの外の状態（データベースなど）で競合する実装も、`checkpoint` を呼べば同じ形で順を強制できる。

## 書き起こすときの決まり

- **仕様に書いていないことを足さない。** ケースは仕様のテストケース（`spec-exit.md` の条件 3）から写す。
  足したくなったら、仕様のほうを直す（利用者に見える結果が変わるなら共有の Q&A 表に起票する）。
- **決まっていないことを、もっともらしい値で埋めない。** 書けないなら仕様が確定していない——`spec-review` に戻す。
