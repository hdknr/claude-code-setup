# 仕様の中間表現（`docs/spec/spec_ir.json`）

確定した仕様（`docs/spec/`。抜ける条件は `spec-exit.md`）を、**機械で読める形**に書き起こしたもの。
`scaffold` がこれを書き、同梱のスクリプトがここから OpenAPI・型・Red テスト・Issue の本文を作る。

**書き起こすのは判断、そこから先は答えが一意に決まる。** 仕様を JSON にするのは `scaffold`（LLM）の仕事で、
生成はスクリプトが行う。だから**この JSON に書いていないことは、生成物にも Issue にも現れない**。

決まりどおりかどうかは、生成のスクリプトが生成の前に確かめる（通らなければ 1 バイトも書かない）:

```bash
python3 <spec-loop の base ディレクトリ>/scripts/scaffold.py --repo <正本リポジトリ> --dry-run
```

## ファイル

- 文字コードは UTF-8。JSON のオブジェクト 1 つ。
- 置き場所は `tree.md`。**`docs/spec/` の中に置く**ので、未決定の印（`spec-exit.md`）の検査はこのファイルにも掛かる。

## 全体

| キー | 書くもの |
| --- | --- |
| `spec_ir_version` | `1` |
| `title` | 仕様の題（空にしない・1 行で） |
| `features` | 機能の配列（1 つ以上） |

**どの文字列にも、孤立したサロゲート（`"\ud800"` のような、JSON として読めるが UTF-8 で書けない文字）を入れない**——キーも値も。

## 機能（`features` の要素）

**1 機能が Issue 1 件になる。**

| キー | 書くもの |
| --- | --- |
| `id` | `F-` に 3 桁以上の数字（`F-001`）。重複させない |
| `title` | 機能の名前（空にしない・1 行で）。Issue の題になる |
| `source` | この機能を書いた仕様のファイルの配列（1 つ以上）。正本リポジトリの根からのパスで、**`docs/spec/` の中の実在するファイル**。**`.` で始まるディレクトリ・ファイルは指さない**（未決定の印の検査がそこを見ない） |
| `qa` | この機能の決定の根拠にした Q&A の `No` の配列（空でもよい）。**Q&A 表に実在し、状態が `反映済み`** |
| `operation` | 入口 1 つ（下） |
| `cases` | テストケースの配列（1 つ以上）。**1 ケースが Red テスト 1 本になる** |

## 入口（`operation`）

| キー | 書くもの |
| --- | --- |
| `id` | 関数名にもなる名前。英小文字で始まり、英小文字・数字・`_` だけ（`calc_discount`）。Python の予約語（`class`・`from` など）は使わない。全機能で重複させない。**`_` を外して語頭を大文字にした名前（型の名前。`calc_discount` → `CalcDiscount`）も重複させない**（`a_1` と `a1`） |
| `method` | 下の「メソッド」のどれか |
| `path` | `/` で始まる 1 行 |
| `input` | 入力の項目（下の「項目」）。空のオブジェクトでもよい |
| `output` | 正常時に返す項目（下の「項目」）。1 つ以上。**`error` という項目は置かない**（失敗の形と見分けられない） |
| `errors` | 失敗時に返すエラーの名前の配列（空でもよい）。英大文字で始まり、英大文字・数字・`_` だけ（`INVALID_RANK`）。重複させない |

`method` と `path` の組は全機能で重複させない。

### メソッド

| メソッド |
| --- |
| `GET` |
| `POST` |
| `PUT` |
| `PATCH` |
| `DELETE` |

### 項目

`{"<項目名>": {"type": "<型>", "enum": [...]}}` の形。項目名は英小文字で始まり、英小文字・数字・`_` だけで、Python の予約語は使わない。
`enum` は省いてよく、書くなら 1 つ以上の値を、その型で、重複させずに並べる。

| 型 | 値 |
| --- | --- |
| `string` | 文字列 |
| `integer` | 整数（`true`・`false` は整数に数えない） |
| `number` | 数（整数でもよい。`true`・`false`・`NaN`・`Infinity` は数に数えない） |
| `boolean` | `true`・`false` |

**入れ子のオブジェクト・配列・null は、いまは持たない。** 要るなら、この決まりを先に広げる。

## テストケース（`cases` の要素）

| キー | 書くもの |
| --- | --- |
| `id` | 機能の `id` に `-C` と数字（`F-001-C1`）。全機能で重複させない |
| `title` | 何を確かめるか（空にしない・1 行で） |
| `input` | 入力。**`operation.input` の項目をちょうど全部**、その型（と `enum`）で |
| `expected` | 正常時に返すもの。**`operation.output` の項目をちょうど全部**、その型（と `enum`）で |
| `error` | 失敗するケースなら、`expected` の代わりに `operation.errors` のどれか |
| `qa` | このケースの根拠にした Q&A の `No` の配列（省いてよい）。機能の `qa` と同じ決まり |

**`expected` と `error` は、ちょうど片方だけ書く。** **決まりに無いキーは書かない**——書いても生成物に現れないので、検査が落とす。

実装は、`input` を受け取って、正常なら `expected` と等しいオブジェクトを、失敗なら
`{"error": "<エラーの名前>"}` を返す。**Red テストはこの等しさと、各項目の型を見る**
（`True == 1 == 1.0` なので、等しさだけでは `boolean` に `1` を返す実装が通る。`number` は整数でも小数でもよい）。

## 書き起こすときの決まり

- **仕様に書いていないことを足さない。** ケースは仕様のテストケース（`spec-exit.md` の条件 3）から写す。
  足したくなったら、仕様のほうを直す（利用者の判断が要るなら Q&A 表に起票する）。
- **決まっていないことを、もっともらしい値で埋めない。** 書けないなら仕様が確定していない——`spec-review` に戻す。

## 例

```json
{
  "spec_ir_version": 1,
  "title": "注文",
  "features": [
    {
      "id": "F-001",
      "title": "注文の割引額を計算する",
      "source": ["docs/spec/order.md"],
      "qa": ["Q-001"],
      "operation": {
        "id": "calc_discount",
        "method": "POST",
        "path": "/orders/discount",
        "input": {"rank": {"type": "string", "enum": ["silver", "gold"]}, "amount": {"type": "integer"}},
        "output": {"discount": {"type": "integer"}},
        "errors": ["INVALID_AMOUNT"]
      },
      "cases": [
        {"id": "F-001-C1", "title": "シルバーで 10000 円未満は割引なし",
         "input": {"rank": "silver", "amount": 9999}, "expected": {"discount": 0}, "qa": ["Q-001"]},
        {"id": "F-001-C2", "title": "金額が負なら拒否する",
         "input": {"rank": "gold", "amount": -1}, "error": "INVALID_AMOUNT"}
      ]
    }
  ]
}
```
