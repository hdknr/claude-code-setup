# 仕様の中間表現（`docs/v<n>/spec/spec_ir.json`）

確定した仕様（`docs/v<n>/spec/`。抜ける条件は `spec-exit.md`）を、**機械で読める形**に書き起こしたもの。
`scaffold` がこれを書き、同梱のスクリプトがここから OpenAPI・型・Red テスト・Issue の本文を作る。

**書き起こすのは判断、そこから先は答えが一意に決まる。** 仕様を JSON にするのは `scaffold`（LLM）の仕事で、
生成はスクリプトが行う。だから**この JSON に書いていないことは、生成物にも Issue にも現れない**。

決まりどおりかどうかは、生成のスクリプトが生成の前に確かめる（通らなければ 1 バイトも書かない）:

```bash
python3 <spec-loop の base ディレクトリ>/scripts/scaffold.py --repo <正本リポジトリ> --dry-run
```

## ファイル

- 文字コードは UTF-8。JSON のオブジェクト 1 つ。
- 置き場所は `tree.md`。**版の `spec/` の中に置く**ので、未決定の印（`spec-exit.md`）の検査はこのファイルにも掛かる。
- **v2 以降は、その版で足した・変えた機能だけを書く**（`features` 以外のキーは省いてよい）。消すのは `removed.csv`。
  **下の決まりは、版を重ね合わせた全体に当てる**（重ね方は `versions.md`。生成のスクリプトが自分で重ねる）。

## 全体

| キー | 書くもの |
| --- | --- |
| `spec_ir_version` | `1`（整数。`1.0` は不可） |
| `title` | 仕様の題（空にしない・1 行で） |
| `features` | 機能の配列（1 つ以上） |
| `impl_module` | （任意）実装を置く Python のモジュール名（`app.core` の形）。省けば `spec_impl`。**Red テストと Issue の本文はこれを指す**——引数ではなくここに書くので、作り直しても変わらず、`--check` もこれで比べる |

**どの文字列にも、孤立したサロゲート（`"\ud800"` のような、JSON として読めるが UTF-8 で書けない文字）を入れない**——キーも値も。

## 機能（`features` の要素）

**1 機能が Issue 1 件になる。**

**どの目的のための機能かは、中間表現に持たない**（#1154）——目的の表（`requirements/purposes.csv`。`tree.md` の「目的と成功の判定」）の指標の行が `機能` の列で機能一覧の `id` を指す。
機能から目的へは、`id`（機能一覧と同じ番号）で指標の行を引き、その `上位` の目的を辿る。結び付けの欠け（目的を指さない機能）は scaffold の関門（`check-design-csv.py`）が止める。

| キー | 書くもの |
| --- | --- |
| `id` | `F-` に 3 桁以上の数字（`F-001`）。重複させない。**機能一覧（`requirements/features.csv`）があれば、その `id` と同じ番号にする**——入口の機能が一覧に無い・一覧の id が中間表現に無いと、生成のスクリプトが止まる（`tree.md` の「機能一覧と中間表現の照合」。#957） |
| `title` | 機能の名前（空にしない・1 行で）。Issue の題になる |
| `source` | この機能を書いた仕様のファイルの配列（1 つ以上）。**重ね合わせた全体の根からのパス**（`spec/order.md`。版のディレクトリのパス `docs/v1/spec/order.md` ではない——後の版で変えても指し先が動かないように）で、**重ね合わせた全体の `spec/` の中の実在するファイル**。**`.` で始まるディレクトリ・ファイルと、形式検査のモデル（`spec/formal/` の中。`tree.md` の「形式検査のモデル」）は指さない**（未決定の印の検査がそこを見ない。scaffold が断る） |
| `qa` | この機能の決定の根拠にした Q&A の `No` の配列（空でもよい）。共有の表の `Q-` も内部の表（`spec/qa-dev.csv`）の `D-` も指せる。**その表に実在し、状態が `反映済み`**。**`暫定反映` は指さない**——利用者が確かめていない回答を開発へ渡さない（scaffold はサインオフの照合を通らない。`qa-csv.md`）。**指していなくても、`暫定反映` の行が表に残れば scaffold は止まる**——仕様には反映されているので、どの機能に効いているかを中間表現からは決められない。**例外は、利用者が仮回答のまま渡すと決めて `scaffold.py --provisional` で作るときだけ**——`暫定反映` の行を指してよく、**効く機能とケースの全部から指す**（どこからも指されない `暫定反映` の行が残れば止まる。指し漏らした機能の本文には仮回答の印が付かない。`handoff-issue.md` の「仮回答の印」。#875） |
| `operation` | 入口 1 つ（下） |
| `cases` | テストケースの配列（1 つ以上）。**1 ケースが Red テスト 1 本になる** |
| `called_by` | （任意）**この機能が他の機能から呼ばれる判定の関数なら**、呼ぶ機能の `id` の配列（1 つ以上）。下の「呼ばれる機能」 |
| `out_of_scope` | （任意）**この機能に関わる範囲の外の行**の原文の配列（1 つ以上）。下の「作らないもの」 |
| `acceptance` | （任意）**関数の 1 回の呼び出しでは表せず、Red テストにしないケース**の、仕様の行の原文の配列（1 つ以上）。下の「Red テストにしない受入基準」 |
| `nfr` | （任意）**この機能に効く性能の要求**——`shared/nfr.csv` の行の `No` の配列（1 つ以上）。下の「性能の要求」 |
| `branches` | （任意）**この機能の呼ぶ側の分岐**——分岐の名前から、見せるもの（`shows`）か該当なし（`none`）の仕様の原文への対応。下の「呼ぶ側の分岐」 |
| `refs` | （任意）**この機能に関係する参考資料**——UI モック・業務フローの図・画面遷移の図など、`requirements/` の中のファイルのパスの配列（1 つ以上）。下の「参考資料」 |

## 呼ばれる機能（`called_by`。#609）

**仕様が、機能を「API・画面・バッチから呼ばれる判定の関数」として書いている**（「この関数を呼ぶ側は、ここでは定めない」のように）なら、
その機能の `called_by` に**呼ぶ機能**——その関数を呼ぶ入口の機能——の `id` を書く。

- **呼ぶ機能も、中間表現に機能として書き起こす。** 関数だけを Issue にすると、それを呼ぶ入口（API がクエリを受けて関数を呼ぶ・応答に欄を足す）が
  どの Issue にも載らず、関数がマージされても利用者からは使えない（#609）。呼ぶ側の振る舞いは、呼ぶ機能のケース（Red テスト）に書く——呼ぶ機能が変わらない版では、その版の Red テストは呼ぶ側を新しく確かめない（下の知らせ）。
- **仕様が呼ぶ側の振る舞いを書いていなければ、仕様が確定していない**——呼ぶ機能をもっともらしく足さず、`spec-review` に戻す。
- **`called_by` の各 `id` は、重ね合わせた全体の中間表現に在る機能**でなければならない。自分自身・重複・空の配列は書かない。
  **呼ぶ関係は循環させない**（辿った先に、`called_by` を持たない入口の機能が要る）。どれかに反すれば、生成のスクリプトは止まる（1）。
  **呼ぶ機能を `removed.csv` で消すなら、`called_by` からも外す**（外さなければ止まる）。
- **`called_by` を書かない機能は、入口（API・画面・バッチ）と読む。** 機械は申告の整合だけを見る——関数に `called_by` を書かなければ通る。
- **v2 以降で、`called_by` を持つ機能を足す・変えるのに、呼ぶ機能をどれもその版で足さず変えていなければ、生成のスクリプトは止めずに名指しで知らせる**（0）。
  関数の中だけの直しはありうるので止めないが、**呼ぶ入口の振る舞いも変わるなら、仕様にその入口の変化を書き、この版の中間表現でも変える**
  ——書かなければ、呼ぶ側の課題がどの Issue にも載らない。
- `called_by` を v2 で足す・外すだけでも、その機能は変更になる（機能のオブジェクトが変わる。ケースは全部 `回帰`）。
- Issue の本文の `## 仕様` に、呼ぶ機能の `id` と題が載る（`handoff-issue.md`）。

## 作らないもの（`out_of_scope`。#851）

**範囲の文書（`spec/scope.md`。`spec-scope.md`）の「範囲の外」の節の行のうち、その機能に関わるもの**——その機能を作る人が、
範囲の外として作らずにおくべき場面——を、機能の `out_of_scope` に**行の原文のまま**並べる。Issue の本文の `## 作らないもの` に写る
（`handoff-issue.md` の「作らないもの」。「次の版の候補」を含む行はそちらの小見出しに分かれる）。

- **原文のまま書く**——重ね合わせた全体の `spec/scope.md` の、見出しに「範囲の外」を含む節の 1 行と、前後の空白を落として一致する文字列。
  表の行なら `| ディスクがいっぱい | 失敗を見せる | 既定の線 |` のような本文の 1 行をそのまま（**表の見出しと区切りの行は挙げない**——本文には生成のスクリプトが付ける）。
  **要約・言い換え・複数行は書かない。** 範囲の文書の行を直したら、ここも同じ文字列に直す（直さなければ生成のスクリプトが止まる）。
- **1 つ以上・重複させない。** 関わる行が無い機能には書かない（本文には「無い」と出る）。
- **どの行が関わるかは書き起こす側の判断**で、機械は原文が在ることだけを見る——関わらない行を挙げても、関わる行を落としても通る。
  **範囲の文書に無い場面を足さない**（足したくなったら `spec-review` に戻して範囲の文書に書く）。
- **`out_of_scope` を v2 で足す・変える・外すだけでも、その機能は変更になる**（機能のオブジェクトが変わる。ケースは全部 `回帰`。`called_by` と同じ）。

## Red テストにしない受入基準（`acceptance`。#1301）

**画面の振る舞い・障害・同時・時間のケースは、関数の 1 回の呼び出し（`input` → `expected`）では表せない。** 表せないケースを書き起こさなければ、
**この JSON に書いていないことは生成物にも Issue にも現れない**ので、仕様レビューで確かめたケースの大半が開発に渡らない。
そのケースを、機能の `acceptance` に**仕様の行の原文のまま**並べる——Issue の本文の `## 受入基準` の中の `### Red テストにしない受入基準` に写る
（`handoff-issue.md` の「Red テストにしない受入基準」）。**Red テストにはならない**——確かめるのは dev-loop の周で、確かめる手段が無ければ dev-loop は縮退の線のとおり BLOCKED にする
（dev-loop の規定は変えない）。

```json
"acceptance": ["| F1-7 | 注文確定の画面で確定を 2 回押す | 注文は 1 件だけ作られ、2 回目の押下は無視される |"]
```

- **原文のまま書く**——機能の `source` の仕様のファイルの 1 行と、前後の空白を落として一致する文字列。表の行なら本文の 1 行をそのまま（**表の見出しと区切りの行は挙げない**——本文には生成のスクリプトが表の見出しを付ける）。
  **要約・言い換え・複数行は書かない。** 仕様の行を直したら、ここも同じ文字列に直す（直さなければ生成のスクリプトが止まる）。**見出しの行（`#`）・表の見出しの行・区切りの行は挙げられない**（`out_of_scope` と同じ読み方で除く）。
- **1 つ以上・重複させない。** 関わるケースが無い機能には書かない（本文にこの小見出しは出ない）。
- **どの行を Red テストにせず `acceptance` に並べるかは書き起こす側の判断**で、機械は原文が在ることだけを見る。**仕様に無いケースを足さない**
  （足したくなったら `spec-review` に戻して仕様のテストケースに書く）。
- **仕様のケースの数え方は、テストケースの番号の形（`spec-exit.md` の「テストケースの番号の重複」。`CASE_NUMBER`・`CASE_HEADER`・テストケースの節の `ID_HEADER`）と同じ**——仕様（`spec/`）の `.md` の、見出しがテストケースの表の表（テストケースの節の中の `ID`・`No`・`項番` の表を含む。#1333）のデータ行の先頭のセルが番号である。
  **`acceptance` に並べた行がその表の行なら、先頭のセルの番号のケースが受入基準になる。** **ケースの `ref`（上の「テストケース」）が番号と一致すれば Red テストになる。**
- **生成のスクリプトは、仕様のケースの内訳を出す**——`仕様のテストケース N 件のうち、Red テスト a 件・受入基準 b 件・どちらにも無い c 件`。**Red テストと受入基準の両方に当たるケースは Red テストに数える。**
  **どちらにも無いケースは、番号と出た場所（`ファイル:行`）を全部名指しする**（1 件でもあれば名指しし、0 件なら `どちらにも無い 0 件` と出る）。**止めない**（終了コードは変わらない）——
  Red テストにする（ケースの `ref` に番号を書く）か、`acceptance` に並べるか、仕様から外すかは書き起こす側が決める。
  **数えるのは重ね合わせた全体の仕様のケース全部**で、機能ごとには数えない。`ref` を書いていない Red テストのケースは数えない（仕様のケースと結べない）。
  番号の形に当たらない行（`acceptance` に並べても、番号の無い行）は内訳の数に入らず、出力にその行数だけを書く。
- **`acceptance` を v2 で足す・変える・外すだけでも、その機能は変更になる**（機能のオブジェクトが変わる。ケースは全部 `回帰`。`out_of_scope` と同じ）。
  **`acceptance` を書かない中間表現の生成物（Issue の本文・`scaffold/`）は、この決まりを足す前と同じバイトである**（出力に内訳の 1 行が足されるだけ）。

## 書き起こす前の見積もり（#1302）

**中間表現を書き起こす前に、仕様のテストケースを 3 つに分けて数え、利用者に示して続けるかを確かめる**（`scaffold` スキルの手順 1a）。
#1296 では、仕様のケースのほとんどが中間表現に乗らないことに**書き起こしの途中で**気づいた——乗らない割合は、書き起こす前に分かる。

| 区分（`class`） | 意味 | 書き起こしたときの行き先 |
| --- | --- | --- |
| `red` | **Red テストにできる**——関数の 1 回の呼び出し（`input` → `expected`）か、この文書の形のどれかで書ける: 前提と後の状態（`setup`・`after`・`seed`。#1298）・実行ごとに変わる出力（`$any`・`$ref`。#1299）・配列と入れ子のオブジェクト（#1300）・トレースのケース（`trace`。#923） | ケースの `ref` に番号を書く |
| `acceptance` | **Red テストにできず、受入基準に回す**——画面の振る舞い・障害・同時・時間など、上の形でも書けない（#1301） | 機能の `acceptance` に行を原文のまま並べる |
| `neither` | **どちらにもできない**——期待が書かれていない・書いてあることが決まっていない・番号の行が仕様の別の行と食い違う、など、**仕様のほうを決めないと書き起こせない** | 書き起こさない——`/spec-loop:spec-review` に戻して仕様で決めるか、仕様から外す（`neither` は利用者と決める） |

- **どれに分けるかは書き起こす側（スキル）の判断**で、**分けた理由を `acceptance`・`neither` の `reason` に 1 行で書く**。機械は決めない——
  **「乗る割合」は Red テスト + 受入基準（開発に渡るケース）の割合で、Red テストだけの割合も併記する。**
  機械で決まるのは、仕様のケースの一覧（`scaffold-estimate.py list`。番号の形は「Red テストにしない受入基準」と同じ）と、
  分け方の**形と網羅**（`scaffold-estimate.py check`。全ケースを 1 つずつ分けたか・仕様に無い番号を分けていないか）と、分けたとおりの**件数と割合**である。
- **見積もりのファイルは `build/scaffold-estimate.json`**（正本の中の `build/`。commit しない。形は `scaffold-estimate.py` の docstring）。
- **結果（分けた件数・乗る割合・どちらにもできないケースの番号と場所）を利用者に示し、続けるかを確かめてから、中間表現の書き起こしに入る。**
  **どちらにもできないケースが 1 件でもあれば、それを名指しして、書き起こす前に決める**——書き起こしの後の内訳（`scaffold.py` の「どちらにも無い」）に初めて現れるのと違い、
  書き起こす前なら、仕様に戻す・外すがまだ安い。
- **止める割合の線（閾値）は決めていない。** 割合に依らず、結果は毎回利用者に示して続けるかを確かめる。理由は 2 つ:
  - **根拠になる実測が 1 点しかなく、今の定義では 0 点**——#1296 の実測は、1 案件（636 件）の 1 ファイル（113 件）を試して、素直に書けた（Red テストにできた）のが 15 件（13%）という値で、
    #1298〜#1301 で書ける形を足す前の、Red テストだけの割合である。この節の「乗る割合」（Red テスト + 受入基準）で測った値は手元に無く、分布も持たない。数字を決めれば、その下は止まり、上は素通りになる。
  - **線を引いても、示すかどうかが変わるだけ**——示して確かめる操作は軽く、線の上で素通りして書き起こしの途中で気づく形（#1296）をまた作る。

  **Red テストだけの割合（併記する値）には、線を引かない理由がもう 1 つある**——その割合は仕様の性質で変わる（画面中心の仕様は低く、計算中心の仕様は高い）ので、一律の線を引くと、どちらかの仕様で誤る。
  受入基準まで含めた乗る割合（1 −『どちらにもできない』の割合）には、この理由は当たらない——乗る割合に線を引かない理由は上の 2 つ（実測が無い・示すかどうかが変わるだけ）である。

  実案件で見積もりと書き起こしの後の内訳を比べ、線を引ける形が見えたら、このファイルに根拠と一緒に書く。
- **見積もりと書き起こしの後の内訳は突き合わせない**（`scaffold.py` の内訳は `ref` と `acceptance` から数える。見積もりは判断の記録で、機械は照合しない）。

## 性能の要求（`nfr`。#852）

**性能の要求の表（`shared/nfr.csv`。列は `nfr.md`）の性能の行のうち、その機能に効くもの**の `No` を、機能の `nfr` に並べる。
Issue の本文の `### 性能予算` に行の数字が写り、性能テスト `scaffold/perf/perf_<機能>.py` が作られる（`handoff-issue.md` の「作らないもの」・`nfr.md`）。

- **指す行は、重ね合わせた全体の `shared/nfr.csv` に 1 行だけ在り、性能の行の形**（`指標` が `p50`・`p95`・`p99`・`最大` のどれか・`上限` が正の数・`単位` が `ms`・
  `対象`・`条件`・`根拠` が空でない 1 行）**でなければならない**。反すれば生成のスクリプトは止まる（1）。**指していない行は見ない**。
- **1 つ以上・重複させない。** 効く行が無い機能には書かない（本文の性能予算は「要求なし」——`nfr.md` の「既定の原則」）。
- **どの行が効くかは書き起こす側の判断**で、機械は行の在ることと形だけを見る。**表に無い数字を足さない**（足したくなったら `spec-review` に戻す）。
- **`nfr` を v2 で足す・変える・外すだけでも、その機能は変更になる**（`out_of_scope` と同じ）。**行の数字だけを変えても機能は変わらない**——
  数字を変えるときは新しい `No` の行にし、`nfr` を差し替える（`nfr.md` の「列」）。

## 参考資料（`refs`。#951）

**仕様（`spec/`）は守るべき性質とテストを書くので、画面の見た目・配置や機能どうしのつながりは落ちる。** 利用者向けの要求（`requirements/`）にある
UI モック・業務フロー（BPMN の書き出し。`tree.md` の「業務フロー（BPMN）」）・画面遷移の図のうち、その機能に関係するものを `refs` に並べる。
Issue の本文の `## 参考資料` にパスが載り、写しが契約 `scaffold/refs/` に置かれる（`handoff-issue.md` の「参考資料」・`tree.md` の「scaffold の出力」）。

```json
"refs": ["requirements/mocks/注文.html", "requirements/flows/受注.svg"]
```

- **重ね合わせた全体の根からのパス**（`source` と同じ形。版のディレクトリのパス `docs/v1/requirements/…` ではない）で、**重ね合わせた全体の `requirements/` の中に、その綴りのまま在るファイル**
  （大文字小文字も同じ。`./`・`../` を含めない）。**`.` で始まるディレクトリ・ファイルと、名前にバッククォート・`\` を含むファイルは指さない**（本文と写しの目録に書けない）。1 つ以上・重複させない。反すれば生成のスクリプトは止まる（1）。
- **参考資料は受入基準ではない**——受入基準は Red テストのまま。モックの見た目を受入基準にしたいなら、仕様（`spec/`）とケースに書く（`spec-review` に戻す）か、
  デザインの正本を参照に置く（`tree.md` の「デザインの正本の参照」。dev-loop が確かめる——中間表現には書かない）。
- **どのファイルが関わるかは書き起こす側の判断**で、機械は在ることだけを見る。関わるファイルが無い機能には書かない（本文には「無い」と出る）。
  **ファイルの形式は問わない**（`.svg`・`.html`・`.png`・`.pdf` など）。図は書き出し（`.svg`）を指す——ソース（`.drawio`・`.bpmn`）は開発する側の手元で開けるとは限らない。
  UI モックの形式と置き場所（`requirements/mocks/`）は `tree.md` の「UI モック」を正とする——React のモック（ディレクトリ）は、入口の `index.html` とソースの `.jsx` をそれぞれ並べる（`refs` はファイルを指す）。
- **`refs` を v2 で足す・変える・外すだけでも、その機能は変更になる**（機能のオブジェクトが変わる。ケースは全部 `回帰`。`out_of_scope` と同じ）。
  **参照先のファイルの中身だけを変えても、機能は変わらない**——その版で Issue は作られず、契約の写しだけが新しくなる（古い写しは `--check` が言う）。
- **画面の表（`requirements/screens/`。`tree.md` の「画面の表」）の画面の仕様書・ワイヤーフレーム・生成したモックは `refs` に書かない**——
  画面の表の `機能` の列がその機能を挙げる画面の分を、生成のスクリプトが引いて本文と写しに足す（`handoff-issue.md` の「画面の表から引く参考資料」。#1099）。
  **機能のオブジェクトに入らないので、画面の表や生成したモックが変わっても機能は変更にならない。**

## 呼ぶ側の分岐（`branches`。#855）

**仕様チェックリストの「呼ぶ側の分岐」の行（`spec-exit.md`）を、入口の機能ごとに書き起こす。** 生成のスクリプトは、ここから
**課題一覧（案）**（`tree.md` の「生成物の置き場所」の `proposals.md`）を作る——Red テストは関数の入力と出力しか確かめないので、
入力が遅れる・呼ぶ処理がやり直されるといった結線の振る舞いは Red テストの外に残る。#402 の実案件では、その結線の課題を手で起票し、
仕様の穴を実装役が実装の途中で見つけた。課題一覧（案）は、その課題の案ごとに**未決定事項**（ここに書き起こしていない分岐）・
**受入基準の雛形**（見せるものの原文）・**作らないもの**（Issue の本文の `## 作らないもの` と同じ中身。`handoff-issue.md`）を付けて出す。
**案は Issue の本文ではなく、生成のスクリプトは登録しない**——登録するかは利用者が決める（scaffold の `SKILL.md` の手順 7）。

```json
"branches": {
  "入力が欠ける": {"shows": "- 入力が欠ける: 「データ欠落」と表示する"},
  "入力の順が崩れる": {"none": "- 入力の順が崩れる: 該当なし（1 回の要求で全部そろって届く）"}
}
```

- **鍵は下の「分岐の名前」のどれか**で、値は `{"shows": <原文>}`（見せるもの）か `{"none": <原文>}`（該当なしと理由）の**どちらか 1 つ**。
  **行ごと該当なし**（入力も呼び出しも外と結ばない純粋な計算。`spec-exit.md` の「呼ぶ側の分岐」）は `{"none": <原文>}` **だけ**を書く（分岐の鍵と混ぜない）。
- **原文は、機能の `source` のどれかの 1 行**——前後の空白を落として一致する文字列（表の行ならその行をそのまま）。**要約・言い換え・複数行は書かない。**
  仕様の行を直したら、ここも同じ文字列に直す（直さなければ生成のスクリプトが止まる）。**その行がその分岐を決めているかは書き起こす側の判断**で、機械は原文が在ることだけを見る。
- **仕様が決めていない分岐は書かない**——課題一覧（案）の未決定事項に出る。**もっともらしい見せるものを足さない**（足したくなったら `spec-review` に戻す）。
  `branches` を書かない入口の機能は、8 分岐が全部未決定と出る。**未決定事項があっても生成のスクリプトは止めない**（案は登録しないので。件数を出す）。
- **呼ばれる関数（`called_by` を持つ機能）には書かない**——分岐は呼ぶ入口の機能に書く（書けば生成のスクリプトが止まる）。課題一覧（案）にも呼ばれる関数の案は無い。
- **案を作るのは、作業中の版で追加・変更した入口の機能だけ**——変わっていない機能・撤去する機能の案は無い（案が無ければ「無い」と出る）。
  **`impl_module` を変えただけで変更になった機能（機能のオブジェクトは前の版と同じ）の案も無い**（Issue の本文は作る——`handoff-issue.md`）。
  凍結した前の版を信じずに全部を追加にしたとき（`versions.md` の「前の版の時点が崩れていたら」）は、変わったかを決められないので全部の入口の機能に案を作る。
- **`branches` を v2 で足す・変える・外すだけでも、その機能は変更になる**（機能のオブジェクトが変わり、機能の指紋も変わる。ケースは全部 `回帰`）。
  **`out_of_scope`・`nfr` と違い、Issue の本文の中身は指紋のほかに変わらない**——変わるのは課題一覧（案）である。そのため、変えていない機能に `branches` を書き足すと、
  実装することの無い変更の Issue ができる。**前の版で抜けた機能に、`branches` のためだけに書き足さない**——その版で足す・変える機能に書く。
  **同じ版で Issue を登録した後に書き足すと、その Issue の機能の指紋が合わなくなる**（dev-loop が差し戻す）——未決定事項は登録の前に片づける（scaffold の `SKILL.md` の手順 4）。

`spec-exit.md` の仕様チェックリストの「呼ぶ側の分岐」の 3 組（入力・呼ぶ処理・量）を、分岐ごとに分けたもの。

## 入口（`operation`）

| キー | 書くもの |
| --- | --- |
| `id` | 関数名にもなる名前。英小文字で始まり、英小文字・数字・`_` だけ（`calc_discount`）。Python の予約語（`class`・`from` など）は使わない。全機能で重複させない。**`_` を外して語頭を大文字にした名前（型の名前。`calc_discount` → `CalcDiscount`）も重複させない**（`a_1` と `a1`） |
| `method` | 下の「メソッド」のどれか |
| `path` | `/` で始まる 1 行。**パスの変数**（`/orders/{order_id}`）は `{` と `}` で項目名を 1 つ囲み、**その名前は `input` の項目でなければならない**（下の「パスの変数」） |
| `input` | 入力の項目（下の「項目」）。空のオブジェクトでもよい |
| `output` | 正常時に返す項目（下の「項目」）。1 つ以上。**`error` という項目は置かない**（失敗の形と見分けられない） |
| `errors` | 失敗時に返すエラーの名前の配列（空でもよい）。英大文字で始まり、英大文字・数字・`_` だけ（`INVALID_RANK`）。重複させない |

`method` と `path` の組は全機能で重複させない。

### パスの変数

- **`{…}` の中身は `input` の項目名**。`input` に無い名前・空の `{}`・対にならない `{` `}`・同じパスに同じ変数を 2 度は書かない。
- **変数の名前だけが違うパスを並べない**（`/items/{id}` と `/items/{key}`）。メソッドが違っても——OpenAPI では同じパスになり、無効になる。
- 生成する OpenAPI では、パスの変数は `in: path`・`required: true` のパラメータになり、**クエリ・ボディには重ねない**。
  残りの項目は、`GET`・`DELETE` ならクエリ、それ以外ならボディ（パスの変数を持つ入口では `<型の名前>Body`）に載る。
  **実装の関数には、パスの変数も `input` の項目の 1 つとして渡る**（Red テストと型は変わらない）。
- **この決まりを外すのは 1 箇所だけ**（#319）——`v<n>` を作るときに、**機能を追加・変更・削除に分けるための比べる相手**
  として読む `v<n-1>` の全体。spec-loop 0.13.0 より前の `scaffold.py` はパスの変数を見ずに通したので、凍結した版が反していても
  直せない。比べる相手の中間表現は、分けること・前の版の Red テスト・Issue の本文（前の版を指す行）にしか使わず、OpenAPI を作らない。
  **それ以外——今の版と、`--upto <n-1>` で前の版の時点を作る・確かめるとき——には当てる**（生成するので外せない）。
  **今の版が反していれば、前の版から持ち越した誤りでも止まる**——`v<n>` で直す。

#### 0.13.0 より前に作った `scaffold/` の移行（1 度だけ）

0.13.0 から、パスの変数を持つ入口の OpenAPI が変わった（path パラメータを宣言し、ボディは `<型の名前>Body` を指す。
前の出力は path パラメータを宣言しない、OpenAPI として無効なものだった）。そのため、それより前に作って commit した
`scaffold/` は、**この決まりに合う中間表現でも、中間表現を変えていなくても** `scaffold.py --check`
（と `--check --upto <n-1>`）で古いと言われる。パスの変数を持たない入口だけなら、出力は変わらず、古くもならない。
**中間表現が決まりに反するなら**、古いではなく「決まりに反する」と言われる（下の 2・3）。

下では、次に作る（または作った）版を `v<n>`、その比べる相手を `v<n-1>` と書く——`docs/v<n>/` がまだ無ければ、`v<n-1>` は最新の版である。
**分かれ目は `v<n-1>` の中間表現で、最新の版ではない**（`docs/v<n>/` が既にあると、最新の版は `v<n>` になる）。

1. **`v<n-1>` の中間表現が決まりに合うなら、`docs/v<n>/` を作る前に、`scaffold.py` で作り直して `scaffold/` を
   commit する。** 以後は `--check` が 0 になる。**`docs/v<n>/` を作った後で、`v<n>` が出力を変えているなら、作り直しは
   `v<n>` の時点を書くので、`--check --upto <n-1>` は 1 のまま残る**（書き込みは `--upto` を取れない）——そのときは
   `docs/v<n>/` を **`docs/` の外へ**退けて作り直し、戻す（`docs/` の中に別の名前で置くと、版の名前の形に合わずに止まる）。
2. **`v<n-1>` の中間表現が決まりに反するなら、`v<n-1>` が凍結しているか（`release-v<n-1>` のタグがあるか。`versions.md` の「凍結」）で分かれる。**
    - **凍結していなければ、`docs/v<n-1>/` をその場で直して作り直す**——パスの変数を `input` に足すか、パスから外す。
      v1 しか無い正本リポジトリで v1 をリリースしていなければ、これに当たる。
    - **凍結していれば、次の版 `v<n>` で直す**——`v<n>` の中間表現で同じように直す。`v<n>` は作れる
      （比べる相手の `v<n-1>` には決まりを当てない。上）。**v1 しか無い正本リポジトリも、v1 をリリースしていれば v2 を作って直す。**
3. 2 の凍結しているとき、**`v<n-1>` の時点の `--check --upto <n-1>` は 1 で止まり続ける**（生成するので、決まりを外せない）。
   `versions.md` の「差分の周を始める前に」の 1 つ目はこの版では確かめられないので、**`v<n>` で直してから作り、`--check` で確かめる**。

### 項目

`{"<項目名>": {"type": "<型>", "enum": [...], "nullable": true}}` の形。項目名は英小文字で始まり、英小文字・数字・`_` だけで、Python の予約語は使わない。
`enum` は省いてよく、書くなら 1 つ以上の値を、その型で、重複させずに並べる。
`nullable` も省いてよく、書くなら `true` だけ（下の「null を許す項目」）。
**配列と入れ子のオブジェクトも型にできる**（下の「配列と入れ子のオブジェクト」。#1300）。

| 型 | 値 |
| --- | --- |
| `string` | 文字列 |
| `integer` | 整数（`true`・`false` は整数に数えない） |
| `number` | 数（整数でもよい。`true`・`false`・`NaN`・`Infinity` は数に数えない） |
| `boolean` | `true`・`false` |
| `array` | 値の並び（0 件でもよい）。要素の項目を `items` に書く。順を問うかは `unordered` で書き分ける（下の「配列と入れ子のオブジェクト」） |
| `object` | 名前つきの値。項目を `properties` に書く |

### null を許す項目（#487）

**`"nullable": true` を書いた項目だけが、その型の値か `null` を持てる**——入力にも出力にも書ける（「ラベル無し」を `null` で返す、など）。
**書かない項目は `null` を拒む**（`nullable` を足す前と同じ。生成物も変わらない）。

- **`true` だけを書く。** `false` は書かない——null を許さないなら省く（同じ意味の書き方を 2 つ作ると、機能の指紋が違う値になる。`handoff-issue.md`）。
- **`enum` と一緒に書いてよい。** `null` は `enum` に並べない——`enum` の値はその型のものだけで、`null` は `nullable` が許す。
- **パスの変数（上の「パスの変数」）には書かない**——パスの値は `null` にならない。
- ケースの `input`・`expected` では、その項目に `null` を書ける。
- 生成物では、OpenAPI の schema の `type` が `["<型>", "null"]` になり（`enum` があれば `enum` の最後に `null` を足す）、
  `types.py` の型は `null` を許さないときの型の後ろに ` | None` を足したもの（`str | None`。`enum` があれば `Literal['a', 'b'] | None`）になる。Red テストは、その出力の項目が `None` のときだけ型を見ない（`None` 以外の値の型は今までどおり見る）。

## 配列と入れ子のオブジェクト（#1300）

**一覧を返す入口（「起点 O で読むと 3 件だけ返る」）や、入れ子の応答（ページの情報）は、項目の型に配列と入れ子のオブジェクトを書いて表す。**

```
{"type": "array", "items": <項目>, "unordered": true, "nullable": true}
{"type": "object", "properties": {"<項目名>": <項目>, …}, "nullable": true}
```

- **`items`**（配列。要る）は要素の項目、**`properties`**（オブジェクト。要る・1 つ以上）は項目名から項目への対応。**中の項目も上の「項目」と同じ決まり**——`string`・`integer`・`number`・`boolean`（`enum`・`nullable` を書いてよい）か、
  さらに入れ子の配列・オブジェクト。項目名の形も同じ。
  **`enum` は `string`・`integer`・`number`・`boolean` の項目にだけ書ける**（配列・オブジェクトには書けない）。**`nullable` は配列・オブジェクト・要素・中の項目のどれにも書ける**（`true` だけ）。
- **値**: 配列は JSON の配列で、要素は `items` の決まりに合う。オブジェクトは、**`properties` の項目をちょうど全部**、その型で持つ（`input`・`expected` の項目と同じ）。
- **順を問う・問わない**: **配列は既定で順を問う**——Red テストは、同じ位置の要素どうしを比べる。**`"unordered": true` を書いた配列は順を問わない**——同じ要素が同じ数だけあれば合う
  （並びだけが違う実装も緑になる）。`true` だけを書く（順を問うなら省く。`nullable` と同じ）。**配列にだけ書ける**。
  `unordered` は、その配列の並びだけに掛かる——要素が配列（入れ子）なら、中の配列は自分の `unordered` に従う。**入力（`input`）の項目に書いても、何も変わらない**（Red テストは入力を書いた順のまま渡す）。
- **`nullable` との組み合わせ**: 配列・オブジェクトの項目が `nullable` なら、`null` か、その型の値。要素を `null` にしたいときは `items` に `nullable` を書く。`null` と空の配列・空でないオブジェクトは別の値。
- **`$any`・`$ref`（上の「実行ごとに変わる出力」）との組み合わせ**:
  - **`$any`** は、配列・オブジェクトの中の値（要素・中の項目の値）にも、配列・オブジェクトの項目の値そのものにも書ける。型は**書く場所の項目の型**と同じで、`array`・`object` も書ける
    （配列・オブジェクトの `$any` は、値を見ずに**形——中の型と `nullable`——に合うか**を見る）。
  - **`$ref`** も同じ場所に書ける。**指すのは `as` で束ねた結果の出力の項目**（一番外の項目）で、**指す項目の形と書く場所の項目の形が同じ**でなければ生成が止まる（形は、中の型と要素・項目の構成。`nullable`・`enum`・`unordered` の違いは問わない）。
    **比べるときの順は、書く場所の項目の `unordered` に従う**。
  - **順を問わない配列（`unordered`）の要素の中には、`$any`・`$ref` を書けない**——どの要素に当たるかが決まらない（生成が止まる。順を問うなら書ける）。
    配列の項目そのものに `$any`・`$ref` を書くのは構わない。
- **パスの変数（上の「パスの変数」）には書けない**——パスの値は 1 つの文字列になる。
- **生成物**: OpenAPI の schema は、配列が `{"type": "array", "items": …}`、オブジェクトが `{"type": "object", "required": […], "additionalProperties": false, "properties": …}`
  （`nullable` は上の「null を許す項目」と同じに `type` へ `"null"` を足す）。**`unordered` は OpenAPI の schema に表せないので、出ない**（Red テストだけが見る）。
  `types.py` は、配列が `list[<要素の型>]`、入れ子のオブジェクトが `TypedDict`（名前は、入口の型の名前に `_` と項目名を Pascal にしたものを足したもの（`_` は項目名の Pascal 化では作れないので、`order.item` と `order_item` は重ならない）。配列の要素なら `_Item` を足す。例: `ListNotesOutput_Notes_Item`）で、
  `nullable` は ` | None` を足す。Red テストは、**項目の型の記述（`OUTPUT_TYPES`）に沿って、値を中まで——要素の型・オブジェクトの項目・`null` の可否——比べる**
  （`true` を整数の要素と見ない・足りない項目も余る項目も違反）。**配列・入れ子を 1 つも使わない機能の生成物は、今までと 1 バイトも変わらない。**
- **v2 以降**: 配列・入れ子の項目の型の記述が前の版と違えば（`nullable`・`unordered` の違い、`integer` から `number` に広げただけの違いも）、その項目を期待に持つケースは変更に数える
  （中の型の違いを項目ごとに見分けない。型の名前だけの項目が `integer` から `number` に広がっただけの違いは、今までどおり変化に数えない）。

    _notes.clear()

    if name == "note":
        _notes.append(values)

        return {"error": "UNKNOWN_ORIGIN"}

## テストケース（`cases` の要素）

| キー | 書くもの |
| --- | --- |
| `id` | 機能の `id` に `-C` と数字（`F-001-C1`）。全機能で重複させない |
| `title` | 何を確かめるか（空にしない・1 行で） |
| `input` | 入力。**`operation.input` の項目をちょうど全部**、その型（と `enum`）で（`nullable` の項目は `null` でもよい。上の「null を許す項目」） |
| `expected` | 正常時に返すもの。**`operation.output` の項目をちょうど全部**、その型（と `enum`）で（`nullable` の項目は `null` でもよい） |
| `error` | 失敗するケースなら、`expected` の代わりに `operation.errors` のどれか |
| `qa` | このケースの根拠にした Q&A の `No` の配列（省いてよい）。機能の `qa` と同じ決まり |
| `ref` | このケースの元になった、仕様の中の行の番号（決定表の `R-F10`・テストケースの `F1-5b` など。省いてよい）。**仕様が番号を振っていれば書く**——生成と `--check` が、機能の `source` の原文にその番号が在るかを確かめる（#465。値が一致するかまでは見ない） |
| `setup` | （任意）`input` で本体を呼ぶ前の状態を作る——入口の呼び出し（`{"operation", "input", "expected" か "error"}`）か、入口の無い前提を作る口 `seed` の呼び出し（`{"seed", "values"}`）の配列（1 つ以上）。下の「前提と後の状態」 |
| `after` | （任意）本体を呼んだ後の状態を確かめる——`setup` と同じ形の配列（1 つ以上）。下の「前提と後の状態」 |
| `as` | （任意）本体の結果を名前で束ねる——`after` の期待の `$ref` が指す。`expected` を持つケースだけ。下の「実行ごとに変わる出力」 |

**`expected` の項目の値には、等しさの代わりに `{"$any": <型>}`・`{"$ref": "<名前>.<項目>"}` を書ける**（実行ごとに変わる出力。下の「実行ごとに変わる出力」）。
**`expected` と `error` は、ちょうど片方だけ書く。** **決まりに無いキーは書かない**——書いても生成物に現れないので、検査が落とす。
**`setup`・`after` は入出力のケースにだけ書ける**（トレースのケースの `setup`・`after` は `trace` の中。上と下の「前提と後の状態」「トレースのケース」）。
**`input`・`expected`・`error` の代わりに `trace` を書いたケースは、トレースのケースである**（下の「トレースのケース」）。**機能には入出力のケース（`trace` でないもの）を 1 つ以上置く**——性能テストはその入力を使う。

実装は、`input` を受け取って、正常なら `expected` と等しいオブジェクトを、失敗なら
`{"error": "<エラーの名前>"}` を返す。**Red テストはこの等しさと、各項目の型を見る**
（`True == 1 == 1.0` なので、等しさだけでは `boolean` に `1` を返す実装が通る。`number` は整数でも小数でもよい。`nullable` の項目が `null` のときは型を見ない）。

## 前提と後の状態（`setup`・`after`。#1298）

**入出力のケースは、`input` の 1 回の呼び出しだけでなく、その前の状態（前提）と後の状態を書ける。** 「同じ番号のレコードが既にある」「作る → 取消にする → 同じキーで送り直す」など、
仕様のテストケースが 1 回の呼び出しで書けないものを写すために使う。

- **`setup`**: 本体を呼ぶ前に、書いた順に呼ぶ。入口の呼び出し（`{"operation": <入口の id>, "input": <入力>, "expected": <出力>}`。`expected` の代わりに `"error": <エラーの名前>`）は、
  **重ね合わせた全体の中間表現のどの機能の入口でもよい**（トレースのケースの `setup`・`after` と同じ決まり。入力はその入口の `input` の項目をちょうど全部、期待は `output` の項目をちょうど全部）。
- **`after`**: 本体を呼んで期待と比べた後に、書いた順に呼んで比べる（`setup` と同じ形）。**本体の戻り値では見えない状態**（作った・変えたレコード）を、読む入口で確かめる。
- **`seed`**: 入口の無い前提——マスタ・利用者・権限など、アプリの入口からは作れないもの——を作る口の呼び出し。`{"seed": "<名前>", "values": {"<項目>": <値>}}`。
  名前と項目の名前は英小文字で始まり英小文字・数字・`_`、値は文字列・数・真偽・`null`（入れ子にしない）。`values` は 1 つ以上。
  **口は実装に求める**（下の「実装に求める口」の `seed`）。**`seed` は `setup`・`after` の中でだけ書ける**（トレースのケースの `setup`・`after` には書けない）。

**`setup`・`after` を書かないケースは、今までと変わらない**——Red テスト・Issue の本文・機能の指紋は、書いていないケースだけの機能では 1 バイトも変わらない
（機能の指紋は機能のオブジェクト全体の sha256 なので、書いたケースを持つ機能の指紋は変わる）。**書いたケースの Red テストは、`reset_state()` を呼んで状態を空にしてから（テストが終わったら、後ろのケースに状態を残さないよう、もう一度呼ぶ）、
`setup` を順に呼び、本体を呼んで `expected`（か `error`）と比べ、`after` を順に呼んで比べる。** `reset_state()` と `seed` の口が実装に無ければ失敗する（実装が無いときも失敗で、エラーではない）。
**入口の名前に `reset_state` は使えない**（`setup`・`after` を書いたケースがあるとき）。**`seed` を書いたケースがあるときは、入口の名前に `seed` も、どの入口の入力にも項目 `seed` も使えない**
（口と重なる。生成のスクリプトが止める。`checkpoint` と同じ扱い）。

**性能テストは `setup` を呼ばず、入出力のケースの `input` だけで測る**（前提の無い呼び出しの時間になる。`references/nfr.md` の「性能テストは `条件` の負荷を再現しない」と同じ限界）。

## 実行ごとに変わる出力（`$any`・`$ref`。#1299）

**成功の応答の URN・版・作った日時のように、実行ごとに変わる出力は、等しさでは比べられない。** 期待の項目の値に、等しさの代わりの比べ方を書く。

| 書き方 | Red テストが確かめること |
| --- | --- |
| `{"$any": "<型>"}` | その項目が、決めた型の値であること（値は見ない）。型は項目の型と同じ（`string`・`integer`・`number`・`boolean`。配列・入れ子のオブジェクトの項目は `array`・`object`で、形——中の型——に合うかを見る）。`enum` は見ない |
| `{"$ref": "<名前>.<項目>"}` | その項目が、`as` で束ねた名前の結果の項目と同じ値であること（`true` を `1` と同じ値とは見ない——項目の型も見る）。指す項目の型は、書く項目の型と同じ |

- **書ける場所**: 入出力のケースの `expected` と、`setup`・`after` の呼び出しの `expected` の、項目の値だけ。**`input` と `seed` の値には書けない**（前に返った値を入力に渡すことはできない）。
  **トレースのケースの `expected`・`setup`・`after` には書けない**。
- **`as`**: ケースの本体と、`setup`・`after` の入口の呼び出しに書ける——結果（実装が返した出力）を名前で束ねる。名前は英小文字で始まり英小文字・数字・`_`、1 つのケースの中で重ならない。
  **期待が `expected` の呼び出しだけ**（`error` の結果は項目を持たない）。
- **`$ref` が指せるのは、呼ぶ順で前の `as` だけ**——`setup`（書いた順）→ 本体 → `after`（書いた順）。後ろの呼び出し・自分自身・束ねていない名前を指すと、生成が止まる。
  `<項目>` は、束ねた呼び出しの入口の `output` の項目。
- **`null` を許す項目**（`nullable`）は、`null` を返しても `$any`・`$ref` に合う（`$ref` は、指した値も `null` のとき）。
- **書かないケースは今までと変わらない**——`$any`・`$ref`・`as` を 1 つも書いていない機能の Red テスト・Issue の本文・機能の指紋は、1 バイトも変わらない。
  書いたケースは `self.dynamic(…)` で比べる（前提・後の状態があるケースは、`reset_state()` を呼ぶところまで前提と後の状態と同じ。実装に求める口は変わらない）。

## トレースのケース（`trace`。#923）

**形式検査（Formal Checker）が範囲の中で出した反例の実行順を、実装の上で再現する Red テストにする。** 並行のテストを流すだけでは、
反例の順はめったに起きない——**実装の口で順を強制する**。仕様を直して反例が消えた後も、そのトレースが「同じ順で同じ誤りを起こさない」ことを確かめる回帰になる。
仕様の側では、spec-review が反例のトレースを仕様のテストケースとして書く（spec-review の `SKILL.md` の手順 4「仕様を直す」）。ここにはそれを写す。

```json
{"id": "F-003-C2", "title": "同じ品を同時に引き当てても売り越さない", "ref": "R-F3",
 "trace": {
   "formal": "stock-reserve",
   "setup": [{"operation": "set_stock", "input": {"item": "a", "qty": 1}, "expected": {"stock": 1}}],
   "calls": {"first": {"operation": "reserve", "input": {"item": "a", "qty": 1}},
             "second": {"operation": "reserve", "input": {"item": "a", "qty": 1}}},
   "steps": [["first", "read"], ["second", "read"], ["first", "write"], ["second", "write"]],
   "outcomes": [{"ok": true}, {"error": "OUT_OF_STOCK"}],
   "after": [{"operation": "get_stock", "input": {"item": "a"}, "expected": {"stock": 0}}]}}
```

| キー | 書くもの |
| --- | --- |
| `formal` | 反例を出した形式検査の対象の名前——重ね合わせた全体の `spec/formal/<対象>/README.md` が在ること（`tree.md` の「形式検査のモデル」。名前は英小文字・数字・ハイフン） |
| `calls` | 同時に走る呼び出し（2 つ以上）。呼び出しの名前（英小文字で始まり英小文字・数字・`_`）→ `{"operation": <入口の id>, "input": <入力>}`。入口は**重ね合わせた全体の中間表現のどの機能の入口でもよい**（書き手と読み手が別の機能のとき）。入力はその入口の `input` の項目をちょうど全部 |
| `steps` | トレース——`[呼び出しの名前, 段の名前]` の並び（2 つ以上）。**段はモデルの行為**（在庫を読む・書く、など）で、名前は英小文字で始まり英小文字・数字・`_`。`calls` の呼び出しはどれも 1 回以上出る |
| `setup` | （任意）呼び出しの前に順に呼ぶもの——`{"operation", "input", "expected" か "error"}` の配列（1 つ以上）。初めの状態を作る |
| `outcomes` | （任意）呼び出しの結果——`calls` と同じ数の、`expected` の形か `{"error": <名前>}` の配列。**どの呼び出しがどれを返すかは問わない**（多重集合として比べる——正しい実装でも、どれが先に通るかは順で変わる） |
| `after` | （任意）呼び出しが全部終わった後に順に呼んで確かめるもの（`setup` と同じ形）。**`outcomes` と `after` の少なくとも片方を書く** |

**ケースの `id`・`title`・`qa`・`ref` は入出力のケースと同じ決まり**で、`input`・`expected`・`error` は書かない。

**ここ（中間表現）に写すのは仕様のテストケースからである**（#1020）——段の並び（`steps`）は、Formal Checker が報告した `トレース` を spec-review が仕様のテストケースに書いたもので、Formal Checker は不変条件の違反の反例なら TLC の `-dumpTrace json` の JSON から `scripts/tlc-trace.py` で出し、出せなければ検査器の出力から写す（`agents/formal-checker.md`）。`calls` の入口と入力・`setup`・`outcomes`・`after`（直した仕様の結果）は、spec-review が仕様のテストケースを書くときに決める——反例からは出ない。変換の対応表の形と止める条件はスクリプトの docstring を正とする。

### 実装に求める口

トレースのケースを持つ機能の Red テストは、実装に次の口を求める（Issue の本文の `## Red テスト` にも出る）:

| 口 | 書くもの |
| --- | --- |
| `checkpoint` | `calls` の呼び出しの入口の関数が受け取るキーワード引数（既定は何もしない関数。`setup`・`after` の呼び出しには渡さない）。**トレースの段の全部について、その段の操作の直前に `checkpoint("<段の名前>")` を呼ぶ**——結果で書かない分岐（在庫が足りず書かずに返す、など）でも、その段の前で呼ぶ。**その段のために排他を取る前に呼ぶ**（テストは呼び出しを `checkpoint` で止めるので、排他の内側で呼ぶと、止められている間ほかの呼び出しが排他で待ち、トレースの順に進められない）。**先にまとめて呼ばない**——続けて呼んでよいのは、1 回の原子的な操作で読むと書くをまとめる実装が、その操作の直前に呼ぶときだけ。1 回も呼ばない・段を飛ばして終わる・トレースの順で次の段と違う段に来る呼び出しがあれば、順を強制できないので失敗にする（口を無視する・一部の段だけに呼ぶ・名前を違える競合する実装を素通りさせない） |
| `reset_state` | `impl_module` のモジュールの関数。状態を空に戻す。トレースのケースのテストの初めに呼ぶ。**前提・後の状態（`setup`・`after`）を書いた入出力のケースも、テストの初めに呼ぶ**（上の「前提と後の状態」） |
| `seed` | `impl_module` のモジュールの関数 `seed(<名前>, /, **値)`。入口の無い前提（マスタ・利用者・権限など）を作る。**`setup`・`after` に `seed` の呼び出しを書いたケースがあるときだけ求める**（名前だけを位置引数に取り、値の項目の名前と重ならない）。トレースのケースは呼ばない |

**口は手段ではなく観測点である**——段の名前は仕様（モデル）の行為の名前で、実装は段の前で知らせるだけ。排他の取り方・書き方は決めない。
**入口の名前に `reset_state`、トレースが呼ぶ入口の入力の項目に `checkpoint` は使えない**（口と重なる。生成のスクリプトが止める）。
**`seed` を書いたケースがあるときは、入口の名前に `seed`、どの入口の入力にも項目 `seed` は使えない**（同じく止める。上の「前提と後の状態」）。

### Red テストが確かめること

1. `reset_state()` を呼び、`setup` を順に呼んで期待と比べる。
2. `calls` の呼び出しをスレッドで同時に走らせ、`checkpoint` で止めて、`steps` の順に 1 段ずつ進める
   （進めた呼び出しが次の段に来るか終わるまで、ほかを進めない）。
3. **その呼び出しが決まった時間（1 段 2 秒）のうちに段に来ない**（排他を待っている）なら、**その順にはならないと読んで、順の強制をやめて全部を走らせる。**
   正しい実装はどの順でも正しいので、これで緑になる。**段に来ずに終わった・トレースの順で次の段と違う段に来た**なら、そこで順の強制をやめ、
   全部の呼び出しが終わった後に失敗にする（口の約束——段の全部について、その段の前で呼ぶ——を守っていない）。
4. 全部の呼び出しが終わったら（上限 60 秒。超えれば固まったと読んで失敗）、例外・`checkpoint` を呼ばなかった呼び出し・3 の段に来なかった呼び出しを失敗にし、`outcomes` を多重集合として、`after` を順に比べる。

**競合する実装**（排他で守らない）はトレースの順を最後まで進められ、反例と同じ誤りの結果になって失敗する。
**守らないこと**: 負荷で呼び出しが 1 段の時間より遅れると、順の強制をやめるので、競合する実装を見逃すことがある。
**口の約束を破る競合する実装**——段の `checkpoint` を排他の内側で呼ぶ・先にまとめて呼んでから操作する——**も見逃しうる**（機械では約束を守ったかを見分けられない。止められた呼び出しが排他を持っていると、ほかが来ないのを排他待ちと読む）。
**口の約束を守る正しい実装を失敗にすることは無い**——ただし、テストは呼び出しを段で止めたまま（排他を持ったまま）ほかを最大 1 段の時間待たせるので、
**排他を待つ時間に上限を持ち、待てなければ段を呼ばずに返す実装**は、その間に待ちを打ち切って失敗になる（段を呼ばずに終わる——3）。
Red テストは Python の `unittest` で、スレッドで走らせる——プロセスの外の状態（データベースなど）で競合する実装も、`checkpoint` を呼べば同じ形で順を強制できる。

## 書き起こすときの決まり

- **仕様に書いていないことを足さない。** ケースは仕様のテストケース（`spec-exit.md` の条件 3）から写す。
  足したくなったら、仕様のほうを直す（利用者に見える結果が変わるなら共有の Q&A 表に起票する）。
- **決まっていないことを、もっともらしい値で埋めない。** 書けないなら仕様が確定していない——`spec-review` に戻す。
- **確かめる手段（入口の名前・項目名・`seed` の口・時計・画面の初期値を返す入口）は、書き起こす側が置いてよい**——範囲と、置けないものは下の「入口と観測点を置いてよい範囲」。

## 入口と観測点を置いてよい範囲（#1333）

**仕様は実現の手段（エンドポイント・スキーマ・event の型）を書かない**（`spec-scope.md` の「縦の線 — どの水準まで書くか」）。中間表現はケースを「どの入口を呼び、何で確かめるか」に書き起こすので、
**仕様に無い入口・観測点は書き起こす側が置くことになる**。上の「仕様に書いていないことを足さない」が禁じるのは**結果**（期待・エラーになる条件・前提の値——利用者に見える振る舞い）を足すことで、
**次の表の手段は書き起こす側が置いてよい**——`spec-review` に戻さない。

| 置いてよいもの | 中間表現の場所 | 決め方 |
| --- | --- | --- |
| **入口の名前・項目名**——入口の `id`・`method`・`path`、`input`・`output` の項目の名前と型、エラーの名前 | 機能の `operation`（上の「入口」） | 内部の Q&A 表（`spec/qa-dev.csv`）に開発者の決定があれば、それに従う。無ければ書き起こす側が決める |
| **前提を作る口**——`seed` の名前と項目。**「今日」「今」を固定する時計も `seed` で置く**（`{"seed": "clock", "values": {"now": "2026-04-01T09:00:00+09:00"}}`。口が何を差し替えるかは実装が決める） | 入出力のケースの `setup`（上の「前提と後の状態」）。**トレースのケースには書けない**（`seed` はトレースの `setup`・`after` に書けない——時計を固定しないと書けないトレースのケースは `acceptance`） | 名前と項目は同上。**値（固定する日時・置くマスタの中身）は仕様のケースの前提から写す** |
| **画面の初期値を返す入口**——画面を開いたときの初期値・No. のまとまり・ダッシュボードの枠を返す入口 | **仕様が「画面を開いたときに初期値を見せる」を振る舞いとして書いた機能**の `operation`（その振る舞いが機能そのもの） | 入口の名前と項目は同上。**返す値は仕様に書いた初期値から写す** |
| **後の状態を読む入口**——本体の戻り値では見えない状態を確かめる | ケースの `after` | **重ね合わせた全体の中間表現のどれかの機能（そのケースの機能自身を含む）の `operation` を呼ぶ**（機能の `operation` は 1 つなので、既にある機能に 2 つ目の読む入口を足せない）。読む振る舞いを仕様がどの機能にも書いていなければ、そのケースは `acceptance`（読む振る舞いを仕様で決めるなら `spec-review` に戻す） |

- **置けないもの**——期待結果の値・エラーになる条件・前提の値（何を置くか）・どの知らせを出すか。仕様に無ければ書き起こせない（`scaffold` の見積もりでは `neither`）——`spec-review` に戻す。
  **入口を置くために、仕様に無い機能を足さない**——置いた入口は、仕様が振る舞いを書いた機能のもの（機能に `operation` は 1 つ）である。観測のためだけの機能を足すと、機能一覧（`requirements/features.csv`）が在る正本では生成が止まり、無ければ作る必要の無い Issue が増える。
- **発行した知らせ（event）を確かめるケースは、受入基準に回す**——中間表現には、発行した知らせを読み返す観測点の形が無い（`setup`・`after` が呼べるのは入口と `seed` だけ）。
  そのケースは機能の `acceptance` に行を原文のまま並べる（上の「Red テストにしない受入基準」。見積もりでは `acceptance`、`reason` に「知らせを読み返す口が中間表現に無い」）。
  **仕様が、知らせを読み返す入口を振る舞いとして書いていれば**（外部の受け手が読む一覧など）、その入口を `after` で呼んで Red テストにする。
- **置いた名前は仕様にも Q&A 表にも書き戻さない**——中間表現と、そこから作る OpenAPI・型・Issue の本文に残る。scaffold は Q&A 表を書かない。
- **置いた手段は、利用者に見える結果を変えない**——同じ仕様から別の名前を置いても、Red テストが確かめる期待の値は同じである。期待の値が手段の選び方で変わるなら、それは手段ではなく結果である（`spec-review` に戻す）。

## 例

```json
{
  "spec_ir_version": 1,
  "title": "注文",
  "features": [
    {
      "id": "F-001",
      "title": "注文の割引額を計算する",
      "source": ["spec/order.md"],
      "qa": ["Q-R-001"],
      "operation": {
        "id": "calc_discount",
        "method": "POST",
        "path": "/orders/discount",
        "input": {"rank": {"type": "string", "enum": ["silver", "gold"]}, "amount": {"type": "integer"}},
        "output": {"discount": {"type": "integer"}},
        "errors": ["INVALID_AMOUNT"]
      },
      "cases": [
        {"id": "F-001-C1", "title": "シルバーで 10000 円未満は割引なし",
         "input": {"rank": "silver", "amount": 9999}, "expected": {"discount": 0}, "qa": ["Q-R-001"]},
        {"id": "F-001-C2", "title": "金額が負なら拒否する",
         "input": {"rank": "gold", "amount": -1}, "error": "INVALID_AMOUNT"}
      ]
    }
  ]
}
```

### 画面のケースの例（`acceptance`。#1301）

関数で表せる割引の判定は `cases` に書き、**画面の振る舞い（確定を 2 回押す）・障害（保存先が落ちる）・同時・時間のケースは、Red テストにせず `acceptance` に仕様の行のまま並べる。**
仕様（`spec/order.md`）にこの表があるとする:

```markdown
| テストケース | 内容 | 期待 |
| --- | --- | --- |
| F1-1 | シルバーで 9999 円 | 割引なし |
| F1-2 | 注文確定の画面で確定を 2 回押す | 注文は 1 件だけ作られ、2 回目の押下は無視される |
| F1-3 | 注文の保存中にデータベースが落ちる | 注文は作られず、画面にやり直しを促す表示が出る |
```

```json
{
  "id": "F-001",
  "title": "注文を確定する",
  "source": ["spec/order.md"],
  "qa": [],
  "operation": {"id": "confirm_order", "method": "POST", "path": "/orders", "input": {"amount": {"type": "integer"}},
                "output": {"discount": {"type": "integer"}}},
  "cases": [{"id": "F-001-C1", "title": "シルバーで 9999 円は割引なし", "ref": "F1-1",
             "input": {"amount": 9999}, "expected": {"discount": 0}}],
  "acceptance": ["| F1-2 | 注文確定の画面で確定を 2 回押す | 注文は 1 件だけ作られ、2 回目の押下は無視される |"]
}
```

`F1-1` は `ref` で Red テストになり、`F1-2` は `acceptance` で Issue の本文の `### Red テストにしない受入基準` に写る。`F1-3` は書き起こしていないので、
生成のスクリプトは `仕様のテストケース 3 件のうち、Red テスト 1 件・受入基準 1 件・どちらにも無い 1 件` と出し、`どちらにも無い: F1-3（spec/order.md:…）` と名指しする。
