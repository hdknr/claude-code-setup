# 版のディレクトリと重ね合わせ

プロジェクトが完成した**あと**のバージョンアップでは、要件の**差分だけ**を回す。
そのために正本リポジトリの `docs/` を**版ごとのディレクトリ**に分け、v2 以降には**前の版からの差分だけ**を置く。

**正本リポジトリは、版が 1 つしか無いうちから `docs/v1/` に置く。** 同梱のスクリプトは、版に分けていない構成
（`docs/shared/` 直下）を読まない。前の構成から移すときは下の「移し方」。

## ツリー

```
docs/
├── v1/                     # 最初の版。全体の仕様（中の構成は tree.md の docs/ と同じ）
│   ├── shared/
│   ├── requirements/
│   ├── spec/
│   ├── feasibility/
│   └── proposal/
└── v2/                     # v1 からの差分だけ
    ├── shared/qa.csv       # 新しい質問と、答えを変えた質問だけ
    ├── requirements/       # 足した・変えた要件のファイルだけ
    ├── spec/spec_ir.json   # 足した・変えた機能だけ
    ├── removed.csv         # 消したもの（下の「削除」）
    ├── feasibility/        # この版の差分の見積り
    └── proposal/           # この版の変更の提案書の手書き部分
```

- **版は `docs/` 直下の `v<n>`**。`n` は 1 から始まる整数で、先頭に 0 を付けない（`v2` は可、`v02` は不可）。
  **番号は 1 から欠けずに続ける。** **`v` の次が数字で、形に合わない名前（`v2-draft`・`v02`）は誤り**——
  黙って飛ばすと、その版の要件が消える。ほかの名前のファイル・ディレクトリ（`index.md` など）は版として読まない。
- **作業中の版は、番号が最大の版。** 作業中かどうかを書いたファイルは置かない。
- **リリースした版は凍結する**——直さない。リリースは git のタグ `release-v<n>` で示す（下の「凍結」）。
- **版の中の置き方**（`shared/`・`requirements/`・`spec/`・`feasibility/`・`proposal/` に何を置くか）は `tree.md`。
  サインオフのタグも版ごと（`signoff-tags.md`）。

## 重ね合わせ

**v<n> の時点の全体 ＝ v1 に v2、…、v<n> の差分を順に重ねたもの。** 重ね合わせは同梱のスクリプトが作る
（**手で作らない**）:

```bash
python3 <spec-loop の base ディレクトリ>/scripts/merge-versions.py docs build/merged
python3 <spec-loop の base ディレクトリ>/scripts/merge-versions.py docs build/merged-v1 --upto 1   # v1 だけ
```

出力は**版のディレクトリと同じ形**（`shared/`・`requirements/`・`spec/`）で、`tree.md` の決まりどおりに読める。
**commit しなくてよい**（同じ入力から同じバイトを作る）。

### 重ね合わせた全体を読むもの

| 読むもの | どう読むか |
| --- | --- |
| 仕様レビューを抜ける条件 1（`check-spec-exit.py`） | `build/merged/shared/qa.csv` と `build/merged/spec` に当てる |
| `scaffold.py` | **自分でメモリ上に重ねる**（`build/merged/` は書かない。同じバイト）。中間表現の `source` は**重ね合わせた全体の根からのパス**（`spec-ir.md`）。**機能を追加・変更・削除に分けるのは、v<n-1> の全体との比較**（下の「版の差分」。`handoff-issue.md`） |
| Issue の本文 | 中間表現は `build/merged/spec/spec_ir.json`（機能の指紋はこの中の機能。撤去の本文は前の版の全体 `build/merged-v<n-1>/`。`handoff-issue.md`）。開発する側は**本文のコマンド**（`--upto <n>` で版を指定する）で作って当てる |

**その版だけを読むもの**——`check-qa-csv.py`（版ごとの `qa.csv`）・`check-feasibility-csv.py` と `schedule-to-gantt.py`
（版ごとの `feasibility/`）・`check-signoff.py` と `build-proposal.py`（`signoff-tags.md`）。
**版ごとに読む検査・資料の生成（`check-qa-csv.py`・`qa-to-pptx.py`・`check-feasibility-csv.py`・`schedule-to-gantt.py`）は、渡されたパスの
末尾 3 段（版・置き場所・ファイル）がディスクの綴りと大文字小文字だけ違えば、読まずにディスクの綴りを名指しして 2 で止まる**
（`check-qa-csv.py` の `misspelled`。#514）——区別しないファイルシステムでは `docs/v2/shared/qa.csv` が `docs/v2/Shared/qa.csv` を開いて
しまい、重ね合わせが断る綴り（下の「名前の綴りは git が見る綴りで決める」）をそこだけが読むため。**MkDocs のフック（`tree.md` の
「ドキュメントのツール」）も、版の中の表に綴りだけ違う名前で届くなら警告して描かない。** どちらも区別するファイルシステムで同じ答えになる。
**読む側は git を使わない**（ディスクの綴りで読む）ので、コミットの綴りは正しいのに手元のフォルダだけ古い綴りが残る形でも止まる
——下の「綴りの誤りの移行」の 3。**`check-signoff.py`・`build-proposal.py` は、表と重ねるものをタグの時点の git の木のパスで読む**ので、
そこではこの形は起きない。**ただし `build-proposal.py` は手書き部分（`proposal/*.md`・`proposal/spec/*.md`）を作業ツリーから読むので、
同じく書いた綴りで探し、綴りだけ違うフォルダ（`Proposal/`）は名指しして 2 で止まる。** 一覧を読めないフォルダ（実行の権限だけ）も、
綴りを確かめられないので止まる。
**前の版の全体と比べるもの**——`diff-versions.py` と、v2 以降の `build-proposal.py` の「前の版からの変更」（下の「版の差分」）。

### 重ねるもの

| 置き場所 | 単位 | 変更 | 削除 |
| --- | --- | --- | --- |
| `shared/qa.csv` | 行（`No`） | 同じ `No` の行を置く | `removed.csv` に種類 `Q&A` |
| `spec/qa-dev.csv`（内部の Q&A 表。`qa-csv.md` の「層」） | 行（`No`） | 同じ `No` の行を置く | `removed.csv` に種類 `Q&A`（番号が `D-` なので、どちらの表の行かは番号で決まる） |
| `spec/spec_ir.json` | 機能（`features` の要素の `id`） | 同じ `id` の機能を**ケースまで丸ごと**置く | `removed.csv` に種類 `機能` |
| `spec/spec_ir.json` | `features` 以外のキー（`title` など） | 同じキーを書く | できない |
| `shared/`・`requirements/`・`spec/` のほかのファイル | ファイル（版のディレクトリからのパス） | 同じパスのファイルを置く | `removed.csv` に種類 `ファイル` |

- **追加は、新しい `No`・`id`・パスで置く。** **番号は版をまたいで重複させない**——新しく足すものは、前の版までの続きの番号にする
  （Q&A の `No` は起票したループの印ごとの連番——振り方は `qa-csv.md` の「番号の振り方」）。
  **同じ番号は「変更」の意味になる**（新しいもののつもりで前の版の番号を書いても、機械には見分けられない）。
- **行・機能の並びは、前の版の順を保つ。** 置き換えはその場で、追加は版の順に末尾へ。
- v2 以降の `spec_ir.json` は**差分だけ**なので、`features` 以外のキーは省いてよい。`features` は配列で置く（空でもよい）。
  中身の決まり（`spec-ir.md`）は、**重ね合わせた全体**に当てる。
- 各版の `qa.csv`・`qa-dev.csv` は、それだけで `qa-csv.md` の決まりを満たすこと（同梱の検査を版ごとに通す）。
- **`feasibility/`・`proposal/` は重ねない。** 版ごとのもの（その版の差分の見積り・変更の提案書）で、出力にも入らない。
- **`.` で始まる名前は読まない**（`.DS_Store` など）。**シンボリックリンクは置かない**（版の外を読ませない）。
- **版の直下の置き場所と `removed.csv` は、この綴りで置く**——大文字小文字・Unicode の正規化だけ違う名前（`Removed.csv`・`Shared/`）は誤りで、
  中身は読まない（#276）。区別しないファイルシステム（macOS の既定）でだけその名前で開けてしまい、区別するファイルシステムや、
  タグから写して重ねる提案書（下の「版の差分」）と答えが食い違うため。**名前の綴りは git が見る綴りで決める**——区別しないファイルシステムでは
  作業ツリーのフォルダの綴りがコミットの綴りと食い違いうる（古い `Requirements/` が `.DS_Store` などで残ると、`requirements/` のファイルもそこに書かれる）ので、
  git の作業ツリーの中では、**どの段の名前も**（版のフォルダ・版の直下・置き場所より深いフォルダとファイル。#569）index の綴りに寄せる
  ——**寄せるのは、ファイルシステムが index の名前と作業ツリーの名前を同じ項目として開くときだけ**（区別するファイルシステムでは綴りだけ違う 2 つは
  別の項目なので寄せない。同じフォルダに綴りだけ違う名前を並べたハードリンクも同じ。#676）
  （`git add` 前の名前と git の外は作業ツリーの綴り。外かどうかは git が `docs` からリポジトリを見つけるかで決める——#572）。綴りだけ違うディレクトリでも、
  `.` で始まらない名前のファイルを持たなければ数えない（タグからも写らない）。
- **置き場所の中の構造ファイル（`shared/qa.csv`・`spec/qa-dev.csv`・`spec/spec_ir.json`）も、この綴りで置く**——綴りだけ違う名前
  （`shared/QA.csv`）は誤りで、中身は読まない（#511）。重ねた全体を決まった名前で開く側（`check-spec-exit.py`・`scaffold.py`）が、
  区別しないファイルシステムでだけ Q&A 表・中間表現として開いてしまうため。
- 綴りの誤りを直すときは、下の「綴りの誤りの移行」。

### 削除（`removed.csv`）

**置かないことは「変えていない」の意味である。** 消すときは、その版の `removed.csv` に書く。

| 列 | 書くもの |
| --- | --- |
| `種類` | `ファイル`・`Q&A`・`機能` のどれか |
| `対象` | `ファイル` なら版のディレクトリからのパス（`requirements/discount.md`）、`Q&A` なら `No`（`Q-R-003`）、`機能` なら `id`（`F-002`） |
| `理由` | なぜ消すか（空にしない） |

- 文字コードは UTF-8（BOM はあってもよい）。1 行目は見出し行で、上の列名と同じ文字列・同じ順。
- **消すものは、前の版までの全体に在ること。** 無いものを消そうとするのは誤り（綴りの誤りを黙って通さない）。
- **同じ版で、置きつつ消さない。** 同じ対象を 2 度書かない。
- **v1 には置かない**（消すものが無い）。
- **`shared/qa.csv`・`spec/qa-dev.csv`・`spec/spec_ir.json` はファイルとしては消せない**——行・機能の単位で消す。

## 版の差分

**v<n> の差分 ＝ v<n-1> の時点の全体と v<n> の時点の全体の比較。** 各スキルの差分モード（その版の分だけを
レビュー会に載せる・レビューする・見積もる・提案する）は、ここで決まる差分を使う。比べるのは同梱のスクリプト
（**手で数えない**）:

```bash
python3 <spec-loop の base ディレクトリ>/scripts/diff-versions.py docs               # 作業中の版
python3 <spec-loop の base ディレクトリ>/scripts/diff-versions.py docs --version 2   # 版を指定
```

| 変化 | 意味 |
| --- | --- |
| `追加` | v<n> の全体にあって、v<n-1> の全体に無い |
| `変更` | 両方にあって、中身が違う |
| `削除` | v<n-1> の全体にあって、v<n> の全体に無い（`removed.csv` の `理由` を添える） |

- 単位は「重ねるもの」と同じ——Q&A は行（`No`）、機能は `id`、ほかのファイルは版のディレクトリからのパス。
  `spec_ir.json` の `features` 以外のキーと、`feasibility/`・`proposal/` は比べない。
- **Q&A は層で 2 つの種類に分けて出す**——`Q&A` は共有の層（`Q-`。`shared/qa.csv`）、`Q&A（内部）` は内部の層
  （`D-`。`spec/qa-dev.csv`。`qa-csv.md` の「層」）。どちらの層かは番号で決まる（`removed.csv` の種類はどちらも `Q&A`）。
  **利用者に見せてよいのは `Q&A` の節だけ**——`Q&A（内部）` は開発者が決めたことの差分で、レビュー会にも提案書にも載せない
  （提案書は比べる前に内部の層を外すので、`Q&A（内部）` の行そのものを持たない）。
- **同じ中身を置き直しただけのものは `変更` に数えない**（比較なので）。何を置いたかは `docs/v<n>/` を開けば分かる。
- **v1 は前の版が無いので、全部が `追加`。**
- 重ね合わせが決まりに反すれば比べない（1）。その版が無い・読めなければ比べない（2）。
- **提案書（v2 以降）の「前の版からの変更」の節は、この比較を `signoff/v<n>/req-<k>` の時点の `docs/` に当てて作る**
  （`signoff-tags.md`。作業ツリーで承認の後に直したものは入らない）。

## 出力先

- **書く前に、前の出力を消して作り直す。** ただし、スクリプトが作った印（`.merged-versions`）の在るディレクトリしか消さない。
  印の無い、空でないディレクトリには書かない——引数を取り違えて正本を消さないため。
- **`docs/` の中には書かない**（次の重ね合わせで入力に混ざる）。**`docs/` を含む場所にも書かない**（前の出力と一緒に入力を消す）。
- **出力先にシンボリックリンクは使わない**（印で持ち主を確かめられない）。
- **印は最後に書く。** 書いている途中で失敗したら、書きかけを消す（用意された空の出力先は、中身だけ消してディレクトリは残す）。
  **書く前に出力の全部をバイトにする**——UTF-8 で書けない文字（対のないサロゲート）は、書き始める前に誤りとする。
- 決まりに反する入力・無い／読めない入力からは何も作らず、**前の出力は消す**（古い全体を今のものと取り違えないため）。
- **重ねた結果で、同じパスがファイルとディレクトリの両方になるのは誤り**（`requirements/a` と `requirements/a/b`）。
- **重ねた結果で、大文字小文字・Unicode の正規化（NFC/NFD）だけが違うパスが並ぶのも誤り**（`requirements/A.md` と
  `requirements/a.md`。フォルダも——`requirements/Sub/` と `requirements/sub/`）——区別しないファイルシステムでは同じ場所に書かれ、片方が黙って消える
  （フォルダは 1 つにまとまる）。前の版のファイル・フォルダを変えるなら、同じ綴りで置く。git の作業ツリーの中では、追跡しているファイルは
  自分の index のパスでだけ数える（index に綴りの違う 2 つが在っても、別の綴りで追跡しているファイルを取り込まない。タグを読む提案書と揃える）。
  追跡していないファイル（`git add` 前・追跡しているファイルのハードリンクを別の名前で置いたもの）も数える。名前は上の「名前の綴りは git が見る綴りで決める」の
  とおりで、ファイル名は（index に無いので）作業ツリーの綴り、それを含むフォルダは同じ項目として開く index の名前があればその綴り、無ければ作業ツリーの綴り
  （作業ツリーのフォルダが `sub/`、index が `Sub/` なら、区別しないファイルシステムでは `Sub/` の下に、区別するファイルシステムでは別の項目の `sub/` の下に出る）。
- どれかの版に `shared/qa.csv` があれば、行がすべて消えても**見出し行だけの `shared/qa.csv` を書く**（出力を `docs/` と同じ形に保つ）。
  `spec/qa-dev.csv` も同じ。

## 差分の周を始める前に

**新しい版（`docs/v<n>/`）を作る前に、前の版 v<n-1> の時点が崩れていないことを確かめる。** 崩れていると、
差分を測る土台が無い——v<n> の Issue の本文は v<n-1> の全体と比べて変わった機能だけに作るので、v<n-1> の時点の
`scaffold/` や実装がその全体に追いついていなければ、追いついていない分は v<n> のどの Issue にも載らない。

| 確かめること | どう確かめるか | 崩れていたら |
| --- | --- | --- |
| `scaffold/` が v<n-1> の時点で新しい | `scaffold.py --check --upto <n-1>`（同梱。0 なら新しい） | v<n-1> で `scaffold` を作り直して登録してから始める（Q&A が `反映済み` でないなら下の「前の版の時点が崩れていたら」） |
| 前の版の Red テストが、実装の上で全部緑 | 開発のリポジトリで `python3 -m unittest discover -s scaffold/tests` | 実装が前の版の仕様に追いついていない（乖離）。**先にそれを直す周を回す**（dev-loop で、前の版の Issue の受入基準に戻す） |

- **どちらも v1 を作る前には要らない**（前の版が無い）。
- **spec-loop 0.13.0 より前に作った `scaffold/` は、1 つ目で古い・決まりに反すると言われることがある**——v<n-1> で作り直せない
  場合を含め、移行は `spec-ir.md` の「0.13.0 より前に作った `scaffold/` の移行」を正とする。
- **2 つ目は開発のリポジトリで見る**——`scaffold.py --red-check` はこの代わりにならない（何を比べ、何を見ないかは `scaffold.py` の docstring を正とする）。
- **確かめずに始めない。** 崩れているのに始めると、v<n> の差分の Red テストが、前の版から持ち越した赤と区別できない。

### 前の版の時点が崩れていたら

**v<n-1> の時点の Q&A（`shared/qa.csv`・`spec/qa-dev.csv`）に `反映済み` でない行（`確認中`・`暫定反映`）が残ると、
v<n-1> の scaffold は作れていない**——`確認中` は仕様レビューを抜ける条件 1 で、`暫定反映` は利用者の確認待ちで止まる。
`scaffold.py` は v<n> を作るとき、**中間表現が指しているかに依らず**この状態を見て止め（1）、ここを指す。
v<n> で同じ Q&A を確定しても止まる——v<n-1> から変わらない機能の Issue が誰にも渡らないので（#335）。

**凍結していなければ、v<n-1> を直して作る:**

1. **`docs/v<n>/` を `docs/` の外へ退ける**（`--upto` 付きの生成は断られる。`docs/` の中に別の名前で置くと、版の名前の
   形に合わずに止まる。`spec-ir.md` の移行の 1 と同じ形）。
2. **v<n-1> の Q&A を確定する**——`/spec-loop:req-loop` で利用者に確かめ、`docs/v<n-1>/` の Q&A 表と仕様を直す
   （`反映済み` にする）。
3. **v<n-1> で `scaffold` を作り、登録する**（`scaffold.py`。登録の前に利用者に確かめる——scaffold `SKILL.md`）。
   `--check` が 0 になる。
4. **`docs/v<n>/` を戻す。** `--check --upto <n-1>` が 0 になり、v<n> を作れる。v<n> で同じ Q&A を置き換えていたなら、
   v<n-1> で確定した回答と食い違わないかを見る。

**凍結していれば（`release-v<n-1>`。下の「凍結」）、直さない。** `scaffold.py` は止めずに、**v<n-1> の時点を信じず、
v<n> の機能を全部追加として**本文を作る（そう出力する。#357）——変わらない機能の Issue も渡るので、v<n-1> から
持ち越した分が抜けない。**v<n> で消した機能の撤去の本文は作らない**（比べる前の版を信じないので。出力が名指しする）。
撤去は利用者に示し、手で Issue にするかを決めてもらう。v<n> の Q&A は今の版の関門どおり、`反映済み` でなければ止まる。

- **凍結を判定できなければ止まる（2）**——`git` を起動できない・浅い clone（タグが見えないのを「凍結していない」と読まない）。
- **タグがあるだけでは凍結と読まない**——タグの後に `docs/v<n-1>/` を直していれば止まる（1。`check-frozen.py` が言うとおり、
  直した分をタグの時点に戻す）。タグの時点に `docs/v<n-1>/` が無ければ判定しない（2）。
  **確かめるのは `release-v<n-1>` だけ**——他の版のタグの状態（直されている・版が無い）は v<n-1> の凍結を変えない
  （それは `check-frozen.py` を CI で回して見る）。
- **凍結した版がこの状態で残るのを、リリースの前に防ぐ**——タグを付ける前に `scaffold.py --check --upto <n>` が 0 であることを
  確かめる（`反映済み` でない Q&A が残れば 0 にならない）。

## 凍結

**リリースした版（`release-v<n>` のタグがある版）の `docs/v<n>/` は、タグの時点から変えない。**
変えたいことは、作業中の版に差分として置く（同じ番号・同じパスで置けば置き換わる。消すなら `removed.csv`）。
同梱の確かめを CI で走らせる:

```bash
python3 <spec-loop の base ディレクトリ>/scripts/check-frozen.py
```

- 命名に合う `release-v<n>` ごとに、タグの時点と HEAD で `docs/v<n>/` が同じか、作業ツリーに `docs/v<n>/` の
  未コミット・未追跡の変更が無いかを見る。**直されていれば 1。**
- **タグの時点に `docs/v<n>/` が無ければ 2**（比べる中身が無いのに「直されていない」とは言わない）。
- リリースのタグが 1 つも無ければ 0（凍結した版が無い。出力がそう言う）。
- タグを取得できるよう、CI では履歴をすべて取る（GitHub Actions なら `actions/checkout` に `fetch-depth: 0`）。
  **浅い clone なら 2**（タグが見えないのを「凍結した版が無い」と読まない）。
- **タグはスキルが付けない。** どの版をリリースしたかは人間が決める。

## 綴りの誤りの移行

**spec-loop 0.38.0 から、版の直下の置き場所・`removed.csv` の綴り違い（`Removed.csv`・`Shared/`）が、0.41.0 から、置き場所の中の
構造ファイルの綴り違い（`shared/QA.csv`・`spec/QA-dev.csv`・`spec/Spec_IR.json`）が、決まりに反する（1）になった**（#276・#511）。
それまで区別するファイルシステム（Linux）では黙って読まれず 0 で通り、区別しないファイルシステム（macOS の既定）では正しい綴りとして
読まれていた正本リポジトリは、この版から 1 で止まる。**0.44.0 から、版ごとに読む側（検査・資料の生成と
MkDocs のフック）も、書いた綴りと大文字小文字だけ違う名前を読まずに名指しして止まる**（#514。上の「その版だけを読むもの」）。次の順で直す:

1. **見つける**——`merge-versions.py docs build/merged` を走らせる。1 なら、出力のうち
   **`… と大文字小文字・Unicode の正規化だけ違う名前は置かない`** を含む行（後ろに「（区別しないファイルシステムでだけ … として開けてしまう）」が続く）が、
   綴りの違うパスと正しい綴りを名指しする。
2. **コミットの綴りを直す**——git が見ている綴り（`git ls-files docs/v2` に出る名前）が誤りなら、`git mv` で改名してコミットする。
   **区別しないファイルシステムでは、フォルダの大文字小文字だけの改名を `git mv` 1 回では行えない**（`Invalid argument` で失敗する）ので、
   別の名前を挟んで 2 段に分ける:

   ```bash
   git mv docs/v2/Shared docs/v2/shared-tmp
   git mv docs/v2/shared-tmp docs/v2/shared
   ```

   ファイルは 1 回で改名できる（`git mv docs/v2/shared/QA.csv docs/v2/shared/qa.csv`。macOS の git 2.54 で確かめた）。
   **凍結した版（下の「凍結」）の綴りを直すと、`check-frozen.py` が 1 になる**——直すかどうか（直して `release-v<n>` を付け直すか）は人間が決める。
3. **作業ツリーにだけ古い綴りが残る形**——コミットの綴りは正しいのに、手元のフォルダ名だけ古い綴りのまま（追跡しない `.DS_Store` が残った
   フォルダに git が書き込んだ）。`git status` は空のまま。**区別しないファイルシステムでは、重ね合わせは index の綴りで読むので 1 にならない**
   （どの段でも。#569）。**ただし版ごとに読む側は git を使わずディスクの綴りで読むので、その形でも止まる**（フックは警告する。#514）
   ——ディスク上で 2 段に改名して揃える（`mv docs/v2/Shared docs/v2/shared-tmp && mv docs/v2/shared-tmp docs/v2/shared`）。
   **区別するファイルシステムでは、綴りの違うフォルダは git にも別の項目**（`git status` に未追跡で出る）なので 1 になる——中身を正しい綴りへ
   移すか、要らなければ消す。
4. 走らせ直して 0 になることを確かめる。**直したコミットに付いていた承認のタグ（`signoff-tags.md`）は、直したコミットに付け直してもらう**
   （タグはスキルが付けない）。

## 移し方（版に分ける前の正本リポジトリ）

版に分ける前の構成（`docs/shared/`・`docs/spec/`… が `docs/` の直下）は、同梱のスクリプトが読まない。次の順で移す:

1. **`docs/` の直下のディレクトリを `docs/v1/` へ移す**（`git mv` で。履歴が辿れる）:

   ```bash
   mkdir -p docs/v1
   git mv docs/shared docs/requirements docs/spec docs/feasibility docs/proposal docs/v1/
   ```

   **在るディレクトリだけを並べる**——無いものが 1 つでも混ざると、`git mv` は何も移さずに失敗する。

2. **中間表現の `source` を、重ね合わせた全体の根からのパスに書き換える**（`docs/spec/order.md` → `spec/order.md`。`spec-ir.md`）。
3. **`scaffold.py` で作り直す。** `scaffold/` の中身は変わらないことがあるが、**Issue の本文は変わる**（中間表現の場所と
   指紋が `build/merged/spec/spec_ir.json` を指す）。**登録済みの Issue は古い場所を指したまま**なので、
   開発中の Issue があるなら、開発する側に場所が変わったことを伝える。
4. **承認を取り直す。** 前の名前のタグ（`req-signoff-v<n>`・`budget-signoff-v<n>`）は読まれない。移したコミットで
   `signoff/v1/req-1`・`signoff/v1/budget-1` を付けてもらう（`signoff-tags.md`。**タグはスキルが付けない**）。
   **中身を変えずに移しただけでも、どのコミットを承認したかは利用者・予算責任者が決める。**
5. **リリース済みなら、移したコミットに `release-v1` を付けてもらう**（凍結の確かめの起点）。
6. 正本リポジトリの `CLAUDE.md`・CI がパスを書いていれば直す。
