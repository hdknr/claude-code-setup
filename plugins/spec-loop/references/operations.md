# 運用の決まりの要約（利用者向け）

spec-loop を回す利用者（発注側と開発の窓口）が、**「いま何が起きていて、次に何が起きるか」を 1 か所で追える**ようにした要約。
よくある問いを順に並べ、それぞれの原本へ指す。

**この文書は要約で、決まりの原本ではない。** 食い違ったら指し先を正とする（要約に写しを増やすと、直すときに一部だけ直し漏れる）。
書き手（エージェント）が利用者に説明するときも、まずこの文書を読み、細部が要るときだけ指し先を読む。

| 知りたいこと | 節 |
| --- | --- |
| 質問が共有の表と内部の表に分かれるのはなぜか。誰が決めるのか | [Q&A 表の 2 層](#qa-layers) |
| 層を移すと、回答はどうなるのか | [層を移すと、回答はどうなるか](#qa-move) |
| 前の回で抜けたのに、なぜ質問が増えたのか。今回の改修と関係の無い質問が出るのはなぜか | [抜けたあとに質問が増える理由](#why-more-questions) |
| 1 回の仕様レビューで何が起きるか。なぜ 2 回で打ち切るのか | [1 回の spec-review の流れ](#review-flow) |
| 「抜けた」とは何を言っているのか | [抜ける条件と、「抜けた」の意味](#exit) |
| 抜けたあとに回し直すのは、どんなときか | [抜けたあとの回し直し](#rerun) |
| 何回まで回るのか。上限に達すると何を訊かれるのか | [実行の上限](#limit) |
| 形式検査は何をいつ検査するのか。検査していない部分はどうなるのか | [形式検査の対象の選び方](#formal) |
| 暫定の回答を採ったあとはどうなるのか | [暫定の回答の流れ](#provisional) |

<a id="qa-layers"></a>
## Q&A 表の 2 層

質問は 2 つの表のどちらかに置く。**分け方の問いは 1 つ**——「どの選択肢を選ぶと、利用者に見える結果（画面・通知・業務の判定）が変わるか」。

| 層 | 表と番号 | 載せる質問 | 決める人 |
| --- | --- | --- | --- |
| 共有 | `shared/qa.csv`（`Q-`） | 選択肢で利用者に見える結果が変わるもの。規約・契約に関わるもの。範囲の線を動かすかどうか | 利用者 |
| 内部 | `spec/qa-dev.csv`（`D-`） | 変わるのが実現の手段・内部の値・運用の手順だけのもの。費用だけが変わるものもここ | 開発者（`回答` に決めた人と日付） |

- **迷ったら共有に置く。** 利用者に聞くほうに倒す。
- **費用だけが変わる質問は、利用者ではなく予算の責任者に回す。** 内部の表に `費用への影響` を書き、feasibility が見積りに拾う。
  **例外は基盤要件**（言語・DBMS・ホスティング環境など）で、費用だけが変わる選択でも共有に置く。
- **内部の表は、利用者に渡すもの・サインオフが比べる範囲に入らない。** 内部で決めても、承認の照合は割れない。
  ただし内部の行も、決めて反映した記録が無ければ仕様レビューは抜けられない。
- **内部に置いた判断は、書き手と別のティアの判定役が確かめる。** 利用者に見える結果が変わると判定された行は共有の表へ移る。

原本: `qa-csv.md` の「層」と「層を移す」、`spec-scope.md` の「振り分けの区分」と「決める順」。

<a id="qa-move"></a>
## 層を移すと、回答はどうなるか

**回答は持ち越さない。** 内部から共有へ移した行は回答待ち（`未回答`・`確認中`）に戻り、利用者に聞き直す。共有から内部へ移した行は、開発者が決め直す。
番号も振り直す（`Q-` と `D-` は別の連番）。

- **前の判断は消さずに写す。** 内部の行に開発者の回答があったなら、その選択肢と決めた人・日付・理由を、移した行の `推奨`・`推奨の理由` に写す。
  推奨は提案側の意見で、回答の推測ではない——利用者は前の判断を見たうえで、同じにも変えることもできる。
  選択肢を言い直して対応づけられないときは、`推奨` を `なし` にして、前の判断を `推奨の理由` に書く。
- **出どころが印で分かる。** 前の回までに開発者が決めていた行を、確かめが「利用者に見える結果が変わる」と判定し直して移したときは、
  起票元の詳細に `確かめの追加で移した。元: <番号>` と書く。**今回の改修から出た質問ではない**と見分けるための印で、元の行に開発者の回答があり、かつ元の行をこの実行で足した・変えていないときだけ付ける（回答待ちだった行と、この実行で足した・変えた行には付けない）。レビュー会の資料の表題に出る。

原本: `qa-csv.md` の「層を移す」。

<a id="why-more-questions"></a>
## 抜けたあとに質問が増える理由

前の回で仕様レビューを抜けていても、次の `spec-review` や `req-loop` で質問が増えることがある。どれも決まりどおりの動きで、主な理由は 3 つある。

1. **要求を変えたので、新しい分岐が出た。** 要求や決定表を足した・変えると、その分岐について仕様レビューが新しい質問を立てる。
   作業中の版が v2 以降なら、レビューの対象はその版の差分で、前の版の決定と矛盾するときだけ全体を指摘の対象にする（`versions.md`・`spec-review` の「差分モード」）。
2. **決まりが増えた。** 前に抜けた時点では確かめていなかった観点を、プラグインの版が上がって確かめるようになった。
   代表は**内部の表の確かめ**（0.104.0 から）で、内部の行を 1 つずつ判定し直し、利用者に見える結果が変わる行を共有の表へ移す。
   **作業中の版が v1 のあいだは、内部の全部の行が確かめの対象になる**（前の版が無いので全行が「足した行」に数えられる）。
   移った行が、**今回の改修と関係の無い質問**として利用者に出る。起票元に `確かめの追加で移した` とあるのがそれで、前の判断は `推奨`・`推奨の理由` に残っている。
   `spec-review` の報告は、移した行を「確かめの追加で移した（前の判断あり）」と「今回の改修・今回の起票から出た」に分けて示し、`req-loop` は資料を渡すときに同じ分け方で伝える。
3. **形式検査の対象が、改修の性質で選ばれた。** 検査の対象を選び直した回では、反例が出て質問になることがある（下の[形式検査の対象の選び方](#formal)）。

原本: `spec-exit.md` の「内部の表の行を確かめる」と「0.104.0 より前に抜けた正本の移行」。

<a id="review-flow"></a>
## 1 回の spec-review の流れ

1 回の実行で起きること（手順の原本は `skills/spec-review/SKILL.md`）:

1. **仕様を書き下す。** 要求から開発者向けの仕様を書く（書き手はスキル本体）。
2. **1 回目のレビュー。** 書き込みツールを持たない 3 つの判定役（Red Team・Domain Checker・Formal Checker）が、書き手と別のティアで仕様を批判する。
3. **指摘を振り分ける。** 6 つの区分——仕様を直す／共有の表に起票する／内部の表に記録する／範囲の外として記録する／実装に渡す／退ける（`spec-scope.md`）。
4. **仕様か範囲の文書を直したなら、2 回目のレビューを 1 回だけ回す。** 仕様も範囲の文書も直さなかった（起票・実装に渡す・退けるだけ）なら、2 回目は回さない。
   内部の表の行を確かめただけでは、2 回目を回す理由にならない。
5. **2 回目のあとで直したなら、直した差分だけに「狭いパス」を 1 回当てる。** 2 回目のあとで直してよいのは、2 回目の指摘への直しだけ。狭いパスの指摘は、その回は直さない（`判断が要る` だけは共有の表に起票する）。
6. **抜ける条件を判定して止まる。** 条件を満たしたときだけ「抜けた」と報告し、満たさない・判定できないなら抜けていないと報告する。多くは利用者の回答待ちで止まる。

**なぜ 2 回で打ち切るのか。** 判定役は毎回何かを見つけるので、「指摘が 0 件になるまで」は終わらない。
実案件では、直すたびに別の箇所に次の指摘が出る回が続き、利用者が消耗して打ち切った。
そこで **2 回目のレビューと狭いパスで打ち切り、収束は件数ではなく重さで読む**（次の節）。3 回目のレビューは回さず、続きは次の回か利用者の判断に回す。

原本: `skills/spec-review/SKILL.md` の手順 5・6、`spec-exit.md` の「指摘の重さ」と「2 回目のあとの直し — 狭いパス」。

<a id="exit"></a>
## 抜ける条件と、「抜けた」の意味

抜けるには次の 5 つをすべて満たす。1 つでも満たさない・判定できなければ、抜けていない。

| # | 条件（要約） | 誰が判定するか |
| --- | --- | --- |
| 1 | Q&A 表（共有と内部）に、仕様に反映した状態でない行が無く、仕様に未決定の印（`TBD`・`TODO`・`未定`・`要確認`）が無く、テストケースの番号が重なっていない。画面の表（任意）があれば、その未決定の印が無く screen-spec の検査が通る | 同梱のスクリプト |
| 2 | 仕様チェックリストの項目が、範囲の中の機能ごとに仕様のどこかに書いてある | Red Team と数え直し |
| 3 | 決定表の各行と範囲の中の各シナリオに、対応するテストケースが仕様にある | 同上 |
| 4 | 形式検査の対象ごとに、検査器が範囲の中で反例を出さず、空振りでないことを確かめた（対象が無ければ「対象なし」） | Formal Checker と検査器 |
| 5 | 最後のレビューの指摘が 1 件残らず振り分け済み（根拠を確かめていない行は数えない）で、足した・変えた内部の行を判定役が確かめ、変わると振り分けた行が内部の表に残らない | `spec-review` の報告と数え直し |

条件 5 で共有の表に起票した行は、`反映済み`（か `暫定反映`）になるまで条件 1 が止める。`暫定反映` の行が残っても条件 1 は満たすが、scaffold は止まる（[暫定の回答の流れ](#provisional)）。

**条件 2・3 に効く指摘は、重さが `判断が要る`・`結果が割れる` のものだけ。** `補い`（言い回し・重複・結果が仕様から 1 つに決まるものの補足）が残っていても満たす。

**「抜けた」は、次のどちらでもない。**

- **承認ではない。** 仕様の承認は、利用者が付けるサインオフのタグ（要求確定と予算の合意の 2 つ。`signoff-tags.md`）で記録する。スキルは付けない。
  `暫定反映` の行が残っていても抜けられるが、利用者が確かめるまで要求確定のサインオフは付けない。
- **網羅の証明ではない。** 条件 2〜4 は、範囲の中を、性質の水準で読む。範囲の外の場面と実現の手段の細部は、満たさない根拠にならない。
  判定役の指摘が 0 件だったことも意味しない（`補い` は残りうる）。
  形式検査は改修の性質で選ぶので、選ばれなかった対象は検査していない（[形式検査の対象の選び方](#formal)）。
  v2 以降の差分モードでは、前の版の部分は、作業中の版の追加と矛盾するときだけ指摘の対象になる（`spec-review` の「差分モード」）。

原本: `spec-exit.md` の冒頭の表と各節、`spec-scope.md`（範囲の線）。

<a id="rerun"></a>
## 抜けたあとの回し直し

**回し直す（`spec-review` を呼び直す）のは、要求が変わったとき。確かめる決まりが増えただけなら、次に回すときにその決まりを当てる**（下の表）。

| いつ | すること |
| --- | --- |
| **要求を変えた** | 起票した質問に回答が来たとき、利用者が要求や決定表を足した・変えたとき。`req-loop` で回答を反映し、その後に `spec-review` を呼び直す。v2 以降は作業中の版の差分がレビューの対象になる |
| **決まりが増えた** | プラグインの版が上がって、仕様チェックリストの行などが増えたとき。**次に `spec-review` を回したとき**、その回のレビューの対象の機能（v2 以降は作業中の版の機能）についてその行を埋める。埋まっていなければ条件 2 の書き漏れとして判定する |
| **回さなくてよい** | 要求も仕様も変わっていないとき。**決まりが増えただけでは、前の版で抜けた仕様を、そのためだけに版を立てて見直す必要はない**（次に要求を変えて回す回で足りる） |

- **作業中の版が v1 のあいだは、回すたびに内部の全部の行が確かめられる。** v1 には前の版が無いので、`spec-review` を回すたびに、内部の表に残る全部の行が確かめの対象になる（[抜けたあとに質問が増える理由](#why-more-questions)の 2）。
  この確かめだけを回す専用の入口は作っていない。
- **リリースした版（`release-v<n>` のタグがある版）は直さない。** 変えるなら作業中の版に差分として置き、消すなら `removed.csv` に書く（`versions.md` の「凍結」）。
- **抜けたあとに残る手順は、利用者の側にある。** サインオフのタグは利用者が付け、scaffold（dev-loop への引き渡し）は抜けた仕様だけを入力にする。
  `暫定反映` の行が残るうちは scaffold が止まる（[暫定の回答の流れ](#provisional)）。

原本: `spec-exit.md` の各項の「移行」と「0.104.0 より前に抜けた正本の移行」、`versions.md` の「凍結」。

<a id="limit"></a>
## 実行の上限

判定役に収束を委ねないために、**回数の上限で利用者に判断を返す。** 数えるのは同梱の `check-review-record.py limit` で、会話や手では数えない。

- **数える対象**: 記録の表（`spec-review/v<n>.csv`）の実行の行のうち、`条件2〜4` が `満たさない` か `判定できなかった` の行。
  `回答待ち`（利用者の回答待ち）と `満たす`（条件 1・5 だけで抜けられなかった回を含む）は数えない。
- **数え始め**は、最後に利用者が `続ける` か `範囲を決め直す` を選んだ行の後（無ければ表の最初）。版が変われば数え直す。
- **既定の上限は 3 つ。** 数えた行が 3 つに達すると、**次の回は判定役を起動せず**、利用者に訊く。正本の `CLAUDE.md` で数を変えられる。
- **訊かれる 3 つの選択肢**:
    - `続ける` — 数え直して、もう一度回す。
    - `範囲を決め直す` — 指摘が集まった機能について、範囲を決め直す質問を共有の表に起票して止まる。回答が来るまで条件 1 が止める。数えた行の `機能` がすべて `-` のときは出ず、`続ける`・`止める` を訊く。
    - `止める` — 止まる。仕様は確定していない。次に呼ばれたときも、まず訊く。
- **別の歯止めもある。** 同じ機能について仕様レビューが起票した行が共有の表に 2 行あるとき、3 行目は個別の質問にせず、その機能の範囲を決め直す質問に置き換える。
  これは機能ごとに質問の行を数える歯止めで、上限（版ごとに実行を数える）とは別の数で、両方を当てる。

原本: `spec-exit.md` の「実行の上限と記録」、`spec-scope.md` の「回を重ねたときの歯止め」。

<a id="formal"></a>
## 形式検査の対象の選び方

形式検査は、**作業中の版の改修の性質で選ぶ。** 対象があっても、当たらなければ「対象なし」とし、理由を書く。

| 対象 | 検査するとき |
| --- | --- |
| 決定表・計算ルール | 作業中の版で、足した・変えた |
| 並行・リトライ・取り消しを含む業務フロー | 改修するシステムに、状態を持つ業務フローを新しく足すか、既存のフローの状態・遷移を変える |
| 権限・ロール | 作業中の版で、組み合わせを足した・変えた |

- **決定表と権限は版から見て、業務フローは改修するシステムから見て決める。** システムに前からあるフローは、版で初めて仕様に書いたものでも「新しく足す」に当たらない。
- **既存の書き手に排他を足すだけの改修**は、性質が比べる値が排他の外の状態から来て、書き手の動いている間に変わりうる場合を除き、形式検査をしない。
  同時実行で成り立つべき性質とそのテスト（条件 2・3）で受ける。
- **検査するときの構成は、性質が破れうる最小（ふつう 2〜3）から始める。** 「反例なし」は、正常な状態に到達でき、わざと壊した版で反例が出る（陽性対照）ことを確かめて、はじめて言える。
- **TLC（業務フローの検査器）は既定で必須。** 業務フローを一度も検査しない正本は、`CLAUDE.md` に宣言して外せる（`README.md` の「前提」）。

**選ばれなかった対象は、この回の形式検査をしていない。** 受けるのは仕様の性質とテスト（条件 2・3）で、形式検査が見つけるはずの穴（抜け・矛盾・反例）は、その対象については確かめていない。
モデルを残す前に抜けた仕様に、比べる基準のモデルを今の仕様から作るには `/spec-loop:formal-baseline` を使う（対象は `spec-review` と同じ決まりで選ぶので、選ばれなかった対象を埋める道ではない。作業中の版がリリース済みなら書かずに止まる）。

原本: `spec-exit.md` の「形式検査の対象」と「改修の性質で選ぶ」、`tree.md` の「形式検査のモデル」。

<a id="provisional"></a>
## 暫定の回答の流れ

利用者の回答を待たずに先へ進めるために、選択肢の 1 つを暫定で採って仕様に反映することがある。

1. **暫定で採ってよいのは、利用者がそう指示したときだけ。** どれを採るかをスキルが決めて書くのは推測である。
   `回答` に、採った選択肢と、暫定であること・誰の指示か・いつかを書く。`状態` は `暫定反映`。**内部の表では使わない**（確かめる利用者がいない）。
2. **暫定の行は、仕様に反映した状態に数える。** 仕様レビューは抜けられる。ただし**要求確定のサインオフは付けない**。
3. **利用者が確かめたら**——同じ選択肢で確定したなら、`回答` を確定の書き方に直して `反映済み` にする（仕様は直さない）。
   違う選択肢になったなら、`回答` を新しい回答に直して `確認中` に戻し、次の反映で仕様を直し直す。
4. **残るうちの扱い**——scaffold は `暫定反映` の行が 1 つでも残れば止まる（利用者が仮回答のまま渡すと決めたときだけ `--provisional`）。
   サインオフの照合は要求確定のタグの時点に残れば止め、提案書は作らない。
