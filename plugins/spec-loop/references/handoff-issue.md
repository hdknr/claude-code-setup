# dev-loop に渡す Issue の本文

`scaffold` が登録する Issue の本文の形。**2 つのプラグインの境界は、この Issue と、そこから指すファイル**
（`spec_ir.json`・Red テスト）である。dev-loop は **Issue 1 件を読むだけで周を始められる**こと——
受入基準・Red テスト・Q&A の回答・仕様の原文を、本文から辿れること——を目的にする。

**本文は同梱のスクリプトが作る。手で書かない・登録の前に書き換えない。** 中身を変えたいなら
`spec_ir.json`（か仕様・Q&A 表）を直して作り直す。

## 1 機能の変化 = Issue 1 件

作業中の版 v<n> の全体と、前の版 v<n-1> の全体を、機能の `id` で比べる（`versions.md` の「版の差分」）。
**追加・変更・削除の機能ごとに 1 件**作り、**変わっていない機能の本文は作らない**（前の版の Issue がある）。
v1 だけなら全部が追加。

| 変化 | 題 |
| --- | --- |
| 追加 | `<機能の id>: <機能の title>`（`F-001: 注文の割引額を計算する`） |
| 変更 | `<機能の id>: <機能の title>（v<n> で変更）` |
| 削除 | `<機能の id>: <前の版の機能の title>（v<n> で撤去）` |

## 印

本文の先頭の 3 行。**dev-loop はこの印で、spec-loop から来た Issue だと知る。**

| 印 | 意味 |
| --- | --- |
| `<!-- spec-loop-handoff: v2 -->` | spec-loop から渡した Issue である。`v2` は本文の形の版 |
| `<!-- spec-loop-feature: <機能の id> -->` | どの機能か（同じ機能を 2 度登録していないかを確かめるのに使う） |
| `<!-- spec-loop-change: <変化>; base=<前の版> -->` | 何が変わったか。`<前の版>` は `v<n-1>`（v1 なら `none`） |

### 変化

| 値 | 意味 |
| --- | --- |
| `add` | v<n> で足した機能（v1 では全部） |
| `modify` | v<n-1> の時点からケース・API・題・出所のどれかを変えた機能 |
| `remove` | v<n> で消した機能（`removed.csv`）。撤去の Issue |

**前の形（`<!-- spec-loop-handoff: v1 -->`）**は先頭 2 行の印だけを持ち、変化の印を持たない——全部が追加で、
再現のコマンドに版の指定が無い。**登録済みの Issue はこの形のまま残る**ので、dev-loop は両方を読む。

## 節

本文はこの順に節を持つ（**変化に依らず 5 つとも**）。

| 節 | 書くもの |
| --- | --- |
| `## 仕様` | 機能の id と題・変化・`spec_ir.json` のパスと sha256・仕様の原文のパス（どちらも**版を重ね合わせた全体** `build/merged/` の中と、その作り方）・API（メソッドとパス、OpenAPI の `operationId`）・型の名前 |
| `## 受入基準` | ケースごとに 1 行: ケースの id・**変化**・何を確かめるか・**Red テストの名前**・根拠の Q&A の No。**この表の Red テストがすべて緑になること**が受入基準 |
| `## Red テスト` | テストのファイルのパスと sha256・回し方・実装を置く場所（モジュール名と関数名）・**前の版の実装の上で失敗するはずのケース** |
| `## Q&A の回答` | この機能とケースが根拠にした Q&A の No・質問・回答・反映先（**生成した時点の Q&A 表から写す**。No だけにしない） |
| `## 仕様の穴を見つけたら` | 実装で決めず、作業中の版の Q&A 表に起票元 `開発` で起票して差し戻すこと（規定の本体は dev-loop の側にある） |

### 受入基準の表の `変化`

ケースの変化は、**Red テストが実行する中身**——ケースの入力・期待（`expected`／`error`）・機能の `operation.id`・
**期待にある項目の**出力の型・`impl_module`——で決める。**題だけの違いは変化に数えない**（テストの振る舞いが変わらない）。
**`integer` を `number` に広げただけの違いも数えない**（前の版で通った値は広げた型にも合う）。期待に無い出力の項目の型は、
そのケースの結果を変えないので見ない。**`impl_module` を変えた版では、機能が同じでも全部の機能が `変更` になる**
（どの Red テストも前の版の実装を探せない）。

| 変化 | 意味 | 前の版の実装の上で |
| --- | --- | --- |
| `追加` | v<n> にだけあるケース（追加の機能では全部） | 失敗しうる（前の版の実装がもう満たすなら緑） |
| `変更` | 両方にあって、Red テストの実行する中身が違う | 失敗しうる（同上） |
| `回帰` | 両方にあって、変わらない | **緑で、緑のままであること**も受入基準 |
| `削除` | 撤去の Issue の、消した機能のケース | テストごと消えている |

- **変更の Issue**: 表の Red テストがすべて緑になること、**`回帰` のケースが緑のまま**であること。ほかの機能の Red テストは、**周の前に緑だった Red テストが、周の後も緑のままであること**（同じ版で足した・変えたほかの機能のケースは、この周の前に失敗していてよい）。
  前の版にあって v<n> に無いケースは、表の下に「削除したケース」として列挙する（その振る舞いはもう求めない）。
- **撤去の Issue**: 消した機能の実装（モジュールと関数）を撤去し、**周の前に緑だった Red テストが、周の後も緑のままであること**。
  **「ほかの Red テストがすべて緑」ではない**——同じ版で足した・変えた機能は、撤去の周の前にまだ実装されずに失敗していてよい（#280）。
  `## Red テスト` は消したファイルと、撤去の前と後に回す全部のコマンドを書く（sha256 は持たない——ファイルが無い）。
  Q&A の回答と仕様の原文は**前の版の時点**のもの。

**Red の状態**: **Red テストと受入基準は、実装が前の版の状態にあることを前提にしない**（#294）。前の版の実装の上で失敗しうるのは
`追加`・`変更` のケースだけで、`回帰` は緑である。`scaffold.py --red-check` は**前の版の Red テストも同じ実装に当てて**、
実装がどこにいるかを確かめてから判定する——`回帰` は緑・`追加`・`変更` は前の版か作業中の版のどちらかの期待を満たすこと。
**前の版の実装がもう満たす `追加`・`変更` は止めずに名指しで知らせ**（#281）、前の版の期待を満たさず作業中の版の期待を
満たすものは「実装は前の版の状態に無い」で止める——**作り直しの経路**（この版の Issue を登録し、実装が始まっている）では
`--in-progress` を付け、それを実装済みとして数える（#282）。判定の表は `scaffold.py` の docstring を正とする。
実装が無ければ、期待が全部失敗のときだけ判定できる。失敗しうるテストの名前は `issues.json` の `red` にもある。

## sha256 で固定する

本文は `spec_ir.json`（重ね合わせた全体の `build/merged/spec/spec_ir.json`。`versions.md`）と Red テストのファイルの
sha256 を持つ。**手元のファイルの sha256 が本文と違えば、
その Issue は手元の仕様と別の時点のものである**——dev-loop は実装に入る前にそれを確かめ、違えば差し戻す。

**作り方のコマンドは版を指定する**（`merge-versions.py docs build/merged --upto <n>`）——後の版（`docs/v<n+1>/`）を
足しても、同じコマンドで同じバイトを作れる（v<n> までの版は凍結している。`versions.md`）。

## 置き場所

生成した本文の出力先は `tree.md` の「生成物の置き場所」。`issues.json` は機能ごとに `feature`・`title`・`change`
（上の変化の値）・`body`・`red`（前の版の実装の上で失敗しうる Red テスト）を持つ。
