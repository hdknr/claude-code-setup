# Q&A 表（共有 `docs/v<n>/shared/qa.csv`・内部 `docs/v<n>/spec/qa-dev.csv`）

**未決定事項の台帳**。エージェントが見つけた未決定事項を 1 行ずつ起票し、
回答（決定）をもらって仕様に反映するまでを追う。決定表の空欄も、仕様レビューの「もし〇〇の場合は？」も、
見積りの費用付きの質問も、すべてここに集まる。**表は 2 つの層に分かれる**（下の「層」）——
利用者に聞く質問は**共有の表**、開発者が決めて記録する質問は**内部の表**に置く。列の決まりは両方で同じ。

**スキルが再開するときは、会話ではなくこの表の `状態` から続きを読む。**

決まりどおりかどうかは、プラグインに同梱の検査で確かめる:

```bash
python3 <spec-loop の base ディレクトリ>/scripts/check-qa-csv.py docs/v<n>/shared/qa.csv     # 版ごとに通す（versions.md）
python3 <spec-loop の base ディレクトリ>/scripts/check-qa-csv.py docs/v<n>/spec/qa-dev.csv    # 内部の表も（あれば）
```

**どちらの層の表かは、ファイルの名前で決まる**（`qa-dev.csv` なら内部）。

## ファイル

- 文字コードは UTF-8（BOM はあってもよい。Excel が付けるため）。
- 1 行目が見出し行。見出しは下の表の列名と**同じ文字列・同じ順**。
- **推奨の 2 列が無い見出しは、前の形（spec-loop 0.17.0 まで）の表である。** 移す手順は `tree.md` の「Q&A 表を移す」——
  検査もフックもその見出しでは落ちる（列の位置で読めないので）。

## 列

| 列 | 書くもの | 空のとき |
| --- | --- | --- |
| `No` | `Q-` に 3 桁以上の数字（`Q-001`）。内部の表は `D-`（`D-001`）。表の中で重複させない | 許さない |
| `起票元` | 下の「起票元」のどれか。詳細は全角括弧で添えてよい（`仕様レビュー（Red Team）`） | 許さない |
| `質問` | 利用者が答えられる言葉で書く | 許さない |
| `選択肢` | `A: …` の形を ` / ` で 2 つ以上つなぐ（`A: 切り捨て / B: 四捨五入`）。ラベルは英大文字 1 字で、重複させない。選択肢の文の中に ` / ` を書かない（区切りと見分けられない） | 許さない |
| `推奨` | 提案する側が推す選択肢のラベル（`B`）。推奨しないなら `なし`（下の「推奨」） | 許さない |
| `推奨の理由` | 推す理由。`推奨` が `なし` なら、推奨できない理由（`事実の確認`・`見積り待ち`） | 許さない |
| `回答` | 回答と、誰が答えたか（`A（業務部が回答）`）。内部の表では決めた人と日付（`B（開発 山田 2026-10-22）`） | まだなら `未回答` と書く。空は許さない |
| `反映先` | 回答を反映した場所（`決定表 4 行目`） | まだなら `—` と書く。空は許さない |
| `状態` | 下の「状態」のどれか | 許さない |
| `費用への影響` | 選択肢ごとの費用の違い（`B は月額が A の約 2 倍`） | 費用に関わらない質問は空でよい。**起票元が `実現性・コスト` の行は空を許さない**（費用付きの質問なので） |

**空を許さない列で「まだ無い」を明示させるのは、書き忘れと区別するためである。**

## 起票元

| 起票元 | 起票するループ |
| --- | --- |
| `要求確定` | 要求確定（決定表の空欄・ヒアリング） |
| `仕様レビュー` | 仕様レビュー（Red Team・Domain Checker・Formal Checker の指摘のうち、利用者の判断が要るもの） |
| `実現性・コスト` | 実現性・コスト（費用付きの質問） |
| `開発` | dev-loop（開発中に見つかった仕様の穴の差し戻し。差し戻しの規定の本体は dev-loop の `references/spec-gap.md`） |

## 推奨

**起票するときは、提案する側の推奨と理由を書く**（`req-loop`・`spec-review`・`feasibility` のどれが起票しても）。
利用者が選択肢を比べるだけでなく、「こちらはこう考える、理由はこう」を見て決められるようにするためである。

- **推奨は提案側の意見であって、回答の推測ではない。** だから `推奨` の列に書き、**`回答` の列には書かない**——
  回答の列に書くと、利用者が決めたように見える。
- **推奨できないときは `なし` と書き、理由を `推奨の理由` に書く**——事実を確かめる質問（だれが更新するか・外部が取得しているか）、
  見積りの後でないと推せない質問（完了時期）など。**空と `なし` は違う**——空は書き忘れで、検査が落とす。
- `推奨` は選択肢のラベル 1 つ（`B`）。選択肢の文に `（推奨: …）` を書き足さない（表示側が見分けられない。前の形の表を移すときは `tree.md`）。
- 費用付きの質問の推奨は、`費用への影響` と合わせて読める理由にする（`B（月額が半分。止めても業務に影響が無いと確かめてから）`）。
- **内部の表でも同じ**——開発者が決める前に、どれを推すかと理由を書く（決めたら `回答` に書く。推奨と違う選択肢でもよい）。

## 層 — 共有の表と内部の表

| 層 | 表 | 載せる質問 | 決める人 | レビュー会の資料 |
| --- | --- | --- | --- | --- |
| 共有 | `docs/v<n>/shared/qa.csv`（番号 `Q-`） | **選択肢によって利用者に見える結果**（画面・通知・業務の判定）**が変わる**もの。規約・契約に関わるもの。範囲の線を動かすかどうか | 利用者 | 載せる |
| 内部 | `docs/v<n>/spec/qa-dev.csv`（番号 `D-`） | 選択肢で変わるのが**実現の手段・内部の値・運用の手順**だけのもの。**費用だけが変わるもの**もここ | 開発者（`回答` に決めた人と日付） | 載せない |

**どちらに置くかの線と迷う例は `spec-scope.md` の「振り分けの区分」を正とする**（判定の問いは「どの選択肢を選ぶと、利用者に見える結果が変わるか」）。

- **内部の表は `shared/` の外に置く。** `shared/` は 2 つのサインオフが比べる範囲（`signoff-tags.md`）なので、
  内部の表を入れると、サインオフの後に開発者が決めるたびに照合が割れる。利用者に渡すもの（`tree.md`）にも入らない。
- **費用だけが変わる内部の質問は、利用者ではなく予算の責任者に回す**——`費用への影響` を書き、`feasibility` が見積りに拾って
  （根拠に `D-` の番号）予算の責任者の合意の対象にする。**「費用が変わるから利用者に聞く」で共有の表へ移さない。**
- 内部の表では **`暫定反映` を使わない**（確かめる利用者がいない）。状態は `確認中` と `反映済み`。
- 仕様レビューを抜ける条件 1 は**両方の表**を見る（`spec-exit.md`）——内部の行も、決めて反映した記録が無ければ抜けない。
- 内部の表の行も、中間表現の `qa` から指せる（`spec-ir.md`）。

### 層を移す

起票した後で、置いた層が違うと分かったら移す。**番号は振り直す**（`Q-` と `D-` は別の連番）:

- **作業中の版の行**——元の表から行を消し、移した先の表で新しい番号を振る。`起票元` の詳細に元の番号を書く
  （`仕様レビュー（Red Team。D-003 から移した）`）。
- **前の版の行**——作業中の版の `removed.csv` に `Q&A` で元の番号を消し（理由に移した先の番号）、移した先の表に起票する（`versions.md`）。
- **回答（決定）は持ち越さない**——共有へ移したなら利用者に聞き直し、内部へ移したなら開発者が決め直す。
- **元の番号を指しているものも、移した先の番号に直す**——中間表現の `qa`（`spec-ir.md`。直さないと `scaffold.py` が「Q&A 表に無い」で止まる）・
  見積りの `根拠`（`feasibility-csv.md`）・本文の `Q-008` のような番号（MkDocs のリンクになる）。

## 状態

| 状態 | 意味 |
| --- | --- |
| `確認中` | 回答待ち、または回答はあるがまだ仕様に反映していない |
| `暫定反映` | 利用者の回答を待たずに暫定の回答で仕様に反映した。利用者の確認待ち。**`回答` が `未回答` でなく、`反映先` が `—` でないこと**。**内部の表では使わない** |
| `反映済み` | 回答を仕様に反映した。**`回答` が `未回答` でなく、`反映先` が `—` でないこと** |

「回答はあるが未反映」は、`確認中` で `回答` が `未回答` でない行として表す（状態を増やさない）。

**仕様に反映した状態は `暫定反映` と `反映済み` の 2 つ**——仕様レビューを抜ける条件 1（`spec-exit.md`）は、
どちらでも満たす。**ただし scaffold は `暫定反映` の行が 1 つでも残れば止まる**（中間表現が指すかどうかに依らない。`spec-ir.md`）——scaffold はサインオフの照合を
通らないので、止めないと利用者が確かめていない回答が Issue になる。**レビュー会の資料に載るのは `反映済み` でない行**で、
`暫定反映` の行も載る（確認してもらうため）。**`暫定反映` の行が残るうちは、要求確定のサインオフを付けない**
（`signoff-tags.md`）。

## 暫定の回答

利用者の回答を待たずに先へ進めるため、選択肢の 1 つを**暫定で**採って仕様に反映することがある。

- **暫定で採ってよいのは、利用者がそう指示したときだけ**——どれを採るかをスキルが決めて書くのは推測である。
- `回答` には、採った選択肢と、**暫定であること・誰の指示か・いつか**を書く
  （`A（暫定で採用。業務部 2026-10-21 の指示）`）。`反映先` は反映した場所、`状態` は `暫定反映`。
- **利用者が暫定の回答を確かめたら**:
    - **同じ選択肢で確定した** — `回答` を確定の書き方（`A（業務部が確認）`）に書き換え、`状態` を `反映済み` にする。
      仕様はもう反映済みなので直さない。`反映先` もそのまま。
    - **違う選択肢になった** — `回答` を新しい回答（誰が答えたか）に書き換え、`状態` を `確認中` に戻す
      （「回答はあるが未反映」）。次の反映で仕様を直し直す。`反映先` は直し直すときの手がかりとして残してよい。

### 暫定の行の判別

**`状態` が `暫定反映` の行と、`状態` が `反映済み` で `回答` に `暫定で採用` を含む行を、暫定の行として扱う**（#374）。
**後に次の書き方が続くものは含むに数えない**——確定した回答が暫定の経緯に触れただけの行を、暫定の行にしない。

| 数えない書き方（`暫定で採用` の直後） |
| --- |
| `しない` |
| `しなかった` |
| `しません` |
| `せず` |
| `していた` |
| `された` |
| `されていた` |

**肯定の書き方（`暫定で採用します`・`暫定で採用する`・`暫定で採用した`・`暫定で採用している`・`暫定で採用し、`）は数える**——どれも、利用者が確かめていない回答を採ったと言っている。
後者は、確かめた後に `回答` を確定の書き方に直し忘れた行か、`暫定反映` の状態を足す前（#325）の書き方の行である。

- **`暫定反映` の行が残るうちは、要求確定のサインオフを付けない**（上の「状態」）。だから提案書の材料に残りうるのは後者で、
  **照合は後者では止まらない**——提案書（`build-proposal.py`）は後者を主な決定事項から外し、
  「利用者にまだ確かめていない決定」の節に載せる。決裁者が合意と取り違えないためである。
- `確認中` の行は、`回答` に `暫定で採用` と書いてあっても暫定の行ではない（まだ仕様に反映していない——未決定の質問として載る）。
- **推奨（`推奨` の列）は判別に使わない**——推奨は提案側の意見で、回答ではない（上の「推奨」）。回答が推奨と同じ選択肢でも、それだけでは暫定ではない。
- 内部の表には暫定の行が無い（`暫定反映` を使わない。提案書にも載らない）。
- **確かめたら、`回答` から `暫定で採用` を消す**（上の「同じ選択肢で確定した」）——残すと、提案書は暫定の行として載せ続ける。

## 本文での番号

要求・仕様・レビューの記録・決定表などの CSV で Q&A 表を指すときは、**素の番号で書く**（`（Q-008）`）。
**手でリンクを書かない**——リンクはページの場所と版に依存するので、書いた文が新しい版・別のページへ移ると切れる。
MkDocs の雛形のフック（spec-loop 0.16.0 以降。既に写した正本への取り込み方は `tree.md` の「ドキュメントのツール」）を使っていれば、
表示のときにフックが Q&A 表のアンカーへのリンクにする。**リンクになるのは Markdown のページと、フックの描画関数が描いた表**——
雛形が描くのは Q&A 表だけなので、**決定表などの CSV の番号は、その CSV を描く描画関数を足すまでリンクにならない**（足し方は `tree.md`）。

- **見出しの中の番号はリンクにならない**（目次が崩れるため）。決定の根拠として飛ばせたいなら、番号を本文にも書く。
- **コードの中の番号もリンクにならない**（インラインのコード・フェンス・字下げのコードブロック）——飛ばせたいならコードの外に書く。
- 見出しかコードかは、**MkDocs が描いた結果で決まる**（フックは描いた後の HTML に掛ける）。アドモニション・箇条書き・引用の中でも同じ。
- **リンクにする版の Q&A 表に無い番号を書くと、表示のときに警告が出る**（`mkdocs build --strict` は落ちる）。
  `docs/v<n>/` の下のページで見るのは v1〜v<n> の表なので、打ち間違いのほかに、**その版より新しい版で起票した番号を
  古い版のページで指していないか**と、**読めない表が無いか**（読めない表の番号は数えない）を疑う。

## 例

```csv
No,起票元,質問,選択肢,推奨,推奨の理由,回答,反映先,状態,費用への影響
Q-001,要求確定（決定表）,シルバー会員で 10000 円未満のとき、割引は A・B のどちらにしますか？,A: 割引なし（0%） / B: 3% 割引,A,ゴールド会員との差をはっきりさせるため,A（業務部が回答）,決定表 4 行目,反映済み,
Q-002,仕様レビュー（Red Team）,決済の途中で通信が切れたとき、注文は A・B のどちらで扱いますか？,A: 取り消す / B: 「決済待ち」で残し、後で再開できる,B,支払いが済んでいるのに注文が消えると問い合わせになるため,未回答,—,確認中,
Q-003,要求確定（決定表）,ゴールド会員の割引の上限は A・B のどちらにしますか？,A: 上限なし / B: 1 回 5000 円まで,A,上限を超える注文は年に数件で、上限の説明のほうが手間になるため,A（暫定で採用。業務部 2026-10-21 の指示）,決定表 7 行目,暫定反映,
Q-004,要求確定（ヒアリング）,お知らせを更新するのはどの部署ですか？,A: 広報 / B: 各事業部,なし,事実の確認（社内の分担を知らない）,未回答,—,確認中,
Q-005,実現性・コスト（運用費の見積り）,夜間（0〜6 時）のシステム停止について、A・B のどちらにしますか？,A: 夜間は止まってよい / B: 24 時間稼働させる,A,夜間の注文は全体の 1% 未満で、月額が半分で済むため,未回答,—,確認中,B は冗長構成が要り、月額が A の約 2 倍（仮の値）
```

## 内部の表の例

```csv
No,起票元,質問,選択肢,推奨,推奨の理由,回答,反映先,状態,費用への影響
D-001,仕様レビュー（Red Team。判定のジョブ）,判定のジョブの再投入が朝のジョブを遅らせたら、どうするか,A: 専用のワーカーを足す / B: 同じワーカーの中でキューを分け、朝のジョブを先に流す,B,朝のジョブの締め切りを守ったまま費用が増えない,B（開発 山田 2026-10-22）,spec/jobs.md 3 節,反映済み,A はワーカー 1 台分の月額が増える（予算の責任者へ。見積りの根拠 D-001）
D-002,仕様レビュー（Domain Checker）,取り込みの再試行の間隔は,A: 10 秒 / B: 60 秒,なし,見積り待ち（API の呼び出しの上限を確かめてから）,未回答,—,確認中,
```
