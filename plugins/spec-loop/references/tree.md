# 正本リポジトリのツリー

要求・見積り・提案書の元ファイルは、**1 つの git リポジトリ（正本）** に置く。
spec-loop のスキルはどれも、このツリーを前提に読み書きする。

**`docs/` は版ごとのディレクトリ（`docs/v1/`・`docs/v2/`…）に分け、v2 以降には前の版からの差分だけを置く。**
版の決まり（作業中の版・凍結・重ね合わせ・削除・移し方）は `versions.md` を正とする。
下の `docs/v<n>/` の中の構成は、**どの版でも同じ**（v2 以降は、足した・変えたものだけを置く）。

```
docs/v<n>/
├── shared/                  # 利用者と予算責任者の両方に見せてよいもの
│   ├── qa.csv               # Q&A 表（列は qa-csv.md）
│   ├── decision_table.csv   # 決定表
│   └── nfr.csv              # 非機能要求の回答
├── requirements/            # 利用者向け：業務ルール・画面・業務フロー
├── spec/                    # 開発者向け：守るべき性質とそれを確かめるテスト（spec-review が書き下す）
│   ├── scope.md             # 範囲の文書：受け持つ範囲・受け持たない範囲（形は spec-scope.md）
│   ├── qa-dev.csv           # 内部の層の Q&A 表：開発者が決めて記録する質問（列は qa-csv.md。shared/ に置かない）
│   ├── formal/              # 形式検査のモデル（決定表の検査・TLA+・Alloy など）
│   └── spec_ir.json         # 仕様の中間表現（scaffold が書き起こす。形は spec-ir.md）
├── feasibility/             # 予算責任者向け：規模の数え方・開発手法・体制・基盤案・見積り
│   ├── schedule.csv         # スケジュールの正本（列は feasibility-csv.md）
│   └── estimate.csv         # 見積りの正本（同上）
├── proposal/                # 決裁者向け提案書の手書き部分
│   └── spec/                # 仕様書の手書き部分（下の「仕様書」。任意）
└── removed.csv              # v2 以降だけ。前の版から消したもの（versions.md）
scaffold/                    # dev-loop に渡す契約（scaffold が生成し、commit する。下の「scaffold の出力」）
├── openapi.json
├── types.py
└── tests/test_<機能>.py     # Red テスト
build/merged/                # 版を重ね合わせた全体（生成物。commit しない。versions.md）
spec-review/v<n>.csv         # 仕様レビューの実行の記録（版ごと。commit する。docs/ の外——列と理由は spec-exit.md の「実行の上限と記録」）
docs/index.md                # 表紙（下の「ドキュメントのツール」。版の外）
docs/qa.md                   # Q&A 表の表示用ページ（同上。正本は各版の shared/qa.csv）
docs/decision-table.md       # 決定表の表示用ページ（同上。正本は各版の shared/decision_table.csv）
mkdocs.yml                   # MkDocs の設定（同上）
hooks/spec_loop_pages.py     # 表示用ページを CSV から作るフック（同上）
```

以下、`shared/`・`spec/` などは**版のディレクトリの中**（`docs/v<n>/shared/`）を指す。

## 置き方の決まり

- **`shared/` には、両方の読者に見せてよいものだけを置く。** 2 つのサインオフが
  同じ中身を見ていたかは、`shared/`・`requirements/`・`spec/`（`qa-dev.csv` を除く）で確かめる（`signoff-tags.md`）。
- **内部の層の Q&A 表（`spec/qa-dev.csv`）は `shared/` に置かない。** 開発者が決めて記録する質問で、利用者に渡さず、
  サインオフも比べない（`qa-csv.md` の「層」）。共有の表（`shared/qa.csv`）に置くのは利用者が決める質問だけ。
- **`requirements/` から `feasibility/` へはリンクしない。** 利用者に見せる費用は、
  `qa.csv` の `費用への影響` の列だけにする。見積りの側は、根拠にした Q&A の番号
  （`Q-F-001` など）や決定表の行を書く。
- **`spec/` は `requirements/` から書き下す。** 利用者の言葉で決まったこと（`requirements/`・
  `shared/` の決定表）を、開発者が実装とテストに使える形に直す。**`spec/` で新しく決めてよいのは、
  利用者の業務に関わらないこと（境界値の扱い・失敗したあとに残る状態など）だけ**——利用者の判断が要ることは
  `qa.csv` に起票する。確定の条件は `spec-exit.md`。
- **`spec/` に書くのは守るべき性質と、それを外から確かめるテストである。** 決めてよいことでも、実現の手段
  （ロック・取引の切り方・内部の戻り値）は `spec/` の決まりにしない。どこまでの場面を受け持ち、どの水準まで書くかの線は
  `spec-scope.md` を正とする。
- **`proposal/` には、ほかのどこにも無い部分だけを手で書く**（背景と目的・推奨案とその理由・
  比較した代替案・リスクと前提条件）。範囲・費用・期間・主な決定事項の表は、
  `shared/`・`requirements/`・`feasibility/` から生成する。**v2 以降の「前の版からの変更」の表も生成する**
  （`versions.md` の「版の差分」）。手書き部分は `proposal/*.md` に置き、
  **ファイル名の順に**提案書の先頭へ並ぶ（`01-background.md`・`02-recommendation.md` のように番号を付ける）。
  **`proposal/spec/*.md` は仕様書の手書き部分で、提案書には入らない**（下の「仕様書」）。

## スライドの置き場所

レビュー会のスライド（`req-loop` が作る）は **`qa.csv` から生成するもので、正本ではない**。

- **`shared/` にも、ツリーのどこにも置かない。** `shared/` は 2 つのサインオフが同じ範囲を
  見ていたかを比べる場所なので、生成物を入れると比べる中身が増える。
- 既定の出力先は **`build/req-loop/qa-review.pptx`**（リポジトリ直下の `build/`）。
  **commit しなくてよい**——同梱の生成スクリプトは、同じ `qa.csv` と引数から同じバイトを作るので、
  レビュー会で見せたものは `qa.csv` の履歴から作り直せる。
- 正本リポジトリの `CLAUDE.md` が出力先や形式を決めていれば、そちらに従う（下）。

## 生成物の置き場所

レビュー会のスライドと同じく、**ガントチャートと提案書も生成物で、正本ではない**。ツリーには置かない。

| 生成物 | 既定の出力先 | 作るスキル |
| --- | --- | --- |
| ガントチャート | `build/feasibility/gantt.svg` | `feasibility` |
| 提案書 | `build/proposal/proposal.md`（と同じ場所の `gantt.svg`。`--pptx` なら `proposal.pptx`） | `proposal` |
| 仕様書 | `build/proposal/spec.md`（と同じ場所の `spec-figure-NN.svg`。`--pptx` なら `spec.pptx`。下の「仕様書」） | `proposal` |
| Issue の本文 | `build/scaffold/issues/<機能の id>.md`（と同じ場所の `issues.json`） | `scaffold` |
| サイト | `site/`（MkDocs の出力。下の「ドキュメントのツール」） | `mkdocs build` |

**commit しなくてよい**——同梱の生成スクリプトは、同じ入力から同じバイトを作る。
提案書は**サインオフのタグの時点の中身**から作るので、タグがあれば作り直せる（`signoff-tags.md`）。

**ガントチャートは、作れなかったとき（引数の誤りのほかの 0 以外）に前の出力を消す**（引数の誤りでは出力先が分からないので消さない）。
消せない（出力先のディレクトリが書けない・辿れないなど）ときは、どの経路でも 2 で止まり、残った前の出力を名指しする
——表が決まりに反していても 1 にしない（#499）。**出力先が symlink なら、リンクも先も消さない**——先を辿れないとき（#535）も、
先が辿れる通常のファイルのとき（#626）も、リンクと先のパスを名指しして 2 で止まる（リンクを消しても先の古い中身は残るため。#625）。
壊れたリンク・ディレクトリを指すリンクは、この道具の出力ではないので消さずに名指しもしない。
終了コードは `schedule-to-gantt.py` の docstring を正とする。

**移行——0.39.0 より前から、ガントチャートの出力先を symlink にしていたら。** 0.39.0（#626）から、出力先が**辿れる先の通常のファイルを指す symlink** のとき、作れなかったときの終わり方が変わった
（先を辿れない symlink は 0.38.2（#535）から同じ形）:

| | 0.39.0 より前 | 0.39.0 から |
| --- | --- | --- |
| リンク | 消す（「前に作った出力を消した」と言う） | 消さない |
| 先の古い図 | 黙って残る | 残り、リンクと先のパスを「前に作った出力を消せない」と名指しする |
| 表が決まりに反するときの終了コード | 1 | **2** |

終了コードの 1 を「表を直す」、2 を「出力先を直す」と分けて扱っていたなら、出力先がそういう symlink（辿れる先の通常のファイル・辿れない先を指すもの）のときは、
表が決まりに反していても 2 になる（壊れたリンク・ディレクトリを指すリンク・輪になったリンクは前と同じく 1。表が正しくて書けないときは前も 2）
——標準エラーに表の違反の行も出ていれば、表も直す（`feasibility` の手順 4）。**以前と同じく 1 で終わらせたいなら、出力先を symlink でなくする**:
リンクを消し（先の古い図は残るので、要らなければ先も消す）、リンクの先のパスか、symlink でない場所を出力先に渡す。表が正しく書けるとき（0。リンクの先に書く）は変わらない。

**提案書と仕様書の場所には、`build-proposal.py` が印 `.build-proposal`（書いた出力の名前の一覧）を置く**（#405）。
次の実行は、作る前に**印が名指しするものだけ**を消す——**印に無いファイルは、名前が `spec.md` でも消さず、上書きもしない**
（上書きになるなら 2 で止まる）。だから手書きの `spec.md` の在る場所に `--out` を向けても消えない。**印を手で直さない。**
`--out` の誤り（名前が無い・ディレクトリ・名前の衝突・前後に空白がある・改行を含むか `#` で始まる・`\` を含む・UTF-8 で書けない名前・辿れない出力先）で止まっても、`--out` の親の印が名指しする前の出力は消す（今回のものと取り違えないため。ディレクトリを渡したなら、その中の印が名指しするものも消す）。
**消せなければ（出力先のディレクトリが書けないなど）作らずに 2 で止まり、消せなかった出力を名指しして印を残す**（#440。次の実行が消せるように）。
**だから作れなかったとき（0 以外）も、出力の場所にファイルが残ることがある**——**印の無いファイル**（spec-loop 0.25.0 までの出力・手で置いたもの）と
**印が読めない場所の出力**は、どの終了コード（1・2・3。`git` を起動できないときの 2 を含む）でも消えない（印が読めなければ、消してよいと確かめられないため）。
**残ったものは名指しされる**（#498。消さない）——作れなかったとき（0 以外。**出力先が決まる前に止まった 2——引数の解釈に失敗した `argparse` の 2 と、`--out` を渡さずに根を求める途中の想定外の例外（辿れない親など）——は名指ししない**）、出力の場所に在る**出力の名前**（`--out` の名前・`proposal.md`・`gantt.svg`・`spec.md`・
提案書と仕様書の PPTX・`spec-figure-<数字>.svg`。大文字小文字を区別しない）のファイルのうち読める印に無いものを「今回の出力ではない」と、読めない印を「印を読めない」と名指しする
（読めない印の場所では、出力の名前のファイルをすべて名指しする）。**出力の名前でないファイル（手書きの `notes.md` など）は名指ししない**——残っていても言われない。
**同じファイルは 1 度だけ名指しする**——「上書きしない」の 2 で、そう言ったファイルは「今回の出力ではない」と重ねて言わない（#551）。
**作れた経路（0）でも、印に無い出力の名前のファイルが残っていれば「今回の出力ではない」と名指しする**（#553。終了コードは 0 のまま、消さない）——
0.25.0 の `proposal.pptx` を `--pptx` 無しで作ったとき・手で置いた `spec-figure-NN.svg` などである（図が減っただけなら、前の図は印に載っているので消える）。出力の場所を読めなければ、0 でも「前の出力が残っているかを確かめられない」と言う。
**残ったファイルを今回の提案書と取り違えない**——0.25.0 までの出力なら下の「前の出力の印（spec-loop 0.26.0）」で手当てする。

Issue の本文は**登録すれば GitHub に残る**ので、commit しなくてよい。**作れなかったときは前の本文を消す**
（古い本文を登録させない）。

## 仕様書

**提案書だけでは「その費用で何を作るのか」が議論できない**（#371）ので、`proposal` は提案書と同じ実行で**仕様書**も作る。
**照合が通らなければ、提案書と同じく作らない**（前に作ったものも消す——消すのは印が名指しするものだけで、印の無い・読めない場所の出力と、消せなかった出力は残る。上の「生成物の置き場所」）。

- **材料は `signoff/v<n>/req-<k>` の時点の、v1〜v<n> を重ね合わせた全体**（`shared/`・`requirements/`・`spec/`。重ね方は `versions.md`）。
  **作業ツリーの仕様は読まない**——承認の後に直した仕様が説明に紛れ込む。**内部の層の Q&A 表は載せない**（`qa-csv.md` の「層」）。
- 機械で載せるもの:

| 節 | 材料 |
| --- | --- |
| 規模 | 要求・仕様のファイルの数・決定表の行・共有の Q&A（決定・暫定・未決定）・中間表現の機能・図の数 |
| 構成の図 | `spec/`・`requirements/` の `.svg` のファイル（`.drawio.svg` を含む）。`.svg` の無い `.drawio` は**載せていないと書く** |
| 機能の一覧 | 中間表現（`spec/spec_ir.json`）の `features`。scaffold の前は無いと書く |
| 決定表 | `shared/decision_table.csv`（1 行目を見出しとして、そのまま表にする） |
| 範囲の外 | 範囲の文書（`spec/scope.md`。`spec-scope.md`）の、見出しに「範囲の外」を含む節の本文 |
| 前の版からの変更 | v2 以降だけ。提案書と同じ比較（`versions.md` の「版の差分」） |
| 仕様と要求のファイル | `spec/`・`requirements/` のパスの一覧 |

- **一意に決まらないもの**——画面の一覧・試作で確かめること・要約・説明のときに確かめたいこと——は、
  作業中の版の **`proposal/spec/*.md`** に手で書く（ファイル名の順に仕様書の先頭へ並ぶ。無ければ無いと書く）。
  提案書の手書き部分と同じく承認の対象ではないので作業ツリーから読むが、**材料は承認された中身だけにする**。
- **図は書き出し済みの `.svg` を写すだけで、draw.io を起動しない**。図の描き方（drawio のソースと書き出し）は #268 で決める。
- **提案書と仕様書は互いを指す**——提案書の冒頭に「何を作るかは `spec.md`」、仕様書の冒頭に「費用・期間・推奨案は提案書」。
- **PPTX**（`--pptx`）は、レビュー会の資料と同じ仕組み（`qa-to-pptx.py`。標準ライブラリだけ）で、Markdown の見出しごとに 1 枚にする。
  **図は PPTX に載せない**（標準ライブラリだけでは SVG を埋められない）——載せていないことをスライドに書く。

## scaffold の出力

**`scaffold/`（リポジトリ直下）は生成物だが、commit する。** Issue が指す受け渡しの契約で、dev-loop は
このファイルに対して実装するからである。**手で直さない**——直したいところは `spec_ir.json` を直して作り直す。
同梱の生成スクリプトは同じ入力から同じバイトを作り、**`--check` で、置いてあるものが古くないかを確かめる**。

| ファイル | 中身 |
| --- | --- |
| `scaffold/openapi.json` | OpenAPI 3.1（JSON） |
| `scaffold/types.py` | 入出力の型（Python の `TypedDict`） |
| `scaffold/tests/test_<機能>.py` | Red テスト（Python の `unittest`。実装が無ければ失敗する） |

**正本と開発のリポジトリが別なら**、`scaffold/` を開発のリポジトリへどう写すかは正本リポジトリの `CLAUDE.md` に
書いてもらう。**Issue の本文が指紋を持つのは、中間表現（重ね合わせた全体の `build/merged/spec/spec_ir.json`）の中のその機能と
Red テスト（sha256）だけ**——`openapi.json`・`types.py` は指紋を持たず、中間表現は `scaffold/` の外にあり、commit もしない。
dev-loop は本文の指紋と sha256 を手元の中間表現と Red テストに当てるので、**開発のリポジトリにも正本の版を写して
重ね合わせるか、どこで当てるかを決めて書く**。

## ドキュメントのツール

**既定は MkDocs。** `docs/` を最初から閲覧できるように、プラグインは雛形（`templates/mkdocs/`）を持ち、
同梱のスクリプトで正本リポジトリへ写す（**手で写さない**）:

```bash
python3 <spec-loop の base ディレクトリ>/scripts/init-mkdocs.py [<正本リポジトリの根>] [--dry-run]
```

- **写すのは、正本リポジトリの `CLAUDE.md` がドキュメントのツールを決めておらず、MkDocs の設定（`mkdocs.yml`・`mkdocs.yaml`）も
  無いときだけ。** 設定が在ればスクリプトは何も写さない。**在るファイルは 1 バイトも変えない**——`pyproject.toml`・`.gitignore` が
  在れば触らず、足りない依存・行を示すので、足すかどうかは利用者が決める。
- 写すもの: `mkdocs.yml`（Material・`use_directory_urls: false`・nav は書かず自動）・`pyproject.toml`（uv。
  **MkDocs は 2 未満に固定**——2.0 は非互換の変更が予告されている）・`.gitignore`（`build/`・`site/`・`.venv/`・`__pycache__/`）・
  `hooks/spec_loop_pages.py`・`docs/index.md`・`docs/qa.md`・`docs/decision-table.md`。閲覧は `uv run mkdocs serve`。
- **CSV は Markdown に写さない。** 表示用のページに印（`<!-- spec-loop: qa -->`）を書き、フックが CSV から描く。
  `qa` の印は、各版の `docs/v<n>/shared/qa.csv` を**版ごとの節**に描く（重ね合わせない。アンカーは `v<n>-q-001`）。
  `decision_table` の印は、各版の `docs/v<n>/shared/decision_table.csv` を**見出しの行どおり**に版ごとの節に描く（#369）。
  CSV の文字は表のセルにだけ置く（段落に置くと、行頭の `!!! ` や字下げがブロックの記法に読まれる）。
  ほかの CSV を描くときは、フックに描画関数を足す。
- **要求・仕様から CSV へ直接リンクしない**——ブラウザでは CSV のページが開けない（#369）。リンクは表示用のページ
  （`docs/qa.md`・`docs/decision-table.md`。版の節は `#v1` のようなアンカー）へ張る。
- **本文の Q&A の番号（`Q-008`）は、フックが Q&A 表（`docs/qa.md`）のアンカーへのリンクにする**（描画関数が描いた表のセルを含む。
  Q&A 表のページそのものは除く）。リンクする版・置き換えないところはフックの docstring を正とする。
  **本文の書き方の決まりは `qa-csv.md` の「本文での番号」を正とする。**
- **既に雛形を写した正本には、新しい雛形は届かない**——`init-mkdocs.py` は設定が在れば何も写さない（在るファイルを変えない決まりは
  変えない）。フックを新しくするときは、下の「Q&A 表を移す」の手順 4 で取り込む。これは「手で写さない」の例外で、取り込むのはフックだけ。
  **印つきの番号（`Q-S-008`。spec-loop 0.24.0 から）をリンクにするのは 0.24.0 以降のフックだけ**——それより前に写したフックは
  印つきの番号を素通しし、リンクにも「表に無い番号」の警告にもしない（黙って素の文字のまま出る）。0.24.0 に上げたら、
  印つきの番号を起票する前に、同じ手順 4 の形でフックを取り込む。
  **spec-loop 0.31.0 で、フックは素の本文の URL の中の番号を書き換えなくなり（#341）、`decision_table` の印を描くようになった（#369）**——
  同じ手順 4 の形でフックを取り込み、雛形の `docs/decision-table.md` を写す（在れば変えない）。それまで CSV へ直接張っていたリンクは
  `docs/decision-table.md` へ張り替える。
- **表示用のページは `shared/` に置かない**（`docs/qa.md` のように版の外に置く）。`shared/` は 2 つのサインオフが比べる範囲
  （`signoff-tags.md`）なので、表示用のファイルを入れると比べる中身が増える。版の外の名前は重ね合わせにも入らない（`versions.md`）。
- **フックはサーバーの起動時にしか読まれない**——直したら `mkdocs serve` を起動し直す。

## プロジェクトに任せること

MkDocs 以外のドキュメントのツール・サイトの分け方・スライドの形式は、**正本リポジトリの `CLAUDE.md` に書いてもらう**。
書いてあれば、そちらが上の既定より先に立つ。

## Q&A 表を移す

**spec-loop 0.18.0 で Q&A 表の見出しが変わった**（推奨の 2 列。`qa-csv.md`）。前の形の表は、同梱の検査（`check-qa-csv.py`）も
雛形のフックも「見出しが違う」で落とし、この節を指す。**移すのは人間とスキルで、道具は無い**——推奨は提案側の判断なので、
機械では埋められない。**1 回で全部移す**（版ごとに形が混ざると、版を重ねるところで前の版の表が落ちる）:

1. **リリースした版（`release-v<n>` のタグ）が無いことを確かめる**（`git tag --list 'release-v*'`）。
   **あれば移さずに止め、人間に訊く**——リリースした版の `docs/v<n>/` は直さない決まりで（`versions.md`・`check-frozen.py`）、
   前の形のまま残すと、それより後の版を重ねるところで落ちる。
   **サインオフのタグ（`signoff/v<n>/req-<k>`・`budget-<k>`）があれば、移した後に両方を取り直す**（`git tag --list 'signoff/*'`）
   ——タグは前の形の表を指したままで、照合（`check-signoff.py`）も提案書（`build-proposal.py`）も、その時点の表を
   「見出しが違う」で読めずに 2 で止まる。**移す前に人間にそう伝え**、移したコミットで新しい `k` のタグを付けてもらう
   （タグは付け直さない。`signoff-tags.md`）。
2. **各版の `docs/v<n>/shared/qa.csv` の見出しの、`選択肢` の後に `推奨,推奨の理由` を足し、全部の行を埋める**:
    - 選択肢の文の末尾に `（推奨: 理由）` を書いていた行は、そのラベルを `推奨` に、理由を `推奨の理由` に移し、選択肢の文から消す。
    - 推奨を書いていなかった行は、起票し直すつもりで推奨と理由を書く。**推せない・決められないなら `なし` と理由**
      （`事実の確認`・`見積り待ち`）。答えが出た行（`反映済み`）を移すだけなら `なし`・`移す前に起票（推奨を記録していない）` でよい
      ——**推奨を後から作らない**（答えを見てから推奨を書くと、回答の推測と区別がつかない）。
    - 書いたら版ごとに `check-qa-csv.py` を通す。
3. **内部の層へ移す行を分ける**——共有の表の行のうち、選択肢で変わるのが実現の手段・内部の値・運用の手順だけのもの（線は
   `spec-scope.md` の「振り分けの区分」）を、作業中の版の `spec/qa-dev.csv` へ内部の表の番号（`D-` に起票元の印。`D-S-001`）で移す（`qa-csv.md` の「層を移す」）。
   移すかどうかに迷う行は共有に残す。**この手順は任意**——移さなくても表は決まりを満たす。
4. **写し済みのフックを取り込む**——プラグインの `templates/mkdocs/hooks/spec_loop_pages.py` と正本の `hooks/spec_loop_pages.py` を比べ、
   正本で足した描画関数と `RENDERERS` の行を残して取り込む。取り込んだら `mkdocs serve` を起動し直し、Q&A 表のページに
   推奨の列と、警告が出ないことを見る。**取り込まないと、前の形のフックは新しい表を「見出しが違う」で警告する**（ページに注意書きが出て、
   `mkdocs build --strict` は落ちる）——黙って崩れた表は出ないが、表示はされない。
5. 見出しを移した表・内部の表・フックを 1 つのコミットにする（版ごとに分けない）。

### 暫定の行を状態へ移す（spec-loop 0.25.0）

**spec-loop 0.25.0 で、暫定の行の判別が `状態` の `暫定反映` だけになった**（`qa-csv.md` の「暫定の行の判別」。#404）。
0.24.0 までは、`反映済み` で `回答` に「暫定で採用」を含む行も暫定とみなし、提案書だけがそれを「利用者にまだ確かめていない決定」に載せていた。
**移さないと、そうした行は確定の行として扱われる**——提案書の主な決定事項に載り、scaffold はその行から Red テストと Issue を作る。
**移すのは人間とスキルで、道具は無い**——利用者が確かめたかどうかは表に無く、機械では決められない:

1. **リリースした版（`release-v<n>` のタグ）が無いことを、表を直す前に確かめる**（`git tag --list 'release-v*'`）。
   **あれば移さずに止め、人間に訊く**——理由はこの節の親（「Q&A 表を移す」）の手順 1 と同じで、リリースした版の
   `docs/v<n>/` は直さない決まり（`versions.md`・`check-frozen.py`）。
2. **サインオフのタグがあれば、表を直す前に人間に伝える**（`git tag --list 'signoff/*'`）。**親の節の手順 1 とは理由が違う**——
   古いタグは移す前の表を指したままで、**照合（`check-signoff.py`）は 0 を返し、提案書（`build-proposal.py`）はその行を
   主な決定事項（合意）として載せる**——0.24.0 までも止まりはしなかったが、その行を「利用者にまだ確かめていない決定」に分けていた。だから古いタグで提案書を作らない:
    - `暫定反映` にした行が 1 つでもあれば、**要求確定のタグは利用者が確かめてから付ける**（`signoff-tags.md`）——残るうちは照合が 3 で止まる。
    - 書き換えだけで済んだ（全部が「確かめた」だった）なら、移したコミットで両方のタグを新しい `k` で付けてもらう（タグは付け直さない）。
3. **候補を洗い出す**——各版の `docs/v<n>/shared/qa.csv` から、`状態` が `反映済み` で `回答` に「暫定」を含む行を拾う。
   **`grep` では拾わない**——`回答` が複数行のセル（引用符で囲んだ改行）だと、「暫定」と `状態` が別の行に出て、`反映済み` の行に見えない。
   表として読む:
   ```bash
   python3 -c 'import csv,glob; [print(p, r["No"], r["回答"].replace("\n", " ")) for p in sorted(glob.glob("docs/v*/shared/qa.csv")) for r in csv.DictReader(open(p, encoding="utf-8-sig", newline="")) if r["状態"].strip() == "反映済み" and "暫定" in r["回答"]]'
   ```
   **拾うのは候補で、判定ではない**——確定した経緯に触れただけの行（「暫定で採用していた B を取り下げ」）も当たる。
4. **1 行ずつ人間に確かめる**（推測で埋めない）:
    - **利用者がまだ確かめていない** — `状態` を `暫定反映` にする（`回答`・`反映先` はそのまま）。
      レビュー会の資料に載り、確かめるまで要求確定のサインオフを付けられず、scaffold も止まる（`qa-csv.md` の表）。
    - **利用者が確かめた** — `回答` を確定の書き方（`A（業務部が確認）`）に書き換える。`状態` は `反映済み` のまま。
5. 移した表を 1 つのコミットにする。版ごとに `check-qa-csv.py` を通す。

## 前の出力の印（spec-loop 0.26.0）

**spec-loop 0.26.0 で、`build-proposal.py` は印 `.build-proposal` が名指しする前の出力だけを消すようになった**（#405。
決まりは上の「生成物の置き場所」）。**0.25.0 までが作った `build/proposal/` には印が無い**ので、次の実行は
`proposal.md` などを**上書きせずに 2 で止まる**（印の無いファイルを、この道具が作ったと確かめられないため）。
**作れない経路（上書きの前に止まるもの——照合が通らない・材料が無い・表が決まりに反する・照合していない・`--out` の誤り・`git` を起動できない・暫定が残る、など。終了コードは 1・2・3）では、
上書きの前に止まるので、0.25.0 の出力はそのまま残る**——「提案書は作っていない」と出ても、`build/proposal/proposal.md` は古いものが在る。
残ったものは「今回の出力ではない」と名指しされる（#498。上の「生成物の置き場所」）。

1. **0.25.0 までの出力が残る場所で走らせたら（どの終了コードでも）、その場所に手で置いたファイルが無いかを人間に確かめる**（推測で消さない）。
2. 手で置いたものが無ければ、出力の場所（既定は `build/proposal/`）を消してから作り直す。
   手で置いたものがあれば、それを残して別の場所を `--out` に渡す。

出力の場所ごと消して作り直せば印が置かれ、以後は 0.25.0 の出力を理由には止まらず、作れなかったときも印が名指しする前の出力は消える。
**名指しされたファイルだけを消すと、今回の `--out` から見て出力の名前でない 0.25.0 のファイル（前に別の `--out` の名前で作った提案書とその PPTX など）が名指しされずに残り**、
後の実行（その名前を `--out` に渡した）で「上書きしない」の 2 になる（#498 より前は `proposal.pptx`・`spec-figure-NN.svg` も名指しされなかった）。
印が置かれたあとも、印が読めないときと、印が名指しする出力を消せなかったとき（2 で名指しする）は前の出力が残る（上の「生成物の置き場所」）。
