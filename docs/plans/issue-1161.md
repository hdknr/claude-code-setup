### 仕様の穴（推奨で決めた。`仕様の穴 = 推奨で決めて起票`）

- **H1（決めること 1）個人名を正本に残すか**: (a) 部署・役職だけを書き、個人名を書かない（推奨）／(b) 個人名も書いてよい。
  推した理由: 正本は git の履歴に残り続け、提案書と同じく決裁者・予算責任者に渡る（`shared/`）。異動のたびに表と履歴の個人名が古くなり、消しても履歴から消えない。答える権限・合意の権限は役職に付くので、照合にも役職で足りる。
- **H2（決めること 2）非公式の影響力（「裏のキーパーソン」）を表に書かせるか**: (a) 書かせない——表には公式の役割と合意だけを書く（推奨）／(b) 書く列を足す。
  推した理由: 表は `shared/` にあり、利用者・予算責任者・決裁者の全員が読み、サインオフで承認される文書になる。特定の人の非公式の影響力を承認の対象の文書に書くと、書かれた人と関係を損ねる。
  その人の判断が要るなら、公式の役割（合意・答える範囲）として表に載せるかを利用者に訊く。
- **H3（案 3）回答者が「その質問の範囲を持つ」かをどう確かめるか**: (a) 機械で見るのは「回答の括弧の答えた人が表の `名前` にあり、`答える範囲` が `なし` でない」まで。質問がその人の範囲かは req-loop が回答を反映するときに範囲の文と照らして確かめる（推奨）／
  (b) Q&A 表に分類の列を足し、範囲を分類で機械に照らす／(c) 範囲を Q&A の番号の一覧で持つ。
  推した理由: (b) は Q&A 表の見出しの行を変えるので、前からの正本の `qa.csv` が全部「見出しの行が決まりと違う」で落ち、凍結した版は直せない。(c) は起票のたびに表を直すことになり、表が古くなる。
  (a) は前からの表を変えず、表の無い正本では何も起きない。
- **H4（案 3）回答者の照合の結果をどの重さで出すか**: (a) 報告だけ——`check-design-csv.py` の出力に出し、終了コードに数えない（推奨）／(b) 未決定（3）に数え、scaffold を止める。
  推した理由: 表を置く前に答えた行（凍結した前の版の `回答` の書き方を含む）は直せないので、(b) では表を置いた正本の scaffold が止まり続ける。範囲の中身は機械で決まらない（H3）。
  報告を読んだ req-loop が、表に無い人の回答を反映せずに範囲を持つ人に確かめる（手順 2）。
- **H5（案 4）サインオフのタグを付けた人と、合意が要る人をどう照らすか**: (a) 承認した関係者をタグの注釈の `承認: ` の行に表の `名前` で書き、`check-signoff.py` が表の合意が要る関係者と並べて報告する——照合の終了コードは変えない（推奨）／
  (b) 注釈に無い関係者がいれば照合を止める／(c) 決まりを文書に書くだけで機械では報告しない。
  推した理由: タグの付け手（git の名前）は表の名前（部署・役職。H1）と一致しないので、照らすには注釈に表の名前を書くしかない。前からのタグは軽量のタグで注釈を持たず、(b) では表を置いた正本で前のタグが全部止まる。
  照合は「2 つの承認が同じ中身を見たか」の関門で、誰が承認したかは人が判断する（Issue も「報告する」）。(c) は spec-loop の「照合を LLM に判断させない」に反する。
