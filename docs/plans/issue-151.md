#### 不変条件 A（#150）: docstring の約束が、実装の挙動を超えない

| 経路（約束が実装を超えうる入口） | どう守るか |

#### 不変条件 B（#150）: 選択肢の採否が、実データの測定に基づいている

#### 不変条件 C（#151）: 「この変異で赤になる」主張が、機械で当てられて実際に赤になる

| 経路（主張が偽のまま緑になりうる入口） | どう守るか |
| --- | --- |
| マーカーが 1 つも収集されない（フェンスの中・書式違い・キー名の typo） | フェンスを剥がしてから拾う。**未知のキーは拒否**（fail-closed）。**収集した件数を必ず出す** |

| 検査が走らなかったのに緑と読む（退避先で base が解決できず SKIP 等） | **陽性対照を必須にする**——変異前に緑でなければ「**当てられなかった**」。**緑と混ぜない** |
| 主張が偽（変異を当てたのに緑のまま） | 「**緑のまま**」として非ゼロ終了 |
| 歯止めを足したのに `check-all.py` に登録し忘れる | `test-check-all.py` の収録漏れ検査が自動で見る ＋ CI にステップを足す |
| 歯止め自体が「置いてあるが何も見ていない」に退化する | `test-check-mutation-claims.py`（**変異テストを含む**） |
| 「守る」の行数と変異の数がずれる | このリポジトリの既存の形にならい、**テスト自身に数えさせる** |

### この環境では証明できないもの（未証明 — 人間レビューに回す）

1. **マーカーを書いていない主張は、この歯止めには見えない。** 散文の主張を全部マーカー化
   したかどうかを機械で数える手段は無い（「主張らしい文」の定義が無い）。
   **これは #151 が設計として受け入れる限界**であり、**塞げると書かない。**
2. **等価変異を区別できない。** 「当てたのに緑」が、**検査の穴**なのか
   **その変異が旧い欠陥を表していない**（＝届いていない）のかは、この歯止めでは決まらない。
   **`SKILL.md` 手順 5 が「緑を砦の穴と読む前に、変異が届いているかを疑う」と書いているのは
   まさにこの区別**で、**判断は人間か関門に残る。** 歯止めが言えるのは「緑のままだった」まで。
3. **`git` に依る主張は当てられない。** 退避先には `.git` を持ち込まないので、
   `check-version-bump.py` のような base を要する検査を `red` に置いた主張は
   **陽性対照で落ちて「当てられなかった」になる**。**黙って通らないが、当てられもしない。**
4. **CI（ubuntu / dash）での挙動は手元（macOS / zsh）では測れない。** PR の CI が実測になる。

## 測定 — #150 の選択肢 1 と 2

**Issue #150 は「実データに当てて件数を見てから決める」と書いている。** 当てた。

**母集団**: このリポジトリの `.md` / `.py` / `.sh` / `.json` / `.yml` / `.yaml` / `.toml`
（`.git` / `site` / `.venv` / `node_modules` / `__pycache__` / `.claude` を除く）。
**収集規則は本体と同じ**（フェンスを剥がす・強調を落とす・同一ファイル内で数が 2 種以上）。
**免除（`dup-counts-ok:`）は適用していない**ので、現行でも既知の 3 件が出る。

| 正規表現 | 発火 | 判定 |
| --- | --- | --- |
| **現行**（`(?:が\|は)` を要求） | **3 件** | すべて既知の実演（免除つき）。**陽性対照——検査は生きている** |
| **助詞を任意化**（`(?:が\|は)?`） | **29 件** | **ほぼ全部が誤検出** |
| **`の` / `を` も許す** | **5 件** | 既知の 3 件 ＋ **新規 2 件はどちらも誤検出** |

**誤検出の中身**（29 件のほうから代表を挙げる）:

- `plugins/dev-loop/skills/dev-loop/SKILL.md` の **`次の…つ`** に
  **2 / 3 / 4 / 5 が同居**——**別々の列挙を指す、すべて正しい記述**である。
  **#150 が名指しした `次の 6 つ` という形そのものが、いちばん当たってはいけない形だった。**
- `docs/plans/issue-110.md` の **`反証…件`** に **0 / 1 / 2 / 9 / 10 / 11 / 12 / 13**
  ——**パスごとの反証の数**で、**違って当然**である。
- `scripts/collect-guard-rejections.py` の **`1,…件`** に **386 / 388 / 534**
  ——**桁区切りのカンマ**を語句として拾っている。

**`の` / `を` を許した 5 件のうち、新規 2 件も誤検出**だった:

- `docs/plugins/dev-loop-design.md`: 「同じ列挙**を 2 箇所**に置けば」（一般論）と
  「同じ列挙**が 5 箇所**にあって」（実測）。**別の主張。**
- `scripts/test-check-description-sync.py`: 「#60 **の 1 件目**」「#60 **の 2 件目**」
  ——**件数ではなく序数**である。

**結論: 選択肢 1 を採る**（docstring を実装に合わせる）。

**理由は「安いから」ではない。** **選択肢 2 はどの広げ方でも成立しない**
——助詞を落とすと**正しい記述どうしが当たる**し、**`次の 6 つ` を拾える広げ方は
`次の…つ` を全部拾う広げ方でもある**。
**これは docstring が「表の行数とずれた範囲参照」を一度規則にしようとしてやめたのと
同じ形**（あちらも現在の main に 3 件当たって 3 件とも誤検出だった）。
**#150 の Issue 本文がその危険を先に名指ししており、測定はそれを裏づけた。**

**したがって `次の 6 つ` 型の食い違いは、引き続き見えないまま残る。**
**これを「直した」と書かない**——**「守らない」に明記して、見えないことを見えるようにする**
のが #150 の成果である。
