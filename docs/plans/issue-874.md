## 設計（この周で決めたこと）

- **基準コミット = 正本リポジトリで本文を生成した時点の HEAD**（`git -C <正本> rev-parse --verify HEAD`）と、そのコミットの日時（`%cI`）。
  scaffold の流れは「生成 → commit → 登録」なので、生成の時点の仕様（`docs/`・`scaffold/`）は未コミットのことがふつうである。基準コミットが表すのは**仕様を書いた人が見ていた既存のシステムの時点**で、仕様そのものの時点は機能の指紋と sha256 が表す。
- **日時を併せて書く**のは、正本と開発のリポジトリが別のとき、開発のリポジトリで `git log --since` に使うため。コミットの日時は生成より前なので、`--since` は多めに拾う（安全な向き）。
- **git の作業ツリーでない・コミットが無い・git を起動できない**なら、止めずに `- 基準コミット: 記録していない（<理由>）` と書き、出力でも知らせる（0）。止めると、git でない試料・既存の使い方が全部壊れる。dev-loop は「点検していない」と読む。
- **本文の生成を決定論のまま保つ**（同じ HEAD なら同じバイト）——生成の時刻は書かない。
- **dev-loop の点検**（`spec-gap.md`）: 指紋・sha256 の照合の後に、基準コミットから後の変化（仕様と契約 `docs/`・`scaffold/`・`build/` の外）を一覧にし、仕様の原文・Q&A の回答・API・型が前提にしている既存のシステムに触れる変化があれば、その前提が保たれているかを読む。崩れていれば（判定できなければ）仕様の穴として「差し戻す」に従う。基準コミットが本文に無い・記録していない・手元で辿れないなら、点検していないことを計画ファイルと PR コメントに名指しする（止めない——登録済みの Issue は全部この行を持たない）。

## 既知の限界・決着済みの論点

| 論点 | 決着 | 理由 |
| --- | --- | --- |
| 基準コミットを生成の時点の HEAD にする（仕様の commit そのものではない） | 採った | 生成 → commit → 登録の順で、生成の時点では仕様が未コミットのことがふつう。基準コミットは既存のシステムの時点を表し、仕様の時点は指紋と sha256 が表す |
| 作業ツリーの未コミットの変更（既存のシステム側）は基準コミットに入らない | 守らない（docstring の守らないものに書く） | 仕様を書いた人が未コミットの既存コードを見ていたかは分からない |
| 印の版（v3）を上げない | 採った | 行を足すだけで印・指紋・sha256 は変わらない（#851 と同じ）。古い本文は行を持たないので「無い」と読む |
| 点検をスクリプトにしない | 採った | どの変化が前提に触れるかは判断で、機械で決まるのは変化の一覧まで |
