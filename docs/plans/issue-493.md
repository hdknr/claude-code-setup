## 判断（仕様の穴——不在の線 `仕様の穴 = 推奨で決めて起票` で推奨により決めた）

1. **並行の周の検査・アプリの起動をどう抑えるか（#493）**
   - 選択肢: (a) 同時に回す周の数に上限 ／ (b) 重い検査・アプリの起動を同じリポジトリでは順番待ちにする（既定 1 本、宣言で増やせる）／
     (c) 資源（ポート・データベース）ごとに宣言して配分する
   - **決めた値: (b)**。`run-serial.py -- <コマンド>` を通す。同じリポジトリ（worktree をまたいで）の枠は `.claude/dev-loop.md` の
     `並行の検査: N` で決め、宣言が無い・読めなければ 1。
   - 推した理由: 負荷を作るのは周そのもの（言語モデルの待ち）ではなく検査とアプリの起動で、しかも検査は周の実装役だけでなく
     Verifier・`/code-review` の体も走らせる。(a) は周の数を絞っても 1 つの周の中の関門どうしの重なりを止めない。
     枠を 1 にすれば、どの資源もコマンドの単位で同時に使われないので、(c) の宣言が無くても安全側になる（宣言の無いリポジトリの既定）。
     (c) の資源ごとの配分は、資源の名前をどのコマンドが使うかを周が知る必要があり、要る実例がまだ無い。
2. **着手できる周を単独で回す・後回しにしてよい条件と台帳への書き方（#493 のコメント）**
   - 選択肢: (a) 負荷・所要時間を測る周と負荷を作る周だけ単独にし、`note` の書き出し `単独: <理由>` で台帳に残す ／
     (b) 台帳に新しい欄を足す ／ (c) 後回しを認めない
   - **決めた値: (a)**。単独の周は、走っている周（`impl`・`gate`）が無いときだけ始め、走っているあいだは次の周を始めない。
     それ以外の理由で着手できる周を後回しにしない（文脈の残りで止めるのは §5 のまま）。
   - 推した理由: 測定は他の周の負荷で結果が変わる（順番待ちの外で走る負荷——言語モデルの体そのもの・順番待ちを通さない操作——が残る）。
     `note` は再開した親が `show` で読むので、親の文脈に依らない。欄を足すと `ledger.py` と台帳の形が変わり、2 つの用途の周は少ない。
3. **版とマージの順（#531）**
   - 選択肢: (1) 周の PR は版を上げずに作り、マージする親が上げる ／ (2) 各周は今までどおり版を上げ、マージの直前に main を取り込んで main より上に上げ直す ／
     (3) 台帳に割り当てた版を持たせ `next` が順を考える
   - **決めた値: (2)**。親は版を割り当てず、台帳に版を書かず、マージの順を版で決めない。マージの直前に、PR が main の先端を含んでいなければ、
     その周の続きとして子に取り込み・上げ直し（`CLAUDE.md` の手順）・全部の歯止め・push・PR 側の CI をさせてから、親がマージする。
     上げ直す版は「main の先端の版から、その周の計画ファイルに書いた上げ方（minor／patch）で 1 つ上げた版」。
     取り込みで版の行と生成ブロックのほかに衝突したら、その解き方は関門を通っていない変更なので、不在の周ではマージせず操作待ちにする。
   - 推した理由: (1) は PR の CI の `check-version-bump.py` が版の上がっていない差分を落とすので、CI を割るか検査を緩めることになる。
     (3) は親が版を割り当てる今の形を台帳に移すだけで、待ちの PR が版を押さえる問題は残る。
     (2) なら待ちの PR は版を押さえず、先にマージする周は何も気にしない。上げ方を計画ファイルに書けば、上げ直す値は main の版から決まり、親の文脈に依らない。

  子孫のプロセスへの枠のファイルの継承（コマンドが残したバックグラウンドのプロセスが枠を持ち続けない）。
