### 仕様の穴（推奨で決めた。`仕様の穴 = 推奨で決めて起票`）

- **H1（決めること 1）ランブックを持つか**: (a) 手順そのもの（ランブック）は範囲の外とし、表は「誰が・いつ・どの目標で」だけを持つ（推奨）／(b) 手順の列（または別の文書）を持つ。
  推した理由: 手順は運用の設計と実装に従って変わる実現の手段で、要求確定の時点では書けない。利用者と約束する（承認する）のは体制と目標で、手順を表に入れると手順を直すたびに 2 つのサインオフの取り直しになる。
- **H2（決めること 2）SLA の違反の扱い**: (a) 返金・減額などの違反の扱いは契約の領域として範囲の外にし、表の決まりに「契約で決める」と書くだけ（推奨）／(b) 表に `違反したときの扱い` の列を足す。
  推した理由: 違反の扱いは契約の条件で、仕様・テストに写らない（scaffold も見積りも使わない）。表に列があると、利用者が契約の担当なしに決めた値がサインオフで承認されたことになる。
- **H3（案 2）SLA をどこに持つか**: (a) 運用要件の表の行の `SLA` の列（`はい`／`いいえ`）で約束するかを示し、可用性などの水準は `nfr.csv` の行を `水準` で指す（推奨）／(b) `nfr.csv` に種類 `SLA` の行を足す／(c) 別の表 `sla.csv` を足す。
  推した理由: SLA の中身（対応の時間帯・一次対応と復旧の目標）は体制の行と同じ粒度で、別の表にすると同じ時間帯と目標を 2 つの表に書く。可用性の数字は既に `nfr.csv` にあり、水準を 2 つの表に書かない（基盤要件の表と同じ線——`tree.md` の「基盤要件」）。
  (b) は `nfr.csv` の 1 行（`上限`・`単位`）に時間帯と担当が入らない。
- **H4 可用性の水準を受ける障害対応の行が無いことを止めるか**（Issue に無い。Issue の「起きうる失敗」の 1 つ目を検査で拾う）: (a) 運用要件の表があるとき、`nfr.csv` の `可用性` の行を `水準` で指す `障害対応` の行が無ければ未決定（3）に数え、scaffold を止める（推奨）／

  推した理由: 可用性の数字だけ決まり、止まったとき誰が対応するかが決まらないまま開発と見積りに進むのが Issue の失敗そのもの。要るかどうかは利用者が決めることなので形式の違反（1）ではなく未決定（3）——CRUD 表の抜け（#1162）と同じ扱い。
