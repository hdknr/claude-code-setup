## 3. verify の受入基準

### 3.1 不変条件

| # | 不変条件 |
| --- | --- |
| **I1** | `SKILL.md` がガードについて述べる運用指示が、**Linux でも成り立つ**（あるいは、成り立たない点が名指しされている） |
| **I2** | 測定は**交絡を潰している**——陽性対照を取り、振る次元を 1 つに絞り、観測窓を書く |
| **I3** | 述べることが**測った範囲を超えていない**（境界を断定しない。#110 で 4 度壊れた型） |
| **I4** | **環境が記録されている**——OS・harness 版・git 版・観測日時 |
| **I5** | 収集スクリプトが**拒否イベントを落としていない**（`<tool_use_error>` の包みを剥がす。#112 でここが 2 度壊れた） |

### 3.2 I1 を破りうる経路（差分ではなく「測定が壊れる入口」から数える）

| # | 経路 | 守り方 |
| --- | --- | --- |
| **P1** | **Linux でガードがそもそも発火しない**（機能が無い・条件が違う）→ 拒否 0 件が出る。**主張が偽でも同じ出力**の典型 | **陽性対照**: macOS で拒否された形を Linux で流し、**拒否が出ること**を先に見る。出なければ「Linux では成り立たない」ではなく「**測定が成立していない**」と判定する |
| **P2** | **harness 版が違う**（macOS 側は 2.1.278）→ **OS の差と版の差が交絡する** | Dockerfile で**同じ版を固定**する。固定できなければ、その旨を明記して結論を弱める |
| **P3** | **認証形態が違う**（API キー / OAuth）→ ハーネスの経路が変わりうる | 使った認証形態を記録する。**これは潰せない可能性がある**（潰せなければ交絡として明記） |
| **P4** | **パスの形が違う**（`/Users` → `/root` 等）→ 理由節に埋まるパスが変わる | 理由節は**パスを伏せて**正規化する（前半 #133 と同じ手） |
| **P5** | **トランスクリプトの置き場所・形式が違う**→ 収集が黙って 0 件になる | **先にレコード件数を見る**。0 件なら収集の失敗と拒否 0 件を区別する |
| **P6** | **worktree 隔離セッションの作り方が違う**→ 隔離されていないセッションを測る | セッションが**隔離下にあること**を、拒否以外の手段で確かめる（陽性対照と同じ観測点） |
| **P7** | **コンテナが aarch64**（ホストが Apple Silicon）→ アーキテクチャと OS が同時に変わる | アーキテクチャを記録する。**振った次元が 2 つ**なので、結論に添える |
