## 決めたこと（Issue が「決める」とした書き方。推奨で決めた——仕様の穴の線）

- **行の見つけ方**: 見出し（`### 呼ぶ側の分岐`）・項目の行（`- 呼ぶ側の分岐:`）・表の行（先頭のセルが `呼ぶ側の分岐`）の 3 つの形を「行」と読む。見出しは次の見出しまで、項目の行は空行の後に分岐の項目が続かなくなるまで、表の行はその行だけが中身。
  - 選択肢: A 3 つの形を読む（推奨）／B 見出しの形だけに決める。推奨の理由: 実案件と試料（`test-scaffold.py`）がすでに 3 つの形を混ぜて書いており、1 つに決めると前に抜けた仕様の書き直しが増える。
- **まとめて書く書き方**: 認める。組の名前（`入力`・`呼ぶ処理`・`量`）に `が`・`の` を続け、その組の分岐を `・`・`、`・`／` で並べる（`入力が欠ける・遅れる・順が崩れる: 該当なし（…）`）。**組の名前だけの項目（`量: …`）はどの分岐にも触れない**——Issue の「量: が上限と重なるのどちらを指すかで読みが割れた」を、読みを割らない側に決めた。
  - 選択肢: A 並べた分岐だけ触れる・組の名前だけは触れない（推奨）／B 組の名前だけは組の全部に触れる／C まとめて書くことを認めない。推奨の理由: B は「量:」の読みが割れた実例をそのまま通す。C は実案件の書き方（Issue の例）を全部書き直させる。
- **別の節を指す書き方（「[価格照会書を出力する] と同じ」）**: 認めない——分岐ごとに書く（検査器は「触れていない」と出し、別の節を指す書き方は認めないと添える）。
  - 選択肢: A 認めない（推奨）／B 指した先の見出しの行が揃っていれば揃いとみなす。推奨の理由: 中間表現の `branches` の原文は機能の `source` の 1 行で（`spec-ir.md`）、指した先の行は別の機能の原文になり、課題一覧（案）の受入基準の雛形が書けない。B は検査器と scaffold の定義を割る（Issue の提案 2 に反する）。
